## 6A 发现书籍数据源与数据治理（仅旁路后端）

本节只描述**旁路后端 `server/`** 的「发现书籍」链路，**不属于主学习链路**。主 App 仍是纯前端离线 PWA，
不依赖本节任何数据。

### 6A.1 数据来源：Project Gutenberg

- 站点：`https://www.gutenberg.org`
- 实际使用的路径（全部为站点公开路径）：
  - `https://www.gutenberg.org/browse/scores/top` —— 热门榜，作为候选书目入口
  - `https://www.gutenberg.org/cache/epub/<id>/pg<id>.rdf` —— 书目元数据（标题、作者、语言、权利声明）
  - `https://www.gutenberg.org/cache/epub/<id>/pg<id>.txt` —— 纯文本正文
  - `https://www.gutenberg.org/cache/epub/<id>/pg<id>.cover.medium.jpg` —— 封面（可能不存在）
- 已否决的候选来源（不要重新考虑）：
  - `loc.gov` —— robots.txt 对 `/search` 为 Disallow，且实际请求返回 403
  - `z-lib` 一类站点 —— 提供仍在版权保护期内的商业作品，直接否决

### 6A.2 robots.txt 遵守规则

- 抓取前**先读** `https://www.gutenberg.org/robots.txt` 并缓存。
- 该文件**仅**禁止 `/ebooks/search` 一类搜索路径；本链路使用的 `/browse/scores/top` 与 `/cache/epub/...`
  **不在禁止列表内**。
- 即使站点未声明 Crawl-Delay，本链路仍自我限流：**每请求 0.8–2.0 s 随机延迟，且全局 ≤ 30 请求/分钟**
  （两者取更严），并发 ≤ 5。
- 请求使用真实浏览器 User-Agent；**不伪装搜索引擎、不使用多账号、不使用代理**。
- 若 robots.txt 日后变更并禁止上述路径，**立即停止抓取**，不等通知。

### 6A.3 版权核验口径（口径 A，不得自动放行）

一本书只有**全部满足**才可入库：

1. RDF 中 `language = 'en'`；
2. **每一位**作者/贡献者都能从 RDF 解析出可靠的卒年（`<pgterms:deathdate>`）；
3. 所有卒年的最大值 ≤ **1975**；
4. 缺卒年、卒年无法解析、语言不符 → 记入失败清单并跳过。

> **⚠️ 关键：不要把美国公有领域等同于其他国家公有领域。**
> `<dcterms:rights>` 的常见文本是「Public domain in the USA」，它**只在美国成立**。
> 中国采用「作者终生 + 死后 50 年」的保护期，比美国更长。举例：热门榜里的
> Agatha Christie（卒 1976）在美国已进入公有领域，但在中国保护至 **2026-12-31**。
> 因此本链路采用「所有作者卒年 ≤ 1975」这一更严格的口径，且**不因为站点声明了 PD 就放行**。
> **这不是法律意见，只是我们内部的一致性口径。**

**不确定数据的处理原则**：证据不足 = 不放行。宁可少收一本书，也不凭推断入库。

### 6A.4 五层数据关系（原始缓存 → embedding）

- ① 原始缓存 `server/.crawl-cache/<id>.json`（含全文，**不进 git**）
  → ② `discovered_books` 书目元数据 → ③ 正文（经 START/END 标记与 Content-Length 双重校验）
  → ④ `discovered_book_chunks`（500 字符/80 字符重叠切块，唯一键 `(book_id, chunk_index)`）
  → ⑤ `embedding` 列 `VECTOR(1024)`，BAAI/bge-m3 **本地离线**生成。
- embedding 输入格式由 `embedding_recipe` 记录版本，当前为 **`v2-title-author-chapter`**
  （`Title:` / `Author:` / `Chapter:` 前缀 + 正文；缺失项整行省略，**绝不伪造**）。
- 切块时可归属到章节的块写真实章节名；**无法可靠归属的写 `NULL`，不猜、不填占位值**。
  `chapter_title IS NULL` 的块是**真实正文**（前言、版权页、版式说明等），**不因无章节归属而删除**；
  语义检索默认在查询时排除它们，数据始终保留。

> **⚠️ 已知副作用：整本无章节的书，在默认检索口径下不可见。**
> 实测：`The String of Pearls`（PG 59828）的 7,044 个 chunk，`chapter_title` **全部为 NULL**。
> 这是**过滤策略的代价，不是数据丢失**——放开过滤即可召回。
> 推论：设计验收 Query 时，锚点必须核实其在**过滤口径下**是否真的存在。

### 6A.5 各类失败的记录方式（禁止静默）

| 失败类型 | 记录位置 | 内容 |
|---|---|---|
| 抓取失败 | `_manifest.json` 的 request_log + 失败清单 | URL、HTTP 状态、耗时、重试次数、错误原因 |
| 版权不通过 | 失败清单 | source_id、书名、原因码（如 `death_year_after_limit`、`language_not_en`） |
| 正文校验失败 | 失败清单 | 期望/实际 Content-Length、Range 续传状态、START/END 标记是否齐全 |
| 章节解析失败 | 该块 `chapter_title = NULL` | **正常结果，不算失败** |
| 封面缺失 | `cover_url = NULL` | 真实缺失，不用占位图 |
| embedding 失败 | ingest 失败清单 | source_id、chunk_index、异常类型 |

任何一类失败都**不得用假数据兜底**，也不得静默跳过——必须有清单可查。

### 6A.6 语义检索的质量验证要求

1. **固定 Query 集**：`server/src/scripts/discover-queries-stage2.txt`（16 条 = 6 固定 + 8 新增定向
   + 2 front matter 探针 + 1 负对照；**探针与负对照不计入命中率分母**，过滤开启口径分母为 **13**）。
2. **四个指标分开记录**：精确检索质量（禁用索引）/ ANN 召回率（与精确的 Top-K 重合率）/
   端到端命中率（Top1 / Top3）/ 延迟（P50 / P95，记录冷热与环境）。
3. **必须用 `EXPLAIN (ANALYZE, BUFFERS)` 确认实际执行计划**，不得凭配置推断用了哪个索引。
4. **不得静默返回空结果**。
5. **基线不可变**：已验收的 Query 与期望书籍不得因「总是错」而事后修改。
6. 命中率变化必须给出逐条 A/B，**不接受「感觉变好了」**。

### 6A.7 当前实测状态（截至 2026-10-10，供参考，不是承诺）

- 库内：10 本书、24,244 chunk、24,244 embedding，全部 1024 维，pgvector **0.8.6** / PostgreSQL 18.6。
- 检索（**过滤开启口径，分母 13 条**）：

  | 口径 | Top1 | Top3 | P50 | P95 | 说明 |
  |---|---|---|---|---|---|
  | **精确检索（禁用索引）** | **10/13（77%）** | 12/13（92%） | 72.8 ms | 87.8 ms | embedding + 语料的能力上限 |
  | **最优 ANN**（m=16 / efC=256 / efS=200，真走索引） | 9/13（69%） | 11/13（85%） | 1.2 ms | 2.7 ms | 与精确结果 Top10 重合率 89.2% |
  | 走索引的 40 组 **区间** | 5 ~ 9 / 13 | — | 0.6 ~ 5.2 ms | 2.3 ~ 21.0 ms | **没有任何一组追平精确检索** |

  ⚠️ 任何引用命中率的表述**都必须带上口径与分母**；分母只有 13 条时，1 条 Query = 7.7 个百分点。

- **结论：当前规模（24,244 chunk）精确检索优先；HNSW 已完成实验验证，但不进入生产。**
- 已留档的规模达标预设参数：`m=16 / ef_construction=256 / ef_search=200`。
  **扩量后须重新实测复核，不得直接套用本次读数。**

### 6A.8 HNSW 实验结论（阶段 B，2026-10-10 完成）

- **结论一句话：规模没到，ANN 换不到召回。** 24k 下精确扫描只要 72 ms（P50），离线检索完全可接受；
  换 ANN 能压到 1.2 ms，但要丢 1 条命中且 Top10 重合率只有 89.2%。
- **参数存在非单调行为，不存在「调大就好」的规律**：
  - `m` 越大越好 ❌：`m=32 / efC=64 / efS=40` 只有 5/13（重合率 48.5%，全矩阵最差一批），
    而 `m=8 / efC=128 / efS=200` 能到 9/13。
  - `ef_search` 越大越好 ❌：同一索引下 40 → 100 → 200 的重合率并非单调上升。
- **优化器会在 ef_search 上切换计划**：`ef_search=100` 时 9 个索引配置**全部**被判成 Seq Scan，
  `ef=40` 与 `ef=200` 反而多数走索引。**因此「ef=100 拿到 6/6」不等于参数选对了，
  而是因为那时根本没走索引。** 需要 ANN 时必须显式控制（`force_index` 或调成本参数），不能交给优化器。
- **HNSW 构建有随机性**：同参数（m=16 / efC=64）两次独立构建，Top10 重合率最大差 **20.8 pp**、
  Top1 差 1 条。**小于约 25 pp 的组间差异属于噪声，不应据此选参数。**
- **索引体积与 `m` 无关**：8 种 `(m, ef_construction)` 组合实测均为 189 MB（构建耗时从 4.7 s 到 32.8 s，
  说明参数确实生效）。
- **归因边界**：N5 / N6 / N8 三条，**精确检索也打不中** —— 属于 embedding 与查询措辞的上限，
  调任何索引参数都救不回来。
- **运维约束**：整表重写 embedding 后必须 `REINDEX`（实测索引会从 189 MB 膨胀到 247 MB）；
  pgvector 0.8.6 不支持索引级 `ef_search`，连接池下必须用**事务内**
  `set_config('hnsw.ef_search', …, true)`，禁用裸 `SET`（会污染连接池）。
- **实验副本不得进生产**：`discovered_book_chunks_exp` 与其索引 `exp_hnsw_idx` 已打 COMMENT
  `Stage B experiment only. Do not use in production API.`，API 与前端**均不得**读写这两个对象。
