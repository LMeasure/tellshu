强波动量，**任何单点采样都不能当作稳态结论使用**。压力决策前应当取多次采样。

### 7.2 内存去向（已按进程树去重，修正初版误读）

| 应用 | 实例数 | 进程数 | 合计 WS | 树根 PPid | 启动时间 |
|---|---|---|---|---|---|
| WorkBuddy | **1** | 11 | ~3743 MB | 11312 (explorer) | 2026-10-20 23:14:28 |
| quark | **1** | 20 | 1611.7 MB | 11312 (explorer) | 2026-10-19 19:25:17 |
| Xmind | **1** | 9 | 746.6 MB | 11312 (explorer) | 2026-10-19 00:38:27 |
| MsMpEng (Defender) | 1 | 1 | 350.6 MB | — | — |
| Memory Compression | 1 | 1 | 386.5 MB | — | — |

**初版错误已修正**：此前把 `Get-Process | Sort WS` 输出里的多行 `WorkBuddy` /
`quark` / `Xmind` 读成「多个实例」，实际各自只是一棵 Electron 进程树
（`type=gpu-process` / `utility` / `renderer` / `crashpad-handler` 等子进程）。
因此「关掉多余的 WorkBuddy 实例」这个建议**不成立**。

⚠ **重要**：WorkBuddy 这棵进程树**承载当前会话**，无论如何不可作为释放对象。
真正可被用户自行评估关闭的是 **quark（~1.6 GB）** 与 **Xmind（~0.75 GB）**，
两者合计约 2.36 GB —— **由用户决定是否关闭，我不代为执行**（杀进程是不可逆操作）。

### 7.3 风险假设（**不是结论，需实测验证**）

以下内容属于**待验证假设**，不是在陈述已发生的事实：

- **假设 A**：`shared_buffers = 2GB` 在 PG 启动时一次性预留（本机
  `shared_memory_type = windows`，共享段 pagefile-backed）。若启动时可用内存低于该量级，
  **推测**会加重 Windows 的内存压缩/换页行为。
  ⚠ **尚不可断言「必然触发压缩或换页」**——当前只有「可用内存」与「配置值」两个数字，
  缺少实际的 PF（page fault）/ 压缩率 / PG 启动耗时等证据。
- **假设 B**：若共享段确实被压缩，**推测**稳态 retrieve 可能漂回几十毫秒级。
  ⚠ **这是风险推测，不是实测结果**。B.12 收尾时实测稳态为 8.44~8.87 ms，
  此后未有任何新的延迟测量。

**验证假设 A/B 所需的完整证据链（复测时必须同时记录，缺一不可）：**

1. 启动前后的**可用物理内存**（多次采样，非单点）；
2. PG 启动是否成功、**启动耗时**（对照历史干净启动 vs fsync 34.26 s 的那次）；
3. `SHOW shared_buffers;` / `SHOW effective_cache_size;` 实际运行态值；
4. **缓冲区命中**：`b12-buffer-probe.py` 的 HNSW 节点 `hit` / `read`
   （B.12 基线：hit 3791.5 / read 0）；
5. **查询计划**：确认仍走 `discovered_book_chunks_embedding_hnsw_idx`；
6. **延迟**：`b12-verify-after-tuning.py` 的 retrieve / encode / e2e P50；
7. Windows 侧 `Memory Compression` 的 WS 与系统提交内存变化。

在拿到上述 1~7 之前，**不应对 `shared_buffers` 做任何调整**，也不应
把这些假设当作已证实的性能结论传播。

   **不要在「服务管理」与「pg_ctl 手动启动」之间反复切换**（这是今天一天启停 5 次的根因）。
3. **（授权后）启动 PostgreSQL** —— 启动前先确认无残留 `postgres.exe`；
   陈旧 `postmaster.pid` 交给 PG 自行判定，不手动删；
   启动后立刻用 `SHOW shared_buffers;` / `SHOW effective_cache_size;` 核实运行态参数。
4. **（授权后）启动 API** —— 验证 `/api/discover/health`、
   实际数据库查询、连接池状态。**PG 重启后 API 连接池会残留失效连接 → 500，
   两者必须同时重启。**
5. **环境稳定后复测 B.12 延迟** —— 按 §7.3 的 7 项证据清单全部留存，
   特别是当时的**可用内存**（多次采样）、**缓冲区 hit/read**、**查询计划**。

## 11. 进程树证据（初版「多个实例」误读的更正依据）

`Get-Process | Sort WS` 只能看到「进程」，看不到父子关系，因此会把同一个 Electron 应用的
多个子进程误读成多个实例。更正时用 `Win32_Process.ParentProcessId` 重建了进程树：

```
WorkBuddy.exe  树根 pid=30988  PPid=11312(explorer)
  ├─ 30756  type=gpu-process
  ├─ 31992  type=utility
  ├─ 34380  type=renderer            1520.8 MB
  ├─ 32788                            391.9 MB
  │   ├─ 30540                        123.9 MB
  │   │   ├─ 37124 / 26380 / 39452
  │   └─ 8360
  └─ 13284  type=crashpad-handler
  → 10 个子进程 + 1 个树根 = 同一个实例，合计约 3743 MB

quark.exe      树根 pid=34676  PPid=11312   共 20 进程，1611.7 MB（2026-10-19 19:25 起）
Xmind.exe      树根 pid=20404  PPid=11312   共  9 进程， 746.6 MB（2026-10-19 00:38 起）
```

⇒ 三个应用的树根 PPid 都是 `explorer`(11312)，说明都是用户交互启动的独立应用，
各自**只有一个实例**。可评估关闭的是 quark 与 Xmind；WorkBuddy 承载当前会话，不可动。
