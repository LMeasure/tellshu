## 1. 运行时事实（选型依据，全部实测）

| 事实 | 数值 | 对部署的含义 |
|---|---|---|
| ONNX 模型（int8 逐通道） | **543MB** | Serverless 函数体积上限（Vercel 250MB）直接出局 |
| PG shutree 库 | **1,287MB**（HNSW 索引 456MB 在内） | 必须是有完整 pgvector 的真实 PG 实例 |
| API 启动耗时 | ~2.7s（模型加载） | 冷启动敏感 → 常驻进程优于按需函数 |
| 连接池 | 5~10 连接 + 每连接执行 3 条 init SQL | 常驻进程模型友好 |
| 检索负载 | 只读、低流量（30 本公版书的功能） | 1~2 核足够；性能瓶颈在 PG 不在 API |
| FastAPI CORS | **未配置** | 前端只走同源相对路径 → 生产必须同源反代（即本方案 §4） |
| retrieve 稳态 | 8.44~8.87ms（依赖 shared_buffers=2GB） | **托管 PG 若只给 256MB~1GB，延迟会退回 30ms 档**——保留 ≤15ms 口径需能自调 PG 参数 |

## 2. 部署方案对比与推荐

| 方案 | 结论 | 关键点 |
|---|---|---|
| Vercel Serverless Functions | ✗ 不可行 | 543MB 超函数体积上限；冷启动 3s+；连接池模型不友好 |
| **云 VPS 一体化（推荐）** | ✓ | 一台 2C4G 轻量服务器同机跑 PG18 + FastAPI；DB 迁移=pg_dump/restore（1.3GB，分钟级）；可调 shared_buffers 保住 8ms 档；Caddy 自动 TLS |
| Fly.io | △ 可选 | Docker 常驻、volumes；需 2GB 内存档（543MB 模型 + PG 不能同机则托管 PG 又回到延迟问题）；费用 ~$5+/月 |
| Railway / Render | △ 可选 | 最简单，但免费档休眠=冷启动 3s + 首次检索慢；付费 always-on ~$5-7/月；PG 多为托管小实例，延迟口径需重验 |
| 家用 PG 暴露公网 + 独立 API 主机 | ✗ 不推荐 | 把 127.0.0.1:5432 暴露公网需端口映射+TLS+强密码，安全面不可接受 |

**推荐：VPS 一体化（2C4G/40G，Debian 或 Ubuntu）**。决定性理由：① 检索链路的性能结论（B.12）依赖本机 PG 的 shared_buffers=2GB，托管小实例会退回 30ms 档；② 避免家用 PG 暴露公网；③ 一个 systemd + 一个 Caddyfile 就能常驻，运维面最小。

## 3. FastAPI 上游部署清单（第 2 步落地物）

1. **代码包**：`api/`（FastAPI 只读）+ `requirements-api.txt` + `bge-m3-onnx/model_int8.onnx`（543MB，gitignore，随包上传或挂 volume）。
2. **数据库**：目标机装 PG18（含 pgvector）；本机执行 `pg_dump -Fc shutree` → 目标机 `pg_restore`；`db-conn-init.sql` 照旧（**`SELECT NULL::vector` 不能省**，否则 GUC 不可见）。
3. **运行**：systemd unit（`Restart=always`，`EnvironmentFile=/etc/shutree-discover.env`，权限 600）或 docker-compose 两个 service。
4. **环境变量**（只进目标机 env 文件，绝不进仓库）：`EMBEDDING_BACKEND=onnx`、`HF_HUB_OFFLINE=1`、`DATABASE_URL=postgresql://...@127.0.0.1:5432/shutree`。
5. **监听**：uvicorn 绑 `127.0.0.1:8000`，由 Caddy 反代对外；防火墙只放 80/443，8000 与 5432 不对公网。
6. **健康检查**：`GET /api/discover/health`（已存在，M4 验收过）；Caddy/监控按它做存活探测。

## 4. Vercel 生产路由（第 3 步的精确配置）

`vercel.json` 的 `rewrites` **数组头部**插入（数组顺序即优先级，**必须在 catch-all 之前**；Vercel rewrites 对未命中静态文件的路径按数组序逐条匹配）：

```json
"rewrites": [
  { "source": "/api/discover/:path*", "destination": "https://<FastAPI公网域>/api/discover/:path*" },
  { "source": "/(.*)", "destination": "/index.html" }
]
```

要点：
- `:path*` 透传必须带（`/health` 等子路径依赖它）；
- `<FastAPI公网域>` 未确定前**不落地此规则**——写死链 destination 会让生产检索比现状（HTML 错误态）更糟；片段保存在此，主机就绪后一次填入；
- 同源反代后 FastAPI 无需配 CORS（§1 事实），前端 `discoverClient` 零改动；
- 旁路后端其余路径（Node 8787 的词典/OCR）同样不在生产拓扑中，将来上线同理在 catch-all 前追加规则。

## 5. 部署后验收（第 4 步，主机就绪后按序执行）

  -H 'Content-Type: application/json' \
  -d '{"query":"crime and punishment","top_k":3}'
# 2) 健康检查
curl -s https://<域>/api/discover/health
# 3) 浏览器真实检索场景（39 项中的真实路径；异常态 mock 场景可同跑）
