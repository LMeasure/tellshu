# 转写链路修复 · 实施前核验报告（终版）

> 核验范围：转写结果持久化与阅读器接入、TXT/SRT/VTT/CSV 导出、学习稿 HTTP 500。
> 方法：只读阅读真实代码 + 对当前运行的本地后端（:8787）、Vite dev（:5173）做实请求复现 + 临时 Vite 死目标实证。
> 结论：下载与 500 的"表象故障"均**非导出/路由代码逻辑错误**，根因在"状态未固化/接线未完成"与"代理层兜底缺失"。

---

## 一、两个问题的真实根因（已实证）

### 1. 学习稿 HTTP 500 —— 来自 Vite 代理层，而非后端路由

- `server/src/routes/ai.ts`（HEAD 已提交版本）本就分层正确：
  - 写 SSE 头**之前**：未接入 503 / 坏请求 400 / 超段数 400（`AI_MAX_SEGMENTS` 默认 1200，257 段不触发），统一 JSON 错误体；
  - 写 SSE 头**之后**：LLM 失败在 `llm.ts` 包成 `LlmError`，路由层转 SSE `error` 事件，**HTTP 状态恒 200**。
- 实测（2026-10-22 13:2x，后端 8787 在跑、AI 已配 DeepSeek）：
  - 直连 `POST 8787/api/ai/study-notes` → **HTTP 200 + 合法 SSE**（4.0s，真实 delta/done）；
  - 经 `5173` 代理同一请求 → **HTTP 200 + 合法 SSE**（3.6s）。
- **实证复现用户看到的 500**：临时起一个 Vite（5199）把代理指向死端口 8999，同一请求 →
  `HTTP/1.1 500 Internal Server Error`（text/plain 空体），服务端日志 `[vite] http proxy error: /api/ai/study-notes / Error: connect ECONNREFUSED`。
- 根因归类：**代理层兜底缺失**。本机既有风险（命令行结束清整棵进程树、后端并不总活着）一旦命中，
  前端拿到裸 500 + 非 JSON 体，`llmClient` 只能显示「请求失败（HTTP 500）」——与用户截图一致。
- 附带发现：该 503/500 若来自代理层，`StudyNotePanel` 的 `status === 503 → 「AI 未接入」空态`会误报
  （后端没启动 ≠ AI 未接入），需按错误码区分。

### 2. 下载无效 —— 导出函数正确，故障在"状态未固化 + 末态丢失"

- `subtitle.ts` 的 `toTxt/toSrt/toVtt` 经单测验证输出正确（序号连续、时间码合法、空段跳过）；`toCsv` 领域函数已在工作树（上一会话未提交成果）但 UI 无按钮。
- `download.ts` 的 Blob + a.click + 1s 延迟回收是标准写法；全仓无 CSP，排除 blob 被拦截。
- 故障真正来源：
  - `MediaTranscriptImport` 的 `transcript`/`media` 是**纯内存态**（`useState(null)`）；刷新后清空，
    `transcript === null` 直接走 EmptyState，导出按钮不渲染；
  - 即使还在页面内，`exportAs` 第一行 `if (transcript === null || media === null) return`——转写成功后
    若用户移除过文件或刷新过，`media` 为 null，点击静默无响应（无错误提示）；
  - 缺 CSV 按钮；`downloadTextFile` 不分格式 MIME、失败静默。

## 二、转写结果进入阅读器：数据流与实现方式

现状（已确认缺口）：

- 转写成功：`transcribeAndSave` → `saveTranscriptRecord` 写 Dexie `transcripts`（id=ASR jobId、segments、duration、language、fileName）。
- 阅读器：`Import.tsx`「我的素材」读 `readings` 表；`Reader.tsx` 按 `doc.id` 打开渲染 `content`。
- **桥接函数已在工作树但接线未完成**：`store.ts` 有 `ensureTranscriptReading`（幂等键 `t_<jobId>`，复用
  `learning.saveReading` 正式领域入口）、`backfillTranscriptReadings`、`getLatestTranscriptRecord`、
  `reconcileTranscriptReadings`；但 `transcribeAndSave` 不调它、`main.tsx` 不跑 reconcile、组件不回读。
- `ReadingType` 已含 `'transcript'`，`ReadingDoc.segments?` 已加，`saveReading` 已透传 segments（上一会话成果，未提交）。

实现方式（复用现有领域层，不绕过；本次补完接线）：

1. `transcribeAndSave` 成功后调 `ensureTranscriptReading(result, fileName)`（独立 try/catch，失败仅告警——
   维持"持久化是增强不是前提"口径，绝不影响转写结果展示）。
2. `main.tsx` 在 `initStorage()` 后跑一次 `reconcileTranscriptReadings()`（幂等补齐历史，失败仅告警）。
3. `MediaTranscriptImport` 挂载回读 `getLatestTranscriptRecord()`：刷新后最近一次转写立即可导出/生成学习稿；
   `exportAs` 不再依赖 `media`，文件名取 `transcript.fileName`。
4. 历史任务重复触发/重复刷新 → 同一 `t_<jobId>` 幂等键，`saveReading` 保留 created_at/进度/书架状态，不产生重复资料。

## 三、历史数据盘点与自动补齐（诚实结论）

| 数据位置 | 状态（实测） | 可否自动恢复 |
|---|---|---|
| 浏览器 Dexie `transcripts` 表 | M1 代码路径保证 done 即写（落库失败仅 console 告警不阻断）；**用户设备上的实际内容无法从本机直读** | ✅ 修复后刷新页面即回读 + 启动自动补齐阅读器关联 |
| 服务端 JobStore（内存 Map + TTL 2h） | 两个历史任务实测 **404**：257 段 `2bc71d3f…`（今日 09:51 生成，已超 TTL）、461 段 `59630b62…`（The Eye of Apollo） | ❌ 内存态，重启/过期即丢，无 API 可捞 |
| 服务端磁盘 `data/asr/out/*.json` | 6 个结果文件在盘上（含上述两个），是 sidecar 产物 | ⚠️ 不在产品数据模型内（红线：PG 不建 asr 表；ASR 领域逻辑不改）。恢复需新增强制导入入口，**超本次范围**，列为后续建议 |
| PG 数据库 | 只存账号/系统配置/发现检索数据，无 asr 表（架构红线） | — |

补齐策略：以 `t_<transcript.id>` 为幂等键，**仅当对应 reading 不存在时新建**，不覆盖、不删除、不重生成；
冲突时保留原数据并报告。不存在"只有前端临时态"的转写——产品链路转写即落 Dexie；若用户设备上
Dexie 确实缺失（当时落库失败 / 换了浏览器 / 清了站点数据），则数据已不在产品任何存储中，
**明确说明无法自动恢复，不谎称可以**；磁盘 out/*.json 仍可作为人工恢复的原料。

## 红线遵守

- 不删除/清空/重建任何既有转写；不重传文件、不重新转写、不要求用户手动导入。
- 不绕过领域层直拼库：复用 `saveReading` / `upsertStudyNote` / `transcribeAndSave` 现有入口。
- 不伪造学习稿/字幕/时间；LlmError/内部堆栈不暴露给用户；失败不影响已存转写与阅读器入口。
- 不改 ASR 领域逻辑（JobStore/TTL/磁盘产物一律不碰）、不改阅读器分页、不换端口、不动锁定依赖。
