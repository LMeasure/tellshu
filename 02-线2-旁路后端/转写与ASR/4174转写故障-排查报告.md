## 1. 结论（根因）

**4174 端口上的 Vite preview 服务已经退出；浏览器里打开的页面是 PWA Service Worker 缓存渲染的「僵尸页」。** 页面外壳能显示（SW 预缓存 + navigateFallback），但转写时 `/api/asr/jobs` 请求打到没有任何进程监听的 4174，在 **TCP 层即连接被拒**，于是浏览器报 `net::ERR_CONNECTION_REFUSED`，fetch 抛出 `TypeError: Failed to fetch`。

**这不是代码缺陷，也不是后端故障**：8787 API 与 8177 ASR sidecar 全部健在，且今天 14:42 还成功跑完一次真实转写（10 分钟中文新闻音频，604.65s / 257 段，结果仍在 JobStore 中可查）。

preview 退出的原因：它此前是以**普通前台命令**方式启动的（`/tmp/preview4174.log` 显示 `vite preview --host --port 4174 --strictPort`），该 CLI 会话结束时整棵进程树被环境清理。这是本环境已知行为（见 MEMORY.md：命令行结束清进程树，常驻服务必须放后台常驻任务）。

### 第 3 步：分层失败定位

| 层 | 判定 | 依据 |
|---|---|---|
| 浏览器 → 4174 预览服务器 | ❌ **失败在这一层** | TCP `Connection refused`（curl 复现 + 浏览器 `ERR_CONNECTION_REFUSED`）。注意：这与「代理目标拒绝」表现不同——后者会经过 preview 转发并返回 HTTP 503 JSON |
| preview → 8787 代理 | ⚪ 未走到（上游已断） | preview 进程不存在 |
| 8787 API | ✅ 正常 | 上述 404 JSON 实证 |
| 8787 → 8177 ASR | ✅ 正常 | 14:42 任务 `73f29bef-3577-4726-b1f0-a9b811b05886` 状态 `done`，`GET /api/asr/jobs/73f29bef-...` 仍返回完整结果（TTL 2h 内），duration 604.65s / 257 段 |

**僵尸页成因**：本应用是 PWA（`vite-plugin-pwa`，`registerType: 'autoUpdate'`，预缓存应用外壳 + `navigateFallback: index.html`）。preview 退出后，已激活的 Service Worker 仍控制 `localhost:4174` 源：导航请求回退到缓存的 `index.html`（所以页面照常打开），而 `/api/asr/jobs` 不在 workbox runtimeCaching 规则内，SW 放行 → 直连网络 → 端口无人监听 → 连接被拒。

### 第 4 步：`getTopURL` / `runtime.lastError` 归因

- **全仓库零匹配**：`getTopURL` 在 `src/`、`server/`、`scripts/` 中 grep 无任何结果；本应用也没有任何 `chrome.*` / `browser.*` API 调用（web 应用，非扩展）。
- `getTopUrl` 是浏览器**扩展 content-script ↔ background 消息传递**的常见命名（Stack Overflow #55583469 等）；页面上下文里调用未定义助手而抛 `ReferenceError`，是扩展注入脚本的典型症状。
- `runtime.lastError`（典型文案 "Unchecked runtime.lastError: Could not establish connection. Receiving end does not exist."）同样只可能来自扩展的 `chrome.runtime` 消息通道。
- **结论：两者均为浏览器扩展注入噪声，与转写故障无因果关系。按用户要求，不改业务代码。** 用户可自行验证：Edge 无痕窗口（默认禁用扩展）打开同一页面，这两条报错即消失。

## 3. 最小修复方案（**待确认后执行**）

纯运营操作，**零代码改动**：

1. **以后台常驻任务方式重启 preview，端口必须仍是 4174**（`vite preview --host --port 4174 --strictPort`）。
   - 为什么必须 4174：IndexedDB / Service Worker / CacheStorage 都按源（`localhost:4174`）隔离。换端口 = 换源 = 用户已保存的转写数据、阅读进度全部「看不见」（不是丢，是留在 4174 源里）。
   - 为什么必须常驻：前台命令随 CLI 会话结束被进程树清理，这正是本次故障的成因。
2. 启动后用户在浏览器**刷新页面**即可（SW autoUpdate 会更新到最新构建；Dexie 数据不受刷新影响）。
3. 随后按用户要求用**真实音频**验证完整链路：浏览器 → `/api/asr/jobs` → 8787 → 8177 → 结果持久化 → 阅读器可见。
4. 验证通过后跑回归四件套（tsc / npm test / build / check_pwa）+ 转写 E2E，提交证据。

备选（不推荐作为日常）：dev 5173 目前活着且代理链正常，可临时测试转写；但 5173 是**不同源**，其 IndexedDB 与 4174 相互独立，且 dev 不启用 SW。只适合临时验证，不适合接着用 4174 里已有的数据。
