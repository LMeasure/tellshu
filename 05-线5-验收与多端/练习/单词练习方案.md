一、功能目标与范围

1.1 功能目标

新增独立的「单词默写」练习模式：

从用户现有生词本中选择待练单词。
隐藏英文单词，展示中文释义。
用户输入英文并提交。
连续正确 3 次后，当前单词完成。
任意一次错误立即将连续正确次数重置为 0。
单词完成后进入下一个待练单词。
保存练习会话、单词结果和必要的统计信息。
本轮结束后，由生词本现有复习机制独立决定下次复习时间。

1.2 MVP 范围

必须实现：

生词本选词。
随机、最近新增、易错词等基础选词模式。
连续正确 3 次的状态机。
错误重置、手动跳过和完成反馈。
会话持久化、暂停恢复和放弃。
桌面端与移动端输入适配。
归属校验（本地 owner）、request_id 幂等提交和单文档写入的数据一致性控制。
练习结果页。
自动化测试与既有功能回归。

暂不实现：

AI 拼写判定。
AI 自适应改变连续正确目标。
复杂拼写错误诊断。
新建一套独立复习算法。
排行榜、社交挑战和复杂成就系统。
完整离线答题队列。

二、不可违反的业务规则

2.1 核心计数

每个单词维护以下运行时计数：

targetCorrect：当前单词所需连续正确次数，默认值为 3。
consecutiveCorrect：当前连续正确次数。
totalAttempts：当前单词的有效提交次数。
correctAttempts：当前单词的正确提交次数。
wrongAttempts：当前单词的错误提交次数。
wordStatus：当前单词的状态。

计数规则：

正确提交：当前单词的 totalAttempts、correctAttempts、consecutiveCorrect 各增加 1。
错误提交：当前单词的 totalAttempts、wrongAttempts 各增加 1，consecutiveCorrect 归零。
连续正确达到 targetCorrect 后，当前单词进入 COMPLETED。
手动跳过进入 SKIPPED，不计入已完成数量。
同一有效请求只能计数一次；重复请求必须返回原处理结果。
单词完成、跳过或不可用后，不得因重复请求重新计数。
目标值通过统一配置定义，不在多个组件中硬编码。

2.2 会话级统计

会话级计数由会话中所有单词的单词级计数聚合得出：

sessionTotalAttempts = Σ word.totalAttempts
sessionCorrectAttempts = Σ word.correctAttempts
sessionWrongAttempts = Σ word.wrongAttempts

会话级正确率：

sessionCorrectAttempts / sessionTotalAttempts × 100%

当 sessionTotalAttempts = 0 时，正确率显示为"—"。

会话级完成率：

completedWords / totalWords × 100%

跳过或不可用的单词不计入已完成数量。跳过操作本身不属于答题提交，不进入正确率分母。

统计口径约束：

单词级计数用于单词详情、易错词排序及单词历史分析。
会话级计数用于本次练习结果页和历史会话对比。
前端不得将某一个单词的计数直接作为整场会话的统计值。
本地会话文档应以持久化队列为事实来源，统一生成会话级聚合结果（`aggregateSession()` 实时算）。
如果存在单独保存的会话级汇总字段，必须保证它与单词级记录一致；不得让两套计数独立演化。

2.3 拼写判定

默认英文大小写不敏感。
去除输入首尾空格。
不自动修正拼写。
不将近似拼写判定为正确。
短语、连字符、撇号等特殊情况，先检查现有词库数据，再定义标准化规则。
拼写判定采用确定性逻辑，不调用 AI。

D6 已裁定（依据阶段一实测数据，`data/linguabase/v1/search-index.json` 22,791 条）：

| 实测事实                                     | 规则                                                             |
| ---------------------------------------- | -------------------------------------------------------------- |
| 含空格 0 条                                  | 无短语答案，无需处理多词比对                                                  |
| 含连字符 70 条（0.3%，如 `baby-sit`）            | **严格比对**：`-` 不等价于空格（`co-pilot` ≠ `copilot`，两者是不同拼写）          |
| 含撇号 0 条                                  | 无需处理 `'`                                                      |
| 含大写 56 条（African / AIDS / Chinese… 均为专有名词） | **大小写不敏感是硬需求**，否则专有名词永远判错                                     |
| 脏数据 1 条 `discombobulated[`              | **选词阶段过滤**（下文正则不放行任何非字母字符），不在默写功能里修数据                        |

**判定公式（唯一口径，不得在其他组件里各写一份）**：

```
normalizeInput(x) = x.trim().toLowerCase()
judgeSpelling(input, answer) = normalizeInput(input) === normalizeInput(answer)
```

**有效答案校验（选词阶段执行，D6）**：答案经 `trim()` 后必须匹配
`/^[A-Za-z]+(?:['-][A-Za-z]+)*$/`，否则该词条**排除出选词池**并记录排除原因（对应 §8「英文为空/异常」）。
宽字符撇号 `’` 一并放行，但当前词库实测为 0 条。

**空白提交**：空白 / 纯空格提交视为**无效提交** —— 不计入 `totalAttempts`、不影响连续正确次数，返回 `result='invalid'`，UI 层在提交按钮上前置拦截。避免误触回车把单词打回 0。

三、状态机设计

3.1 单词状态

PENDING：待练。
IN_PROGRESS：练习中。
COMPLETED：本轮完成。
SKIPPED：用户主动跳过。
UNAVAILABLE：词条已删除、失效或没有有效答案。

3.2 会话状态

IN_PROGRESS：进行中。
PAUSED：暂停。
SESSION_COMPLETED：全部处理完成。
ABANDONED：用户主动放弃。

3.3 状态转换
当前状态   事件   条件   新状态及动作
PENDING   开始练习   词条有效   转为 IN_PROGRESS

IN_PROGRESS   正确提交   未达到目标   保持 IN_PROGRESS，连续正确次数加 1

IN_PROGRESS   正确提交   达到目标   转为 COMPLETED，保存完成结果

IN_PROGRESS   错误提交   任意情况   保持 IN_PROGRESS，连续正确归零，累计错误次数加 1

IN_PROGRESS   手动跳过   用户确认操作   转为 SKIPPED

PENDING 或 IN_PROGRESS   词条失效   已删除或无有效答案   转为 UNAVAILABLE，记录原因并推进队列

当前词条终态   自动推进   还有待练词条   加载下一词

当前词条终态   自动推进   没有待练词条   转为 SESSION_COMPLETED

IN_PROGRESS   暂停或退出   —   转为 PAUSED

PAUSED   恢复   会话有效   转为 IN_PROGRESS

PAUSED   放弃   用户确认   转为 ABANDONED

COMPLETED、SKIPPED 或 UNAVAILABLE   再次检查词条有效性   任意情况   保持原终态，不执行状态转换

表中"新状态及动作"统一描述状态结果和必要副作用，不再混用纯状态名与动作描述。

词条失效转换约束：

词条失效转换仅适用于 PENDING 和 IN_PROGRESS 状态。

以下状态属于终态：

COMPLETED
SKIPPED
UNAVAILABLE

终态词条不得因恢复会话、重新查询生词本或其他设备修改词条而被重新分类。

具体要求：

恢复会话时，可以检查所有队列词条，但只有 PENDING 和 IN_PROGRESS 词条允许因失效转为 UNAVAILABLE。
COMPLETED 词条即使对应的生词本条目已被删除，也必须保留原完成状态及历史计数。
SKIPPED 词条保持跳过状态，不得被重新标记为完成或不可用。
UNAVAILABLE 词条保持不可用状态，不得重复增加不可用计数。
会话级 completedWords、skippedWords、unavailableWords 必须依据各词条唯一的当前状态计算，不得因重复检查重复累计。
队列推进、状态变更和会话统计必须保持一致。

3.4 推进规则

单词完成后显示"连续正确 3 次"，停留 1–2 秒后自动进入下一词。
用户可以点击"继续"立即进入下一词。
手动跳过后立即进入下一词，并提示该词未完成。
如果当前词条在会话过程中被其他设备删除，标记为 UNAVAILABLE，提示用户后自动推进。
当前会话中的词条队列不因生词本后续新增词条而自动改变。

四、会话、队列与恢复

> **D1 重锚定**：以下所有「服务端」= **本地事实源（Dexie / IndexedDB）**。述树主学习链路纯离线（`server/` 五个迁移无任何学习数据表；`auth` 本地桩、`sync` 远端内存桩），MVP 不存在可依赖的服务端。

4.1 队列持久化

创建会话时，必须向本地 Dexie 持久化完整的有序词条清单，**以「会话 + 队列」单文档形式一次性写入**（至少包括）：

会话 ID。
词条 ID。
队列位置。
创建时的必要词条快照（word / definition_zh / ipa / pos）。
当前词条状态。
计数和完成状态。
会话状态、开始 / 暂停 / 结束时间。
已处理请求映射表（幂等回放用）。

**为什么必须是单文档**：`src/services/storage/types.ts` 的 `TableService` 只有单表单行 CRUD，**没有任何事务 API**，Dexie 实例不外泄。只有把队列内嵌进会话文档，一次 `put()` 才能同时完成「计数更新 + 状态变更 + 队列推进」，**天然原子**，且不必扩张存储契约（见 §5.1 / §5.4）。

恢复会话时，必须从 Dexie 读取持久化的会话文档，恢复原始队列顺序和剩余词条，不得依赖前端内存中的临时数组（React Router 无 keep-alive，组件卸载即丢）。

4.2 恢复内容

恢复时保留：

consecutiveCorrect。
totalAttempts。
correctAttempts。
wrongAttempts。
当前队列位置。
所有词条状态。
已完成、已跳过和不可用的单词。
会话开始时间和累计耗时信息。

已删除的词条恢复时标记为 UNAVAILABLE，记录原因并继续后续词条。仅 PENDING 和 IN_PROGRESS 状态的词条允许执行此转换；终态词条保持原状态不变。

**存量事实**：`domain/learning.removeFromVocab()` 是**硬删除、本地不写墓碑**（软删 `deleted_at` 只出现在同步载荷里）⇒ 「已删除」只能靠会话恢复时 `vocab.get(word_id) === undefined` 判定，这也是队列必须保存词条快照的原因（词条删了仍能展示与统计）。

4.3 并发会话

每个本地用户（当前恒为 `owner: 'guest'`）最多允许一个活跃默写会话。
再次进入时，若存在活跃会话，提供"恢复练习"或"放弃并新建"选项。
新建会话不能静默覆盖旧会话。
原子性由 **Dexie 单文档 `put()`** 提供：在同一个 `put()` 内完成「检查是否已有活跃会话 → 创建」，不使用事务 API（当前存储抽象层没有）。
多标签页并发：两个标签页同时新建时，后写入的 `put()` 覆盖先写入的同 key 文档 ⇒ 约定**以 `id` 唯一键写入并在写入前后各校验一次活跃会话**，冲突时后进入的标签页走「恢复练习」路径。真正的 multiprocess 互斥在 IndexedDB 上做不到，也不假装做得到。
暂停超过 7 天时，提示用户恢复或放弃；MVP 不静默删除历史记录。**暂停超期判定在本地执行**（比较 `paused_at` 与 `Date.now()`）。

五、数据模型与存储原则

阶段一已审查完毕，结论：**优先复用既有 `vocab` / `reviewLog`，不新造等价结构**；会话统一为单文档。

5.1 单文档模型（定稿，替代原「会话表 + 队列表」两张表）

```
表 spellingSessions（Dexie version(10) 新增）
行 = {
  id, type: 'spelling', owner: 'guest',
  status: 'IN_PROGRESS' | 'PAUSED' | 'SESSION_COMPLETED' | 'ABANDONED',
  selection_mode: 'random' | 'recent' | 'wrong',
  target_correct, total_words, current_position,
  started_at, updated_at, ended_at?, paused_at?,
  queue: [ ...词条，见 5.2 ],
  processed_requests: { '<request_id>': <AttemptResult> }
}
```

索引建议：`id, status, started_at, owner`（见 5.4）。**不给 queue 内的字段建索引**（IndexedDB 不索引对象数组的内嵌属性）。

5.2 队列词条（内嵌文档）

```
{
  word_id, word, definition_zh?, ipa?, pos?,      // 快照：词条被删也能展示与统计
  position, status: 'PENDING'|'IN_PROGRESS'|'COMPLETED'|'SKIPPED'|'UNAVAILABLE',
  consecutive_correct, target_correct,
  total_attempts, correct_attempts, wrong_attempts,
  last_attempt_at?, unavailable_reason?,
  srs_reported: boolean                            // D2：防重复调用 recordQuiz
}
```

⚠️ 命名说明：`consecutive_correct` 与 `VocabEntry.consecutive_correct` **同名但语义完全不同** ——
前者是本会话文档内的计数（目标 3，会话结束即失去意义），后者是跨会话持久、阈值 5、驱动 SRS 晋级的字段。
**默写计数绝不写入 `VocabEntry`**，两者分属不同存储实体，互不干扰。

5.3 会话级聚合：**一律实时计算，不存汇总字段**

会话级 `total_attempts / correct_attempts / wrong_attempts / completed / skipped / unavailable / accuracy / completion_rate`
在渲染时由 `aggregateSession(queue)` 现算（与现有 `getLayerCounts` / `getDailyStats` 的实时聚合风格一致）。
这样 §2.2「如果存在单独保存的会话级汇总字段，必须保证它与单词级记录一致」这条风险**从根上不存在**。

原 5.1 的会话级聚合字段与 5.2 的 `word_snapshot` / `word_version` 选项**予以删除**（已被 §5.1/§5.2 覆盖）。

5.3.1 答题事件

MVP **不新增逐次答题事件表**，复用既有 `reviewLog`（`word_id / at / correct / quiz_form`，已有 `word_id` 索引）：
单词 COMPLETED 时由 D2 的交接点写入一条 `quiz_form='spelling'`。
用户的错误输入**不落盘**（符合方案原「数据最小化」原则，也符合产品红线「不保存不必要的学习明细」）。

5.4 索引建议

根据真实数据库字段和查询计划确认后，再决定是否创建索引。

优先检查：

活跃会话：单列 `status`（等值查 IN_PROGRESS），配合走一次全表过滤即可，规模小不建议复合索引。
历史会话：`started_at`（倒序取最近 N 条）。
多端隔离：`owner`（与现有 vocab / reviewLog 一致，当前恒为 `'guest'`）。
~~会话词条队列 (session_id, position)~~：单文档内嵌，无需索引。
~~单词历史记录 / 到期复习查询~~：沿用既有 `reviewLog.word_id` 与 `vocab.next_review`，不新增。

**执行前必须走既有迁移规范**：`src/services/storage/web.ts` 只允许**新增** `version(n).stores({...})`，不得改历史版本 ⇒ 本功能新增 **version(10)**。迁移在阶段三执行；阶段二不涉及任何 schema 改动。

六、接口设计（本地函数契约）

**已确认**：述树无常驻学习服务端，因此本功能的「接口」是 **`src/domain/spelling.ts` 的本地函数契约**，不是 HTTP。
分层遵循前提卡：页面 → `src/domain`（业务规则，平台无关）→ `src/services/storage`（持久化）。
阶段二交付的全部是**纯函数**：不 import 任何 storage，可在 Node/tsx 下直接单测。

6.1 获取待练单词

输入：

选词模式。
选词数量。
可选的词库或筛选条件。

输出：

实际选中的词条。
实际选词数量。
队列顺序。

如果请求数量大于可用词数，按实际可用数量创建会话并提示用户。

6.2 创建会话

负责：

验证当前本地 user_id 与会话归属一致（本地实现无多用户场景；`owner` 当前恒为 `'guest'`，字段保留以兼容将来账号接入）。
检查是否已有活跃会话：存在活跃会话时不允许静默新建，必须走「恢复练习」或「放弃并新建」。
创建会话并**一次性 put** 完整有序队列（单文档，见 §5.1）。
初始化计数和状态。
校验并排除不可用词条（英文无效 / 无释义），记录排除原因。

6.3 提交答案

逻辑请求（`ApplyAttemptOptions`）：

{ word_id, input, request_id, now? }

逻辑响应（`AttemptResult`，同时也是写入 `processed_requests[request_id]` 的回放值）：

{ request_id, word_id, result, word_status, consecutive_correct, target_correct,
  total_attempts, correct_attempts, wrong_attempts,
  next_word_id, session_status, progress, srs_due, at }

其中 `progress` = `{ completed, skipped, unavailable, total }`（均为**会话级实时聚合**，不是当前单词的值）。
`total_attempts / correct_attempts / wrong_attempts` 是**当前单词级**值（原方案口径不变）。

要求：

用户身份从**本地认证上下文**获取 user_id，校验与会话归属一致。
验证会话归属（session 存在且 owner 一致）与词条归属（word_id 在会话队列内）。
验证当前词条仍处于允许提交的状态；终态词条直接返回当前状态，不重新计数。
使用 request_id 保证幂等：命中 `processed_requests` 直接回放原结果。
计数更新、词条状态更新、请求结果记录及队列推进在**同一次 `put()`** 内完成，保持一致。
重复请求返回原始处理结果，不重复计数。
本地实现无跨用户访问路径，天然不向他人暴露数据（数据只在本机 IndexedDB）。

**result 取值（阶段二实现落地时补全了两项）**：`'correct' | 'wrong' | 'invalid' | 'skipped' | 'terminal'`。
`'invalid'` = 空白提交：**不计入 total_attempts，不影响连续正确次数**（见 §2.3）。
`'terminal'` = 词条已是终态（COMPLETED / SKIPPED / UNAVAILABLE），本次**未计数、不推进**（方案 §2.1「终态不得因重复请求重新计数」）。

**会话非 IN_PROGRESS 时的行为**：`PAUSED` / `ABANDONED` 下提交**抛错**（属于调用方状态违规，要立刻暴露）；
`SESSION_COMPLETED` 下**不抛**，走到这里的词条必然已是终态，按 `terminal` 返回 —— 会话结束后用户又点一下是正常交互，不该崩。

**SRS 交接点（D2）**：当且仅当词条由非终态转为 `COMPLETED` 时，由调用方（阶段三）执行一次
`recordQuiz(word_id, true, 'spelling')`，并置 `srs_reported = true`；恢复会话后见到 `srs_reported === true` 不得重复调用。
`SKIPPED` / `UNAVAILABLE` **不调用**；默写过程中的单次对错也**不调用**。
响应里的 `srs_due = true` 表示「本次产生了交接义务」，由调用方负责执行，成功后调用 `markSrsReported()` 落标记。

6.4 其他接口职责

获取会话进度（`aggregateSession`）。
暂停或恢复会话。
跳过当前词条（同样使用 request_id 保证幂等，重复请求返回原处理结果，不重复推进）。
放弃会话。
获取练习历史。
获取会话结果。

**已确认的最终契约**（路径在本行定稿，不再变更）：

八、异常处理

| 场景        | 处理方式                                                                                      |
| --------- | ------------------------------------------------------------------------------------------- |
| 生词本为空     | 展示 `EmptyState` 和添加生词入口（不使用假数据）                                                            |
| 英文为空 / 含非字母字符（如 `discombobulated[`） | **选词阶段排除**并记录排除原因；不在默写功能里修数据（阶段一实测：此类 1 条）                                                  |
| 释义为空      | 默认排除并提示补全（阶段一实测：缺释义 5 条）                                                                      |
| 当前词条已删除   | 标记 UNAVAILABLE，提示并推进（本地为硬删除 ⇒ 靠 `vocab.get(word_id)` 查不到判定；终态词条不重分类）                      |
| 网络中断      | **本地实现无网络依赖**：提交不经过网络，不存在「假报成功」路径。若 Dexie `put()` 抛错，保留输入并提示失败                             |
| 重复提交      | request_id 命中 `processed_requests`，返回原处理结果，不重复计数                                            |
| 会话过期      | 暂停超 7 天提示「恢复 / 放弃」，判定在本地执行；不静默删除历史记录                                                        |

| 请求数量超限    | 按实际可用数量创建会话并提示用户                                                                              |
| Dexie 写入失败 | `put()` 失败**不返回成功**；单文档写入保证状态和计数不发生部分提交                                                      |

原「完整离线答题队列」不适用：本功能本身全离线，无需离线队列。
