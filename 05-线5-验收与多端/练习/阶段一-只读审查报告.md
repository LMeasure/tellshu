## 0. 一句话结论

方案整体自洽，但它的**一半前提在当前架构里不存在**：述树主学习链路是**纯前端离线**（Dexie/IndexedDB，无账号、无服务端、无跨设备同步），方案里的「服务端权限校验 / 服务端持久化队列 / 服务端原子创建 / 跨设备恢复」四项没有落点。

因此阶段二必须先把「服务端」语义**重新锚定到本地单一事实源 + 本地幂等 + 本地原子写**，否则方案里的 P0/P1 验收项无法被执行。其余部分（连续正确 3 次状态机、错误重置、跳过、会话统计口径、拼写判定）都能在现有分层里干净落地，且有现成代码可复用。

## 3. 阶段一「必须额外核实」的 5 个问题 —— 逐条回答

### Q1. 现有数据模型是否明确区分单词级计数与会话级统计？
**否。** 当前只有两层：
- 单词级：`VocabEntry.consecutive_correct`（跨会话持久，用于 SRS 晋级，阈值 `PASS_THRESHOLD = 5`）、`srs_step`、`in_wrong_pool`；
- 事件级：`reviewLog`（每次作答一行：`word_id / at / correct / quiz_form`）。
**没有会话级实体**，所以「会话级 vs 单词级」目前不存在混淆风险——但这也意味着方案 §2.2 的约束（"不得让两套计数独立演化"）**建议直接按「只存单词级 + 事件级，会话级一律实时聚合」实现**，从根上消除漂移。

### Q2. 现有结果页和历史记录采用何种正确率口径？
- `/result`（PracticeResult）**没有任何真实口径**：答对显示 `— / —`、完成度 `0%`、连续天数 `0 天`，页面上明写「真实成绩将在接入学习数据与分层掌握后计算（Phase 1）」。这是**诚实的未接入占位**，不是假数据，但也不是可复用的口径实现。
- 历史记录只有 `reviewLog` 逐次事件；`getDailyStats` 用 `reviewLog` 行数当「当日复习次数」，**没有正确率**概念。
→ 方案 §2.2 的正确率口径（`correct / total × 100%`，跳过不入分母，total=0 显示"—"）是**全新定义，无历史包袱**，落到新会话表即可。

### Q3. 恢复逻辑是否会对已完成 / 已跳过词条执行失效转换？
**不存在该风险**（此前没有任何恢复逻辑）。但有一个相关事实要注意：
`removeFromVocab()` 是 **硬删除**（`T.vocab.delete(word_id)`），本地不写墓碑；软删 `deleted_at` 只出现在同步载荷里。所以方案里的「词条已删除 → UNAVAILABLE」只能靠**会话恢复时 `vocab.get(word_id) === undefined` 来判定**，且必须与「终态词条」区分开（终态不重分类）。

### Q4. 会话统计是实时聚合还是保存汇总值？如何保证一致？
**既有实现全部是实时聚合**：`getLayerCounts()` / `getDueReviews()` / `getStreakDays()` 都是 `toArray()` 后 filter/sort/reduce，没有汇总字段。
→ 建议新功能**沿用实时聚合**：会话表只存单词级计数，结果页用时现算。这样方案 §2.2「如果存在单独保存的会话级汇总字段，必须保证它与单词级记录一致」这条风险**直接不存在**。

### Q5. 数据库事务和幂等机制能否保证状态、计数、队列推进原子一致？
**不能，且这是当前抽象层的硬缺口：**
- `TableService`（`src/services/storage/types.ts`）只有 `get / put / add / delete / toArray / bulkGet / bulkPut / count / whereIndex / whereStartsWith / clear`，**没有任何事务 API**；Dexie 实例 `db` 是 `web.ts` 的模块私有变量，不外泄。
- 现状代码甚至有 TOCTOU：`addToVocab()` 是 `get()` 后 `put()`，两个 await 之间无保护。
- `reviewLog.uid` 是 UUID，索引**不唯一**（`reviewLog: '++id, word_id, at, uid, owner'`），只作同步标识，不作幂等键。
→ **最小改造方案**：把「会话 + 队列」设计成**单文档**（session 行内嵌 `queue: WordAttempt[]`），一次 `put()` 完成「计数更新 + 状态变更 + 队列推进」，天然原子；幂等用 `word_id + request_id` 记录在文档内（`processedRequests: Record<string, Result>`），重复请求直接回放原结果。这样完全不需要动存储抽象层。

## 4. 真实数据事实（拼写判定标准化的依据）

抽样自 `data/linguabase/v1/search-index.json`（22,791 条，实测）：

| 事实 | 数量 | 对拼写判定的影响 |
| --- | --- | --- |
| `word` 含空格（短语词） | **0** | 无需处理短语/多词答案 |
| `word` 含连字符 | **70**（`add-on`、`baby-sit`、`drive-in`…） | 需定义连字符规范化（建议：判定时 `-` 与空格等价或直接按原样严格比） |
| `word` 含撇号 | **0** | 无需处理 `'` |
| `word` 含大写 | **56**（`African`、`AIDS`、`Chinese`、`Catholic`… 均为专有名词） | 大小写不敏感是**必须**的，否则专有名词永远判错 |
| 脏数据 | **1** 条：`discombobulated[`（GRE8000，尾部多一个左方括号） | 按红线「不编造」：如实保留原文，判定时不要偷偷 strip——建议这类词直接判「无法判定 → 提示数据异常」或原样严格比（用户打不出 `[`） |
| 中文释义缺失 | 5 条 | 方案 §8「释义为空 → 排除并提示补全」有真实触发场景 |
| 音标缺失 | 5 条 | 影响结果页/详情展示，不影响默写 |

补充事实：生词本里持久化的 `definition_zh` 是**带词性前缀**的（如 `n. 算盘`，来源 `hit.zh` / `w.definition_zh`）。若展示时不想带前缀，可复用 `src/lib/wordSense.ts` 的 `parseDefinitionZh`。

## 6. 接口契约建议（本地领域层，非 HTTP）

遵循现有分层：页面只调 `src/domain`，`domain` 调 `src/services/storage`，纯规则可单测。

```
src/domain/spelling.ts        （纯函数，零 storage 依赖，tsx 可单测）
  judgeSpelling(input, answer): 'correct' | 'wrong'
      // trim + toLowerCase + 连字符规范化；不纠错、不做近似；空答案 → 'wrong' 并记录异常
  applyAttempt(word, input, targetCorrect): { word, result, consecutiveCorrect, ... }
      // 状态机单步：PENDING/IN_PROGRESS → 正确+1 / 错误归零；达标 → COMPLETED
  aggregateSession(session): { total, correct, wrong, accuracy, completed, skipped, unavailable, ... }
      // 会话级一律实时聚合，total=0 时 accuracy 返回 null（前端渲染 "—"）

src/domain/spellingSession.ts （持久化，import storage）
  createSession({ mode, count, targetCorrect }): SpellingSession   // 内嵌 queue，单次 put
  getCurrentSession(): SpellingSession | null                       // 活跃会话（本地唯一）
  submitAttempt(sessionId, wordId, input, requestId): AttemptResult // request_id 幂等
  skipWord(sessionId, wordId, requestId)
  pauseSession / resumeSession / abandonSession
  listHistory(limit)
```

存储形状（**单文档**，绕开无事务的限制）：

```
表 spellingSessions：'id, status, started_at, owner'
行 = {
  id, owner: 'guest', status: 'IN_PROGRESS'|'PAUSED'|'SESSION_COMPLETED'|'ABANDONED',
  selection_mode, target_correct, total_words, current_position,
  started_at, updated_at, ended_at, paused_at,
  queue: [{ word_id, word_snapshot:{word, definition_zh, ipa, pos}, position,
            word_status, consecutive_correct, target_correct,
            total_attempts, correct_attempts, wrong_attempts,
            last_attempt_at, unavailable_reason? }],
  processedRequests: { '<request_id>': <AttemptResult> }   // 幂等回放
}
```

Dexie 需新增 **version(10)**（规则：只允许新增，不改历史版本）。索引建议 `status`（查活跃会话）+ `started_at`（历史倒序）；**不要**在未审查前给 `queue` 内字段建索引（内嵌数组无法索引，也不必）。
