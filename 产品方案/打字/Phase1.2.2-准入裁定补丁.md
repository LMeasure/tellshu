## 1. 事项 1 · U11 产品统计口径：活动错词 vs 历史 stale 事件

### 1.1 1.2.1 遗留的口径空缺（必须先承认）

U11 记录的是：`assertLock`（读会话表）与 `insertIfAbsent`（写事件表）是**跨表两个独立请求**，接管瞬间旧标签 in-flight 事件仍可能落盘为 stale。1.2.1 只写了「事件行保留，错词计数仍真实（用户确实按错了）」，**没有定义它是否进入「活动错词本」**。

而 V1.2 §1.5 的聚合公式是：

```text
covered = ∪ { r.covered_event_ids | r.kind='reset' ∧ owner ∧ word_id }
active  = { e.event_id | e.kind='error' ∧ owner ∧ word_id } \ covered
wrong_count = |active|
```

该公式**只按 kind / owner / word_id 过滤，无 epoch、无处置结果过滤** → stale 事件必然被计入 `active`。于是出现自相矛盾：

| 维度 | D12（1.2.1 §3.3d）规定 | 旧聚合公式给出 |
| --- | --- | --- |
| 当前会话连对次数 | stale **不归零** | — |
| 错词本显示 | — | 该词 `wrong_count +1`（「你错了 1 次」） |
| 用户可解释性 | 接管后的旧标签错误，用户当前无法重练 | 列表里凭空多一个词 |

**「记了错但不算错」是两套互相冲突的口径**，必须在准入前定死。

### 1.2 推荐口径：把「一个计数」拆成两个指标（待批准）

| 指标 | 定义 | 用途 | 是否含 stale | 是否含已 covered |
| --- | --- | --- | --- | --- |
| **`active_wrong_count`** | 当前需要重练的、本代次有效且未被 reset 覆盖的 error 事件数 | 错词本列表、排序、徽标、重练选词、`last_wrong_at` | **否** | 否 |
| **`total_error_events`** | 该 `(owner, word_id)` 下历史全部 error 事件行数 | 审计 / 历史视图 / 容量统计 / 学习报告 | **是** | 是 |

- 两个指标都**不物理删除任何行**；都从事件表重算，不引入物化缓存（沿用 V1.2 §4.3）。
- `last_wrong_at` 按 `active_wrong_count` 对应的事件集取 `MAX(occurred_at)`，**仅用于 UI 展示**，不参与任何判定。
- 错词本页面与任何结果页展示的「错误次数」统一指 `active_wrong_count`；若展示 `total_error_events`，必须显式标注「含历史 / 含已移除」，不得混用同一个「错误次数」文案。

### 1.3 三类事件处置矩阵（推荐口径的完整定义）

| 类别 | 持久化判定 | `active_wrong_count` | `total_error_events` | 活动错词本列表 | 归零 | SRS |
| --- | --- | --- | --- | --- | --- | --- |
| **本代次有效 error** | 会话凭证为 `'zeroed'`（或会话活跃且凭证缺失、待结算）且未被 `covered` | 计入 | 计入 | 显示 | 归零 `cc=0` | 仅达标 `COMPLETED` 时 |
| **stale（旧锁代次）** | 会话凭证为 `'stale'` | **不计入** | **计入** | **不显示** | **不归零** | 不触发 |
| **已被 reset 覆盖** | `event_id ∈ ∪ covered_event_ids` | 不计入 | 计入 | 不显示 | 已终结 | 不触发 |

> 「历史 stale 事件」归属：保留在事件表（append-only），单列为**历史 / 审计**口径；是否提供 UI 查看入口属 D6 扩展，本补丁不新增入口、不擅自决定。

### 1.4 判据必须落在持久化凭证上，**不得**用 `status` / `occurred_at`

这是本节最关键的一致性约束。V1.2 §2.1 明确规定「事件 `status` 仅展示 / 加速，允许落后或超前，**不是正确性依据**」；1.2.1 也把 stale 标在 T-C 的 `status='settled_skipped'` 上。若错词本聚合用 `status` 过滤：

- T-C 失败 / 崩溃 → stale 事件的 `status` 仍是 `recorded` → **被误算进 `active_wrong_count`**；
- 重试路径中 `status` 超前 → 又被误排除。

结果随事务成功与否漂移，不可接受。`occurred_at` 同理（V1.2 已废弃一切时间比较）。

**方案：把结算凭证的值从布尔扩展为处置枚举**（设计提案，须 D12 一并批准）：

```ts
type SpellingSettlement = 'zeroed' | 'stale'

interface SpellingSession {
  // ...既有字段
  // 兼容：历史值 `true` 一律按 'zeroed' 解读，避免旧文档迁移
  applied_error_event_ids?: Record<string, true | SpellingSettlement>
}
```

- 在**同一个 T-B `updateAtomic` 事务**内原子写入：
  - 本代次：`cc=0` + `applied_error_event_ids[E] = 'zeroed'`；
  - stale：**不归零** + `applied_error_event_ids[E] = 'stale'`；
- 错词本聚合是**只读跨表**：按 `E.session_id` 精确 `SESSIONS.get(id)` 读凭证（**禁用 `getResumableSession()`**，V1.1 §2.4 已明确它会写错文档），按凭证值分类；会话文档不存在 → 归入「历史」，不计入活动（是否计入待 D6 确认）。
- 判据只含 `event_id` 成员关系与处置枚举，**无时间比较、无 status 依赖**。
- T-C 的 `status='settled_skipped'` + `stale_epoch` 仍写，但**降级为纯展示态**；它落后或失败都不影响聚合结果。

## 2. 事项 2 · D10：Dexie / memory「同引用跳过写回」精确契约

### 2.1 原状态与缺口

1.2.1 §1.3(c) 只给了一句「reducer 返回**同一引用**时，`updateAtomic` 应跳过写回（不执行 `put`）」，缺少：签名、四种返回值的语义、事务作用域、两驱动实现骨架、一致性要求、以及「调用方如何正确命中」的硬约束。补充如下（**设计提案，待批准**）。

### 2.2 精确签名与四条判定规则

```ts
type AtomicReducer<T> = (current: T | undefined) => T | undefined

interface AtomicOutcome<T> {
  changed: boolean          // 本次是否发生了写操作
  value: T | undefined      // 事务提交后的最新值（含未变化分支）
}

updateAtomic<T>(
  key: string | number,
  reducer: AtomicReducer<T>,
): Promise<AtomicOutcome<T>>
```

| reducer 返回 | 判定 | 写操作 | `changed` | 理由 / 约束 |
| --- | --- | --- | --- | --- |
| 与 `current` **同一引用**（`next === current`，`Object.is` 语义） | 跳过 | **零写入**（不调用 `put` / `add`） | `false` | P0-1 命中分支依赖此条；不触碰 `updated_at` 等任何字段 |
| **新对象**（即使 `JSON.stringify` 相同） | 写回 | `put(next)` | `true` | **不做深比较**；调用方想跳过必须显式返回入参引用，不能靠值相等 |
| `undefined` | no-op | **零写入、不删除** | `false` | 明确 `undefined` ≠ 删除；删除走独立 `delete()`，防止纯函数误删行 |
| 抛错 | 回滚 | 零写入 | —（异常向上抛） | 错误不吞、不落 `dead`；重试策略由编排层决定 |

补充规则：

- `current === undefined`（key 不存在）时，reducer 必须返回**新对象**才算写入；返回 `undefined` 是 no-op。
- reducer 必须是**同步纯函数**；若返回 Promise / thenable，驱动应抛 `TypeError`（契约违反），不得 `await` 后继续执行。
- `changed=false` 时 `value` 返回 `current`（可能是 `undefined`），调用方不得假定一定拿到实体。

### 2.3 事务作用域与两驱动实现骨架

**共同约束**：`get` 与 `put` 必须在**同一个 readwrite 事务**内完成；不得读完后另开事务写（否则回到 `get→check→put` 非原子）。传给 reducer 的必须是**副本**，`===` 判定基于「传给 reducer 的那个对象」，不是驱动内部存储对象。

```ts
// web.ts（Dexie；平台 API 只在本文件）
return db.transaction('rw', this.table, async () => {
  const cur = (await this.table.get(key)) as T | undefined
  const next = reducer(cur)                       // 同步纯函数
  if (next === cur || next === undefined) return { changed: false, value: cur }
  await this.table.put(next as any)
  return { changed: true, value: next }
})
```

> ⚠️ `db.transaction` 回调内**只能 await 本表的操作**；任何跨表 / 网络 / 定时器 await 都会让 Dexie 事务自动提交并失效。回调的 `return` 值在事务**提交后**才 resolve。

```ts
// memory.ts（整段同步，中间不得 await / 不得 yield）
const cur = this.rows.has(key) ? this.copy(this.rows.get(key)!) : undefined
const next = reducer(cur)                        // 同步；抛错直接向上，rows 未改
if (next === cur || next === undefined) return Promise.resolve({ changed: false, value: cur })
this.rows.set(key, this.copy(next))
return Promise.resolve({ changed: true, value: next })
```

> ⚠️ memory 侧**不得 `await this.get(key)` / `await this.toArray()`**：这些方法返回 `Promise.resolve(...)`（`memory.ts` L103-105、L129-131【实测】），await 会让出微任务队列，破坏「读与写之间不让出执行权」的线性化。Dexie 靠 IDB 事务锁，memory 靠同步代码段，两者语义必须等价。

### 2.4 六条两驱动一致性要求（C39/T62 覆盖）

1. 相同 `current` + 相同 reducer → 两驱动得到相同的 `changed` 与相同的 `value`；
2. `changed=false` 时：memory 侧内部 `rows` 对象引用不变；Dexie 侧事务内**无 `put` 调用**（用事务 hook / mock 探针断言，不能只看最终值）；
3. 并发 N 次 `updateAtomic` 对同一 key → 串行化，无 lost update；
4. reducer 抛错 → 零写入、两驱动都向上传播同一错误类型；
5. `next === cur` 分支 → `updated_at` / `queue` / `processed_requests` 等字段**一个都不变**；
6. `undefined` 分支 → 行仍存在（`get(key)` 可读）、不误删。

### 2.5 对 P0-1 的硬约束与三个原语的边界

- **代码评审检查点**：`applyTypingErrorEvent` 命中凭证分支必须写 `return s`，**禁止** `return { ...s }` 或任何重建对象的写法 —— 否则 D10 契约失效，T-B 会产生一次多余写回，1.2.1 §1.3(c) 的论证不成立。
- 三个单表原语职责不得混用：`insertIfAbsent`（主键幂等追加，无读改写）、`updateAtomic`（单 key 读改写）、`appendFromSnapshot`（读一批 + 追加一条，D11）。**不得用 `updateAtomic` 实现追加**（key 不存在时语义不同），也不得用 `insertIfAbsent` 实现读改写。
- 状态：**待批准**（内容补全，但 D10 本身仍未获批准）。

## 4. 事项 4 · D12：stale 事件是否计入活动错词本

### 4.1 明确推荐：**不计入**

> stale 事件**不计入 `active_wrong_count`、不出现在活动错词本列表、不进入重练选词**；但**计入 `total_error_events`**，永久保留在事件表（append-only），归「历史 / 审计」口径。完整矩阵见 1.3，判据见 1.4。

### 4.2 三条理由

1. **消除自相矛盾**：D12 规定 stale **不归零**。若错词本却显示「错了 1 次」，用户会问「为什么错了却没清零」—— 两套口径互相打架。
2. **产品语义**：活动错词本 = 「当前需要重练的词」。stale 来自**已被接管、已失效的旧标签**，用户当前会话既不会因它归零、也无法在当前会话重练它，把它列进待练清单不可解释。
3. **一致性**：stale 已写 `'stale'` 凭证终结重放、不触发 SRS；若又计入活动计数，等于「记错但不算错」，与「结算凭证 = 唯一正确性依据」的协议冲突。

### 4.3 历史 stale 事件的处置

- **不物理删除**（沿用红线：只有 `clearAll()` 物理删除）；
- 不显示「已入册 / 已记录」数字、不假报成功（D5 精神）；
- 是否提供「历史 / 已移除」查看入口属 D6 扩展，本补丁**不新增入口**、不擅自决定；
- `total_error_events` 可用于未来的学习报告，但**必须与 `active_wrong_count` 使用不同文案**，不得统称「错误次数」。

### 4.4 实现该口径的连带依赖（必须一并批准）

采纳「不计入」**必须同时批准 1.4 的凭证枚举**（`true | 'zeroed' | 'stale'`）与 1.5 的五处连带修订。否则只能退回用 `status` 过滤，而 `status` 非权威（T-C 失败即误算），口径无法成立。

### 4.5 若负责人选择「计入」的连带后果（如实列出，不隐藏）

| 后果 | 说明 |
| --- | --- |
| 必须同步修改 D12 的「不归零」口径 | 要么 stale 也归零（则会抹掉新标签已累积的 `cc`，回到 U1 竞态），要么接受「错词本 +1 但进度不变」的长期不一致 |
| 错词本出现不可解释的词 | 接管场景下用户无法归因，且 `active_wrong_count` 与会话状态机长期背离 |
| 1.2.1 U11 的产品影响描述需回滚 | 「错词计数多 1」将成为**预期行为**而非残留 |
| 测试矩阵 | C45/T68 的期望需整体反转，且需新增「错词本与状态机不一致」的验收说明 |

### 4.6 状态

**待批准**。D12 本轮补充了「活动错词本口径」条款，但 D12 本身及 1.2.1 中「凭证语义扩展 / stale 处置 / `settled_skipped` 语义扩展」**仍全部待批准**，无一自动生效。

## 5. 事项 5 · D13：reset 点击与事件落盘之间的产品语义

### 5.1 时间窗定义

```
用户点击「移除」
   → 同步生成 reset_event_id（冻结此刻的意图）
   → appendFromSnapshot：进入 IDB 事务 → 读快照 → build → 写 reset 行（T-R 提交）
   → 列表刷新
```

「点击」是**不可持久化的内存事件**；「T-R 提交」是**唯一可持久化的线性化点**（1.2.1 §2.3(2)）。两者之间的异步窗口内可能落盘新 error、发生刷新 / 关闭 / 失败 / 重复点击。

### 5.2 六条产品语义（推荐，待批准）

| # | 语义 | 理由 |
| --- | --- | --- |
| 1 | **不采用乐观移除**：点击后按钮禁用 + 「正在移除…」；仅在 T-R 落盘成功后才刷新列表 | 与「绝不假报成功」（V1.1 D5 / 前提卡红线）一致；乐观更新在失败时会闪烁回滚 |
| 2 | **先后以「T-R 与 T-A 的 IDB 事务全序」判定，不以「点击时刻」判定** | 点击时刻无法持久化、跨标签不可比、依赖客户端时钟；沿用 V1.2「不用 `occurred_at`」原则 |
| 3 | **窗口内落盘的 error 一并按全序处理**：排在 T-R 之前 → 进入快照 → 一并移除；排在之后 → 保留为活动错词 | 两种结果各有确定语义，无中间态；不特殊处理、不弹二次确认 |
| 4 | **失败**：T-R 失败 / `dead` → 列表不变，显示「移除失败，请重试」+ 重试入口；重试**复用同一 `reset_event_id` 与冻结快照**（不重算） | 防止 1.2.1 S2「重试扩大 covered」缺陷；绝不显示「已移除」 |
| 5 | **刷新 / 关闭**：T-R 未提交 → 视为未发生，下次进入按当前活动集重算；已提交 → 按 `event_id` 集合重放幂等 | 与 P0-2 / C30/T53 一致 |
| 6 | **重复点击**：按钮禁用 + 同一 `reset_event_id` 幂等，不产生第二条 reset | 与 C41/T64 一致 |

### 5.3 窗口内事件的判定表

| 窗口内发生的动作 | 相对 T-R 的位置 | 产品结果 | 用户可见 |
| --- | --- | --- | --- |
| 新 error 落盘（并发 T-A 先提交） | T-R 之前 | `E ∈ covered`，一并移除 | 列表刷新后不显示该次错误 |
| 新 error 落盘（T-A 后提交） | T-R 之后 | `E ∉ covered`，保留 | 列表刷新后显示 1 个新错词（`active_wrong_count=1`） |
| 用户刷新 / 关闭页面 | T-R 未提交 | 移除未发生 | 重进后原错词仍在 |
| T-R 写入失败 | — | 移除未发生，可重试 | 「移除失败，请重试」 |
| 重复点击 | — | 幂等，仅 1 行 reset | 无重复条目 |
| 系统时钟回拨 / 同毫秒 | — | 判定不变 | 仅「最近错误时间」展示可能乱序（U6） |

### 5.4 与「取得锁之前不启用输入」的关系

D13 在 1.2.1 中还包含「`inputEnabled` 闸门」。本补丁**不改该条**：错词本页的「移除」按钮同样应在页面完成初始化（若存在活跃会话，则含锁身份确认）后才可用；未就绪时禁用，避免无归属的 reset 事件。无活跃会话场景见 U12（范围外）。

### 5.5 状态

**待批准**。六条语义均为推荐口径，不擅自生效。
