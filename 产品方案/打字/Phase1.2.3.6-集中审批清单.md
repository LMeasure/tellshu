### 2.1 D28 · O1 监控边界澄清（含 O1/O2/O3）`【需批准】`

- **当前问题**：1.2.3.3 §2.6 把「不处理 thenable」与「依赖全局 `unhandledrejection` 监控」写在同一句；C109/T132 断言「O1 下被监控捕获」；主 App `src/` 无任何 rejection 监听。需澄清 O1 主行为、监控是否只是事后观测、以及后续 rejection 如何处置。
- **可选方案**（O1/O2/O3 逐项代价）：

| 选项                               | 做法                                                                                               | 代价与风险                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| **O1 不处理**                       | 只抛 `SnapshotContractError`，不触碰 `P`；监控仅**可选事后观测**                                                 | 控制台噪声；Node 15+ 默认 `throw` 可能致命；M1–M9 漏捕获（跨 realm / 自定义 thenable / 配置静默等）；**监控不构成处理保证** |
| **O2 挂 no-op rejection handler** | `try { (P as PromiseLike).then(undefined, () => log('discarded_thenable_rejection')) } catch {}` | 会**调用 `then`**（Proxy trap / assimilation 风险）；吞掉错误须记原因码；**仅处理拒绝，不撤销副作用**                |
| **O3 仅对原生 Promise 挂**            | `P instanceof Promise` 时挂 catch                                                                  | 跨 realm / iframe 判定不可靠；与 M2 叠加漏捕获面更大                                                   |

另有 1.2.3.4 §1.3 的**表述澄清建议**（O1a 不处理无监控 / O1b 不处理 + 事后观测），属措辞澄清，**不新增、不替换选项**。

| **B 单类 + reason 判别** | 仅 `SnapshotError`，调用方 `switch (e.reason)`                                                                                    | 类型面最小；易漏分支；两驱动只需同一 reason                   |

|                         |            |        |        |                                                                                                                                                                                                                         |
| ----------------------- | ---------- | ------ | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 另有 `phase` 修订建议（\`setup | buildViews | reader | assert | finalize`）、`reason` 优先级建议（`DATABASE_CLOSED`>`TRANSACTION_ABORTED`）、`THEN_READ_FAILED`改名`THEN_PROBE_FAILED`、建议新增 `UNSUPPORTED_CLONE_ENV`/`THEN_HANDLER_THREW`/`ERROR_NORMALIZATION_FAILED\` 三个 reason（**均为建议，不新增源码类型**）。 |

### 2.3 D30 · memory 拷贝语义与降级候选（含 K1–K4）`【需批准】`

- **当前问题**：U32 未闭合 —— `canClone=false` 时 `copy()` 返回原引用（`memory.ts` L98-101 / L189-190，注释说明是有意降级），`put/get/toArray` 均共享引用；`rows` private、快照 / 冻结零落地；`DataCloneError` 时既有 `Promise.resolve(<同步求值>)` 同步抛（U35）。
- **可选方案**（K1–K4 逐项代价）：

| 候选              | 做法                                                                 | 代价与风险                                                                  |
| --------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| **K1 拒绝服务**     | `canClone=false` → 抛 `UNSUPPORTED_CLONE_ENV`，该环境不提供 `readSnapshot` | 该环境不可用 memory 快照；但**不伪造只读副本**，语义最诚实；需 UI 降级文案                          |
| **K2 手写深拷贝**    | 按 `StorageSchema` 逐类型递归复制                                          | 须覆盖 `Date`/`Map`/`Set`/`BigInt`/循环引用；维护成本高；落在 `memory.ts` 并行改动文件       |
| **K3 深冻结**      | 递归 `Object.freeze` 视图与返回值                                          | 不改变引用共享事实（reader 仍持有 `rows` 内对象）；与 Dexie 结构化克隆语义不一致；业务层派生对象受限          |
| **K4 JSON 序列化** | `JSON.parse(JSON.stringify(...))`                                  | 丢失 `undefined`/`Date`/`Map`/`Set`/`BigInt`，**静默改数据**，违反前提卡红线，既有报告标为不推荐 |

共同约束（1.2.3.4 §4.4）：**不得静默回退引用共享**；`DataCloneError` 须按类型化错误传播；`views` 失败后不得跨调用复用。

- **`【Agent 推荐（非决定）】`**：沿用 1.2.3.4 既有倾向 **K1**（语义最诚实、改动面小），但须负责人确认「该环境下 memory 驱动不提供快照」这一产品降级是否可接受。

## 4. 特别复核（对应交付要求「三、特别复核」）

> **以下六条是对既有条目适用范围的收窄 / 澄清，不是新编号、不改写旧结论**，须作为第 2 章相应决策项的**审批附加条件**写入回执。

### 复核 1 · C141 不得把 `await` 普通值等同于 Promise 返回契约

- **原文**（1.2.3.5 §2.6 L249）：「五路径 × A1–A4：用 awaitability 而非 `instanceof Promise`；断言无同步抛、rejection 为 `SnapshotError`、字段两驱动一致；跨 realm Promise 通过；断言检测方向与返回方向未混用」。
- **复核结论**`【设计推导】`：`await 42` 也会成功并得到 `42`，因此「`await p` 成功」**不能证明**返回的是 Promise；`awaitability` 只是**必要条件**，不是充分条件。1.2.3.5 §2.1 的 A1 判据 `typeof p.then === 'function'` 本身是 thenable 判据（强于 `instanceof Promise`），但 C141 的断言描述若被实现成「`await` 能走通即通过」，会漏掉「返回普通值」这一违约。
- **审批附加条件**：C141 须同时断言 ① 返回值**对象本身**是 thenable（`p` 为对象/函数且 `typeof p.then === 'function'`）；② 调用过程**无同步抛**；③ rejection 路径错误为 `SnapshotError` 且字段一致；④ 不得用「`await` 普通值成功」作为返回契约的证明；⑤ 检测方向（reader 返回值不得 thenable）与返回方向（`readSnapshot` 必须返回 Promise）不得共用同一辅助断言。
- **影响既有编号**：C130/T153、C141/T164（仅收紧断言，不改原结论）；归入 D32 审批附加条件。

### 复核 2 · C145「总函数」必须限定正常运行环境

- **原文**（1.2.3.5 §2.6 L253）：「注入 `null` / 原始值 / 抛 getter / Proxy / 循环引用 / thenable / `Symbol` 作为 `cause`：**断言恒返回 `SnapshotError`**……」。
- **复核结论**`【设计推导】`：「恒」在**错误构造基础设施失效**时不成立：`Error` / `SnapshotError` 构造器被篡改或不可用、`super()` 抛错、原型链被污染、`globalThis.Promise` 被替换、日志序列化依赖的 `structuredClone` 被删、OOM / 栈溢出、宿主强制终止 —— 此时连错误对象都无法构造，不可能「恒返回 `SnapshotError`」。
- **边界契约（审批附加条件）**：① 「总函数」限定为**正常运行环境**（Error / Promise / 日志基础设施可用、内存未耗尽、原型未被篡改）；② 基础设施失效时降级为「**不吞错、不伪造成功、以最小代价把原始异常向上抛**」，若仍能记日志则记 `ERROR_NORMALIZATION_FAILED`；③ 明确此时 C6 / G1 / G4 **不保证**，须写入验收文档作为**环境前提**而非实现保证；④ C145 的测试范围限定为「可注入的异常 `cause` 形态」，不含基础设施破坏场景。
- **影响既有编号**：C145/T168、C112/T135、C127–C129/T150–T152（仅限定适用范围）；归入 D29 / D32 审批附加条件。

### 复核 3 · T-A 预加载顺序尚未实测，不得标记为可用

- **原文**（1.2.3.5 §3.3 L295）：T-A 「✅ 最可靠」；代价列「慢；需新增测试脚本（非源码）」。
- **复核结论**`【只读核实】`+`【设计推导】`：表中「✅ 最可靠」是相对 T-B 的**方案比较判断**，**不是「已验证可用」**。关键未验证点：tsx 进程启动 → 预加载脚本 patch `globalThis.structuredClone` → 动态 import `memory.ts` 的**实际顺序**；`--import` / `--require` 与 ESM 加载时序、tsx loader 介入时机、静态 import 提升都可能让 patch 晚于模块求值（`canClone` 已固化）。

- **影响既有编号**：T-A、C146–C148/T169–T171、U39（不改原结论）。


### 复核 4 · T-B cache-busting 尚未验证，不得标记为可用

### 复核 5 · U39 漏测结论限定当前条件
