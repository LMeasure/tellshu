## 0. 必须首先确认的三件事（最高优先级）

本轮审查发现，**任务书《十二、本轮 Agent 的实际执行要求》中关于现有产品的若干前提与代码事实不符**。这直接影响整个架构方向，必须在设计阶段 1 之前由产品方拍板：

### 0.1 述树当前是「纯 Web PWA」，不是微信小程序

任务书写道「当前述树主要以微信小程序形式运行」「保留现有微信小程序」，但代码事实是：

- 《产品前提卡》第 1 节明确定位：**「形态：纯 Web SPA（PWA，可添加到主屏幕）。不是小程序、不是原生 App」**。
- 全仓搜索 **零个**微信小程序特征文件：无 `.wxml` / `.wxss` / `.wxs` / `app.json` / `project.config.json`，无 `Page(` / `Component(` 小程序全局函数，无 `wx.*` 运行时 API 调用（仅文档与个别注释里出现「微信」字样，属叙述性文本）。
- 技术栈是 React 18.3 + TypeScript 5.5(strict) + Vite 5.4 + Tailwind 3.4 + zustand 4.5 + Dexie 4.4，配 `vite-plugin-pwa`，是一个标准的 Web 单页应用。

**结论**：本工作区里没有、也从未有过微信小程序代码。「保留小程序」这一要求，要么指向一个**本工作区之外的独立小程序生产仓库**（需产品方提供访问），要么任务书对产品形态的表述需要更正——**述树历来就是网页应用**。

> ⚠️ 这是全局性前提偏差。若确实存在独立小程序仓库，本次 PC Web 改造必须拿到它才能谈「共用后端/数据库/用户体系」；若不存在，则任务书里大量「小程序×Web 双端」的论述需要改写为「Web 桌面端 × Web 移动端」。

### 0.2 主应用「没有后端」，所有学习数据在本地

任务书假设存在「统一 API / 业务服务层 / 统一数据库 / 文件对象存储」供双端共用。代码事实是：

- 《产品前提卡》第 1 节：**「后端：主 App 没有（无 BaaS、无服务端接口）」**。核心学习链路（背单词 / 生词本 SRS / 阅读器）**完全离线**，数据全部落在浏览器本机 **Dexie / IndexedDB**。
- 唯一的「后端」是独立旁路 `server/`（Express + pg），只服务 **OCR 识别、词典扫描入库、检索同步、格式转换（PDF→PNG）、ASR 转写、LLM 学习稿**。它**不持有任何用户学习进度/阅读记录/个人资料**。
- 另有独立的「发现书籍检索」FastAPI 只读服务（:8000，由 vite 代理 `/api/discover`），其源码不在本仓库（需确认位置）。

### 0.3 现有的「登录 / 同步」是本地桩，不是真实功能

仓库里确有 `src/services/auth/`、`src/hooks/useAuth.ts`、`src/services/sync/`、`src/components/account/`，但经逐文件核对，**均为本地桩（stub）**：

- `auth/web.ts` 注释原文：「本地桩：登录即生成一个 userId 并写入 Dexie `session` 表。**不校验密码**（云端接入后由 Supabase 做邮箱+密码校验）」。令牌只是写进 Dexie 的 UUID，不进 localStorage。
- `sync/remote.ts` 注释原文：「本地桩实现：用一个**内存 Map 模拟云端**……仅本地桩，**进程重启即清空**；Supabase 接入后由真实实现替换。」——**它根本不是跨设备同步**，连一次页面刷新后的持久化都做不到（内存）。
- `StartLogin.tsx` 文案：「游客模式仅本地数据，登录后可跨设备同步（Phase 2）」「本地桩阶段不校验密码强度；密码字段仅占位」。

**结论**：任务书要求的「PC 用户独立可靠登录入口」「同一用户多设备访问同一账户」「跨端实时一致」「微信 OpenID 不能直接当 PC 凭证」——这些能力**当前全部不存在**，属于需要**从零新建**的后端基础设施，而非「适配」。

> 阶段 0 的判断标准原文是「先弄清楚现有述树是什么，再决定怎样让它兼容 PC」。事实是：它已经是一个网页应用，只是被刻意做成了「手机模拟器」的样子；而任务书设想的「共享后端/账号/同步」整套都不存在。因此本项目的真实工作量 = **(A) 把现有网页做成桌面友好的响应式布局** + **(B) 新建账号与跨端同步后端**（后者才是大头，且风险最高）。

- **领域层 `domain/`**：SRS 状态机、统计口径、词典检索/合并、拼写/学习稿逻辑——纯 TS、不碰存储，**直接复用**。

- **业务组件**：Reader、WordDetail、各学习流组件——**逻辑与内部结构复用**，仅外层布局/导航需适配。

## 6. 必须重新实现（C 类，当前为零）

1. **真实用户体系与认证后端**（任务书 §四.3）：邮箱+密码（或未来微信 OAuth）注册/登录、密码强度与重名校验、JWT 短时效 access + 服务端刷新令牌、RBAC、退出/过期/权限校验。当前桩**完全没有**这些。
2. **跨设备同步服务**：per-user 服务端存储 + 客户端 pull/push（替换 `LocalSyncStub` 内存 Map），解决「小程序的阅读进度/学习记录/个人资料在 PC 可见」。这是任务书 §八跨端一致性测试的**前提**，目前不存在。
3. **桌面导航/布局系统**：左侧栏 + 顶栏的响应式外壳（B 类是改，C 类是「这套桌面布局体系本身」需要新建，含抽屉、右键菜单、键盘快捷键框架）。
4. **账号/用户中心后端支撑**：`/profile` 的账号区目前接桩，需真实后端支撑资料、设置、登出。
5. **（若确有小程序）小程序↔Web 账号打通中间件**：把微信 OpenID 与 Web 账号做映射，不互相当凭证。

> C 类是任务书真实工作量所在，也是数据安全与跨端一致性的核心风险区。它**不是适配，是从零建设**。

## 7. 当前项目存在的技术债务

1. **手机模拟布局**：`app-frame` 把整个 Web 应用锁死在 375px 居中列里，桌面端两侧留白、无利用宽屏——这是「PC 不可用」的直接原因，也是最大一笔布局债。
2. **auth/sync 是占位桩**：注释指向「Supabase 接入后替换」，但 Supabase 未引入、接口契约也未定型；现在任何「已支持登录/同步」的表述都是**虚假**的。
3. **数据天然不跨端**：核心数据设计就是「每台设备一份 IndexedDB」，没有服务端真相源。要做跨端，等于改变数据架构根基。
4. **PWA 持久化隐患**：iOS Safari 对「未安装到主屏幕」的站点 7 天不活跃会清空 CacheStorage/IndexedDB（前提卡已注明）。桌面 Chrome 用户若不「安装」，数据同样随站点数据清理丢失——跨端同步后端能缓解，但不能靠前端解决。
5. **代理目标硬编码**：`vite.config.ts` 里 `/api → 127.0.0.1:8787`、`/api/discover → 127.0.0.1:8000` 是开发/本机值，生产需反向代理规则接管（前提卡已提示）。
6. **检索服务无 CORS**：发现书籍 FastAPI 未配 CORS，前端靠同源 `/api/discover` 代理转发才能用；生产部署必须配代理或 CORS。
7. **多 Agent 并发改同一仓库**：当前工作区有大量其他 Agent 的未提交改动（见 §12 Git 快照），且前提卡正本被多会话高频改写——协作层面的集成风险高。

## 9. 推荐技术方案（最小改造、复用优先）

**总原则**：述树已是 Web 应用，**PC Web 不是另起一套，而是让同一份 Web 代码响应式地适配桌面**；同时把任务书假设的「共享后端/账号/同步」作为**独立新建工作流**推进。这样最贴合「一次开发、多端复用」与「兼容优先、数据安全优先」。

### 9.1 表现层：响应式同一代码库（不重写）
- 保留 React SPA，引入桌面断点；`AppShell` 按视口在「移动底部 Tab」与「桌面左侧栏+顶栏」间切换。
- 业务逻辑/领域层/服务层零改动复用；只新增桌面布局壳 + 少量响应式样式。
- 延续现有设计令牌（CSS 变量）与 `components/ui`，不换设计语言。

### 9.2 认证：新建后端，替换本地桩（C 类）
- 技术选型建议 Express（与现有 `server/` 同栈，便于复用 pg 连接池/迁移机制）或独立 auth 服务。
- 邮箱+密码注册/登录；密码哈希（bcrypt/argon2）；JWT access（短时效，如 15min）+ refresh（服务端存储、可吊销）；会话过期/退出/权限校验；限流。
- 令牌存储：Web 端用 httpOnly+SameSite=Lax Cookie（规避 XSS 窃取），**不进 localStorage/URL**（已踩过红线）。
- 若确有小程序：提供微信 OAuth 登录，OpenID 仅作身份来源，映射成本地用户 UUID，**绝不直接当 PC 凭证**。

### 9.3 同步：per-user 服务端真相源（C 类）
- 服务端按 `user_id` 存学习进度/阅读记录/生词本/设置/素材元数据；客户端 pull/push（复用现有 `sync/engine.ts` 的 enqueue→push→pull 编排，只把 `RemoteSyncClient` 从内存桩换成真实 HTTP 实现）。
- 明确分级：词库（只读、人人相同）实时；学习进度/阅读记录准实时（秒级）；素材大文件走对象存储+元数据同步。
- 冲突策略：字段级 last-write-win + 版本向量，禁止前端缓存冒充同步。

### 9.4 部署（任务书 §五）
- `tellshu.com`（PC 主站）+ `www` 跳转主域；静态 PWA 走 CDN/对象存储；`api.tellshu.com` 独立部署后端（保留现有 `server/` 旁路服务，不混提交）。
- 全站 HTTPS、HTTP→HTTPS 跳转、证书自动续期（如 Let's Encrypt / Caddy）；安全响应头；DB 不暴露公网；`.env` 不进 Git；上传类型/大小/权限校验；接口限流。
- 生产/测试环境隔离。
