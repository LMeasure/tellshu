## 2. P0-2 · D23 thenable 与异步副作用

### 2.1 时序分析：检测器抛错时，Promise 已经跑起来了

`【设计推导】` 以 1.2.3.2 §3.1 L201-221 的检测骨架为基准，逐时刻展开：

| 时刻 | 事件 | 已发生且不可撤销的事 |
| --- | --- | --- |
| t0 | 进入 `db.transaction('r', tables, ...)` | 事务开启 |
| t1 | `await buildViews(tables)` | 事务内读完成，得到 `views` |
| t2 | `reader(views)` 被同步调用 | —— |
| **t3** | **`reader` 内部创建 Promise `P`** | `new Promise(executor)` 的 **executor 同步执行**；`async` 函数体在首个 `await` 前**同步执行**；`void fetch(...)` / `setTimeout(...)` / `db.table(...).put(...)` / 外部 `db.transaction('rw', ...)` **已发出** |
| t4 | `reader` 返回 `P`（或返回同步值但内部 `void` 了 `P`） | —— |
| **t5** | `assertNotThenable(P)` 读到 `P.then` 是函数 → 抛 `SnapshotContractError` | 检测发生在**副作用起点 t3 之后** |
| t6 | Dexie 事务回调抛错 → 事务 abort / 结束；memory 侧须包装为 rejected Promise | 只影响 `readSnapshot` 自身与本次事务 |
| t7 | `readSnapshot` 的 Promise reject | 调用方看到类型化错误 |
| **t8** | **`P` 继续运行**：resolve / reject；t3 发起的写、网络、定时器继续发生 | **检测器对 `P` 及其副作用没有任何回滚 / 补偿能力** |

**核心结论**`【设计推导】`：`assertNotThenable` 只在 t5 产生一个**契约违反信号**，它既不撤销 t3 的副作用，也不结束 t4 返回的 Promise，更不影响 reader 通过外部句柄发起的操作。`readSnapshot` 失败**不等于**「什么都没发生」。

### 2.2 五类后续行为分析

`【设计推导】`

| # | 情形 | 后果 | 契约要求 |
| --- | --- | --- | --- |
| S1 | `P` 后续 **reject** 且无人处理 | 浏览器触发 `unhandledrejection`；Node 可能告警或按配置终止进程；源码中**无全局监听**（0.2 已核实零落地） | 必须明确处置选项（见 2.6），不得静默假设「不会有事」 |
| S2 | `P` 内部自带 `.catch` | 不会 unhandled，但**副作用仍在**；错误被 reader 自己吞掉，原语无从得知 | 只记「契约违反」主错误，不声称副作用已清理 |
| S3 | `then` **getter** 有副作用 / 抛错（L1） | 检测代码读 `value.then` 时即触发：可写全局变量、发请求、改计数、抛异常；若 getter 返回非函数还能**绕过**检测 | 读取必须 `try/catch`；「检测过程抛错」统一归类为契约违反，而非 reader 结果错误；承认**检测本身可能执行用户代码** |
| S4 | **Proxy trap**（L3/L6） | `get` trap 可让首次读 `then` 返回非函数（绕过）、二次返回函数；`getOwnPropertyDescriptor` / `has` trap 可产生副作用；`then` 是函数但**调用它**也有副作用 | 检测为 best-effort；所有已知绕过须在测试中记录为**限制**，不得声称「检测成功」 |
| S5 | reader 在 `r` 事务内通过**外部句柄**发起操作 | 若用事务内 `db.table(...).put()`，Dexie 只读事务会抛 `ReadOnlyError` / `TransactionInactiveError`；若另开 `rw` 事务或直接用表句柄，**不受本次 r 事务管辖**，可能真实写入并破坏快照一致性 | 「零写入」只能约束**原语自身**，不能约束 reader；须收窄 1.2.3.2 §3.3 / C91/T114 的「零写入」措辞为「驱动自身零写入」 |
| S6 | 嵌套 Promise / 伪 thenable（L2） | 返回同步对象但字段里藏着未等待的 Promise → 检测放行 | 归入不保证清单 |

> 另需注意：`【设计推导】` 若为「挂 no-op rejection handler」而调用 `P.then(...)`，这一步本身会**调用 thenable 的 `then`**（S4 的 Proxy 风险），且可能触发 Promise assimilation。因此「处理后续拒绝」与「不触碰 thenable」两个目标存在冲突，必须作为待批准选项明确取舍。

### 2.3 Dexie 事务 abort 与 memory 错误传播的统一契约

`【设计提案】【需批准】` 沿用 1.2.3.2 §3.3 的两驱动对齐要求，补成可执行的最小契约（C1–C7）。错误体系采用类型化错误 + 全局规范化处理，结构化日志贯穿请求 ID、不记录行内容 / 用户标识：

```ts
type SnapshotPhase = 'open' | 'buildViews' | 'reader' | 'assert' | 'commit'
type SnapshotReason =
  | 'THENABLE_RETURNED' | 'THEN_READ_FAILED' | 'READER_THREW'
  | 'BUILD_VIEWS_FAILED' | 'TABLE_NOT_DECLARED'
  | 'TRANSACTION_ABORTED' | 'DATABASE_CLOSED' | 'CLONE_FAILED'

class SnapshotError extends Error {
  constructor(
    readonly phase: SnapshotPhase,
    readonly reason: SnapshotReason,
    readonly driver: 'dexie' | 'memory',
    readonly requestId: string,
    message: string,
    options?: { cause?: unknown },
  ) { super(message, options) }
}
// 结构化日志（不记 reader 返回值、不记行内容、不记 owner / word_id 明文）：
// { level:'warn', event:'snapshot_error', requestId, driver, phase, reason, tables }
// 全局处理器只向客户端暴露 { code: reason, message: '数据读取失败，请重试' }，绝不返回堆栈。
```

| # | 契约条款 | Dexie 侧 | memory 侧 |
| --- | --- | --- | --- |
| **C1** | `readSnapshot` **恒返回 Promise**，任何失败以类型化 rejection 传播，**永不同步抛错** | 事务回调内抛错由 Dexie 包装为 rejection | 必须 `try/catch` → `Promise.reject(e)`，或实现声明为 `async`（无 `await` 时仍在同段同步执行，不引入微任务让出）；**禁止** `Promise.resolve(reader(views))` 的裸写法 |
| **C2** | 检测只产生 `SnapshotContractError`，**不等待、不 assimilate、不尝试撤销** thenable | 同 | 同 |
| **C3** | thenable 后续 rejection 的处置按 2.6 选定选项落地；若挂 handler，须记 `discarded_thenable_rejection` 原因码 | 同 | 同 |
| **C4** | 失败时**不返回任何视图 / 结果**，`views` 不缓存、不复用、不跨调用泄漏 | 事务 abort，已发起的读被取消 | 丢弃本次 `views` 副本，下一次调用重建 |
| **C5** | **原语自身零写入**；检测抛错时 Dexie `r` 事务 abort；不宣称 reader 无副作用 | 事务内不写 | 不写 `rows` |
| **C6** | 两驱动错误类型 / `phase` / `reason` / `driver` / `requestId` 一致；UI 只见规范化错误结构 | 同 | 同 |
| **C7** | `db.close()` / 升级中断 → `SnapshotTransactionError`，交 U16 恢复链，**原语内不重试**；memory 侧不伪造成功 | 抛 `DATABASE_CLOSED` / `TRANSACTION_ABORTED` | 单测只验证「不静默吞错 + 错误传播」 |

> `【设计推导】` C5 的措辞必须收窄：原语保证的是「自己不写」，**不保证 reader 不写**（S5）。1.2.3.2 §3.3 / C91/T114 / C96/T119 中「零写入」的实施断言应理解为「驱动自身零写入」，本轮以新增编号 C114/T137 固化，不改写旧编号结论。

### 2.4 运行时检测无法证明没有未等待的异步副作用

`【设计推导】` 给出构造性反例（不是推测）：

```ts
// reader 返回同步值，检测完全放行，但异步副作用确实存在
readSnapshot(tables, (views) => {
  void Promise.resolve().then(() => externalWriteProbe())  // fire-and-forget
  return computeStats(views)                              // 同步纯值
})
```

- 该 reader 的返回值不是 thenable → `assertNotThenable` 通过 → 原语返回成功；而 `externalWriteProbe()` 在微任务中执行，**发生在 `readSnapshot` 的同步段之外**。
- TypeScript 也无法阻止：`reader: (views) => T` 只约束返回类型，`void` 表达式、闭包捕获外部句柄、动态 `import()` 均不受类型系统约束；`async reader` 甚至能让 `T` 推断为 `Promise<X>` 而编译通过（1.2.3.2 §3.1 L195）。
- 检测器只在 `reader` **返回之后**观察返回值，对 reader 执行**期间**的行为零可见性；L4/L5 已列此边界。
- 因此：运行时检测、TS 类型、lint、代码审查、探针测试都只能**降低风险**，**不构成形式化证明**。这与 U25 一致，本轮把它写成契约里的「不保证清单」而不是隐含假设。

### 2.5 最小安全契约：保证什么、不保证什么

`【设计提案】【需批准】` **不得夸大保证**，以下两栏必须一并写入实现文档与验收标准。

| 保证（可自动化断言） | 不保证（必须明示，不得写入验收结论） |
| --- | --- |
| G1 恒返回 Promise；失败为类型化 rejection，永不同步抛 | N1 不保证 reader 无未等待的异步副作用 |
| G2 失败时不返回视图 / 结果，`views` 不复用 | N2 不保证已启动的 Promise / 副作用被撤销或补偿 |
| G3 原语自身零写入；Dexie `r` 事务在抛错时 abort | N3 不保证 thenable 后续 rejection 被处理（除非 C3 选项落地） |
| G4 错误带 `phase/reason/driver/requestId`，结构化日志不含行内容与隐私 | N4 不保证检测覆盖 getter / Proxy / 嵌套 Promise / 原型污染 |
| G5 两驱动错误类型与原因码一致 | N5 不保证检测过程本身无副作用 |
| G6 事务中断交 U16、原语内不重试、不静默成功 | N6 不保证 reader 通过外部句柄发起的操作受本事务管辖 |
| G7 「快照内部非混合但允许稍旧」边界不变 | N7 不保证「失败 = 什么都没发生」；不保证全局最新状态 |

### 2.6 待批准选项：thenable 后续 rejection 如何处置

`【需批准】` 三选项并列，**本报告不裁定**，归 D26。

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| **O1 不处理** | 只抛 `SnapshotContractError`，完全不触碰 `P`；依赖全局 `unhandledrejection` 监控 | 控制台噪声；Node 可能按配置终止；需另立全局监控（源码当前零落地） |
| **O2 挂 no-op rejection handler**（设计倾向，非裁定） | `try { (P as PromiseLike<unknown>).then(undefined, () => log('discarded_thenable_rejection')) } catch {}` | 会**调用 `then`**（S4 Proxy 风险、可能触发 assimilation）；吞掉错误须记原因码；**仅处理拒绝，不撤销副作用** |
| **O3 仅对原生 Promise 挂** | 仅 `P instanceof Promise`（或等价判定）时挂 catch，自定义 thenable 不触碰 | 跨 realm / iframe 的 Promise 判定不可靠；仍有覆盖缺口 |

> 无论选哪项，都必须配套：① 日志只记原因码与 `requestId`，不记 `P` 的内容；② 明确 O2/O3 的「处理拒绝」**不等于**「清理副作用」；③ 把 N1–N7 写入验收文档。

## 3. P0-3 · D24 非法 owner 的统计归属

### 3.1 归属红线：非法 / 缺失 owner 不能直接归属于当前 owner

`【设计推导】`＋`【需批准】`

| 理由 | 依据 |
| --- | --- |
| 归属未知即不得推定 | 前提卡红线「绝不编造数据」；把 `owner` 缺失的行算进当前账号，等于凭空指定归属 |
| 会污染统计与隐私边界 | 别的用户 / 脏数据被计入当前账号的 `total_error_events` 与错词本，且可能进入重练选词 |
| 与既有分类冲突 | 1.2.3.1 §1.3 第 4 行：`E.owner` 缺失 / 非法 → `UNCLASSIFIABLE`；第 5 行 `S.owner !== E.owner` → `OWNER_MISMATCH`。若统计层又把它归入当前 owner，两处判据自相矛盾 |
| 自动补齐被禁止 | 1.2.3.2 §4.2 / §4.4 已明确禁止自动补 `guest` / 自动迁移 `owner` |

> **`'guest'` 的边界**`【只读核实】`：`web.ts` L160 / L167 / L173 的 v8 升级确实把**存量行**缺失的 `owner` 补成 `'guest'`，因此 `'guest'` 是**合法 owner 值**。但那是历史迁移对既有数据的处理，**不得据此把新发现的非法 / 缺失 owner 自动补成 `'guest'`** —— 后者属于造数。`【设计推导】`

**`isValidOwner` 建议定义（待批准）**：`typeof v === 'string' && v.trim().length > 0`（与 1.2.3.1 §1.3 的「缺失 / 非字符串 / 空」判据一致）；空白串、非字符串、`null`、`undefined` 一律落入不可归属分区。

### 3.2 三分区计数：互斥、完备、只让一份进入统计

`【设计提案】【需批准】` 本条是对 1.2.3.2 §4.1 / §4.3 中 `errors` 未定义来源的**精确化补充**，不改写旧结论：

```ts
const all = views.all('spellingErrorEvents').filter(E => E.kind === 'error')

const current_owner_events = all.filter(E => isValidOwner(E.owner) && E.owner === currentOwner)
const other_owner_events   = all.filter(E => isValidOwner(E.owner) && E.owner !== currentOwner)
const unattributable_local = all.filter(E => !isValidOwner(E.owner))

// 互斥且完备（C118/T141 断言）：
// current_owner_events.length + other_owner_events.length + unattributable_local.length === all.length

const errors = current_owner_events          // ← 唯一进入统计的集合
const total_error_events  = errors.length
const active_wrong_count  = errors.filter(E => classify(...) ∈ {PENDING_CURRENT, SETTLED_ZEROED}).length
const distinct_word_count = new Set(errors.map(E => E.word_id)).size
```

| 指标 | 定义 | 单位 | 是否展示 | 是否进列表 / 重练 / 导出 |
| --- | --- | --- | --- | --- |
| `current_owner_events` | owner 合法且 === 当前 owner 的 `kind='error'` 行 | 事件条数 | ✅ 主统计（即 `total_error_events`） | ✅ 唯一数据源 |
| `other_owner_events` | owner 合法但属于其它 owner 的行 | 事件条数 | **按 3.3 待批准选项决定** | ❌ 一律不进 |
| `unattributable_local` | owner 缺失 / 非法 / 空白 / 非字符串 / `null` 的行 | **本地异常记录条数** | ✅ 必须提示（不得静默丢弃） | ❌ 一律不进 |

`【设计推导】` 关键澄清：`other_owner_events` 是**正常隔离数据，不是异常**，不应触发数据异常横幅；`unattributable_local` 才是需要「不静默丢弃」的本地异常记录。用户所说「区分三类 + 不静默丢弃异常」对应的是后者，二者的产品语义必须分开。

> 与 1.2.3.2 §4.3 的关系：旧表把 `total_error_events` 写作「同一 `errors` 集合的行数」，本轮明确 `errors === current_owner_events`，**其它两分区不得混入 `errors`**；`abnormal_counts` 是否含被 `COVERED` 遮蔽的异常仍取决于 **D22**（未批准）。`【需批准】`

### 3.3 UI 文案：不泄露其它 owner 数据，又不静默丢弃异常

`【设计提案】【需批准】`

| 场景 | 推荐文案 | 禁止 |
| --- | --- | --- |
| 主统计 | 「**当前账号**的历史错误记录 N 条」 | 「全部历史记录 N 条」「累计犯错 N 次」「历史犯错 N 次」 |
| 无法归属的本地异常 | 「另有 **N 条本地记录**归属信息异常，未纳入统计」+「查看明细」 | 静默不显示、「暂无数据」、把 N 并入主统计、自动补 `guest` 后计数 |
| 「查看明细」 | 只读展示**原因码分类计数**（不展示原始行） | 展示 `word_id` / `word` / `occurred_at` / `session_id` 明文 |
| 其它 owner（展示级别待裁定） | 见下表 O1–O3 | 展示其它 owner 的词条 / 时间 / 会话 ID；把其它 owner 行写进错词本、重练、导出 |
| `total>0 && active=0` | 「有 N 条历史记录暂无法归类，数据可能不完整」+ 入口 | `EmptyState`「暂无错词」、写 0、假报「已同步」 |

**其它 owner 展示级别（三选项，待批准，归 D27）**：

| 选项 | UI 行为 | 隔离强度 | 代价 |
| --- | --- | --- | --- |
| **O1（设计倾向，非裁定）** | 完全不展示 `other_owner_events` 的存在或数量；只显示 `unattributable_local` 的异常提示 | 最强 | 用户对「本地还有别的数据」无感知；内部对账靠日志原因码 |
| O2 | 布尔级提示「检测到其它账号的数据，按隔离规则未展示」+ O1 的异常提示 | 中 | 仍泄露「其它账号数据存在」这一事实 |
| O3 | 显示 `other_owner_events` 计数（不显示内容） | 弱 | 泄露其它账号数据规模；**不推荐** |

**不泄露的硬约束**`【设计推导】`：错词本列表、重练选词、导出、UI 文案、结构化日志**只能**从 `current_owner_events` 构造或引用聚合计数；内部排查日志如需定位，只记 `session_id` 哈希与原因码（沿用 1.2.3.1 §3.3），不记用户标识与词条明文。`views.all()` 会读到其它 owner 的原始行 —— **「读到 ≠ 展示」**，须以同步纯函数的输出边界强制隔离（见 3.4 与 U29）。

### 3.4 全表读取 vs 索引读取：五个维度的取舍

`【设计推导】【需批准】` 不写成「全表一定更好」。

| 维度 | 全表快照读取 + 同步纯过滤 | 索引等值读取（`whereIndex('owner', x)`） |
| --- | --- | --- |
| **隔离** | 过滤规则集中在同步纯函数，可审计；但**其它 owner 的原始行进入进程内存**（U29），须靠「输出只含聚合数 + 原因码」约束 | 进程内只接触当前 owner 行，**隔离更强**；但规则依赖索引正确性 |
| **性能** | O(全表)；本地事件表容量 / 聚合耗时 / IndexedDB 配额**无实测**（U3 / U14 / U24，7–11 MB/年仅为估算，不得引用为事实） | O(命中集)，更快 |
| **异常发现能力** | ✅ **能**发现 owner 缺失 / 非法行（它们不进索引），满足「不静默丢弃异常」（U26） | ❌ 索引不收录缺失 / 非法字段行 → **静默漏掉**，连计数都算不出 |
| **一致性** | 与 `readSnapshot` 同一快照，内部非混合（U19 已解） | 多次独立只读请求，可能混合快照 |
| **两驱动** | 全表副本 + 同一纯函数 → 语义一致 | `whereIndex` 索引白名单分叉（F9 / U22）；`value=undefined` 时 memory 会匹配缺失字段行而 Dexie 不会 |
| **schema / G9** | 不改 `stores()`、不加索引、不依赖版本号 → 设计上不冲突（但落在并行改动文件，仍受 G9 验收第 5 条管辖） | 需为新表建 `owner` 索引 → **改 schema / 加索引，受 G9 管辖，当前禁止** |

**设计倾向（非裁定）**`【需批准】`：短期取全表快照 + 三分区，理由是异常发现能力与两驱动一致性，且不依赖 schema；但必须接受「其它 owner 原始行进入进程内存」的隔离弱化（U29），并以输出边界约束。长期若 G9 关闭、容量压测通过，可评估改用索引读取以恢复强隔离与性能，**但必须同时补一条独立的「异常探测」路径**（例如全表 `count()` 与三分区之和的对账），否则 U26 会复发 —— 不能只换查询方式就宣称隔离与异常发现都解决。
