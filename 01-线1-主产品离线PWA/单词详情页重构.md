## 一、先说结论：需求 5 有一半做不到，我没硬凑

你要的「每个释义下方展示对应释义的例句」，**现有数据支撑不了**。我实测了全部 22,791 条真实词条（5 个词本全量）：

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| 总词条 | 22,791 | |
| 能从 `definition_zh` 解析出词性分组 | **99.9%** | 词性前缀内嵌在释义串里，需求 4 完全可做 |
| 有多词性分组 | 8,585（37.7%） | 如 `by` = prep. + adv. |
| 例句条数 | **97.8% 恰好 3 条** | 生成时写死的 3 条 |
| 释义总数 | 71,513（平均 3.14 / 词） | |
| **释义数 == 例句数** | **5,070（22.2%）** | 只有这些能证明一一对应 |
| `senses` 字段（义项标签） | **0% 存在** | 类型里声明了，数据没落 |

你举的例子 `He arrived at the solution by a simple process of deduction.` 也不在库里——`by` 的 3 条例句是 stood by the window / written by / by Friday。

**所以我的处理**：
- **22.2% 的词**（释义数 == 例句数）→ 按数据顺序一一绑定，释义下直接挂自己的例句 + 喇叭 + 麦克风。
- **其余 77.8%** → 例句集中展示，卡片上明写「例句未标注对应释义，集中展示」。
- **绝不硬配**。硬配的后果是 77.8% 的词张冠李戴（比如 by 的「由某人完成」会挂上 Please finish by Friday），那是给用户错误示范。

**想让 100% 的词都支持**：重跑数据管线（`D:\English\export_full_to_shushu.py`），给 `examples` 加一个 `sense_index` 字段标明归属。前端不用改，绑定逻辑会自动全部走 paired 分支。

### 录音评分的两条路（需求 3）

| 路线 | 触发条件 | 分数来源 | UI 标注 |
| --- | --- | --- | --- |
| 真实 | 浏览器支持语音识别（Chrome） | `pronunciationScore(句子, 识别文本)`，归一化编辑距离 | 无标注（就是真分） |
| 模拟 | 不支持识别（iOS Safari / Firefox / 离线） | `mockFollowScore`：录音时长 vs 句子词数的语速合理性（40–98 分） | 角标写明 **·模拟** |

两条路**互斥**——识别与 MediaRecorder 抢同一个麦克风会互相掐死，所以先判识别能力，可用就直接 return 不再开录音。
模拟分只衡量「说得流不流畅、快不快」，**不代表发音准不准**，所以必须标注。

## 五、已知取舍 / 下一步

1. **需求 10 未做**（学习进度跳过已学组、最多加载 5 组）—— 它属于 `/learn` 学习流，等你确认详情页风格后再做。
2. **需求 9 的「每个页面都有返回箭头」只在详情页落地**，其余页面仍沿用原布局，推广时一起补。
3. **弹窗定位**用的是 `getBoundingClientRect` + `fixed`：滚动时会自动关掉弹窗（fixed 定位跟不上滚动），这是刻意的，避免弹窗飘到屏幕外。
4. **想让所有词都支持「释义对应例句」**：重跑数据管线给 `examples` 加 `sense_index`，前端零改动。
5. 详情页的搜索框输入走的是全词库 `search-index.json`（约 4MB，首次加载约 1–2 秒），之后内存常驻。
