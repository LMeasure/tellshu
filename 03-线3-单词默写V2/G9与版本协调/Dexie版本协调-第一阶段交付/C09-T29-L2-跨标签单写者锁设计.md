## 1. C09/T29 残留窗口定义（锁要解决的问题）

> `Phase1.1` L393：**C09｜事件 `add` 尚未落盘时另一标签已提交｜—｜残留窗口，未解决：如实记录，不宣称覆盖｜物理先后｜B / 待裁定 D4**。

这是设计要解决的原始缺陷：标签 A 判定一个错误、准备写入事件行，但事件行**尚未持久化**的瞬间，标签 B 已接管并完成提交，A 的延迟写入落盘后既无会话锁校验（T-A 走 `insertIfAbsent` 单请求，绕过会话表 `updateAtomic`），又无代次标识，于是被结算为「当前会话错误」→ 错词本出现不属于当前会话的词、凭证永不生成、drain 永久 pending。

**统一锁的解法**（α）：用 `active_tab_id`（当前持锁标签）+ `lock_epoch`（持锁代次，fencing token）把「跨标签单写者」显式化，使 A 的延迟写入能被识别为 stale 并终结重放。

## 3. 已有权威设计（fencing token + 旧持有者拒绝 + takeover/release）

### 3.1 fencing token：`lock_epoch` + `tab_id`

```ts
interface SpellingSession {
  // ...既有字段 + V1.2 的 applied_error_event_ids / active_tab_id
  lock_epoch?: number    // 每次成功 takeover 在同一 updateAtomic 内 +1
}
interface SpellingErrorEvent {
  // ...V1.1 定义字段
  tab_id: string         // 写入时的持锁标签
  lock_epoch: number     // 写入时的锁代次快照
}
```

`lock_epoch` 与 `tab_id` 是**行内字段，不是索引字段**：Dexie `stores()` 字符串只列索引，新增行内字段**不改变 schema、不额外触发版本号升级**（Phase1.2.1 §3(b) 实测）。settle 按既有 `session_id` 索引取事件，epoch 在 reducer 内比较。

### 3.2 旧持有者拒绝写入：`appendErrorEventIfOwner` 契约

```text
1. 同步 assertLockHeldLocally(myTab)        —— 内存标志，仅 acquireLock 成功后为 true（关闭 R3）
2. await SESSIONS.get(sid)                 —— 独立【只读请求】，精确按 sid
   校验 active_tab_id === myTab && lock_epoch === myEpoch
   否则：拒绝落盘 → UI 冲突面板（关闭 R1/R4 的入口）
3. 构造 E（含 tab_id=myTab、lock_epoch=myEpoch、session_id、word_id、event_id）
4. await EVENTS.insertIfAbsent(E)          —— T-A，独立单表请求
5. 不再二次校验（写入已成事实）；由 settle 的 (d) 按 epoch 收敛
```

⚠️ 步骤 2 与 4 是跨表两个独立请求，不是原子事务，TOCTOU 窗口仍在（U11）。`assertLock` 的读不得包装成 `updateAtomic`，也不得宣称「校验与写入原子」。

### 3.3 settle 的代次校验与 stale 处置（关闭永久 pending）

```ts
function settleReducer(s: SpellingSession, E: ErrorEvent, myTab: string) {
  if (s.active_tab_id !== myTab) throw new Error('TAB_LOCK_LOST')   // 冲突面板
  if (s.applied_error_event_ids?.[E.event_id] === true) return s     // P0-1 二次检查（最高优先）
  if (E.lock_epoch !== (s.lock_epoch ?? 0)) {
    return { ...s, applied_error_event_ids: { ...(s.applied_error_event_ids ?? {}), [E.event_id]: true } } // stale：写凭证、不归零、不 SRS
  }
  return applyTypingErrorEvent(s, E)                                  // 本代次：归零 + 写凭证
}
```

- T-C 把 stale 事件标 `settled_skipped` + 原因码 `stale_epoch`（不记隐私）；**事件行保留**，错词计数仍真实（用户确实按错了）。
- 因为写了凭证，drain 不再无限重放；因为不归零，新标签的连对进度不受影响；因为不 `COMPLETED`，不触发 `srs_due`/`recordQuiz`。

### 3.4 九条写入路径锁覆盖表（全部覆盖，负责人点名清单）

| # | 路径 | 写哪张表 | 锁校验位置 | 失败行为 | 需 epoch |
| --- | --- | --- | --- | --- | --- |
| 1 | `error event insert` | 事件表（T-A） | 前置 `assertLockHeldLocally` + `SESSIONS.get(sid)` 校验；行内带 `tab_id`/`lock_epoch`；**跨表非原子** | 拒绝落盘 → 冲突面板；已 in-flight 落盘者由 settle 判 stale | 是 |
| 2 | `settle` (T-B) | 会话表（`updateAtomic`） | reducer 内 `active_tab_id===myTab` + epoch 校验 + **凭证二次检查** | `TAB_LOCK_LOST` → 冲突面板；stale → 写凭证 + `settled_skipped` | 是 |
| 3 | `submitAttempt` | 会话表（`mutate`→`updateAtomic`） | reducer 内；提交前 `settle(sid)` 屏障 | `TAB_LOCK_LOST` → 不判分、不 SRS | 是 |
| 4 | `skip` | 会话表 | reducer 内 + 前置屏障 | 同上 | 是 |
| 5 | `pause` | 会话表 | reducer 内 | `TAB_LOCK_LOST` → 不改状态 | 是 |
| 6 | `resume` | 会话表 | reducer 内；**resume 成功后先 `drainPendingErrors()` 再解锁输入** | 同上 | 是 |
| 7 | `abandon` | 会话表 | reducer 内 | 同上 | 是 |
| 8 | `takeover` | 会话表（**改锁本身**） | **唯一例外**：不校验 `active_tab_id===myTab`；改为「用户显式确认 + 无条件覆写 `active_tab_id=myTab` + `lock_epoch+1`，同一 `updateAtomic`」 | 未确认不执行；确认后旧标签全部写入被拒 | 是（递增） |
| 9 | `release` | 会话表（清空 `active_tab_id`） | reducer 内校验 `s.active_tab_id === myTab` 才清；**不匹配则 `return s` 不写回** | 旧标签不得清掉新锁（关闭 R4） | 否 |

### 3.5 事务边界（不得合并描述）

所有 `updateAtomic` 仍是**单表单事务**；`assertLock` 的 `SESSIONS.get` 是**独立只读请求**；`insertIfAbsent` 是**独立单表请求**。四者不构成跨表原子事务。锁的可靠性来自：① 同一会话文档 rw 事务串行化；② 接管在同一 `updateAtomic` 内原子递增 `lock_epoch`；③ stale 事件可识别且可终结。**不来自跨表原子性**。

## 4. 锁过期（设计提案 · 待批准）

> **现状**：权威设计用 `takeover`（用户显式确认 + `lock_epoch+1`）实现「锁转让」，但**未定义无显式释放时的自动过期**（如持锁标签崩溃、未走 `release`）。本小节为本次新增设计提案。

**提案要点**：
- 引入**软租约（lease）**：`spellingSessions` 增加 `lock_held_at?: number`（最近一次取锁/心跳时间戳，行内字段，不触发版本升级）。
- 取锁/心跳成功时写 `lock_held_at = Date.now()`。
- 新标签尝试 `acquireLock` 时，若 `active_tab_id !== myTab` 且 `now - lock_held_at > LEASE_MS`（建议 30s，待产品裁定），允许**强制覆写**并 `lock_epoch+1`，原持有者后续写入被判 stale。
- 禁止用 `Date.now()` 单调性做正确性判据（U6 时钟回拨仅影响展示）；过期判定只用于「允许强制接管」的**安全兜底**，最终正确性仍由 `lock_epoch` fencing token 保证。

**待裁定**：LEASE_MS 取值、是否需要在 UI 提示「原持锁标签疑似失联」、与 `release` 显式释放的优先级。

## 5. 心跳延迟（设计提案 · 待批准）

> **现状**：权威设计无心跳原语。本小节为新增提案，用于维持 §4 的软租约，并覆盖「持有者短暂卡顿但仍在」不被误过期。

**提案要点**：
- 持锁标签在 `inputEnabled=true` 期间，周期性（建议 10s，待裁定）执行 `renewLease()`：`updateAtomic` 内校验 `active_tab_id===myTab && lock_epoch===myEpoch` 后写 `lock_held_at=now`；任一不匹配则本地置 `inputEnabled=false` 并进入冲突面板。
- 心跳延迟/丢帧：单次要跳不立即判失锁，需连续缺失 `>= LEASE_MS/心跳周期` 次才允许 §4 强制接管；避免 GC 停顿、后台标签页节流（见 §6）导致的误过期。
- 后台标签 `setInterval` 被浏览器节流至 1/min，故心跳周期与 LEASE_MS 必须考虑节流下限，否则后台持锁标签必被误过期——此点为设计必须显式处理项。

**待裁定**：心跳周期、连续缺失阈值、节流下的租约参数。

## 6. 标签休眠（设计提案 · 待批准）

> **问题**：浏览器对后台标签页的 `setInterval`/`setTimeout` 强制节流（通常 ≥1s，部分 ≥1min），`requestAnimationFrame` 暂停。若持锁标签被切到后台，其心跳（§5）与锁维持会被节流，可能触发 §4 误过期；反之若它是旧持有者，其延迟写入（T-A）可能在被接管后很久才落盘（R1/R2 的极端化）。

**提案要点**：
- 切后台（`visibilitychange → hidden`）时：持锁标签立即触发一次 `renewLease()`；并**放宽** §4 对其的过期判定（后台标签享更长 `LEASE_MS_BACKGROUND`，待裁定），使后台持锁不被前台标签误接管。
- 旧持有者切后台后复活（R3）：输入闸门 `inputEnabled` 在 `acquireLock()` 前恒为 false（硬闸门，§3 权威设计），故后台/休眠期间不会产生无锁事件；复活后若锁已易主，其写入被 §3.2 拒绝或判 stale。
- `visibilitychange → visible` 时：立即 `renewLease()` + 重新 `getSessionById` 重读 `lock_epoch`，若发现锁已被接管 → 进入冲突面板，不沿用内存旧 `myEpoch`。

**待裁定**：`LEASE_MS_BACKGROUND` 取值、休眠复活后是否自动发起 takeover 提示。

## 7. 锁不可用时的安全降级（设计提案 · 待批准）

> **触发场景**：`acquireLock()` 因 IDB 连接异常 / 升级 blocked（U16 S5）/ 事务抛错而无法取得锁；或多标签抢夺导致反复 takeover 抖动。

**提案要点（安全降级优先级）**：
1. **取锁失败 → 只读 + 禁用输入**：`inputEnabled=false`，页面进入「正在取得本会话的写入权…」或冲突面板，**不发起任何 9 条写入路径**（含 T-A `insertIfAbsent`）。不静默失败、不假报成功（对应 U16 S5 只读约束）。
2. **升级 blocked → 明确提示 + 只读**：依 V1.2.7 L254 提示「关闭其他标签页以完成更新」；本任务页面零写入，已落盘事件与凭证不动。
3. **连接中断 → 丢弃内存态，等重连**：按 U16 铁律 2，重连后必须重走「`db.open()` → `getSessionById` → `acquireLock`（重读 `lock_epoch`）→ `drainPendingErrors` → `inputEnabled`」，不得沿用旧锁/旧 epoch。
4. **反复 takeover 抖动 → 进入冲突面板，交由用户显式决策**：不自动循环抢锁；提示「另一标签页正在使用本会话」。
5. **降级绝不发生**：伪造成功、沉默丢弃错误事件、或无锁直接写盘（违铁律与 R1–R4）。

## 8. 与 C09/T29 的关系（降级但未消除 · 如实记录）

> `Phase1.2.1` §8.1 **U1**：跨标签情形 2（事件未落盘、另一标签已提交）经 `lock_epoch` **降级但未消除**——旧代次事件不再死锁/误归零/误触发 SRS，但**错词本仍可能多一条 stale 记录**。彻底消除需 L3 跨表事务（不推荐本轮）。

即统一锁把 C09/T29 从「永久 pending / 错词本出现异词」降级为「一条真实错误被记为 stale（计入错词本、不影响当前会话连对、drain 不再重放）」。这是**设计层已知的残留窗口**，不宣称已完全消除（U11）。是否接受「错词本可能多 1 条 stale 记录」属 **D12** 产品口径裁定范围。
