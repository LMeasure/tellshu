## §2 结论

### §2.1 共置污染假设：**未获支持**

- 轮 1：A 215.95 ms → B 92.46 ms，看起来隔离省了一大截；
- 轮 2：**A 48.24 ms → B 116.53 ms**，臂 A 反而更快 —— 方向完全反转。

两轮结论互相矛盾，且**组间差远小于组内波动**，因此不能说「分进程能稳定降低 retrieve」。

### §2.2 真正的主导因素：页缓存冷缺失

- 加了预热的臂 C 两轮 retrieve P50 = 9.4 / 9.41 ms —— **两轮几乎完全一致**；
- 共置 + 预热的臂 D retrieve P50 = 9.5 ms。

**D（9.5 ms）与 C（9.41 ms）同量级** —— 编码就在 API 进程内也没关系。这直接说明：只要页缓存是热的，共置不会拖慢检索。

> 定案：189 ms 的 retrieve 里，绝大部分不是「编码抢走资源」，而是**索引页不在内存里**。编码位置是次要变量。

### §2.3 归因链

```
内存不足（负载 91~95%，可用 0.6~1.4GB）
   → 456MB HNSW 索引 + 808MB 堆无法常驻 OS 页缓存
   → 每条新 query 触发冷读（EXPLAIN 显示 shared_read ≈ 4000 块 / 次）
   → retrieve 从 9ms 涨到 48~216ms
```

编码的 2GB 常驻**加重**了这个局面（它挤占了本就不够的内存），但它不是开关——把编码挪到另一个进程（臂 B）并没有稳定解决问题，因为那 2GB 仍然在同一台机器的内存里。

## §3 预算定标

| 指标 | 当前常态（臂 A：共置 + 冷缓存） | 硬件可达（臂 D：共置 + 预热） | 说明 |
|---|---:|---:|---|
| encode P50 | 130.94 | 128.59 | 两臂同为共置，无 HTTP 编码往返；隔离臂 C 是 152.44 ms，多出的约 23.8 ms 就是编码调用的 HTTP 往返 |
| retrieve P50 | 75.13 | 9.5 | **差值几乎全是冷读开销**，不是编码开销 |
| e2e P50 | 215.4 | 137.31 | |
| e2e P95 | 644.75 | 150.41 | |

### §3.1 决策树落点

- 臂 B e2e P50 落在 200~280ms → 目标 e2e ≤ 280ms，且需配合其它手段
- 但按 §2 的结论，**这个决策树的前提本身不成立**：臂 B 的 e2e 高低由页缓存状态决定，不是由部署形态决定。所以定标不能只看部署形态，必须同时给「缓存热」与「缓存冷」两个口径。

### §3.2 两个口径的预算

| 口径 | 触发条件 | e2e P50 | 说明 |
|---|---|---:|---|
| 乐观（页缓存常驻） | 内存充裕 / 索引被反复访问 | 137.31 ms | 实测最优臂 D，是**硬件条件下能做到的最好值** |
| 悲观（页缓存冷） | 内存紧张 / 冷启动后首批 query | 215.4 ms | 当前本机常态 |

**不要在两者之间取一个数当预算** —— 那是把 10 倍的波动抹平成一个假数字。

### §4.1 预期决策表（仍为预期，未实测）

| 方案 | 编码 P50 | 常驻内存 | recall 影响 | 全库重算 | 对**本轮根因**的作用 |
|---|---:|---:|---|---|---|
| torch FP32（当前） | 130.94 ms（实测） | ~2.2 GB | baseline | 不需要 | — |
| ONNX FP32 | 预期 ~70–100 ms | 预期 ~1.2 GB | 预期 <0.1% | 不需要 | 腾出约 1.0 GB 给页缓存 |
| ONNX INT8 | 预期 ~45–70 ms | 预期 ~0.57 GB | 预期 <0.5% MTEB | **需要（58,332 条）** | 腾出约 1.6 GB 给页缓存 |

**关键修正**：B.9 假设 ONNX 的价值是「编码快 3 倍」，B.10 的归因显示真正的杠杆是**它把常驻内存从 2.2GB 压到 0.57GB，腾出的 1.6GB 正好可以用来让索引常驻页缓存**。也就是说 ONNX 打的是 §2.3 归因链的源头，而分进程没有。

> ⚠ 上表除实测两行外全为预期（他人硬件外推）。上 INT8 前必须做 B.9 §7.4 的准入清单，尤其是「INT8 query 向量 vs FP32 库向量」的 McNemar 召回对照。

## §5 监控端点

### §5.1 GET /api/discover/status

聚合 health + quick regression，供外部监控一次调用拿全。
**不跑 EXACT**（那要 20 秒），N* 用缓存斜率算，斜率来源会在响应里标明。

```jsonc
{
  "timestamp": "...",
  "health": { status, database{ef_search, iterative_scan, guc_match},
              plan{type, index, rows_returned}, embedding, latency_profile, pool },
  "regression_quick": { row_count, n_star_400ms_long_query, occupancy_pct, status,
                        slope_ms_per_1k_rows, slope_source, caveat },
  "status_elapsed_ms": 12.3
}
```

### §5.2 GET /api/discover/health 新增 latency_profile

```jsonc
"latency_profile": {
  "mode": "colocated",        // 或 isolated —— 两者 retrieve 不可混着看
  "source": "_b10-arm-A-r2.json",
  "mode_match": true,         // false = 这份数据与当前部署形态不一致，别拿去做预算
  "encode_p50_ms": ..., "retrieve_p50_ms": ..., "e2e_p50_ms": ...
}
```

值从 `.crawl-cache` 里**最近一次压测**读取并缓存在内存，health 不实时跑压测。
优先取与当前形态一致的那份；取不到才回退，并用 `mode_match=false` 标出来 —— 不假装匹配。

## §9 待决策

1. **是否分进程部署编码服务？** — 本轮实测**不支持**「分进程能稳定降低延迟」。建议：先不为此投入部署复杂度，把力气花在内存上。
2. **是否实施 ONNX INT8（含全库重算）？** — 它才是打在根因上的手段（降常驻内存 1.6GB）。但本轮因 PyPI 不可达未能验证；且全库重算 58,332 条是真实工程量。建议网络恢复后按 B.9 §7.4 准入清单做。
3. **监控是否接入 cron？** — 端点与脚本已就绪。
4. **API 是否绑定 0.0.0.0 + 鉴权？** — 当前仅 127.0.0.1，对外暴露前需补鉴权/限流/优雅停机。
5. **是否接受「双口径预算」？** — 单一数字预算会把 10 倍波动抹平，建议按 §3.2 分口径。
