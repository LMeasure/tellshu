## 1. 执行摘要

Phase 0.6 已完成技术审计，识别出 3 项 P0、6 项 P1、3 项 P2 风险，并明确了「系统当前**无真实用户身份**、文件接口零授权、ASR 无进程故障隔离」等事实。Phase 0.7 不写代码，而是把 Phase 0.6 暴露的技术风险翻译成**必须由产品拍板的决策**（D1–D7），并固化为 Phase 0.8 的硬约束。

七项决策的核心立场：
- **身份模型（D1）**：推荐「近期单用户私有实例 + 能力令牌过渡，远期多用户账户」的分阶段路线，但**最终选型保留给用户**。
- **保留期限（D2）**：给出每类数据的**保留框架与建议默认值（均标待批准）**，明确不凭空设定业务期限。
- **游客限制（D3）**：明确机制（IP/会话/令牌限额、文件大小、滥用防护），但**免费额度数值待成本测算后由产品定**。
- **管理员密钥（D4）**：给出生成/存储/轮换/吊销/审计/隔离/应急全流程设计。
- **费用与资源（D5）**：区分实测/估算/待测，给出 4C16G / 8C16G 下的资源与并发边界。
- **ASR 架构（D6）**：推荐**独立 systemd sidecar**；明确「仅加异常处理器 ≠ 进程故障隔离」。
- **RPO/RTO（D7）**：给出三档恢复目标供产品选择，**不声称已达到**（无演练数据）。

> 本轮止步于决策，**不进入 Phase 0.8 实施**。

## 3. 七项决策分析

### D1：用户身份模型

| 方案 | 开发成本 | 安全边界 | 迁移成本 | 未来扩展 |
|---|---|---|---|---|
| **A 单用户私有实例** | 极低（现状即用） | 依赖网络隔离（反向代理/IP 收敛），无应用层身份 | 低（未来加身份可叠加） | 弱（难支撑多用户/付费） |
| **B 多用户账户体系** | 高（建 `app_users`、补 `owner_id` 列、RLS、配额、会话） | 强（per-user 隔离 + RLS，V1.2.x 已有成熟设计但未实施） | 高（Dexie `owner='guest'`→真实 sub、多表补列） | 强（付费/多端/配额天然支撑） |
| **C 游客 + 注册并存** | 中（B 的子集 + 游客降级路径） | 中（注册用户强隔离，游客限功能/限额） | 中（先落地 B 的账户骨架，游客为默认角色） | 强 |

**当前事实**：系统无真实账户（`auth/web.ts` 本地桩、`app.ts` 无用户鉴权中间件、全表无 `owner_id`）【当前源码验证】。前提卡确认「初期免费、主学习链路纯离线、server 仅旁路」【待产品决策/历史报告】。

**推荐（待批准）**：**分阶段**——近期采用 **A + 能力令牌过渡**（维持 guest 模型，Convert 三接口改签名短效令牌授权，反向代理收敛 `/api/*`），不等产品决策即可消除 R1；远期在产品确认多用户后迁移 **B/C**。C 是 B 的友好默认（游客即未注册角色），推荐作为 B 的落地形态。

**保留用户最终决定权**：A / B / C 的最终选型由产品拍板；本文不擅自确定。

### D2.1 七类文件统一生命周期矩阵（R3）

> 目标行为统一遵循：当前**内存态/无清理** → 目标**DB 状态机 + 软删 + TTL + 孤儿对账**；TTL 起算点 = 终态时间（completed/failed）或用户删除触发时间。

| 数据类型 | 当前行为 | 目标行为 | 存储位置 | 状态机 | TTL 起算 | 用户删除 | 物理清理 | 备份 |
|---|---|---|---|---|---|---|---|---|
| OCR 原图 | 落盘无删、无接口、`store_failed` 孤儿(`ocr/storage.ts`,`pipeline.ts:190-199`) | 软删 + 保留期后物理删 + 孤儿对账 | `data/ocr/<yyyy>/<mm>/<hex24>` | created→uploaded→processing→completed→expired→deleting→deleted | 终态/软删时刻 | 软删记录→清理任务到期删盘 | TTL 清理任务 | 定期(不可再生) |
| OCR 结果 | 仅 DB、行永久(`scan_records`) | 随原图软删 | DB(text/jsonb) | 同上 | 随原图 | 随原图 | 随原图 | 随主库 |
| ASR 原始媒体 | 终态删 `in/`(`mediaStore.ts:40-47`)、重启残留 | 软删 + 保留期 + 持久化前置 | `data/asr/in/<jobId>/` | 同上(需 `asr_jobs` 表) | 终态/保留期 | 经 `asr_jobs` 定位删盘 | TTL 清理 | 可选 |
| ASR 转录结果 | 内存态、重启即失(R6) | 落 `asr_jobs` 表持久化 | DB(`asr_jobs.transcript`) | queued→running→done/failed→expired | 终态/保留期 | 经 `asr_jobs` 删 | TTL | 不备份(可重算) |
| ASR `out/*.json` | 永不清理、Node 不读(R7) | **完成即删**(死写入) | `data/asr/out/` | 写入→完成即删 | 完成时刻 | 不适用 | 完成即清 | 不备份 |
| Convert 源 | Worker 删盘留行(R5) | 删盘 + 行软删 + 无任务孤儿 TTL | `data/convert/<uuid>` | created→uploaded→processing→(deleted) | 终态/孤儿检测 | 无端点 | TTL(24h 孤儿)+Worker | 不备份 |
| Convert 结果 | TTL 1h 删盘留行 | 删盘 + 行软删 | `data/convert/<taskId>/` | 同上 | 终态 + 1h | 无端点 | TTL(`index.ts:39`) | 不备份 |

**ASR 原始媒体与转录结果持久化前置条件（关键）**：在 D1 身份模型落地前，ASR 媒体/结果须用**任务能力令牌（`task_token`）**绑定归属，使「用户删除」可定位对应 `in/` 文件与 `asr_jobs` 行；若采用单用户私有实例（D1-A），「用户删除」退化为「实例所有者删除或保留期到期」。引入 `asr_jobs` 表是 R6 持久化的前提，亦为 D2 清理提供状态真相源【架构建议】。

### D3：匿名用户与游客限制

**现状成本/滥用面（【当前源码验证】）**：
- 匿名上传/OCR：`POST /api/ocr/material` 受 `OCR_PUBLIC_ENABLED`（`config.ts:166`），开启即匿名触发 OCR 计费【当前源码验证】。
- 匿名 ASR：`POST /api/asr/jobs` IP 限流 10/h（`routes/asr.ts:48`）【当前源码验证】。
- 匿名 Convert 上传/任务：`routes/convert.ts:149` IP 限流 30/h、`:183` 无额外限额【当前源码验证】。
- 匿名 AI 学习稿：`POST /api/ai/study-notes` IP 限流 10/h（`routes/ai.ts:51`）【当前源码验证】。
- 匿名翻译：`POST /api/translate` 无显式限额【当前源码验证】。

**防护方案（架构建议，数值均待产品确认）**：
1. **服务端会话签发**：即使游客，也由服务端签发匿名会话令牌（随机、`session` 表或内存），用于配额计数——**不是前端假 token**（`auth/web.ts` 本地桩不计数，须改为服务端计数）【当前源码验证】【架构建议】。
2. **配额存储**：服务端存储配额计数（PG `resource_usage` 或 Redis），按**会话/令牌/IP** 维度；不依赖前端【架构建议】。
3. **IP 信任代理**：真实 IP 由反向代理（Caddy）可信注入 `X-Forwarded-For`，**禁止客户端伪造**；配额按可信 IP + 会话联合计数，防单 IP 刷【架构建议】。
4. **令牌轮换**：匿名会话令牌短效（如 1h）可轮换，计数随令牌；旧令牌过期即停计【架构建议】。
5. **限额绕过防护**：单 IP 限速 + 每会话限额 + 每令牌限额 + 文件大小（`multer` 50MB，`http/upload.ts`）+ 行为异常（验证码）【当前源码验证】【架构建议】。
6. **限额分层（区分维度）**：
   - **单文件限制**：50MB（`http/upload.ts`）【当前源码验证】。
   - **请求总量**：每会话/每日请求数上限（待成本测算）【待产品决策】。
   - **并发缓冲**：同时在处理任务数（如 ≤2）防止积压【架构建议】。
   - **各模块限制**：OCR/ASR(`routes/asr.ts:48` 10/h)/Convert(`routes/convert.ts:149` 30/h)/AI(`routes/ai.ts:51` 10/h) 分别限额，现有 per-IP 基线保留并细化【当前源码验证】。
7. **可观测**：限流命中、配额耗尽统一埋点告警【架构建议】。

### D5：费用与资源控制

> 区分：**实测**（已测数字）/ **估算**（推算）/ **待测**（需成本/压测）。

| 项目 | 资源特征 | 可信度 | 备注 |
|---|---|---|---|
| OCR 单次 | PaddleOCR CPU 推理，耗时 ∝ 图片尺寸/页数；内存随并发 | **估算/待测** | `OCR_PUBLIC_ENABLED` 控可用性【当前源码验证】 |
| ASR 单次 | whisper-small int8 模型 **~461MB**（常驻 ~0.5GB），CPU 推理耗时 ∝ 音频秒数，单 worker 串行（`job_queue.py` 单队列） | **历史实测**(模型体积)/**估算**(吞吐) | Phase 0.5-R 已记模型体积 |
| Convert 单次 | CPU 转换，耗时 ∝ 页数/格式；单 Worker PG 轮询（`worker.py`） | **估算** | 源 50MB 上限【当前源码验证】 |
| AI 外部 API | LLM token 成本，取决于提供商/模型；SSE 学习稿端点存在（`routes/ai.ts:51`）但成本未知 | **待测** | 仓库无单价 |
| 磁盘增长 | OCR 原图无清理 = 最大不确定项（`ocr/storage.ts`）；ASR `out/` 累积；Convert 结果 1h TTL | **当前源码验证**(无清理)/**估算**(增量) | Phase 0.6 §10 公式 |
| 并发上限 | 4C16G：CPU 瓶颈（ASR/Convert 串行 + OCR/AI 外部），限流兜底；8C16G：推荐候选，余量更宽 | **源码推断/估算** | Phase 0.5-R：4C16G=低成本试运行、8C16G=优先候选待压测 |

**结论**：在 4C16G / 8C16G 下，单实例并发由「ASR 单 worker 串行 + Convert 单 Worker 轮询 + 外部 API 限额」自然封顶；**具体可支撑并发数与单次成本需压测/成本测算后填入 Phase 0.8 验收基线**。

### D6：ASR 架构决策

| 方案 | 故障隔离 | 自动恢复 | 任务持久性 | 改造范围 | 备注 |
|---|---|---|---|---|---|
| 一：Node 管理 sidecar + 补强 | **弱**（同进程组；仅加全局异常 handler 减少孤儿，但 SIGKILL/外部杀仍遗留） | 部分（handler 内 `close()`） | 需另引 DB | 中 | **注意：增加异常处理器 ≠ 完整进程故障隔离**【架构建议/源码推断】 |
| 二：sidecar 独立 systemd | **强**（OS 级独立单元，`Restart=on-failure` 自愈） | **强**（systemd 拥有 PID） | 需另引 DB（可选） | 中（去 Node spawn、加 unit） | **推荐** |
| 三：独立 Worker + 持久队列 | 最强（独立进程 + 队列） | 最强 | 天然（队列/DB） | 大（重写任务模型） | 过度工程（当前单 worker 串行足量） |

**推荐（待批准）：方案二（独立 systemd sidecar）**【架构建议】。理由：以最小改造（移除 `sidecar.ts:39-58` 的 Node `spawn`、改 `asr_provider` 指向由 systemd 托管的 `http://127.0.0.1:8177`）彻底消除孤儿进程与永久 503（R2）。

**服务与 Node 的关系（关键澄清）**：sidecar 与 Node 是**两个独立的 systemd unit**（`shushu-server.service` 与 `shushu-asr.service`），通过回环 HTTP 协作。**sidecar 的生命周期独立于 Node**：Node 崩溃 / SIGKILL / 重启**不影响** sidecar 运行，sidecar 也**不随 Node 退出而退出**（**明确：不得要求独立 sidecar 随 Node SIGKILL 一同退出**）。Node 仅作为 sidecar 的 HTTP 客户端，经 `waitReady` 轮询 `/health` 重连【架构建议】。
- systemd 单元要点：`shushu-asr.service` 设 `Type=simple`、`Restart=on-failure`、`RestartSec=3`、`KillMode=control-group`；`shushu-server.service` 的 `After=`/`Requires=` **不**把 asr 设为子进程【架构建议】。

方案一的补强（全局 handler、`main().catch` 关 sidecar、启动清 8177、清 `out/`、`asr_jobs` 持久化）作为**近期快速加固**保留，但明确其不构成完整故障隔离【架构建议】。任务持久化：引入 `asr_jobs` 表承载状态/归属/结果，使 Node 重启可恢复/重同步（R6）【架构建议】。

**验收指标（供 Phase 0.8 实现，均待实测验证）**：
1. **服务自动恢复**：`shushu-asr.service` 进程被杀后，systemd 在 `RestartSec` 内自动拉起，`/health` 恢复 200【架构建议】。
2. **Node 重连**：Node 在 sidecar 重启期间返回 503（不崩溃），sidecar 恢复后 Node 自动重连恢复，无需重启 Node【架构建议】。
3. **健康状态恢复**：sidecar `/health` 就绪即恢复；`main().catch`/SIGKILL 不再导致 sidecar 孤儿（因 systemd 拥有 PID）【当前源码验证】【架构建议】。
4. **重复启动防护**：systemd 确保单一实例（`RuntimeDirectory`/`PIDFile` 或 `ExecStartPre` 检测端口），防止双起【架构建议】。
5. **端口冲突处理**：sidecar 启动前检测 8177 占用；若被残留占用则清理或失败告警（systemd 防重复实例为主手段）【架构建议】。
6. **无 `out/*.json` 累积**（沿用 R7）【当前源码验证】。

### D7：RPO / RTO

> 给出**三档供产品选择**；当前无任何恢复演练，**不声称已达到任何目标**（【未证实】）。

**备份一致性设计（R4）**：
- **PG 与文件 RPO 分别定义**：DB RPO = 允许丢失的 DB 变更时长；文件 RPO = 允许丢失的用户文件时长。OCR 原图/ASR 媒体不可再生 → 文件 RPO 须与备份频率对齐（如 T2 ≤ 1h 增量）【架构建议】。
- **文件备份最大延迟**：定义 `file_backup_max_lag`（T2 ≤ 1h），超过即告警；增量备份以 `checksum`/`mtime` 去重【架构建议】。
- **异地复制确认**：异地备份投递后校验对象存在 + `sha256` 一致（确认回执），失败告警重投【架构建议】。
- **DB-文件一致性恢复**：以 DB `scan_records.image_path` / `convert_files.storage_path` 为真相源，恢复后校验文件存在；缺失标记 `missing` 并触发重新上传/用户通知【架构建议】。
- **误删除恢复**：文件级时间点恢复（从最近备份提取单文件）；DB 级 PITR；恢复后跑孤儿检测对账【架构建议】。
- PG WAL 归档当前**未配置**（Phase 0 已记）【历史实测】。
- 三档均为**待产品选择**；选定后由 Phase 0.9 实现并**用真实演练验证**，验证前不得宣称达标【未证实】。

## 6. 对 Phase 0.8 的技术约束（§四 七项问题输入）

> 下列为**硬约束**，Phase 0.8 修复设计必须满足；每条锚定 Phase 0.6 证据。

1. **Convert IDOR（R1）— 能力令牌协议（详细）**：任务创建 `POST /api/convert/tasks` 成功时由服务端签发**签名能力令牌**（HMAC-SHA256，密钥 `CONVERT_TOKEN_SECRET` 经 env 注入，`server/.env` 不进仓库）【架构建议】【当前源码验证(端点 `convert.ts:183-212`)】：
   - **令牌交付**：随响应体返回，客户端存入内存（**禁止 localStorage、禁止 URL query**，防日志/代理泄露）【架构建议】。
   - **任务绑定**：payload 含 `taskId`；`/zip`(`convert.ts:256-301`) 必须校验 `taskId` 匹配。
   - **文件绑定**：payload 含 `fileIds[]`（结果文件集合）；`/download?fileId=`(`convert.ts:238-253`) 校验 `fileId ∈ fileIds`；**ZIP 多文件授权**：令牌授权整个任务结果集，`/zip` 一次校验令牌有效 + `taskId` 匹配即可，内部按 `fileIds` 逐个读取，**杜绝凭单 fileId 猜测他人文件**【架构建议】。
   - **操作 scope**：`download`/`zip`/`ocr`(`convert.ts:304-344`) 分别或合并 scope，令牌 scope 须覆盖所请求操作【架构建议】。
   - **防重放**：令牌含 `nonce`（单次使用，服务端记录已用 nonce）+ `exp`（如 15min）；同 nonce 幂等去重；5xx 可**安全重试**，4xx 立即失败不重试【架构建议】。
   - **吊销 / 轮换**：轮换 `CONVERT_TOKEN_SECRET` 即全局失效（旧令牌验签失败）；支持双密钥并行过渡（旧密钥宽限期）；可选 `jti` 黑名单【架构建议】。
   - **安全重试**：客户端 5xx 指数退避 ≤3 次；4xx 立即提示；令牌过期返回 401 → 前端重新建任务获取新令牌【架构建议】。
