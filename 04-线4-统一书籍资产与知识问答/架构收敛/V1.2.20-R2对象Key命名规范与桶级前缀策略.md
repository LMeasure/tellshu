## 3. 对象 Key 规范（输出 1）

### 3.1 命名空间总表

| 类别 | Key 形式 | 产生者 | 生命周期 | 对应 PG 字段 |
|---|---|---|---|---|
| 正式对象（canonical） | `blobs/{sha256}` | 服务端 Promotion（COPY） | 不可变；仅按 `ref_count=0 AND delete_pending` 决策删除（**删除契约冻结，见 §6**） | `content_blobs.r2_object_key`（V1.2.17 §3.1，UNIQUE NOT NULL） |
| 临时 / 分段对象 | `uploads/{session_id}/{sha256}` | 服务端签发的预签名 PUT 或 `CompleteMultipartUpload` | 短期；Promotion 成功后清理；由 `uploads/` 生命周期规则兜底 | `upload_sessions.temp_object_key`（V1.2.17 §4.4(b)） |
| 备份 manifest | **不是 R2 对象** | — | 落 PG 表 `backup_manifests`（V1.2.19 §6） | `backup_manifests.r2_object_list`（jsonb） |

> **`metadata.gen` 不是 Key 的一部分**：V1.2.17 §7.6 / V1.2.19 §7.1 的 `gen` 是 R2 对象**元数据标签**（信任式，R2 不强制），用于恢复分类；不得拼进 Key。同理 R2 `VersionId`、ETag、UploadId 均不得进入 Key。

### 3.2 三环境独立 Bucket 与「Key 不含环境标识」（决策 2）

```
dev      → BUCKET_DEV      （配置项，占位，不写真实值）
staging  → BUCKET_STAGING  （配置项，占位，不写真实值）
prod     → BUCKET_PROD     （配置项，占位，不写真实值）
```

- **环境隔离边界是 Bucket，不是 Key**。三个 Bucket 内 Key 空间**同构**：同一份内容在 dev 与 prod 中都是 `blobs/{sha256}`，字符串完全相同。
- **明确否决**共桶 + `{env}/` / `dev/blobs/...` 前缀方案（本轮候选题中曾提出，现由决策 2 否决），避免后续再提。
- 推论（须落实为服务端约束）：
  1. Bucket 名、Access Key / Secret、Account ID **全部来自环境变量**，启动时集中校验、缺失即快速失败；**不硬编码、不写入代码库、不在本文或任何输出中出现真实值**；真实 `.env` 不提交，仅 `.env.example` 占位。
  2. 启动时校验三桶名**两两互不相同**，防止三环境误指同一桶（配置漂移）。
  3. `user_assets.bucket`（V1.2.17 §3.1 已有字段）语义收敛为「该资产所在环境 Bucket 标识」，取值必须来自服务端配置白名单，**禁止由请求参数/客户端传入**。
  4. **冻结屏障按桶独立控制**：`pause_uploads` / `freeze_outbox` / 桶策略 Deny 须对目标 Bucket 单独生效；「冻结了一个桶」不等于「三个桶都静默」。备份时若只对 prod 做屏障，须明确声明备份作用域，不得跨桶宣称静默（见 §5.6、§7 #14）。
- 三桶配置**必须形状同构**（生命周期规则、前缀策略、TTL、CORS 规则形状一致，仅 Bucket 名与凭证不同），否则 U-4 在 staging 的实测结论无法迁移到 prod。启动时做配置形状一致性校验（设计级，U-4 才能实测）。

### 3.3 正式对象 Key（决策 4）

```
blobs/{sha256}
sha256 := 内容字节流的 SHA-256 摘要，小写十六进制，恰好 64 字符，字符集 [0-9a-f]
正则   := ^blobs/[0-9a-f]{64}$
```

- **小写强制**：大写摘要、混合大小写、非 hex 字符、长度 ≠ 64 一律拒绝。大小写归一不得依赖客户端（否则同一内容可能生成两个 Key，破坏内容寻址去重与 `content_blobs.sha256` 主键一致性）。
- **暂不分层目录**（决策 4）：否决 `blobs/{前2位}/{次2位}/{sha256}`。R2 为扁平 Key 空间、`/` 仅是 Key 字符而非真实目录；分层在当前规模无收益，却会让 §4 的 prefix 规则与 §5 的枚举逻辑复杂化。
- **不可变 + 内容寻址**：`blobs/{sha256}` 一旦存在即不可覆盖写入；同内容跨用户共享同一 Key（V1.2.17 §3.7 的跨用户共享与 N-07 侧信道隔离前提）。V1.2.18 §4.2 Q4 已判定：同 sha256 ⇒ 同内容，两 COPY 竞争幂等无损坏。
- **DB 层强制（设计级 DDL，不执行）**：
  ```sql
  -- 设计级伪代码，不执行
  ALTER TABLE content_blobs
    ADD CONSTRAINT ck_r2_object_key_format
    CHECK (r2_object_key ~ '^blobs/[0-9a-f]{64}$');
  ```
  > 与 V1.2.17 §3.1 已有 `r2_object_key text UNIQUE NOT NULL` 叠加；UNIQUE 防重、CHECK 防格式越界。sha256 由**服务端**根据内容字节计算，不信任客户端声明值（见 §3.5）。

### 3.4 临时 / 分段对象 Key（决策 3）

```
uploads/{session_id}/{sha256}
session_id := 服务端签发的 UUIDv4，小写规范形式（36 字符，含 4 个连字符）
sha256     := 同 §3.3
正则       := ^uploads/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}/[0-9a-f]{64}$
```

- 与 V1.2.17 §4.1 既有草案**一致**（`uploads/{session_id}/{sha256}`），本轮由负责人决策**正式确认**，无需修改该处草案。
- `session_id` 为**服务端签发**的幂等键（贯穿上传、COPY、PG 提交、重试，V1.2.17 §4.1）；客户端不得自报 session_id，服务端须校验签名/会话归属后再签发预签名 URL。
- **UploadId 不进 Key、不进 URL 路径**（V1.2.19 §7.2）：`CreateMultipartUpload` 返回的 UploadId 持久化于 PG `upload_sessions` 行，仅由服务端签发的分片 PUT URL 内部携带。
- 单 PUT 与分段上传**共用同一临时 Key 形式**：单 PUT 直接 PUT 到 `uploads/{sid}/{sha256}`；分段上传 `CreateMultipartUpload(key=uploads/{sid}/{sha256})`，Complete 后在该 Key 产生 temp 对象。两条路径在 temp 对象处汇合，之后走**同一条 Promotion**（§5），避免两套晋升逻辑分叉。
- **DB 层强制（设计级，不执行）**：`upload_sessions.temp_object_key` 加同型 CHECK 正则；`UNIQUE(session_id, sha256)` 防同会话重复 Key。

### 3.5 禁止进入 Key 的信息（决策 5）

| 类别 | 禁止项 | 原因 |
|---|---|---|
| 身份 / 归属 | `owner_id`、`user_id`、租户 ID、邮箱、账号名 | 内容寻址跨用户共享；Key 带归属会泄漏「此内容属于谁」，直接破坏 V1.2.17 §3.7 / N-07 的侧信道隔离 |
| 业务元数据 | 书名 / title、`business_ref`、书籍 ID、章节名 | 用户或业务可控；可变、可枚举、可注入 |
| 原始文件信息 | 客户端文件名、扩展名、Content-Type、Content-Disposition | 可控字符串，URL 编码歧义与路径穿越风险 |
| 环境 / 部署 | `dev` / `staging` / `prod`、Bucket 名、Account ID、区域 | 决策 2：环境隔离由 Bucket 承担，Key 中不得含环境标识 |
| 时间 / 随机 | 时间戳、日期、随机后缀、请求 ID | 破坏内容寻址幂等；同内容产生多个 Key |
| 语法危险字符 | `..`、连续 `//`、前导 `/`、空格、Unicode、`%`、URL 编码、`?`、`#`、控制字符 | 路径穿越、Key 歧义、列举漏项 |

**强制机制（服务端唯一生成权）**：
1. 客户端请求**只提交内容**（或内容分片），**不得提交 Key、sha256、session_id、Bucket 名**；服务端由内容字节计算 sha256 并生成 Key。
2. 服务端在签发任何预签名 URL 之前，用 §3.3/§3.4 白名单正则校验待签 Key；校验失败即拒绝，不降级、不"清洗后放行"。
3. 字符集白名单：`[0-9a-f]`、`-`（仅 UUID 连字符）、`/`（仅两处固定分隔）。其余一律拒绝。
4. DB 层 CHECK 作为最后一道（§3.3/§3.4），防止绕过服务端直接写库。
5. **风险点登记（需负责人后续裁定，本轮不擅改）**：V1.2.17 §3.1 中 `user_assets.object_key` 注释为「资产级 key（**可与 blob key 不同**）」。该自由度为决策 5 留下潜在绕道——若该字段被写入含书名/business_ref 的 Key，会绕过白名单。建议二选一：① 收敛为「必须等于 `content_blobs.r2_object_key`」并加 CHECK；② 废弃该冗余字段，改为按 `blob_sha256` 关联查得。本轮**仅登记，不修改**（§9）。

| PG 字段 | 值 | 约束 |
|---|---|---|
| `content_blobs.sha256` | 小写 64 hex | PK |

### 4.1 三桶配置项总表（形状同构）

> 表中「🚫 禁止」为**硬门禁**：任何在 `blobs/` 上配置 Expiration / Delete 类生命周期规则的行为，等价于静默删除正式内容，属最高危误配（§7 #8）。

### 4.2 prefix 边界必须精确（决策 6）

- Cloudflare R2 生命周期规则按 `Filter.Prefix` 匹配（上一轮官方文档/博客已核实）→ 前缀字符串必须写全为 `uploads/`（含尾斜杠）。写成 `uploads`（少斜杠）会扩大匹配范围，误伤任何以 `uploads` 开头的 Key。
- `blobs/` 前缀**不得被任何规则覆盖**，包括无 Filter 的全桶规则（全桶 `Expiration` 会连带删除 blobs/）。配置校验须显式断言「不存在命中 `blobs/` 的规则」。
- 规则数量上限 1,000（官方博客已核实，文档事实）；本设计仅用 2~3 条规则，远低于上限。
- 三桶各自独立配置、独立校验；不得假设「配了 prod 就等于配了三桶」。

### 4.3 `blobs/` 禁止自动 Expiration（决策 6，硬性）

- 正式内容的删除**只能**来自 V1.2.17 §3.3/§3.4 的业务删除决策链（`ref_count=0 AND delete_pending` + 执行期行锁重验），且该链**当前被 §6 契约冻结 gate 阻断**。
- 对象过期删除是**存储侧**行为，PG 完全不知情：一旦 `blobs/` 被自动删除，PG 中 `content_blobs` 行、`asset_blob_refs` 引用、`user_assets` 记录仍在 → 读到 404，属**静默数据丢失**，且没有任何 DB 层机制能发现。
- 因此：`blobs/` 的 Expiration 规则数必须为 **0**。这是可静态校验的配置不变量（设计级；真实校验须 U-4 在真实 R2 上执行）。

### 4.4 `uploads/` 自动清理与 Promotion / 屏障 / 在途请求的协调（决策 6 核心）

**R2 生命周期的两类规则须区分**（上一轮官方文档/博客已核实）：
- `Expiration{Days}`：作用于**已完成的临时对象**（`uploads/{sid}/{sha256}`）。
- `AbortIncompleteMultipartUpload{DaysAfterInitiation}`：作用于**未 Complete 的分段上传**（UploadId + 已上传分片，不是对象）。默认 7 天（官方镜像已核实，可用自定义规则调整）。

**时序不等式（设计级，数值待 U-1/U-4 决策，不硬编码）**：

```
设 T_upload_max   = 单次上传（含全部分片）最大允许时长
  T_promote_max   = Complete → Promotion COPY → PG 提交 最大时长
  T_freeze_max    = 备份冻结屏障最大持续时长
  T_url_ttl       = 预签名 URL TTL 上限（当前设计 60s）
  T_reaper_grace  = Reaper 清理宽限期
  B               = 安全余量 buffer

约束 1（在途不被误删）:
  Expiration.Days > T_upload_max + T_promote_max + T_reaper_grace + B
约束 2（屏障期不被自动 Abort 打断）:
  AbortIncompleteMultipartUpload.DaysAfterInitiation
      > T_upload_max + T_freeze_max + B
约束 3（生命周期不得作为同步屏障依赖）:
  冻结正确性只由「停发新 URL + 显式 Abort 在途 UploadId + 桶策略 Deny PUT + 等待 TTL 失效」保证；
  生命周期规则仅作纵深防御的兜底清理。
约束 4（Reaper 与 Promotion 互斥）:
  Reaper 清 temp 前取 pg_advisory_xact_lock(hashtext('promote:'||sid))（V1.2.17 §4.5），
  且仅对 status IN ('aborted','expired') 且超 grace 的会话清理。
```

- **约束 3 的依据**：对象过期删除是**异步**的（官方博客：对象通常在 `x-amz-expiration` 后 24 小时内移除；存量对象可能更久）。生命周期既不能在指定时刻精确生效，也不能保证「屏障开始时已全部清完」，因此**不得**用它来实现静默窗口。V1.2.19 §4.1 步骤 2 的静默保证来自显式动作，本轮予以重申。
- **约束 1 的依据**：若 temp 对象在 `Complete` 之后、`Promotion` 之前被 Expiration 删除，COPY 源消失 → canonical 缺失（可用性缺口）。V1.2.18 §4.2 Q5 已判定「R2 COPY 在源删除后的行为【待实测】(U-4)」，故不能依赖"源删了 COPY 还能成功"。
- **约束 2 的依据**：V1.2.19 §5.2 / §7.7 已指出分段自动 Abort 与冻结竞态；FREEZE 显式 Abort 优先，且生命周期窗口须大于屏障时长，避免屏障中途异步 Abort 造成状态抖动。
- 显式 `AbortMultipartUpload` 与生命周期自动 Abort 可能并发 → 对已 Abort / 不存在的 UploadId 调用须按幂等 no-op 处理（V1.2.19 §7.6）。

### 4.5 配置来源与安全（工程约束，设计级）

- 三桶名、凭证、Account ID 全部来自环境变量；启动时集中校验必填项与三桶名互异性，失败即快速失败。
- 真实密钥只存在于 `.env` / 环境变量，**绝不写入代码库或本文**；仅 `.env.example` 提供占位值。
- 桶策略 / 生命周期的变更视为**基础设施变更**，须走与 DB 迁移同等级的可回滚流程；本轮未执行任何此类变更。
- 结构化日志中禁止记录凭证、预签名 URL 全文、UploadId；请求 ID 贯穿（设计级要求，本轮未改代码）。

### 4.6 桶级配置校验清单（U-4 才能实测）

1. 三桶名互不相同、各自凭证可用、无跨桶误指。
2. 三桶生命周期规则形状一致，且**不存在命中 `blobs/` 的 Expiration 规则**（硬断言）。
3. `uploads/` 规则的 `Filter.Prefix` 精确为 `uploads/`。
4. 约束 1~4 的数值在真实时延下成立（须实测 `T_upload_max` / `T_promote_max` / `T_freeze_max`）。
5. 桶策略 Deny PUT `uploads/*` 在 freeze 窗口对**每个桶**生效（**R2 是否支持条件式前缀拒绝，上一轮未获官方确认，标 U-4**）。
6. 预签名 URL TTL 钳制 ≤60s 的签发与到期行为。
7. 生命周期异步生效的实际延迟分布。

> 以上 7 项**全部未执行**；本轮仅定义验收断言。

### 5.1 与既有文档的收敛关系（决策 3）

| 来源 | 原表述 | 本轮处置 |
|---|---|---|
| V1.2.17 §4.2 | `created → uploading → promoting → committed`，终态 `aborted/expired` | **扩展**（不推翻）：拆出分段子状态，统一为 §5.2 一张表 |
| V1.2.19 §4.1 步骤 2 | `WAIT_INFLIGHT` 含 `('created','uploading','promoting','initiated')` | **补充**：还须含 `parts_in_flight`、`completed_unpromoted`（见 §5.5） |
| V1.2.19 §7.1 | `CreateMultipartUpload(key=blobs/<sha256> **或** uploads/<sid>/<sha256>)` 二选一 | **收敛为** `uploads/{session_id}/{sha256}`（决策 3）；`blobs/` 只由 Promotion COPY 产生 |
| V1.2.19 §7.5 | 「`CompleteMultipartUpload` → 原子成为对象 key = **canonical promotion**」 | **修正**：Complete 只在 `uploads/` 产生 **temp 对象**，不是 canonical；canonical 由后续 Promotion COPY 产生 |
| V1.2.19 §7.5 | 「完成后将 VersionId/gen 记入 `content_blobs`」 | **修正**：Complete 后不得写 `content_blobs`；须待 Promotion 提交后才记 |

> 上表为「既有文档变更清单」的核心条目，**本轮未修改任何既有文档**（详见 §9）。

### 5.2 组合状态机（PG 会话状态 × R2 对象状态）

```
PG upload_sessions.status（本轮统一，服务端唯一写者）:

  created ──CreateMultipartUpload(uploads/{sid}/{sha256})──▶ initiated
  initiated ──签发分片 PUT URL / UploadPart──▶ parts_in_flight
  parts_in_flight ──CompleteMultipartUpload──▶ completed_unpromoted
  completed_unpromoted ──条件UPDATE + 咨询锁──▶ promoting
  promoting ──同步 COPY → blobs/{sha256} → PG 提交──▶ committed
  committed ──Reaper/Outbox 清 temp──▶ cleaned(temp 已删，PG 会话终态)

  任一非终态 ──Abort / 过期 / FREEZE──▶ aborted | expired（终态）

  单 PUT 路径: created ──预签名 PUT 直接落 temp──▶ completed_unpromoted（汇合）
```

| 状态 | R2 侧事实 | PG 侧事实 | 屏障 WAIT_INFLIGHT |
|---|---|---|---|
| `created` | 无对象 | 会话行、temp_object_key 已定 | ✅ 覆盖 |
| `initiated` | UploadId 存在，无对象、无完成对象 | `status=initiated`，UploadId 已持久化 | ✅ 覆盖 |
| `parts_in_flight` | UploadId + 若干分片，无对象 | 同上 | ✅ **本轮新增覆盖** |
| `completed_unpromoted` | **temp 对象存在** `uploads/{sid}/{sha256}`，canonical 无 | 已完成标记，**`content_blobs` 无行** | ✅ **本轮新增覆盖** |
| `promoting` | temp 存在；COPY 在途/已完成；canonical 可能有 | 持 `pg_advisory_xact_lock`，条件 UPDATE 已赢 | ✅ 覆盖 |
| `committed` | canonical 存在；temp 待清 | `content_blobs` + `asset_blob_refs` + `user_assets` 已提交 | 终态 |
| `aborted/expired` | 无对象或 temp 待清；UploadId 已 Abort | 终态 | 终态 |
| `cleaned` | temp 已删 | 终态 | 终态 |

### 5.3 各转移的动作、幂等键与时序约束（设计级，不执行）

| # | 转移 | 动作 | 幂等键 / 守卫 | 时序约束 |
|---|---|---|---|---|
| 1 | `created → initiated` | `CreateMultipartUpload(key=uploads/{sid}/{sha256}, metadata={gen})` → 持久化 `(session_id, upload_id, key, parts_expected, fence_gen_at_init)` | `session_id`；条件 UPDATE `status='created'` 受影响 1 行 | UploadId 存 PG，不进 Key/URL 路径（V1.2.19 §7.2） |
| 2 | `initiated → parts_in_flight` | 签发分片 PUT URL（TTL ≤60s） | `session_id` + UploadId | 分片 5 MiB~5 GiB、≤10,000 片、非末片同尺寸（官方镜像，文档事实）；URL 不暴露归属信息 |
| 3 | `parts_in_flight → completed_unpromoted` | `CompleteMultipartUpload(UploadId, parts)` → temp 对象 | UploadId；Complete 幂等重放须返回同一结果 | **同步完成后再置状态**（V1.2.18 Q1）；**不写 `content_blobs`** |
| 4 | `completed_unpromoted → promoting` | `UPDATE ... SET status='promoting' WHERE session_id=:sid AND status='completed_unpromoted'`；取 `pg_advisory_xact_lock(hashtext('promote:'||sid))` | 条件 UPDATE 受影响 1 行赢；0 行 → 幂等查回现状 | V1.2.17 §4.3 |
| 5 | `promoting → committed` | 同步 `CopyObject(uploads/{sid}/{sha256} → blobs/{sha256})`；**永远 COPY 不 HEAD**（N-07）；COPY 成功后同一事务写 `content_blobs` / `asset_blob_refs` / `user_assets`，记 VersionId/gen，置 `committed` | `session_id`；`call_id`/key 幂等 | **COPY 必须同步完成后再 COMMIT**（V1.2.18 §4.2 Q1：PG 锁不围栏 R2 异步操作）；Reaper 与 Promotion 共用同一咨询锁 |
| 6 | 任意 → `aborted/expired` | `AbortMultipartUpload(UploadId)`（幂等）+ 清 temp；置终态 | UploadId / key 幂等 | FREEZE 时对所有 `initiated`/`parts_in_flight` 显式 Abort（V1.2.19 §7.3，E-3 闭合） |
| 7 | `committed → cleaned` | 删 temp 对象 | key 幂等 | Reaper 仅对终态且超 grace 清理；须与 §4.4 约束 1 的 Expiration.Days 协调 |

> **PG 锁 ≠ 跨系统锁**（V1.2.18 §2 硬标准 3、§4.2 Q1）：`pg_advisory_xact_lock` 只串行化 PG 状态转移；R2 COPY / 分片上传不受其约束。真正的保护来自「同步完成后再 COMMIT」+「Reaper grace > 最大 COPY 时长」。本轮状态机**显式写入**该约束，不把 PG 互斥描述为跨系统围栏。

### 5.4 崩溃窗口与恢复动作（设计推演，未实测）

| 崩溃点 | 残留状态 | 恢复动作 |
|---|---|---|
| CreateMultipartUpload 后、PG 落库前 | R2 有 UploadId，PG 无记录 | `ListMultipartUploads(prefix='uploads/')` 枚举 → Abort 孤儿 UploadId（V1.2.19 §7.7） |
| 分片上传中 Worker 崩溃 | UploadId + 部分分片 | 重读 PG `upload_sessions` 行 → 重签分片 URL 续传，或 Abort |
| Complete 后、置 `completed_unpromoted` 前 | temp 对象已存在，PG 状态滞后 | 按 key 幂等查回；temp 对象不得被误判为孤儿删除（**依赖 §4.4 约束 1**） |
| COPY 成功、PG 提交失败 | canonical 存在，`content_blobs` 无行 | V1.2.17 §4.4(a) canonical 孤儿回收（执行期重验 ref_count=0） |
| PG 提交成功、客户端超时 | 已 committed | 同 `session_id` 重试 → 条件 UPDATE 0 行 → 查回已 committed asset 返回（V1.2.17 §4.7） |
| Promotion 中 DB 断连 | 咨询锁自动释放，COPY 可能仍在 R2 飞 | 因设计要求 COPY 同步完成后再 COMMIT，断连即事务回滚；残留由孤儿回收 + Reaper grace 兜底（V1.2.18 时序 2~4） |
| FREEZE 中 Abort 调用失败 | 在途 UploadId 未终止 | 重试 + `ListMultipartUploads` 复核；**未确认全部 Abort 前不得宣布静默成立**（V1.2.19 §9 #18） |

### 5.5 与备份冻结屏障的协调（本轮新增缺口）

- V1.2.19 §4.1 步骤 2 的 `WAIT_INFLIGHT` 枚举为 `('created','uploading','promoting','initiated')`，**缺 `parts_in_flight` 与 `completed_unpromoted`**。决策 3 引入「Complete → temp 对象 → Promotion」后，存在一个真实窗口：**temp 对象已存在、canonical 尚未产生、PG `content_blobs` 无行**。
- 若屏障未覆盖 `completed_unpromoted`：备份在 CAPTURE 阶段枚举 R2 时会看到一个「PG 无对应行、gen 已写入」的 temp 对象，而 PG 资产集不含它 → manifest 与 PG 备份的分类口径不一致；若该会话在屏障后才 Promotion，则产生 `gen>fence_gen` 的 canonical，恢复时按 V1.2.19 §8 step 7 隔离 KEEP（安全但产生需人工裁定的隔离项）。
- **本轮设计要求**：`WAIT_INFLIGHT` 覆盖 §5.2 表中全部非终态（含 `parts_in_flight`、`completed_unpromoted`），处置为「等待其完成 Promotion 至 `committed`，或显式 Abort 至终态」，二者必居其一后才可宣布静默。
- 该要求为 **设计已提出 + 静态推演通过**；是否足以闭合，须 U-4 真实 R2 + 真实 PG 预演验证（尤其 `ListMultipartUploads` 能否完整枚举在途 UploadId）。

### 5.6 三桶独立下的屏障作用域（决策 2 推论）

- 冻结标志 / 桶策略 / Worker 停摆是**按环境/Bucket**生效的。若备份目标为 prod，则须对 `BUCKET_PROD` 完成完整屏障；dev/staging 仍在写入不影响该备份点，但**不得宣称「PG 与 R2 均无写入」为全局真**——须在 manifest / 备份记录中标注 `backup_scope_bucket`。
- 恢复 Runbook（V1.2.19 §8）的隔离 R2 视图同样须绑定到具体 Bucket，避免恢复实例误连 prod 桶。

## 6. 删除契约（输出 4）：冻结，不预先拍板（决策 7）

### 6.1 契约冻结声明

> **本轮不对「R2 是否启用版本化」以及「DELETE 是物理删除还是插入删除标记」下任何结论。** 该契约由 U-4 通过**官方文档核实 + 真实环境测试**后，由负责人拍板。在此之前，所有物理删除路径处于 **BLOCKED** 状态（设计级 gate，本轮不执行任何 DDL/DML/API 调用）。

已核实 / 未核实的证据分层（诚实登记）：

| 事实 | 来源 | 可信层级 |
|---|---|---|
| 「Deleting objects from a bucket is irreversible」（Wrangler 删除警示） | Cloudflare 官方 `r2/objects/delete-objects/` | 官方**文档事实**（但其与版本化开启时的交互未核实） |
| R2 版本化可能默认开启、DELETE 只加删除标记、旧版本仍可访问、`force:true` 硬删 | 第三方工程报告 | **第三方，未官方核实**；官方版本化子页上一轮 WebFetch 404 |
| 条件删除（指定 VersionId 删除）的形态与可用性 | 未核实 | **U-4 待核实** |
| `ListObjectVersions` / 版本枚举能力 | 未核实 | **U-4 待核实** |

> **不得**把第三方报告当作设计前提。V1.2.19 §5.2、§9 #12 中「R2 版本化默认开启」的表述属预置假设，本轮在 §9 降级登记为「待 U-4 核实」，但**不修改原文**。

### 6.2 双分支语义对照（仅列可能性，不选边）

| 维度 | 分支 A：版本化关闭 / DELETE 为物理删除 | 分支 B：版本化开启 / DELETE 产生删除标记 |
|---|---|---|
| `DeleteObject(blobs/{sha256})` 后 | 对象不可恢复、不再计费 | 删除标记成为 latest；**旧版本仍存在、仍计费、仍可按 VersionId 读取** |
| V1.2.17 §3.4「R2 DELETE 成功后硬删 `content_blobs` 行」是否成立 | ✅ 成立（内容确已不可恢复） | ❌ **不成立**：对象旧版本仍在，硬删 PG 行会造成 PG 与 R2 状态不一致，并使「旧引用无法复活」的 FK 论证失效 |
| 物理删除的正确做法 | 直接 DeleteObject | 须枚举并删除**全部版本**（指定 VersionId / force 等，形态待 U-4 核实） |
| manifest `r2_object_list` 枚举 | 枚举 latest 即可 | 必须 `ListObjectVersions` **枚举所有版本**（V1.2.19 §6 / §8 step 6 已预留 `version_id`） |
| 恢复分类（V1.2.19 §8 step 7） | 按 key 存在/不存在分类 | 须按 (key, version_id, gen) 分类，并处理删除标记 |
| 隐私 / 成本影响 | 删除即终止 | 若未删净旧版本，用户「已删除」内容仍留存并计费 → **隐私与成本双重风险** |

### 6.3 契约未定时的安全边界（gate）

1. **BLOCKED 路径**：`r2_delete_object(v_key)` + `DELETE FROM content_blobs WHERE sha256=:s`（V1.2.17 §3.4）在契约确定前**不得进入实现/执行**。本轮仅登记，未执行任何 DDL/DML。
2. **允许保留的路径**：`ref_count` 维护、`delete_pending` 置位与取消、Outbox 事件排入（不执行删除）、对账查询——这些是 PG 侧逻辑，不触碰 R2 物理对象。
3. **U-4 前置硬门禁**：在版本化状态、删除语义、版本枚举能力三项**未经官方文档确认且未在真实 R2 实测**前，不得将任何删除路径标记为可用，也不得把「删除契约」标为设计闭环。
4. **三桶一致性**：版本化开关在 dev/staging/prod 必须一致，否则 U-4 结论不可迁移，且会出现「同一代码在三环境删除语义不同」。
5. **恢复 Runbook 依赖**：V1.2.19 §8 的隔离与分类逻辑在分支 B 下须重做验证；契约未定 ⇒ 恢复成功判定中的「所有版本已正确分类」暂标 **【未证明】**。
