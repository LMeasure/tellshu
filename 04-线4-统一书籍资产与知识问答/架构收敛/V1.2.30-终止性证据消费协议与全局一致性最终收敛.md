## 1. 执行摘要与结论

### 1.1 一句话结论

V1.2.29 把「证据真实性」「未消费状态」「已消费状态」压进同一个 `terminalProofValid()`，导致 T-TERMINALIZE 成功后 `consumed_at IS NOT NULL` 反过来使 `terminalProvenState()` 恒 FALSE，且共享证据无数据库级互斥、消费 UPDATE 无 CAS/RETURNING 检查、证据绑定不完整、三主体无可信根。本轮**拆出三个互不循环的谓词**、**引入独立可变消费槽位表**、**给出可直接翻译为 PostgreSQL 的一次性消费原子事务**、**补全 15 项强绑定与三主体信任边界**、**统一九步闭环**，并**交叉核对五张全局矩阵**；全部为设计规格层修正，**运行时 `terminal_proven` 仍不可达、T-REQUEUE 仍关闭、四档准入一个都不提升**。`[推演]`

### 2.2 P0-1 / P0-2 的形式化复现（消费后状态验证失败）

```
设证据 E、旧请求 O、T = T-TERMINALIZE。
V1.2.29 §7.2 定义：
    terminalProofValid(E) := 白名单 ∧ 可得性 ∧ 六通道 ∧ … ∧ (证据未被消费 IS TRUE)   ... (a)
    terminalProvenState(O) := (O.request_terminality='terminal_proven')
                            ∧ (O.unresolved_request IS FALSE)
                            ∧ terminalProofValid(被引用的证据链, O.snapshot_id)      ... (b)
V1.2.29 §7.3 步骤 ④：T 成功时 UPDATE r2_evidence_record SET consumed_at = now()      ... (c)

T 成功 COMMIT 后：
    (c) ⇒ E.consumed_at IS NOT NULL ⇒ 「证据未被消费」= FALSE
    (a) ⇒ terminalProofValid(E) = FALSE
    (b) ⇒ terminalProvenState(O) = FALSE
    V1.2.29 §8.3 T-REQUEUE 守卫含 terminalProvenState() ⇒ 恒 FALSE ⇒ 0 行拒绝

∴ 即使未来 U-4 全部实测通过、C1–C6 证据齐备、T 成功提交，
   T-REQUEUE 仍被自己刚刚产生的消费事实否决 —— 协议自相矛盾。
```

> **判定**：`[推演]` 这不是「正确的 fail-closed」，而是**证据生命周期谓词混用导致的规格级死锁**：`consumed_at` 既是「消费已成功」的证据，又是「证据仍可用」的否决条件。**修复方式不是放宽检查，而是把「未消费」从已消费状态谓词中彻底移除**（§6.3）。修复后 `terminal_proven` **运行时仍不可达**（因 U-4 未实测、`r2_operation_id` 恒 NULL），安全条件零降低。`[推演]` + `[待R2]`

### 2.3 P0-3 / P0-4 的形式化复现（共享证据竞态）

```
设两个不同旧请求 O1、O2（不同 outbox_id），共享同一份证据 E（同一 sid）。
V1.2.29 §7.3：
    T1: SELECT ... FROM object_outbox WHERE outbox_id=O1 FOR UPDATE;   ┐
    T2: SELECT ... FROM object_outbox WHERE outbox_id=O2 FOR UPDATE;   ┘ 互不相交，均成功
    T1: terminalProofValid(E) 求值（含「证据未被消费」）→ TRUE
    T2: terminalProofValid(E) 求值（含「证据未被消费」）→ TRUE   ← E 尚未被任一事务写
    T1: UPDATE object_outbox SET terminal_proven ... (ROW_COUNT=1 ✓)
    T2: UPDATE object_outbox SET terminal_proven ... (ROW_COUNT=1 ✓)
    T1: UPDATE r2_evidence_record SET consumed_at=now() WHERE sid=E AND consumed_at IS NULL  → 1 行
    T2: 同上 → 0 行（无 CAS 检查、无 RETURNING、无 ROW_COUNT 断言）→ **静默忽略**
    T1: COMMIT ; T2: COMMIT
∴ 结果：两条旧请求同时进入 terminal_proven，但只有一份证据被消费；
        T2 制造了「旧请求已终结、证据未（为其）消费」的半完成状态。
```

> **判定**：`[推演]` 锁住**各自**的 outbox 行**不能**保护**共享**证据；且 `consumed_at IS NULL` 写在 WHERE 里却没有对结果做断言，等价于把 CAS 结果丢弃。§7 用「独立槽位表 + 全局锁顺序 + 条件 UPDATE + RETURNING + 严格 1 行」四点一并修复。`[推演]` + `[待PG]`

```
      public_key, valid_from, valid_to, revoked_at, compromised_at, org_unit, created_at )
      -- append-only 版本表；轮换 = 新 key_id，不 UPDATE 旧行

【可变消费状态 —— 唯一允许 UPDATE 的对象，DB 级并发互斥锚点】
  r2_evidence_consumption (
      evidence_snapshot_id  uuid PRIMARY KEY,       -- ★ 每个快照恰一个消费槽位
      state                 text NOT NULL DEFAULT 'created'
          CHECK (state IN ('created','verified','consumable','consumed','rejected')),
      created_at            timestamptz NOT NULL DEFAULT now(),
      verified_at           timestamptz,
      -- 消费事实（一旦写入，不可变）
      consumed_at           timestamptz,
      consumed_by_outbox_id uuid,
      consumed_by_request_id / consumed_by_attempt_no / consumed_by_lease_epoch,
      consumed_by_op_type / consumed_by_environment / consumed_by_bucket / consumed_by_canonical_key,
      consumption_txid      xid8,                  -- pg_current_xact_id()
      consumption_db_role   text,                 -- current_user，仅证明 PG 会话角色
      rejected_at           timestamptz,
      reject_reason         text,
      CHECK ((state = 'consumed') IS NOT TRUE
             OR (consumed_at IS NOT NULL AND consumed_by_outbox_id IS NOT NULL
                 AND consumption_txid IS NOT NULL AND consumption_db_role IS NOT NULL)) IS TRUE),
      CHECK ((state <> 'consumed' AND consumed_at IS NOT NULL) IS NOT TRUE)
  )
  -- 权限：shutree_terminality_exec 仅对 state/consumed_*/consumption_* 有 UPDATE；
  --       collector 仅 INSERT(created)；其余角色仅 SELECT；所有角色 REVOKE DELETE/TRUNCATE
```

> **为什么必须拆表（N-1）**：`[推演]` V1.2.29 让同一张「append-only 证据表」承载可变的 `consumed_at`，触发器 `trg_no_mutation_after_terminal()` 与消费 UPDATE 直接冲突。拆表后：**证据本体零 UPDATE（可审计）**，**消费状态单点可变（可互斥）**，二者职责正交。
> **为什么必须用槽位主键（N-2）**：`[推演]` 六通道证据记录共享一个 `evidence_snapshot_id`，故唯一约束不能加在证据行上；把它加到**独立的消费槽位表**上，既允许六行证据，又保证「一份证据恰一个消费事实」。
> **禁止 `revoked` 状态（任务书 §三 3.2）**：见 §5.4。全部对象均为**设计提案**，`[待决策]`（入 schema）+ `[待PG]`（行为实测）。

### 5.2 六状态定义与合法转换

| 状态 | 语义 | 唯一写入者 | 写入方式 | 事务边界 | 终局？ |
|---|---|---|---|---|---|
| `created` | 采集者已登记原始证据 + 建立消费槽位；尚未独立复核 | ① `collector` | `INSERT r2_evidence_record` + `INSERT r2_evidence_consumption(state='created')` | 单事务，两 INSERT 同生共死 | 否 |
| `verified` | 独立复核记录已落库且结果为 `confirmed` | **DB 触发器** `trg_evidence_verification` | `AFTER INSERT ON r2_evidence_verification` → `UPDATE slot SET state='verified' WHERE state='created' RETURNING … INTO STRICT` | 与复核 INSERT **同一事务** | 否 |
| `consumable` | 六通道全部 `verified` + 签名 / 密钥 / 绑定 / 时间序 / 白名单全部通过 | **DB 触发器** `trg_evidence_verification` | 同触发器第二步：`NOT EXISTS` 未复核通道 → `UPDATE slot SET state='consumable' WHERE state='verified' RETURNING … INTO STRICT` | 同上 | 否 |
| `consumed` | 已被**某个具体旧请求**一次性消费 | ③ `shutree_terminality_exec`（T-TERMINALIZE） | **条件 UPDATE / CAS**，`RETURNING … INTO STRICT` + `ROW_COUNT = 1` | **与 `terminal_proven` 同一原子事务** | ✅ **终局、不可逆** |
| `rejected` | 真实性 / 复核 / 绑定任一失败，或验证主体给出 `contradicted` / `insufficient` | ② `verifier` / DB 触发器 | `UPDATE slot SET state='rejected', rejected_at=now(), reject_reason=… WHERE state IN ('created','verified','consumable')` | 单事务 + 审计 | ✅ **终局、不可逆** |
| `revoked` | — | — | **明确禁止该状态**（§5.4） | — | — |

**合法转换白名单（由 `BEFORE UPDATE ON r2_evidence_consumption` 触发器强制，`[DB]` + `[待PG]`）**

| # | From → To | 触发者 | 前置条件（全部 `IS TRUE` 收口） | 禁止 |
|---|---|---|---|---|
| T-E1 | `created` → `verified` | DB 触发器 | 存在 `verification_result='confirmed'` 的复核行 ∧ `verified_payload_sha256 = payload_sha256` ∧ `verifier_id ≠ collector_id` | 跳过复核 |
| T-E2 | `verified` → `consumable` | DB 触发器 | 同 sid 的 C1–C6 六通道**各有**一条 `confirmed` 复核 ∧ 共享 `evidence_snapshot_id` ∧ 签名/密钥 ID 有效 ∧ 时间序 `collected_at < verified_at` ∧ `evidence_source ∈ 封闭白名单 ∧ 来源可得性='available'` ∧ `r2_operation_id IS NOT NULL` | 六通道缺一 / 证据拼接 |
| T-E3 | `consumable` → `consumed` | ③ T-TERMINALIZE | `Authentic() ∧ Consumable()` ∧ 锁顺序 ∧ CAS **恰 1 行** ∧ 主行 CAS **恰 1 行** | 重复消费 / 跨请求消费 |
| T-E4 | `created`/`verified`/`consumable` → `rejected` | ② verifier / 触发器 | 复核结果为 `contradicted` / `insufficient`，或 `Authentic()` 任一子式 FALSE | 从 `consumed` 转入 |
| T-E5 | `consumed` → **任意** | — | **拒绝（`RAISE EXCEPTION`）** | 回退 / 复位 / 二次消费 / 删除 |
| T-E6 | `rejected` → **任意** | — | **拒绝** | 恢复 / 复活 |
| T-E7 | 任意 → `revoked` | — | **状态不存在**（CHECK 不含该值） | 引入撤销态 |

> **来源可得性恒 FALSE 的后果**：`[推演]` + `[待R2]` T-E2 要求「来源可得性 = available」且 `r2_operation_id IS NOT NULL`；V1.2.29 §5.4 已登记白名单 4 来源**全部无真实证据来源**，U-4 #11 未实测 → 这两项在当前运行时**恒 FALSE** ⇒ **没有任何证据能进到 `consumable`** ⇒ `consumed` / `terminal_proven` / T-REQUEUE 全部不可达。这是**预期的 fail-closed**，不是状态机死锁（隔离是合法稳态，§12.3）。

### 5.3 六个特别问题的逐条回答（任务书 §三 3.2）

| # | 问题 | **明确回答** | 保证来源 | 标签 |
|---|---|---|---|---|
| 1 | 证据提交后是否允许修改 | **不允许**。`r2_evidence_record` / `r2_evidence_verification` / `evidence_signing_key` / `adjudication_log` 全部 `REVOKE UPDATE, DELETE, TRUNCATE` + `BEFORE UPDATE OR DELETE` 触发器 `RAISE`；`state` 变更只发生在**独立槽位表** | `[DB]`（权限 + 触发器），超级用户旁路 `[待决策]` | `[待PG]` |
| 2 | 证据验证通过后是否允许替换 | **不允许**。`evidence_snapshot_id` 与 `payload_sha256` 绑定；「替换」只能以**新 `evidence_record_id` + 新 `evidence_snapshot_id`** 重新走「采集 → 独立复核 → consumable」全链，旧证据不得被覆盖、不得因新记录而复位；`UNIQUE(…, payload_sha256)` 阻止相同内容重复登记 | `[DB]`（PK + UNIQUE + FK） | `[待PG]` |
| 3 | 证据消费后是否允许重复消费 | **不允许**。CAS `WHERE state='consumable' AND consumed_at IS NULL` + 槽位 PK + `BEFORE UPDATE` 触发器 T-E5；`consumption_txid` 唯一；任何第二次消费 0 行 → ROLLBACK | `[DB]` + `[TX]` | `[待PG]` |
| 4 | 证据被撤销后是否允许恢复 | **不适用**：`revoked` 状态**被禁止**。未消费证据失效一律进 `rejected`（T-E4，终局，T-E6 禁止恢复）；密钥撤销是**另一个对象**（`evidence_signing_key.revoked_at`，append-only），不可恢复；已消费证据永不被撤销 | `[DB]`（CHECK + 触发器） | `[待PG]` |
| 5 | 旧请求身份变化后，原证据是否仍然有效 | **失效**。`Authentic()` 与 CAS 对 15 项绑定字段逐项 `IS NOT DISTINCT FROM`；任一字段变化 → `Authentic()` FALSE → `consumable` 拒绝 / `ProvenState()` FALSE。且 `object_outbox` 身份列由 `BEFORE UPDATE` 触发器冻结（`[DB]`）；若真发生变化，只能来自超级用户旁路 → 审计告警 + 保持隔离 | `[DB]`（触发器 + FK），旁路检测 `[待决策]` | `[待PG]` |
| 6 | 证据记录与审计记录是否能够被删除或修改 | **不能**。四张证据/审计表 append-only；`REVOKE DELETE/TRUNCATE` + `BEFORE DELETE` 触发器；`admin_action_log` 留痕；超级用户 `DISABLE TRIGGER` / 直改目录只能**检测**不能**阻止**（V1.2.26 §6.2.3 固有残留，如实保留） | `[DB]` + `[待决策]` | `[待PG]` |

> **不可变消费事实（任务书 §三 3.2 逐字）**：`[推演]` 证据一旦消费，`consumed_at` / `consumed_by_*` / `consumption_txid` / `consumption_db_role` 与 `adjudication_log('terminality_proven')` 构成**永久、不可变、不可删除**的消费事实；T-E5 明确禁止任何回退。密钥撤销、证据矛盾、人工裁定都**只能追加 `adjudication_correction` 记录并把请求保持/重回隔离**，**不得**改写、清空或回退消费事实与 `request_terminality`（单向不可回退，沿用 V1.2.28 §14 #12）。

### 5.4 为什么明确禁止 `revoked` 状态

| 维度 | 论证 |
|---|---|
| 撤销发生在消费**之后** | 会使已成立的 `terminal_proven` 与可能已执行的 T-REQUEUE 失去依据，而消费事实又不可回溯 → **协议不可判定**；若强行允许，等于给「已证明终止」开一个事后反转口，与「一次性消费 + 不可变事实」直接冲突 |
| 撤销发生在消费**之前** | 语义与 `rejected` **完全重合**（都是「这份证据不再可用」），新增状态只增加写入路径与攻击面，无新信息 |
| 密钥 / 凭证撤销 | 属于**签名密钥对象**的生命周期，不是证据对象的状态；用 `evidence_signing_key.revoked_at` / `compromised_at` 表达，`Authentic()` 每次重新求值即可阻断后续消费（§10.2 #6 / §10.2 #5） |
| 可信撤销主体 | 当前**不存在**可信身份系统 → 任何「撤销」都可能由普通应用角色或管理员伪造；引入该状态等于新增一条「仅凭角色即可改变证据有效性」的旁路（任务书 §六 / §七 明确禁止） |
| **结论** | `[推演]` + `[待决策]` **本轮明确禁止 `revoked` 状态**；状态机 CHECK 值域不含 `revoked`；任务书 §九 的「撤销与消费并发」故障用例按**密钥撤销 / 撤销尝试**解释并在 §15 FI-14 覆盖 |

## 6. 三个证据谓词的正式定义

### 6.1 `terminalEvidenceAuthentic()` —— 证据真实性（叶子谓词）

| 项 | 定义 |
|---|---|
| **签名** | `terminalEvidenceAuthentic(sid uuid, ob object_outbox) → boolean`（三值逻辑，调用方一律以 `IS TRUE` 收口） |
| **输入** | `sid`：证据快照 ID（**仅作查找键**）；`ob`：已 `FOR UPDATE` 锁定的**旧请求行**（只读，不修改） |
| **输出** | `TRUE` 仅当下列 A1–A9 **全部** `IS TRUE`；任一 `NULL` / `FALSE` / `UNKNOWN` → `FALSE`（V1.2.24 R2/R6/R7） |
| **前置条件** | 证据记录行、复核记录行、签名密钥行**均已在库中**；调用方已取得证据槽位行锁（§7.3 LO-1）；不要求证据处于任何特定消费状态 |
| **拒绝条件** | 缺任一记录 / 任一子式 UNKNOWN / `evidence_source` 不在封闭白名单 / 来源可得性 ≠ `available` / `r2_operation_id IS NULL` / 任一绑定字段不匹配 / 密钥已撤销或泄露 / 六通道未齐 / 时间序倒置 / `verifier_id = collector_id` |
| **调用位置** | ① `terminalEvidenceConsumable()` 的第一子式（T-TERMINALIZE 前置）；② `terminalProvenState()` 的第一子式（T-REQUEUE / T-SKIP / 屏障 / 人工转交 / 死信恢复）；③ 只读对账作业；④ 故障注入求值 |
| **不读什么** | **绝不读** `slot.state` / `consumed_at` / `consumed_by_*`（消费状态）；**绝不读** `ob.request_terminality` / `ob.unresolved_request`（主行终态）；**绝不接收任何调用方布尔参数** |
| **保证来源** | `[DB]`（FK / UNIQUE / CHECK / 触发器 / 签名密钥 FK）+ `[R2]`（白名单来源真实性，**当前零项成立**）+ `[待PG]` + `[待R2]` |

```
terminalEvidenceAuthentic(sid, ob) :=
    (A1  EXISTS r2_evidence_record  WHERE evidence_snapshot_id = sid)                    IS TRUE
AND (A2  同 sid 的 C1..C6 六通道各有且仅有一条 r2_evidence_verification，
          verification_result = 'confirmed'，verified_payload_sha256 = payload_sha256)    IS TRUE
AND (A3  evidence_source ∈ {'r2_request_status_receipt','r2_signed_terminal_assertion',
          'r2_credential_expiry_receipt','r2_key_write_fence_receipt'} 正向 IN，
          且 来源可得性 = 'available'，且 该来源 ∈ allowed_sources(ob.op_type))          IS TRUE  -- ★ 当前恒 FALSE
AND (A4  r2_operation_id IS NOT NULL 且由外部证据验证服务签名确认)                        IS TRUE  -- ★ 当前恒 FALSE（U-4 #11 未实测）
AND (A5  签名数学正确 ∧ signature_key_id 指向 evidence_signing_key 中
          signed_at 时刻有效的版本 ∧ 该版本当前未 revoked / 未 compromised)                IS TRUE
AND (A6  verifier_id IS DISTINCT FROM collector_id
          ∧ verifier.org_unit IS DISTINCT FROM collector.org_unit)                        IS TRUE
AND (A7  15 项绑定逐项 IS NOT DISTINCT FROM ob 既有列
          ∧ 全部通道共享同一 sid ∧ env/bucket/canonical_key 符合 V1.2.20 §3 规范)         IS TRUE
AND (A8  collected_at < verified_at < now()，且 collected_at 来自可信时间源)             IS TRUE
AND (A9  NOT EXISTS 跨 env / 跨 op_type / 跨 request_id 的证据拼接)                       IS TRUE
  ... 整体 IS TRUE 收口
```

> **A3 / A4 是本轮「运行时仍不可达」的正式承载**：`[推演]` + `[待R2]` V1.2.29 §5.4 已登记白名单 4 来源全部「无真实证据、不能承诺」；U-4 #11 未实测请求级取证能力 → `r2_operation_id` 恒 NULL。**因此 `Authentic()` 当前恒 FALSE**，由它派生的两个谓词也恒 FALSE，`terminal_proven` 不可达。本轮**不编造**该字段的取值、不假设存在服务端请求标签。

### 6.2 `terminalEvidenceConsumable()` —— 可消费性（仅首次消费前）

| 项 | 定义 |
|---|---|
| **签名** | `terminalEvidenceConsumable(sid uuid, ob object_outbox) → boolean` |
| **输入** | 同 `Authentic()`；额外只读 `r2_evidence_consumption` 槽位行 |
| **输出** | `TRUE` 仅当 C1–C5（下式 5 个子式）全部 `IS TRUE` |
| **前置条件** | **必须已取得槽位行 `FOR UPDATE`**（§7.3）；调用方必须是 `shutree_terminality_exec`；当前事务**尚未**写任何状态字段 |
| **拒绝条件** | `Authentic()` FALSE；`state ≠ 'consumable'`；`consumed_at IS NOT NULL`；`consumed_by_outbox_id IS NOT NULL`；`consumption_txid IS NOT NULL` |
| **调用位置** | **仅** T-TERMINALIZE 的 CAS 前置门（§7.4 G4 / §11 步骤 4）。**T-REQUEUE、T-SKIP、屏障解除、人工转交、死信恢复一律禁止调用本谓词** |
| **不读什么** | 不读 `ob.request_terminality` / `ob.unresolved_request`（避免 §2.3 的循环条件复发） |
| **保证来源** | `[DB]`（槽位 CHECK + PK + 触发器）+ `[TX]`（锁顺序）+ `[待PG]` |

```
terminalEvidenceConsumable(sid, ob) :=
    (terminalEvidenceAuthentic(sid, ob) IS TRUE) IS TRUE
AND (slot.state = 'consumable') IS TRUE
AND (slot.consumed_at IS NULL) IS TRUE
AND (slot.consumed_by_outbox_id IS NULL) IS TRUE
AND (slot.consumption_txid IS NULL) IS TRUE
  ... 整体 IS TRUE 收口
```

### 6.3 `terminalProvenState()` —— 已消费状态（严禁「尚未消费」）

| 项 | 定义 |
|---|---|
| **签名** | `terminalProvenState(ob object_outbox) → boolean` |
| **输入** | `ob`：已锁定的**旧请求行**；`sid` 取自 `ob.accepted_snapshot_id`（**由 T-TERMINALIZE 落库**，不接受调用方传入的任意 sid） |
| **输出** | `TRUE` 仅当 P1–P13（下式 13 个子式）全部 `IS TRUE` |
| **前置条件** | T-TERMINALIZE **已成功 COMMIT**；本次调用发生在 T-REQUEUE / T-SKIP / 屏障判定 / 人工转交 / 死信恢复的**读取阶段**；不修改任何状态 |
| **拒绝条件** | `Authentic()` FALSE；`state ≠ 'consumed'`；`consumed_at IS NULL`；`consumed_by_outbox_id IS DISTINCT FROM ob.outbox_id`；四元组与当前旧行不一致；`ob.request_terminality ≠ 'terminal_proven'`；`ob.unresolved_request IS TRUE`；`ob.accepted_snapshot_id` 与槽位 sid 不一致；存在未裁定的 `adjudication_correction` 矛盾记录 |
| **调用位置** | T-REQUEUE 守卫、T-SKIP 分支 2、静默屏障解除判定、人工转交、死信恢复、只读对账 |
| **🔴 严禁** | **绝不包含** `consumed_at IS NULL` / `state = 'consumable'` / `terminalEvidenceConsumable()` / 任何「尚未消费」子式（任务书 §三 3.1 逐字） |
| **保证来源** | `[DB]`（槽位 CHECK + 主行 CHECK/FK/触发器）+ `[TX]`（T-TERMINALIZE 原子提交）+ `[待PG]` |

```
terminalProvenState(ob) :=
    (ob.request_terminality = 'terminal_proven') IS TRUE
AND (ob.accepted_snapshot_id IS NOT NULL) IS TRUE
AND (ob.unresolved_request IS FALSE) IS TRUE
AND (terminalEvidenceAuthentic(ob.accepted_snapshot_id, ob) IS TRUE) IS TRUE      -- ★ 不含消费状态
AND (slot.state = 'consumed') IS TRUE
AND (slot.consumed_at IS NOT NULL) IS TRUE
AND (slot.consumption_txid = ob.terminal_proof->>'consumption_txid') IS TRUE
AND (slot.consumed_by_outbox_id  IS NOT DISTINCT FROM ob.outbox_id)     IS TRUE
AND (slot.consumed_by_request_id IS NOT DISTINCT FROM ob.request_id)     IS TRUE
AND (slot.consumed_by_attempt_no IS NOT DISTINCT FROM ob.attempt_no)     IS TRUE
AND (slot.consumed_by_lease_epoch IS NOT DISTINCT FROM ob.lease_epoch)   IS TRUE
AND (slot.consumed_by_op_type / consumed_by_environment /
     consumed_by_bucket / consumed_by_canonical_key 逐项与 ob 一致)      IS TRUE
AND (NOT EXISTS 未裁定的 adjudication_correction)                         IS TRUE
  ... 整体 IS TRUE 收口
```

> **「证据已被正确消费」与「消费对象与当前旧请求完全一致」的双重校验**：`[推演]` 仅检查 `state='consumed'` 不足以防止 O2 引用 O1 的消费事实；必须**同时**校验 `consumed_by_outbox_id` 与 15 项绑定中的身份四元组、环境、Key、操作类型逐项 `IS NOT DISTINCT FROM`。这正是 §2.3 P0-3 的协议级补丁。

### 6.4 三谓词无循环依赖的形式化证明

```
【依赖图（有向边 X→Y 表示 X 的求值需要 Y）】
  terminalEvidenceConsumable ──→ terminalEvidenceAuthentic
  terminalProvenState        ──→ terminalEvidenceAuthentic
  terminalEvidenceAuthentic  ──→ (只读证据表 / 复核表 / 密钥表 / ob 的身份列)
  无其他边。
  ∵ Authentic 不读 slot.state / consumed_at / ob.request_terminality / ob.unresolved_request
  ∴ 图中不存在任何回到 Consumable 或 ProvenState 的路径 ⇒ DAG，无环。

【跨事务写入 / 读取分离】
  事务 T-TERMINALIZE：
      守卫 = Consumable(sid, ob)   —— 读「证据未消费」，**不读** ob.request_terminality / unresolved_request
      写入 = ob.request_terminality='terminal_proven', ob.unresolved_request=false,
             ob.accepted_snapshot_id=sid, slot.state='consumed', slot.consumed_*
      ⇒ 守卫所读字段 ∩ 本事务所写字段 = ∅      （循环条件消除，沿用 V1.2.29 §7.2 的拆分思想）
  事务 T-REQUEUE / T-SKIP / 屏障：
      守卫 = ProvenState(ob)       —— 读「已消费 + 已终结」
      写入 = 旧行 recovery_phase='requeued'、新 bundle、新 object_outbox
      ⇒ 不写 request_terminality / unresolved_request / slot 任何字段
      ⇒ 守卫所读字段 ∩ 本事务所写字段 = ∅

【消费后状态验证不再失败】
  T-TERMINALIZE COMMIT 后 slot.consumed_at IS NOT NULL：
      Consumable() → FALSE  ✔（本就只应在首次消费前成立，符合语义）
      Authentic()  → 与消费状态无关，取值不变  ✔
      ProvenState()→ 要求 consumed_at IS NOT NULL，故可成立  ✔
  ∴ §2.2 的矛盾消除；且因 A3/A4 恒 FALSE，ProvenState() 运行时仍恒 FALSE。
```

> **「严禁将『尚未消费』作为已消费状态持续成立的条件」的落地**：`[推演]` 该约束在 §6.3 以「🔴 严禁」+ 逐项 P1–P13 定义（其中 P5 要求 `slot.state='consumed'`、P6 要求 `consumed_at IS NOT NULL`，**无任何 `IS NULL` 子式**）+ §6.4 DAG 证明三重固化；静态检查见 §18.2 #2。**运行时恒 FALSE 的结论不因谓词拆分而改变**（任务书 §七 安全约束）。

## 7. 一次性消费事务完整伪代码、锁顺序与并发分析

### 7.1 竞争场景（任务书 §四 4.1，逐字落地）

> **场景**：两个**不同** `object_outbox` 请求 O1、O2 同时尝试消费**同一份** `r2_evidence_record`（同一 `evidence_snapshot_id = sid`）。
> **明确否定**：`[推演]` **不能假设锁住各自的 outbox 行就能保护共享证据**。`O1 FOR UPDATE` 与 `O2 FOR UPDATE` 是两把互不相交的行锁；共享对象 `r2_evidence_consumption(sid)` 若无独立 `FOR UPDATE`，两事务可各自通过前置门、各自写主行，制造**双 `terminal_proven` + 单消费事实**的半完成状态（§2.3 已形式化复现）。
> **本轮解法**：所有消费者**统一先锁同一个共享槽位行**（`FOR UPDATE`），把二维竞争降为一维串行；outbox 行锁退居第二位。

### 7.2 统一锁顺序（任务书 §四 4.2 #1 / #2）

| 级 | 对象 | 锁模式 | 键 | 保证来源 | 目的 |
|---|---|---|---|---|---|
| **LO-0** | advisory xact lock | `pg_advisory_xact_lock(hashtextextended('shutree:evidence:'‖sid, 0))` | `sid` | `[TX]` + `[APP]` + `[待PG]` | 死锁规避：与密钥撤销事务共用同一命名空间，保证全局一致起点 |
| **LO-1** | `r2_evidence_consumption` 槽位行 | `FOR UPDATE` | `evidence_snapshot_id` | **`[DB]`** + `[待PG]` | **共享证据的数据库级并发互斥**（唯一锚点） |
| **LO-2** | `object_outbox` 旧请求行 | `FOR UPDATE` | `outbox_id` | **`[DB]`** + `[待PG]` | 旧请求状态串行；**必须晚于 LO-1** |
| **LO-3** | `r2_evidence_record` / `r2_evidence_verification` / `evidence_signing_key` / `backup_control.fence_gen` | **只读，不加锁** | — | `[DB]`（append-only / 不可变） | 求值；不可变行无需行锁 |
| **LO-4** | `adjudication_log` / `outbox_audit` / `adjudication_correction` | `INSERT`（append-only） | — | `[TX]` | 审计追加 |

> **「先读键、后按序加锁、锁后重读」**：`[推演]` T-REQUEUE 需要先从旧行取得 `accepted_snapshot_id` 作为 `sid`。为不破坏 LO-1 先于 LO-2，规定：先用**不带锁的 `SELECT`** 读出 `sid` 作为**提示（hint）**，随后严格按 LO-0 → LO-1 → LO-2 加锁，**加锁后重新 `SELECT … FOR UPDATE` 并重读全部字段、重新求值全部守卫**；不得信任锁前快照。此模式沿用 V1.2.28 §5.1 ② 的「锁后重读」纪律。
> **与跨代事务族的隔离**：T-CROSSGEN 族（REGISTER / DECIDE / DISPATCH / REVOKE）按 V1.2.28 §5.1 的「槽位行 → 审计 → 槽位 UPDATE → log」顺序，**只锁 `cross_gen_decision_slot`**，与本族的 `r2_evidence_consumption` 无交集；两族唯一可能相交的是 `object_outbox` 旧行（REGISTER 用 `FOR SHARE` 只读）。为消除该相交，§13 P1-4 规定跨代事务**不得**对 `object_outbox` 取 `FOR UPDATE`，只取 `FOR SHARE` 且置于其自身槽位锁之后；两族之间不形成环。`[推演]` + `[待PG]`
> **隔离级别**：READ COMMITTED 及以上；REPEATABLE READ / SERIALIZABLE 下等待方可能收到 `40001 serialization_failure` 而非 0 行 → 重试协议上游未定义，标 `[待PG]` + `[待决策]`（沿用 V1.2.28 §5.4 说明）。

### 7.3 并发时序与胜负规则（任务书 §四 4.2 末段）

| 时序 | T1（消费 O1） | T2（消费 O2，同 sid） | DB 结果 |
|---|---|---|---|
| t1 | LO-0 advisory(sid) 取得 | — | — |
| t2 | LO-1 `FOR UPDATE` 槽位(sid) **取得** | LO-1 `FOR UPDATE` 槽位(sid) **阻塞等待** | `[DB]` 行锁互斥 |
| t3 | LO-2 `FOR UPDATE` O1 取得 | 继续等待 | — |
| t4 | G1–G4 全部 `IS TRUE` | 继续等待 | — |
| t5 | W1 CAS `state='consumable'` → **RETURNING 1 行** | 继续等待 | `[DB]` |
| t6 | W2 主行 CAS → **1 行**；W3 审计 INSERT；COMMIT | 继续等待 | `[TX]` |
| t7 | 释放锁 | **获得槽位锁**，锁后重读 `state='consumed'` | `[DB]` |
| t8 | — | G4 `Consumable()` = FALSE（A3/A4 亦恒 FALSE）→ **0 行 + `T-TERMINALIZE_rejected_not_consumable` 审计后 COMMIT 退出** | fail-closed |
| 最终 | slot 恰 1 个 `consumed`，O1 `terminal_proven`，O2 保持隔离 | — | 无半完成状态 |

> **胜负规则（明确）**：`[推演]` **先取得 LO-1 共享槽位行排他锁者胜**；胜者完成「消费 + 终态 + 审计」单事务提交。**败者在锁后重读发现 `state='consumed'` 后，以「0 行 + 独立审计记录 + COMMIT」幂等退出**，不重试消费、不改写证据、不改写主行、不创建新 attempt。若胜者 ROLLBACK，败者获得锁后按正常路径重新求值（可成为新的胜者）。
> **T1 与 T2 角色对称**：胜负只由锁获取顺序决定，**与 outbox_id 大小、请求先后、角色、人工指定无关**。
> **失败事务如何退出**：分两类 —— ① 前置门 / 幂等拒绝（无写入）→ 追加审计后 **COMMIT**（保留审计）；② CAS 行数异常 / 任一步骤异常（**可能已有写入**）→ **整事务 ROLLBACK**，告警由**独立事务或对账作业**补写（因为回滚会一并撤销本事务内的 log INSERT，沿用 V1.2.28 §5.4 L461 的教训）。

### 7.4 完整事务伪代码（可直接翻译为 PostgreSQL；任务书 §四 4.2 十项逐条对应）

```sql
-- ============================================================================
-- T-TERMINALIZE (V1.2.30)  设计级 PL/pgSQL 伪代码，不执行
-- 角色 shutree_terminality_exec；输入 :old_id (outbox_id)、:sid (evidence_snapshot_id)
-- ★ 禁止任何调用方布尔参数（:officially_verified_by_u4 / :terminality_rechecked 已彻底删除）
-- 十项要求对照：#1 锁顺序 §7.2 / #2 证据行 DB 互斥 LO-1 / #3 CAS / #4 RETURNING
--              #5,#6 严格 1 行 / #7 原子事务 W1+W2+W3 / #8 任一失败全回滚
--              #9 无「证据已消费、旧请求未终结」 / #10 无「旧请求已终结、证据未消费」
-- ============================================================================
BEGIN;  -- READ COMMITTED 及以上；SERIALIZABLE 重试协议 [待决策]

  -- 【LO-0】advisory xact lock，与密钥撤销事务共用命名空间（死锁规避）      [TX]/[APP]
  PERFORM pg_advisory_xact_lock(hashtextextended('shutree:evidence:' || :sid::text, 0));

  -- 【LO-1】★★ 共享证据的数据库级并发互斥：所有消费者必争此行            [DB]
  SELECT evidence_snapshot_id, state, consumed_at, consumed_by_outbox_id,
         consumed_by_request_id, consumed_by_attempt_no, consumed_by_lease_epoch,
         consumed_by_op_type, consumed_by_environment, consumed_by_bucket,
         consumed_by_canonical_key, consumption_txid
    INTO ev
    FROM r2_evidence_consumption
   WHERE evidence_snapshot_id = :sid
     FOR UPDATE;
  IF NOT FOUND THEN
     INSERT INTO outbox_audit(...) VALUES (..., 'T-TERMINALIZE_rejected_no_slot');
     COMMIT; RETURN;                                   -- 失败出口 F1
  END IF;

  -- 【LO-2】旧请求行锁（必须晚于 LO-1）                                     [DB]
  SELECT outbox_id, request_id, attempt_no, lease_epoch, lease_owner,
         op_type, environment, bucket, canonical_key,
         status, request_phase, request_terminality, unresolved_request,
         terminal_at, accepted_snapshot_id
    INTO ob
    FROM object_outbox
   WHERE outbox_id = :old_id
     FOR UPDATE;
  IF NOT FOUND THEN ROLLBACK; RETURN; END IF;          -- 失败出口 F2

  -- 【G1】前置状态：★ 不读本事务将写入的任何值（消除循环条件，§6.4）
  IF (ob.status = 'unknown' AND ob.request_phase = 'failed'
      AND ob.request_terminality = 'non_applied_observed'
      AND ob.unresolved_request IS TRUE
      AND ob.terminal_at IS NULL) IS NOT TRUE THEN
     INSERT INTO outbox_audit(...) VALUES (..., 'T-TERMINALIZE_rejected_precondition');
     COMMIT; RETURN;                                   -- 失败出口 F3
  END IF;

  -- 【G2/G3】证据真实性 + 请求绑定 + 终止性（单一叶子谓词；不读消费状态）
  IF (terminalEvidenceAuthentic(:sid, ob) IS TRUE) IS NOT TRUE THEN
     INSERT INTO outbox_audit(...) VALUES (..., 'T-TERMINALIZE_rejected_inauthentic');
     COMMIT; RETURN;                                   -- ★ 当前恒走此分支（A3/A4 恒 FALSE）
  END IF;

  -- 【G4】证据是否可以被消费（仅首次消费前；不读主行终态）
  IF (terminalEvidenceConsumable(:sid, ob) IS TRUE) IS NOT TRUE THEN
     INSERT INTO outbox_audit(...) VALUES (..., 'T-TERMINALIZE_rejected_not_consumable');
     COMMIT; RETURN;                                   -- 失败出口 F4（并发败者亦走此）
  END IF;

  -- 【W1】★ 一次性消费：条件 UPDATE（CAS）+ RETURNING INTO STRICT + 严格 1 行   [DB]
  UPDATE r2_evidence_consumption
     SET state                       = 'consumed',
         consumed_at                 = clock_timestamp(),
         consumed_by_outbox_id       = ob.outbox_id,
         consumed_by_request_id      = ob.request_id,
         consumed_by_attempt_no      = ob.attempt_no,
         consumed_by_lease_epoch     = ob.lease_epoch,
         consumed_by_op_type         = ob.op_type,
         consumed_by_environment     = ob.environment,
         consumed_by_bucket          = ob.bucket,
         consumed_by_canonical_key   = ob.canonical_key,
         consumption_txid            = pg_current_xact_id(),
         consumption_db_role         = current_user      -- ★ 仅证明 PG 会话角色
   WHERE evidence_snapshot_id = :sid
     AND (state = 'consumable') IS TRUE                 -- CAS 条件 1
     AND (consumed_at IS NULL) IS TRUE                  -- CAS 条件 2
     AND (consumed_by_outbox_id IS NULL) IS TRUE        -- CAS 条件 3
     AND (consumption_txid IS NULL) IS TRUE             -- CAS 条件 4
  RETURNING evidence_snapshot_id, consumption_txid
      INTO STRICT cs;                                  -- ★ 0 行抛 NO_DATA_FOUND，>1 抛 TOO_MANY_ROWS
  GET DIAGNOSTICS v_ev_rows = ROW_COUNT;
  IF v_ev_rows <> 1 THEN
     ROLLBACK;                                         -- 失败出口 F5：0 行 / 多行均不得继续
     RETURN;
  END IF;

  -- 【W2】★★ 旧请求 terminal_proven：与 W1 同一原子事务，第二个 CAS          [DB]
  --        ★ unresolved_request=false 与 terminal_proven 在【同一 UPDATE 语句】写入，
  --          杜绝「先解除屏障再验证证据」与「提前解除屏障」窗口
  UPDATE object_outbox
     SET request_terminality = 'terminal_proven',
         terminal_proof      = jsonb_build_object(
                                 'evidence_snapshot_id', :sid,
                                 'consumption_txid',     cs.consumption_txid::text,
                                 'binding_digest',       md5(ob.request_id || '|' ||
                                     ob.attempt_no::text || '|' || ob.lease_epoch::text || '|' ||
                                     ob.environment || '|' || ob.bucket || '|' || ob.canonical_key)),
         accepted_snapshot_id = :sid,
         accepted_at          = clock_timestamp(),
         db_writer_role       = current_user,           -- ★ 仅证明 PG 会话角色（V1.2.29 §4.4）
         unresolved_request   = false
   WHERE outbox_id = :old_id
     AND (request_terminality = 'non_applied_observed') IS TRUE
     AND (unresolved_request IS TRUE) IS TRUE
     AND (terminal_at IS NULL) IS TRUE
  RETURNING outbox_id, request_terminality INTO STRICT pr;
  GET DIAGNOSTICS v_ob_rows = ROW_COUNT;
  IF v_ob_rows <> 1 THEN
     ROLLBACK;                                         -- 失败出口 F6：W1 已写亦一并回滚
     RETURN;
  END IF;

  -- 【W3】审计（与 W1/W2 同事务、同生共死）                                  [TX]
  INSERT INTO adjudication_log(...) VALUES (..., 'terminality_proven', :sid, cs.consumption_txid);

COMMIT;   -- ★★★ 唯一提交点：W1 + W2 + W3 原子提交
-- 未到达此点的任何异常/失败均 ROLLBACK ⇒ 不存在两种半完成状态（#9 / #10）
```

**十项要求逐条对照（任务书 §四 4.2）**

| # | 要求 | 落地位置 | 保证来源 |
|---|---|---|---|
| 1 | 确定统一的锁顺序 | §7.2 LO-0～LO-4 + §7.4 注释 | `[TX]` + `[APP]` + `[待PG]` |
| 2 | 证据记录必须进行数据库级并发互斥 | LO-1 `r2_evidence_consumption … FOR UPDATE`（PK = sid） | **`[DB]`** + `[待PG]` |
| 3 | 消费操作必须采用条件更新 / CAS | W1 的 4 条 `WHERE … IS TRUE` + W2 的 3 条 | **`[DB]`** + `[待PG]` |
| 4 | 使用 `RETURNING` 或等价方式检查实际更新结果 | W1 / W2 均 `RETURNING … INTO STRICT` | **`[DB]`** + `[待PG]` |
| 5 | 必须严格要求成功影响一行 | `INTO STRICT`（异常即中止）+ `ROW_COUNT <> 1 → ROLLBACK` 双重 | **`[DB]`** + `[TX]` + `[待PG]` |
| 6 | 更新影响零行或多行均不得继续 | `STRICT` 对 0 行抛 `NO_DATA_FOUND`、对 >1 抛 `TOO_MANY_ROWS`；显式 `IF <> 1 THEN ROLLBACK` | **`[DB]`** + `[待PG]` |
| 7 | 证据消费与旧请求 `terminal_proven` 状态写入同一原子事务 | W1 + W2 + W3 单 `BEGIN … COMMIT` | **`[TX]`** + `[待PG]` |
| 8 | 任一条件失败，整个事务回滚 | F2 / F5 / F6 及所有异常 → `ROLLBACK` | **`[TX]`** + `[待PG]` |
| 9 | 不允许「证据已消费、旧请求未终结」 | W2 失败 → ROLLBACK 连带撤销 W1 | **`[TX]`** + `[DB]` |
| 10 | 不允许「旧请求已终结、证据未消费」 | W2 仅在 W1 恰 1 行之后才发出；W2 的 `WHERE` 亦要求主行仍为 `non_applied_observed` | **`[TX]`** + `[DB]` |

> **为什么 `INTO STRICT` 与 `ROW_COUNT` 要同时用**：`[推演]` `STRICT` 是**数据库层**的 0 行 / 多行异常保护（即使有人删掉显式 IF 仍 fail-closed）；`GET DIAGNOSTICS + IF` 是**协议层**的可审计断言（便于写入审计与故障注入 FI-03 / FI-04 的观测点）。二者叠加，`[待PG]` 验证 `RETURNING … INTO STRICT` 与 `ROW_COUNT` 在 PG 18 的实际行为。
> **多行在结构上已不可能**：`evidence_snapshot_id` 是槽位表**主键**、`outbox_id` 是 `object_outbox` 主键 → 两条 UPDATE 最多影响 1 行（`[DB]`）。**仍保留 `= 1` 显式检查**，因为任务书第 6 项要求「多行亦不得继续」，且主键被超级用户 `ALTER INDEX … INVALID` 旁路时显式检查是最后一道防线（如实登记超级用户旁路）。

### 7.5 CAS 结果检查的拒绝表

| CAS 结果 | W1（证据） | W2（主行） | 处置 | 审计 |
|---|---|---|---|---|
| 1 行 | ✅ | ✅ | 继续 → W3 → COMMIT | `terminality_proven` |
| **0 行** | 任一 | — | **ROLLBACK 全事务** | 独立事务补写 `T-TERMINALIZE_cas_zero_rows` |
| **>1 行** | 任一 | — | **ROLLBACK 全事务 + 告警** | 独立事务补写 `T-TERMINALIZE_cas_multi_rows` |
| 异常 `NO_DATA_FOUND` / `TOO_MANY_ROWS` / `23505` / `40001` | — | — | 事务中止 → 等价 ROLLBACK | 独立事务补写 + 对账作业 |
| W1=1 且 W2=0 | — | — | **ROLLBACK（撤销 W1）** | `T-TERMINALIZE_state_write_failed` |
| W1=0 而 W2 被执行 | — | — | **结构上不可能**（W2 在 W1 之后且 W1 非 1 即 ROLLBACK） | — |

### 7.6 失败出口总表

| 出口 | 触发 | 事务动作 | 数据库最终状态 | 审计 |
|---|---|---|---|---|
| F1 | 槽位不存在 | COMMIT（仅审计） | 主行、证据均不变 | `T-TERMINALIZE_rejected_no_slot` |
| F2 | 旧请求行不存在 | ROLLBACK | 全不变 | 独立补写 |
| F3 | 前置状态不符 | COMMIT（仅审计） | 保持 `non_applied_observed` + `unresolved_request=TRUE` | `T-TERMINALIZE_rejected_precondition` |
| F4 | `Authentic()` / `Consumable()` FALSE（**含并发败者**） | COMMIT（仅审计） | 保持隔离稳态 | `T-TERMINALIZE_rejected_inauthentic` / `_not_consumable` |
| F5 | W1 CAS 非 1 行 / `STRICT` 异常 | **ROLLBACK** | 全不变 | 独立补写 `cas_zero_rows` / `cas_multi_rows` |
| F6 | W2 CAS 非 1 行 | **ROLLBACK（连带撤销 W1）** | 全不变（无「证据已消费、请求未终结」） | 独立补写 `state_write_failed` |
| F7 | W3 / COMMIT 前任何异常 | **ROLLBACK** | 全不变 | 独立补写 |

> **所有失败出口均不写 `unresolved_request`**：`[推演]` `unresolved_request=false` 只在 W2 的单条 UPDATE 内与 `terminal_proven` 同步写入；W2 未成功即回滚 → 屏障输入保持 TRUE → `canEnterSilentWindow_promotion()` 中 `COUNT(*) WHERE unresolved_request=true = 0` 不成立 → 静默屏障持续 ABORT（V1.2.23 §8.4）。

## 8. 幂等性七场景（任务书 §四 4.3）

> **总纪律**：**不得将业务幂等键等同于证据真实性**。`idempotency_key` / `request_id` / `outbox_id` 只用于**请求去重**，绝不进入 `terminalEvidenceAuthentic()` 作为「证据为真」的依据；A1–A9 才是真实性的唯一来源。`[推演]`

| # | 场景 | 定义 | 协议行为 | 最终状态 | 保证来源 / 标签 |
|---|---|---|---|---|---|
| **I-1** | **同一个请求重复提交** T-TERMINALIZE | O1 与 sid 相同，两次调用 | 第一次胜者 CAS 1 行 → COMMIT；第二次取得槽位锁后锁后重读 `state='consumed'` → `Consumable()` FALSE → **F4：0 行 + 审计 + COMMIT 幂等退出** | 恰 1 条 `consumed`、恰 1 条 `terminal_proven`；无第二条审计 `terminality_proven` | `[DB]` + `[TX]` + `[待PG]` |
| **I-2** | **同一个请求重复消费** | 已消费槽位被再次执行 W1 | W1 CAS `state='consumable'` 为 FALSE → `RETURNING` 0 行 → `STRICT` 异常 / `ROW_COUNT=0` → **ROLLBACK**；`BEFORE UPDATE` 触发器 T-E5 亦拒绝 | 消费事实零变化；`adjudication_log` 零新增 | `[DB]` + `[TX]` + `[待PG]` |
| **I-3** | **不同请求消费同一证据** | O1、O2 共享 sid（§7.1 场景） | 败者锁后重读 `state='consumed'` → `Consumable()` FALSE → F4；即使绕过，`ProvenState()` 的 `consumed_by_outbox_id IS NOT DISTINCT FROM ob.outbox_id` 也会拒绝 O2 | **恰一胜**；O2 保持隔离；无双 `terminal_proven` | `[DB]` + `[TX]` + `[待PG]` |
| **I-4** | **相同证据内容重新上传** | 相同 `payload_sha256` + 相同绑定再次 INSERT | `UNIQUE(bound_request_id, bound_attempt_no, bound_lease_epoch, op_type, env, bucket, canonical_key, payload_sha256)` → `23505` → 该 INSERT 事务回滚 + 告警；**不得**创建新 `evidence_snapshot_id`、**不得**复位已有槽位 | 证据行数不变；槽位 `state` 不变（含 `consumed` 不可复位） | `[DB]` + `[待PG]` |
| **I-5** | **同一证据跨环境使用** | 证据在 `env=A` 采集，被 `env=B` 的请求引用 | A7 的 `bound_environment` / `bound_bucket` / `bound_canonical_key` 与 `ob` 逐项 `IS NOT DISTINCT FROM` 失败 → `Authentic()` FALSE → F4；且三环境独立 Bucket 台账（V1.2.20 §3）二次校验 | 保持隔离；`evidence_cross_env_rejected` 审计 | `[DB]` + `[待R2]` |
| **I-6** | **事务提交成功但响应丢失** | W1+W2+W3 COMMIT 成功，调用方未收到响应并重试 | 重试命中 I-1（F4 幂等退出）；对**查询类**调用方，`terminalProvenState()` 因 `consumed_*` 与 `ob` 完全一致而 `IS TRUE` → **返回与首次一致的成功结果**，不重复写、不创建新 attempt | 记录数不变；新 attempt = 0 | `[DB]` + `[TX]` + `[待PG]` |
| **I-7** | **数据库事务回滚但外部操作已经发生** | PG 事务 ROLLBACK，而 R2 侧证据采集 / 对象写入已在外部产生副作用 | ① 本事务**不执行任何 R2 操作**（T-TERMINALIZE 纯 PG）；② R2 侧采集属采集者事务，按 I-4 内容哈希幂等重登记，不产生新证据事实；③ PG 回滚不「撤销」外部副作用，故 `unresolved_request` **保持 TRUE**、事件维持隔离，由只读漂移检测（`late_side_effect_suspected`）+ 人工裁定处置（V1.2.28 §7.6）；④ **不得**把 PG 回滚解释为「外部副作用已消失」 | 保持隔离 + 屏障 ABORT；追加 `adjudication_correction` | `[TX]` + `[APP]` + `[待R2]` |

> **I-7 的诚实边界**：`[原文]` + `[待R2]` PG 事务与 R2 之间**没有分布式事务**；`lease_epoch`、行锁、CAS 只作用于 PG 内部（V1.2.22 §5.4 L301）。因此「外部操作已发生而 PG 回滚」**无法由数据库消除**，只能保持隔离并留痕。这正是「长期隔离作为技术安全策略」不可放弃的原因（§12.3）。

## 10. 三主体可信身份体系及信任边界（任务书 §六）

### 10.1 三主体定义

| 主体 | 职责 | 允许写入 | 禁止 | 身份要求 | 当前状态 |
|---|---|---|---|---|---|
| **① 证据采集主体 `collector`** | 从 R2 服务端 / 可信验证服务取得原始证据，登记 `r2_evidence_record` + 创建槽位 `created` | 仅 `r2_evidence_record` / `r2_evidence_verification` 之外的 `INSERT`（经受控函数）；槽位 `created` INSERT | ❌ 写复核表；❌ 写 `object_outbox`；❌ 调用 T-TERMINALIZE；❌ 写槽位 `consumed` | `collector_id` + 独立密钥 + 独立角色 + 签名 | 🔴 **无此主体 / 无签发体系** `[待决策]` |
| **② 独立验证主体 `verifier`** | 独立复核，写 `r2_evidence_verification`（append-only） | 仅 `r2_evidence_verification` INSERT | ❌ 写证据表；❌ 写槽位；❌ 写 `object_outbox`；❌ 调用 T-TERMINALIZE | `verifier_id ≠ collector_id` + **不同 org_unit / 不同信任锚 / 不同密钥** + 独立角色 + 签名 | 🔴 **无此主体** `[待决策]` |
| **③ 数据库写入主体 `shutree_terminality_exec`** | 只依据已存在的证据链求值，执行 T-TERMINALIZE 的 W1/W2/W3 | 槽位 `state`/`consumed_*` UPDATE；`object_outbox` 限列 UPDATE；`adjudication_log` INSERT | ❌ 写证据本体 / 复核表；❌ 自行出具「已验证」结论；❌ 接收任何调用方布尔参数 | `current_user` 覆写 `db_writer_role`（**仅此义**） | ⚠ 角色规格存在，`[待PG]` + `[待决策]` |

> **三主体不是同一信任层**：`[推演]` ①② 属于**外部信任层**（须 PKI / KMS / 组织隔离）；③ 属于 **PG 内部权限层**（`current_user`）。二者不可互相替代，③ 的任何角色都不能证明 ①② 的独立性或证据真实性（A/B 分离）。

## 11. T-TERMINALIZE 完整事务（任务书 §十 #9 / §七）

### 11.1 九步统一闭环（严格顺序，任务书 §七）

| 步 | 判定 | 谓词 / 字段 | 求值或写入时点 | 属性 | 失败出口 |
|---|---|---|---|---|---|
| **1** | 证据是否真实可信 | `terminalEvidenceAuthentic()`（A1–A9） | T-TERMINALIZE G2（消费前） | 只读门 | F4 |
| **2** | 证据是否绑定当前旧请求 | `Authentic()` 的 A7 子式（15 项 `IS NOT DISTINCT FROM`） | 同上（同一次求值） | 只读门 | F4 |
| **3** | 证据是否具有终止性 | `Authentic()` 的 A3/A4 + C1–C6 六通道 + `allowed_sources(op_type)` | 同上（同一次求值） | 只读门 | F4 |
| **4** | 证据是否可以被消费 | `terminalEvidenceConsumable()`（C1–C5） | T-TERMINALIZE G4（消费前） | 只读门 | F4（并发败者） |
| **5** | 证据是否已被当前请求合法消费 | `terminalProvenState()`（P1–P13） | **T-TERMINALIZE 成功 COMMIT 之后**，由 T-REQUEUE / T-SKIP / 屏障 / 人工转交 / 死信恢复求值 | 只读门 | `T-REQUEUE_rejected_terminality_unproven` |
| **6** | 旧请求是否进入 `terminal_proven` | W2 单条 UPDATE 写入；由步骤 5 的 P1 校验其落库结果 | T-TERMINALIZE W2（与 W1/W3 原子） | **写入（被步骤 5 校验）** | F6 → ROLLBACK |
| **7** | `unresolved_request` 是否可以解除 | **与步骤 6 同一 UPDATE 语句**写入 `false`；由步骤 5 的 P3 校验其落库结果 | T-TERMINALIZE W2 | **写入（被步骤 5 校验）** | F6 → ROLLBACK |
| **8** | 静默屏障是否允许解除 | `canEnterSilentWindow_promotion()` 原五项 + 新增两项（§12.2） | 步骤 5 成立之后，屏障求值（只读） | 只读门 | ABORT |
| **9** | T-REQUEUE 是否允许创建新 attempt | `terminalProvenState()` + §12.1 全门禁 + U-4 已验证 + 负责人重开裁定 | 步骤 5～8 全部成立之后 | **写入（仅未来）** | 0 行 + 审计 |

> **九步顺序的准确语义（消除「5 在 6 之前还是之后」的歧义）**：`[推演]`
> - 编号 **1→9 是任务书 §七 规定的「验证 / 依赖顺序」（gate chain）**，**不是**单个事务内的语句时序，也**不是**纯粹的时间先后。
> - **时点分组**：步骤 **1–4** 是 T-TERMINALIZE 内的**消费前只读门**；步骤 **6/7** 是 T-TERMINALIZE W2 的**原子写入**（`terminal_proven` 与 `unresolved_request=false` 同一 UPDATE 语句）；步骤 **5、8、9** 是 T-TERMINALIZE **成功 COMMIT 之后**由下游事务求值的门。
> - **无循环的关键**：步骤 5 的 `terminalProvenState()` **内部包含** P1（校验步骤 6 的写入结果）与 P3（校验步骤 7 的写入结果），即「**5 验证 6/7 已正确落库**」，而**不是**「6/7 依赖 5 的结果」；T-TERMINALIZE **内部不调用** `terminalProvenState()`（否则 §2.2 的循环条件复发）。依赖边方向恒为 `写入(6/7) → 校验(5) → 屏障(8) → 重排(9)`，**是 DAG，无环**。
> - 步骤 5 之前仍必须先有步骤 1–4 成立并完成 W1/W2 原子提交；**任一门不成立即 fail-closed，不得跳步**。

### 12.1 T-REQUEUE 完整门禁（任务书 §十 #10）

```sql
BEGIN;
  -- 【提示读取】不带锁地取 accepted_snapshot_id 作为 sid hint（不得信任其值）
  SELECT accepted_snapshot_id INTO :sid_hint FROM object_outbox WHERE outbox_id = :old_id;

           WHERE evidence_snapshot_id = :sid_hint FOR UPDATE;   -- ★ 与 T-TERMINALIZE 同锚点、同顺序

     ) IS NOT TRUE THEN
     INSERT INTO outbox_audit(...) VALUES (..., 'T-REQUEUE_rejected_terminality_unproven');
     COMMIT; RETURN;                          -- ★ fail-closed：保持隔离，绝不重排
  END IF;

  -- 以下为「未来真实能力证据取得后」的条件性规格，当前运行时不可达：
```

| 对未实测 R2 能力的依赖 | ✅ 零依赖 | ❌ 依赖 U-4 #1/#3/#5/#10/#11/#12/#13 等未实测能力 |

| 静默屏障正确性 | ✅ `unresolved_request` 保持 TRUE → 持续 ABORT | ❌ 提前置 false → 误放行 |

| 代价 | ⚠ 该事件永不自动恢复；业务层如需继续须**新建会话 / 新上传**（不修改旧终局记录） | — |
| **结论** | **更可靠，作为技术安全策略保留** | 更不可靠 |

> **评估结论**：`[推演]` + `[待决策]` 沿用 V1.2.29 §8.5：在 R2 能力证据缺位、且**无法证明旧请求不会产生迟到副作用**的前提下，把不确定性**留在不产生新副作用的一侧**。本轮**不因协议收敛而取消长期隔离**；产品语义的最终确认仍属负责人职权，标 `[待决策]`，本轮不擅自拍板。
