## 复核 A ｜ B4 跨表数据归属约束的可实现性

### A1. V1.2.5 原设计
B4（V1.2.5 修订点 5）给出 9 张私有表的 PK/FK/唯一/索引/`owner_id NOT NULL` 规范，并提出两条防跨用户约束：
- 私有 `user_book_chunks` 防引用他人 `user_books`：`CHECK (owner_id = (SELECT u.owner_id FROM user_books u WHERE u.user_book_id = user_book_chunks.user_book_id))`。
- `kb_books` 跨用户引用禁止：`CHECK` 该 `user_books.owner_id = kb_books.owner_id`。
- 私有表由 `shutree_migrator` 拥有，`shutree_app` 非所有者。

### A2. 当前数据库证据
- 私有表（`user_*`/`knowledge_*`/`book_*`/`kb_*`/`app_users`）**当前全部不存在**（探针 `information_schema.tables` 仅命中 3 个 PG 系统对象 `user_defined_types`/`user_mapping_options`/`user_mappings`，非业务表）。约束是**前瞻设计**，无存量数据。
- 现有可参照的真实结构（`server/sql/002_discover.sql`）：`discovered_books.id BIGSERIAL PRIMARY KEY`、`discovered_book_chunks.book_id BIGINT NOT NULL REFERENCES discovered_books(id) ON DELETE CASCADE`、`unique (book_id, chunk_index)`；`entries.id bigserial PRIMARY KEY` 等。
- **PostgreSQL 硬限制（官方文档确认）**：普通 `CHECK` 约束**只能引用同一行的列**，或调用 `IMMUTABLE` 函数；**不能在 CHECK 里写子查询去查别的表**。因此 V1.2.5 的两条 `CHECK (... = (SELECT ...))` 是**非法 DDL**，执行时会报 `cannot use subquery in check constraint`——必须在实施前改为可实现方案。

### A3. 发现的问题
1. V1.2.5 的跨表归属校验写成「CHECK + 子查询」，PostgreSQL 不支持，迁移会直接失败 → **P0 设计缺陷，必须修正后才能写 B4 迁移**。
2. 跨用户引用的正确机制必须是**复合外键（composite FK）**，而非 CHECK。

### A4. 修订后的设计（复合唯一 + 复合外键，优先于触发器）
核心思路：在被引用表上建 `(id, owner_id)` 唯一约束，引用表同时携带自己的 `owner_id` 并建复合外键 `(id, owner_id) → 被引用表(id, owner_id)`。因为复合 FK 要求引用的 `(id, owner_id)` 对在被引用表中真实存在，而 `owner_id` 在被引用表里是真实 owner，引用表的 `owner_id` 必须等于父行的 owner，从而**结构性禁止跨用户引用**，无需触发器。

逐表清单（**N/A = 公共表，按 B4 决策不加 owner_id、不建跨用户约束**）：

| 表名 | 被保护的数据关系 | 现有约束 | 建议约束（V1.2.6） | 是否需要迁移历史数据 |
|---|---|---|---|---|

| `entries` / `toc` / `grammar_rules` / `scan_records` / `words`（公共） | N/A | 见 001_init.sql | 不加 owner_id | 否 |

### A5. 实施前置条件
- 修正 V1.2.5 的两条非法 CHECK（改为上表复合 FK）。
- `app_users` 须在 `user_books`/`kb_books` 的 `owner_id` FK 之前建好（或 FK 延后用 `ALTER TABLE ... ADD CONSTRAINT`）。
- 表创建顺序：`app_users` → `book_*` → `user_books`/`knowledge_bases`（带复合唯一）→ `user_book_chunks`/`user_bookshelf`/`kb_books`（复合 FK 引用已存在的父表）；若一次性建表有顺序冲突，用 `ADD CONSTRAINT` 后挂。

### A6. 验收方案
1. `information_schema` 断言：每张私有表 `owner_id NOT NULL`、复合唯一/复合外键存在。
2. **构造越权 INSERT**：向 `user_book_chunks` 插入一条 `(user_book_id=他人, owner_id=他人)` → 复合 FK 拒绝（错误 23503）。
3. 构造 `kb_books` 引用他人 `user_books` → 复合 FK 拒绝。
4. RLS 下用户只见自己 `owner` 行（沿用 V1.2.5 B3 验收）。
5. 公共 `discovered_*` 行数/向量零变化。

### A7. 回滚方案
新增表为 greenfield（无用户数据），`DROP TABLE` 安全；`DROP COLUMN` 公共兼容列（如 `section_type`）可逆。按 V1.2.5 修订点 2 红线：不得 DROP 含用户数据的表（本阶段尚无）。

### A8. 未解决风险
- **循环外键**：不存在。`user_book_chunks`→`user_books`→`book_editions`（公共）、`kb_books`→`user_books`+`knowledge_bases`；无反向引用，无环。
- **级联误删跨用户**：不可能。所有级联都在同一 owner 内；`app_users` 删除级联清空该用户全部数据（预期行为）。
- **并发插入归属安全**：复合 FK 在语句/提交时由 PG 强制；子表携带的 `owner_id` 必须与其父一致，并发事务无法伪造他人 `(id, owner_id)` 对（该对只存在于父表的真实 owner 行）。
- 若未来需要「私有块引用公共 discovered_chunks」则超出当前设计，须另行评审（当前私有书仍走自有 `user_book_chunks`）。

### A9. 是否需要项目负责人决策
- `book_works`/`book_editions`/`book_content_versions` 是否也加 owner（本设计定为**公共、不加 owner**，仅 `user_*` 加 owner）——建议在 D4 拍板时一并确认。其余为技术实现细节，无需代决。

## 复核 B ｜ B1 全库运行时权限清单

### B1. V1.2.5 原设计
B1（V1.2.5 修订点 1）给出跨 Express/FastAPI/Worker 的运行时权限矩阵（表级读写），并要求生成 `shutree_app` 精确 GRANT 清单；未覆盖序列、函数、触发器、Schema、默认权限、迁移执行器。

### B2. 当前代码/数据库证据（实际访问路径，非模块推断）
- **Express（`server/src`）**：`repository.ts` 对 `scan_records`/`entries`/`toc`/`grammar_rules` 做 INSERT/UPDATE/SELECT；`convertStore.ts` 对 `convert_files`/`convert_tasks` 做 INSERT/SELECT/UPDATE；SQL 中调用 `shutree_merge_text` 等函数（`shutree_merge_text(existing, EXCLUDED.merged)`）。
- **FastAPI（`api/`）**：`retrieve.py`/`main.py`/`b11_common.py` 对 `discovered_book_chunks`/`discovered_books` **仅 SELECT**；`db.py` 用 `set_config('hnsw.ef_search', %s, true)` 事务级设置（**参数化、非裸 SET**）。
- **Worker（`server/convert_worker/db.py`）**：对 `convert_tasks`/`convert_files` 做 UPDATE/INSERT/SELECT（值走参数元组，非值拼接）。
- **ASR 服务（`server/asr_service`）**：无 DB 连接（审计确认）。
- **迁移执行器（`server/src/scripts/migrate.ts`）**：`client.query(sql)` 直连 `DATABASE_URL`（当前 = `postgres` 超管）按文件名升序执行 `sql/*.sql`；SQL 中 `CREATE TABLE/FUNCTION/SEQUENCE` 的对象归属 = 连接角色 → 若切到 `shutree_migrator`，新表即归其所有。
- **开发/实验脚本**（`api/*.py` 的 `b10-*`/`b11_*`/`test_m4_*`、`server/src/scripts/*.ts` 的 `crawl-books`/`design-b6-*` 等）：均为 ad-hoc/离线评测，**非生产常驻进程**；当前也走 `postgres`。本轮不逐一审计（超出运行时范围），但建议它们统一用只读角色或 migrator，**不得用超管**。
- **DB 实况（探针）**：当前唯一登录角色 = `postgres`（rolsuper/rolbypassrls/rolcreaterole/rolcreatedb 全 true）；全部 9 张表 owner=`postgres`、RLS=false；**RLS 因超管而整体失效（P0 真实缺口，本轮重新实测确认）**。

### B3. 发现的问题
1. 权限矩阵缺**序列 / 函数 / 触发器 / Schema / 默认权限 / 迁移角色**粒度。
2. **`shutree_app` 必须被授予序列 USAGE**：`repository.ts` 经 `entries`/`toc`/`grammar_rules` 的 bigserial 自增与 `dictionary_sync_seq`（触发器 `shutree_touch_sync_seq` 内 `nextval`）都需 USAGE，否则 INSERT 失败。
3. **`shutree_app` 必须被授予函数 EXECUTE**：`shutree_merge_*` 在 INSERT…ON CONFLICT 中被 SQL 直接调用。
4. **`search_path = "$user", public`（默认）存在对象遮蔽风险**：若 `shutree_app` 可建名为 `shutree_app` 的同名 schema，未限定的函数调用会被优先解析到该 schema 的恶意同名函数。`public` 默认对 PUBLIC 开放 CREATE，亦需收回。
5. 现有函数**全部 `prosecdef=false`（无 SECURITY DEFINER）**、触发器函数均为 INVOKER——**无经函数间接提权的路径**（好）；但仍需在新增任何函数时守住该红线。

### B4. 修订后的逐对象 GRANT/REVOKE 草案
| 对象 | 运行时 `shutree_app` | 迁移 `shutree_migrator` | 库所有者 `postgres`（超管，禁入运行期/连接池） |
|---|---|---|---|
| Schema `public` | `USAGE`（**收回 CREATE**） | `USAGE` + `CREATE`（建对象） | 所有者 |
| 公共表 `discovered_books`/`discovered_book_chunks` | `SELECT` | 所有者 | — |
| 公共表 `entries`/`toc`/`grammar_rules`/`scan_records`/`words` | `SELECT, INSERT, UPDATE` | 所有者 | — |
| `convert_files`/`convert_tasks` | `SELECT, INSERT, UPDATE` | 所有者 | — |
| 序列 `dictionary_sync_seq` 及全部 `*_id_seq` | `USAGE` | 所有者 | — |
| 函数 `shutree_*` | `EXECUTE` | 所有者 | — |
| 触发器（自动触发） | 无需授权（随表 DML 触发） | 所有者 | — |
| 新建私有表 `user_*`/`knowledge_*`/`book_*`/`kb_*`/`app_users` | `SELECT, INSERT, UPDATE, DELETE` | 所有者（**非 shutree_app 所有**） | — |
| 角色自我权限 | `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOINHERIT` | `CREATEDB` 受控、`NOSUPERUSER` | — |

**REVOKE / 禁止项**：`shutree_app` 不得拥有任何表（RLS 才对其生效）；不得具有 `CREATE` on `public`；不得经任何路径获得超管/ BYPASSRLS；`postgres` 凭据绝不进运行期连接池或前端。
**search_path 加固（P1）**：在 `api/db.py` 与 `server/src/db/pool.ts` 的连接初始化里显式 `SET search_path = public`（或专用 `app` schema），并 `REVOKE CREATE ON SCHEMA public FROM PUBLIC, shutree_app`；消除遮蔽向量。
**SECURITY DEFINER**：保持现有「无」；任何新增函数若需 DEFINER 必须单独评审（限定 `search_path`、最小权限、不读 GUC 作身份）。

### B5. 验收矩阵（方案，不实际执行权限变更）
1. 正常业务请求可执行（公共检索 / 词典入库 / 格式转换均 200）。
2. `shutree_app` 读取无关表（如 `pg_catalog` 越权或不存在表）失败。
3. `shutree_app` 写入公共表越权列 / `knowledge_bases` 失败（42501）。
4. `shutree_app` 执行未授权函数失败（42501）。
5. `shutree_app` `CREATE TABLE` 失败（无 CREATE）。
6. `shutree_app` `ALTER POLICY` / `CREATE POLICY` 失败（无 RLS 写权限）。
7. `shutree_migrator` 能完成 `npm run db:migrate`（建表/函数/序列）。
8. Worker 用 `shutree_app` 只能动 `convert_*` 两张表，读不到 `user_*` 用户数据（RLS + 无 GRANT 双重）。
9. 连接池复用后权限上下文不污染（沿用 `set_config(...,true)` 事务级，A 提交后 B 的 GUC/权限为默认 NULL/最小）。

### B6. 实施前置条件
- 修正 A 的非法 CHECK 后才能建私有表。
- `shutree_migrator` 必须先行创建并由 `migrate.ts` 使用（改 `DATABASE_URL` 指向 migrator 凭据，原 `postgres` 凭据保留给管理/备份）。
- 先行 `pg_dump` + 角色备份（见 V1.2.5 修订点 6）。

### B7. 回滚方案
应用层把运行期 `DATABASE_URL` 切回 `postgres`（临时，仅回滚期）；角色与 GRANT 保留无害；按 V1.2.5 修订点 2 红线：回滚不得恢复超管为长期运行态。

### B8. 未解决风险
- 若 `shutree_app` 经 `INHERIT` 继承了某高权角色组，则可能绕过——必须 `NOINHERIT`（已在草案）。
- 开发/实验脚本若误用超管凭据，仍可能引入越权操作；建议统一只读角色（P2，非运行期阻断）。

### B9. 是否需要项目负责人决策
- B1 角色整改本身依赖 D6（是否启动角色整改）与 D1（是否采用 Supabase Auth，二者独立）；权限草案本身无需代决。

## 复核 C ｜ B7 Dexie v13 前进式降级

### C1. V1.2.5 原设计
B7（V1.2.5 修订点 4）提出：当前 Dexie `shushu-learn` 为 **v11**（原生 IDB 版本 = `11 × 10 = 110`）；升级路径为 v12（新增 `owner` 索引）+ v13（前进式兼容分支，使 `owner` 可选/可空），**禁止以降低 version 号回滚**；升级夹具需满足备份/幂等/断点恢复/多标签页/并发新数据/真实浏览器验收。

### C2. 当前代码证据（真实 `src/services/storage/web.ts`，本轮重读）
- 最后一个版本块为 `this.version(11).stores({ wordLearningSessions: 'id, book, level, updated_at, owner' })`（无 upgrade，纯新增表）。**当前确为 v11，与 V1.2.5 描述一致**；v12/v13 尚未落地（其他会话的 `M` 改动未改变版本号）。
- 升级纪律（文件头注释）：「只允许新增 version(n).stores，不改历史版本；删表/改主键需单独设计」。
- 多标签页：Dexie 原生仅在**一个标签页**执行 upgrade，其余标签页触发 `blocked` 事件（需处理，否则静默失败）；本文件无显式 `blocked` 监听（**缺口**）。
- 离线同步：`sync_queue`/`sync_meta` 仅服务词典数据（`v9` 注释明确 transcripts/studyNotes 不进 sync_queue）；`owner` 字段已在 v8 起多表存在（默认 `'guest'`）。

### C3. 关键事实更正与确认（DEXIE 官方文档核对）
- **Dexie 官方文档明确**：`db.version(n)` 的底层原生 IDB 版本 = **`n × 10`**（Issue #59，为避免与裸 IndexedDB 版本号冲突）。故 v11→原生 110、v12→120、v13→130。**V1.2.5 的「×10」与「v110 基线夹具」前提正确**，本轮初判的质疑不成立，特此更正。
- **降低 version 号不可行**：IndexedDB 拒绝以低于已记录版本的号打开（`VersionError`）；故「前进式降级」= 增 v13（原生 130）而非回退到 120/110，方向正确。
- **跨版本 upgrade 回调**：从 v11 跳到 v13 时，Dexie 只执行 v12、v13 的 `.upgrade()`，v1–v11 的 schema 已在旧安装应用过（Dexie 仅对 >旧版本号的 version 跑 upgrade 回调）。因此 v13 的 upgrade 只需处理「v11→v13」增量（如把 owner 置可选/默认值），**不得重复 v1–v11 的历史 modify**。

### C4. 修订后的设计
- **v12（原生 120）**：`user_books` 等「服务端私有表对应的本地镜像」若引入，按文件头纪律**只新增 stores + 必要 upgrade**；本阶段核心是给现有表加 `owner` 索引（若尚未加）——但当前 v11 已大量含 `owner` 索引（`vocab`/`reviewLog`/`collections`/`spellingSessions`/`wordLearningSessions` 等），故 v12 仅需在「尚未索引 owner 的表」补索引（如 `readings` 已有 `on_shelf` 但 owner 未索引？检查：`readings` 索引为 `id, created_at, type, on_shelf`——**无 owner**；`recitations`/`transcripts`/`studyNotes`/`annotations` 亦无 owner）。v12 增量：`readings`/`recitations`/`transcripts`/`studyNotes`/`annotations` 补 owner 索引（纯索引，无数据破坏）。
- **v13（原生 130，前进式兼容/降级）**：upgrade 仅做「确保 owner 列存在且可空/有默认值（如 `'guest'`）」；业务代码用 feature flag 决定是否写/读 owner。**不降 version 号，不重放 v1–v11**。
- **断点恢复**：upgrade 内步骤幂等（同 version 仅执行一次）；若中途崩溃，重开浏览器 Dexie 会以原版本号重新触发未完成 upgrade（IndexedDB 事务原子性保证半完成态回滚），可重入。
- **多标签页**：在 `open()` 处增加 `db.on('blocked', ...)` 处理——提示用户关闭其他标签页后再升级，**不得静默失败**（补 V1.2.5 未覆盖的缺口）。
- **并发新数据**：upgrade 事务期间用户的写走 Dexie 自身事务队列（IDB 串行化），不丢。
- **旧客户端访问新库**：原生 130 的旧客户端（代码仍是 v11）无法打开 130 库——必须由**发版**保证所有客户端同步升级；跨版本不兼容时以「强制刷新/发版」为边界，不试图在旧代码里兼容新 schema。

### D4. 修订后的设计：优先路线 B（补元数据），对不可归章块走独立 front-matter 分类
