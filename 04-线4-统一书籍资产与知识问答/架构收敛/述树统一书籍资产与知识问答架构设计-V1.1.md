## 3. 任务一：Supabase 账号体系评估

### 3.1 现状调查（事实）

| 维度 | 现状 | 证据 |
|---|---|---|
| 登录入口 | `authService.login/register` 均为本地桩，**注册=登录**，不校验密码 | `src/services/auth/web.ts:27-34` |
| 本地 UUID 桩 | `createSession` 每次生成**随机** `user_id = uuid()`，与邮箱无关；`access_token`/`refresh_token` 也是随机 uuid，1 小时过期 | `web.ts:14-21` |
| Token 存储 | 写入 Dexie `session` 表，**不进 localStorage**（合规红线） | `web.ts:22`；`V1 §8` |
| 前端用户态 | `getCurrentSession()` 取 `session` 表首行；「已登录」=`session` 表非空 | `web.ts:41-44` |
| 真实身份校验 | **无**。后端 `server/` 与 `api/` 的书籍/检索接口**不校验任何用户身份** | `retrieve.py` / `main.py` 无 auth 中间件 |
| PG 用户归属 | 全部书籍/分块表**零 user_id 列**（31 列实测） | `V1 §7.3` |
| 同步桩 | `LocalSyncStub` = 进程内 `Map`，重启即清空；仅覆盖 4 类实体（不含 `readings`/`annotations`） | `src/services/sync/remote.ts:16-33` |
| 小程序端 | **不存在**（全项目无 miniprogram/wx 相关代码，`V1 §4.3`） | `grep miniprogram\|小程序` 零命中 |
| PC/移动共享登录 | 不存在（纯本地 Dexie，换设备不可恢复） | `V1 §8` |

**关键判断**：现有系统**没有任何服务端用户身份**。述树的「用户」是一个本地随机 uuid，不绑定邮箱、不跨设备、不上云。所有书籍资产（30 本 discovered_books、58,332 分块、用户导入书）都**没有归属字段**。这意味着账号体系是从零搭建，而不是「替换一个已有的」。

代码已预埋迁移接缝：`web.ts:7-8` 注释「云端接入后由 Supabase 做邮箱+密码 + 重名/密码强度校验」，`remote.ts:14` 注释「Supabase 接入后由真实实现替换」。

### 3.2 Supabase 三项能力相互独立（必须分开评估）

| 能力 | 做什么 | 述树是否需要 |
|---|---|---|
| **Supabase Auth** | 邮箱/密码、OAuth、JWT 签发、会话刷新、邮箱验证、密码重置 | ✅ 需要（自建安全的认证体系成本高） |
| **Supabase Database** | 托管 Postgres（含 `auth.uid()` 等扩展函数） | ❌ **不必要**——已有自托管 PG，含完整书籍语料与 HNSW 索引 |
| **Supabase Storage** | 私有/公共对象存储、带签名的临时下载 URL | ⚠️ 可选——用户主动上传的原始书文件可存这里，也可自建对象存储 |

### 3.3 方案比较

| 方案 | 认证 | 数据库 | 文件存储 | 主要风险 |
|---|---|---|---|---|
| **A 自建** | 自建 JWT/会话 | 现有 PG | 自建对象存储 | 自行维护密码哈希、重置、OAuth、刷新令牌安全；工作量大、易出错 |
| **B1 ✅推荐** | Supabase Auth | 现有 PG（加 RLS） | 自建或对象存储 | 自托管 PG 上实现 RLS 需 JWT 校验胶水层（FastAPI 验 JWT 后 `SET` 会话 GUC）；`auth.uid()` 需自实现为读 GUC 的函数 |
| **B2** | Supabase Auth | Supabase PG | Supabase Storage | **数据与索引大迁移**：58,332 分块 + 456MB HNSW 索引迁到 Supabase PG；pgvector 版本/参数需重验；延迟变公网；平台锁定 |
| **B3** | Supabase Auth | 现有 PG | Supabase Storage | 多服务集成（Auth 在 Supabase、数据在本地、文件在 Supabase），跨服务一致性/GUC 传递略复杂 |

### 3.4 推荐：B1（必要时文件存储用 B3）

**为什么不是 B2**：现有 PG 已稳定运行、语料冻结、HNSW 索引已建（456MB，构建需数小时），迁到 Supabase 托管 PG 没有任何收益，只有迁移风险与公网延迟。Supabase 的 `auth.uid()` 是「托管 PG」专属能力，迁移数据库**仅仅是为了用这个函数**，得不偿失。

**为什么是 B1**：Supabase Auth 是唯一「自建成本高且易踩坑」的部分（密码强度、邮箱验证、会话刷新、OAuth）。其余部分（数据、RLS、文件）在现有基础设施上扩展即可：
- 认证：Supabase Auth 签发 JWT（含 `sub` = 用户 UUID）。
- 数据：现有 PG 增加 `owner_id` 列与 RLS；FastAPI 层用 Supabase 公钥验 JWT，把 `sub` 写入会话级 GUC `app.current_user_id`，再用自定义函数 `current_user_id()` 读取——等价于 Supabase 的 `auth.uid()`，但跑在自托管 PG 上。
- 文件：用户上传的原始书文件走 B3 的 Supabase Storage 私有桶（按 `user_id/` 前缀隔离），或自建对象存储。

**需要替换的现有代码**：`src/services/auth/web.ts`（整文件，替换为 Supabase Auth 客户端）、`src/services/sync/remote.ts` 的 `LocalSyncStub`（替换为真实 `RemoteSyncClient`，把 readings/annotations/transcripts 纳入同步）。

**必须保留的数据**：用户本地 Dexie 的 `readings`/`annotations`/`transcripts`/`studyNotes` 等——它们是用户的核心资产，**不因接入账号而清空或强制上传**。

**是否需要重新登录**：需要（新账号体系与旧随机 uuid 不兼容），但属于一次性、无数据损失的切换：旧本地数据继续留在 Dexie，登录后仅在「服务端功能」（上传/知识库/问答）使用 Supabase `sub`。

**本地数据如何关联**：用户首次用 Supabase 登录后，在 Dexie `session` 表记录 `supabase_uid`；本地阅读数据可保持本地（默认），仅当用户**主动选择上传**时才与服务端 `owner_id` 关联（见 §5.4）。失败回滚：账号接入是增量能力，旧代码路径保留，回滚即关闭认证中间件、恢复 `LocalSyncStub`。

## 4. 任务二：Work / Edition / Content Version 身份模型

### 4.1 三层定义

**Work（作品层）**——抽象意义上的作品，与载体无关。
- `work_id`（UUID，新体系主键）
- `canonical_title`（标准作品名）、`original_title`（原作名）
- `author`、原始语言 `original_lang`、作品简介 `description`
- `merge_key`（归并依据哈希）、`merge_status`（`auto`/`confirmed`/`split`）、`merged_into`（纠错撤销）
- 例：《悲惨世界》是一部 Work，不因出版社/语言/格式而分裂。

**Edition（版本层）**——某个具体版本。
- `edition_id`（UUID）、`work_id`（FK）
- `language`、`translator`、`publisher`、`publish_year`、`edition_note`
- `is_abridged`（是否删节）、`format`（epub/txt/pdf）、`isbn`（如有）
- `source_site` + `source_id`（外部来源标识，Gutenberg 的 `source_id` 落在**这一层**）
- 不同译本、不同语言、删节版**不得仅凭书名+作者合并**。

**Content Version（正文版本层）**——某 Edition 的实际正文内容快照。
- `content_version_id`（UUID）、`edition_id`（FK）
- `source_file_ref`（原始文件引用）、`normalized_content_ref`（标准化正文）
- `content_sha256`（内容指纹）、`parser_version`、`parsed_at`
- `chapter_schema_version`、`chunk_strategy_version`、`embedding_model`（如 `BAAI/bge-m3`）、`embedding_version`、`index_status`
- 明确区分：① 用户原始上传文件 ② 标准化可阅读正文 ③ 章节目录 ④ 检索分块 ⑤ 向量索引——**五者分离，禁止混为一体**。

### 4.2 身份归并规则（防错误合并）

| 规则 | 触发 | 动作 |
|---|---|---|
| **强标识匹配** | 同一 `source_site`+`source_id`（如 Gutenberg book id） | 自动并入同一 Edition |
| **弱标识候选匹配** | 归一化书名 + 作者 + 语言 高相似（≠ 唯一） | 记为候选，置信度 < 阈值时**不自动合并** |
| **冲突检测** | 同一 `merge_key` 命中不同 Work，或不同 ISBN/语言 | 标记 `merge_status=split`，人工仲裁 |
| **人工确认** | 弱匹配置信度不足（如《红楼梦》不同译本） | 进入人工确认队列，未确认前各自独立 |
| **错误归并撤销** | 用户/审核发现错并 | 记录 `merged_into` 历史，支持拆分回滚 |

> 铁律：**不得仅用「标准化书名 + 作者」作为唯一身份**。例：Gutenberg 的《Jane Eyre: An Autobiography》与某用户上传的同名中译本，属于同一 Work、不同 Edition（语言/译者不同），必须分开。

### 4.3 与现有数据映射（逻辑映射，不执行迁移）

| 现有数据 | 新模型目标 | 处理方式 |
|---|---|---|
| `discovered_books`（30 行，BIGSERIAL） | Work + Edition | 每行拆为 1 Work + 1 Edition：`source_site`+`source_id`→Edition 来源；title/author/lang→Work/Edition 字段。**保留 BIGSERIAL 作为 `legacy_book_id` 做回溯，不丢弃** |
| `discovered_book_chunks`（58,332） | Content Version / Chapter / Chunk | `book_id`→映射到的 `content_version_id`；`chapter_title`→Chapter 表；`content`→Chunk；`embedding`→Embedding（带 `embedding_model` 版本） |
| Dexie `readings`（`id=r_<ts>_<rand6>`） | Work / Edition / Content Version | 用户导入书：新建 Work+Edition+Content Version；`readings` 记录关联 `content_version_id`。**原 `r_` id 保留为本地兼容键** |
| 本地原始正文（浏览器内字符串） | Content Version | 上传后落对象存储 `source_file_ref`，标准化后落 `normalized_content_ref` |
| Embedding（1024 维，bge-m3） | Content Version / Chunk | 记录 `embedding_model`+`embedding_version`，换模型时旧向量保留为独立版本 |

## 5. 任务三：公共书籍与用户私有书籍的权限隔离

### 5.1 数据分类

| 类别 | 定义 | 存储 |
|---|---|---|
| **公共书籍** | Gutenberg 等来源、版权与使用条件已核验 | 现有 PG `discovered_books`/`chunks`（无 owner） |
| **用户私有书籍** | 用户**主动上传**，仅归属上传用户 | 新表 `user_books`/`user_book_chunks`/`user_book_embeddings`，带 `owner_id` |
| **用户书架关系** | 用户对书籍的收藏/管理（`user_bookshelf`） | 关系表，不带正文 |
| **用户知识库关系** | 用户授权 AI 检索的书籍集合（`knowledge_bases`/`kb_books`） | 关系表，不带正文 |

> 关键：**「书存储在公共库」≠「所有用户能读其全部内容」**。公共书默认所有人可检索/阅读；私有书仅 `owner_id` 可见。知识库是「被授权检索的书籍集合」，移除书籍**只删关系，不删原书、不影响其他用户**。

### 5.2 权限隔离规则（安全设计）

- **用户身份验证**：所有写/私有读接口经 Supabase JWT 中间件（§3.4），解析 `sub` → 会话 GUC `app.current_user_id`。
- **数据归属**：私有书表一律 `WHERE owner_id = current_user_id()`；公共书表无 owner，所有人可读。
- **API 查询权限**：`/api/books/:id` 若 `owner_id` 非空且 ≠ 当前用户 → 404（不暴露「存在但不可见」）。
- **RLS（§5.3）**：私有表启用行级安全，兜底防止绕过应用层。
- **向量检索权限过滤**：见 §5.3（HNSW 过滤影响）。
- **对象存储权限**：私有书原始文件存私有桶 `user_id/` 前缀；下载用**带签名、短时效**的临时 URL，绝不暴露永久直链。
- **删除/撤销授权**：删私有书 → 删正文+分块+向量+文件（级联）；移出知识库 → 只删 `kb_books` 关系。
- **对话引用权限**：引用块带 `owner_id`，读取时校验。

**可验证安全用例（设计，本轮不执行）**：
1. 用户 A 用 book_id 猜用户 B 的私有书 → 返回 404，不泄露存在性。
2. 用户 A 直接调向量检索接口带 B 的 `owner_id` 参数 → 服务端忽略/拒绝，强制用 JWT 的 `sub`。
3. 用户 A 请求 B 的私有书文件签名 URL → 401。
4. 用户 A 读取 B 的对话引用 → 403。
5. 删除用户 → 级联清理其私有书/知识库/对话，公共书不受影响。

### 5.3 RLS 与向量检索安全分析（重点）

**RLS 可行性（自托管 PG）**：`current_user_id()` 实现为读 GUC 的 `STABLE` 函数（`RETURN current_setting('app.current_user_id', true)`），FastAPI 每连接验 JWT 后 `SET LOCAL app.current_user_id = 'sub'`；私有表 `CREATE POLICY ... USING (owner_id = current_user_id())`。`SET LOCAL` 随事务结束自动清空，连接池复用时无泄漏。

**对现有 API 与连接池的影响**：现有 `DiscoverPool`（`db.py`）已用 `ThreadedConnectionPool` + 每连接 init 语句；增加 `SET LOCAL` 在事务内即可，不污染连接池（与 `ef_search` 的处理方式一致，`db.py:88-89`）。**对公共检索（discover）无影响**——公共路径不查私有表。

**HNSW 过滤对召回率与性能的影响（必须量化）**：pgvector 的 HNSW 在带 `WHERE owner_id = ?` 过滤时，若候选集小（某用户私有书少），可能退化为扫描或降低召回。缓解：
- 公共检索走无过滤 HNSW（现状）。
- 私有/知识库检索**先按关系表取 `content_version_id` 集合，再用 `WHERE id = ANY(ARRAY[...])` 做 HNSW 过滤**——把「用户可见范围」作为小集合 IN 过滤，避免大表 `owner_id` 过滤的退化。
- 必要时对私有表**独立建 HNSW 索引**或按 `owner_id` 分区。

**后台 Worker 的用户上下文**：用户上传的解析/分块/向量化是后台任务，必须显式携带 `owner_id`（不能依赖会话 GUC）；任务表记录 `owner_id`，Worker 取任务时按 `owner_id` 写对应私有表。

### 5.4 用户主动上传流程（仅设计，本轮不上传任何文件）

```
用户主动选择本地书籍
  → 展示上传说明（隐私/用途/存储位置/可删除性，明确「不默认上传现有本地书」）
  → 用户勾选确认
  → 上传原始文件（进度条；失败可重试；可取消）
  → 文件安全检查（类型白名单、病毒/损坏检查）
  → 解析正文 → 生成章节（弱标识匹配现有 Work/Edition，命中则关联，否则新建）
  → 建立检索分块 → 生成向量（记录 embedding_model/version）
  → 落私有表（owner_id = 当前用户）+ 对象存储（user_id/ 前缀）
  → 自动加入该用户知识库
  → 可阅读、可问答
```
支持：上传前告知、进度、失败重试、重复上传识别（按 `content_sha256` 去重）、删除原始文件、删除标准化正文、移出知识库、取消上传、数据导出、账户删除（级联清理）。

## 6. 任务四：NULL 章节分块分类与修复方案

### 6.1 分类结果（事实，只读 SQL 实测）

| 类别 | 分块数 | 说明 |
|---|---|---|
| **6 本问题书（章节识别彻底失败）** | **11,328（19.4%）** | `chapter_title` 全 NULL，正文**全部**不可召回 |
| **其余 24 本书的 paratext（封面/版权/目录/译者注/插图）** | **441** | 正文**章节已正确识别**，这些 NULL 块是正文前置材料 |

**6 本问题书明细**（V1 §7.7，确认未变）：String of Pearls(7044)、Lady of the Lake(1378)、Meditations(1085)、Manon Lescaut(906)、Love Letters of Mary Wollstonecraft(542)、Dr. Jekyll(373)。根因：`ingest-books.py:313-348 build_chapter_anchors()` 依赖 crawler 的 `chapters[]` 行号，crawler 无法识别时返回空数组 → 全部分块 NULL。

**441 差额的来源（抽样实测，仅短片段）**：441 块分布在 24 本书，抽样内容均为 paratext：
- 标题/版权页：`"JANE EYRE AN AUTOBIOGRAPHY by Charlotte Brontë"`、`"MOBY-DICK or, THE WHALE By Herman Melville CONTENTS"`、`"CRIME AND PUNISHMENT By Fyodor Dostoevsky"`。
- 目录（TOC）：`"BOOK XIX. BOOK XX. BOOK XXI."`、`"CHAPTER 16. The Ship. CHAPTER 17. The Ramadan."`、`"CONTENTS CHAPTER..."`。
- 译者注/前言：`"Transcriber's Note: The Table of..."`、`"IMITATION OF HORACE PREFACE"`。
- 插图：`"[Illustration]"`、`"[Cover Illustration]"`。

→ **结论：441 ≠ 解析失败**。这些书的正文章节**已被正确分块并可召回**（它们在 20 本「可召回书」之列）。441 块被排除是**正确行为**——它们本就不是答案承载的正文。

### 6.2 修复方案（分两类，不混为一谈）

| 类型 | 处理方式 | 算法改动 |
|---|---|---|
| **6 本问题书（11,328 块）** | 重新识别章节边界：对 crawler 失败的书改用**段落启发式兜底**（如正则匹配 `CHAPTER`/`BOOK`/`ACT`/`SCENE` + 罗马/阿拉伯数字），或人工补 `chapters[]`；重跑 `build_chapter_anchors` 后回填 `chapter_title` | 需要（仅数据修复 + 章节识别兜底，不动检索算法） |
| **24 书 paratext（441 块）** | **显式标记** `section_type ∈ {title_page, copyright, toc, preface, transcriber_note, illustration}`，保持非召回（当前 `chapter_title IS NULL` 已等价于排除）。建议把过滤条件从「`chapter_title IS NOT NULL`」语义化为「`section_type = 'body'`」，使意图清晰 | 不需要（仅加标签，不改检索结果） |

**铁律**：不得把 441 个 paratext 块统一改成一个字符串后放开检索（会引入大量无答案的封面/目录噪声，污染召回）。

### 6.3 评测口径修正（避免静默排除）

现有 `discover-query-set-v3.json` 的 `counting_rule`：目标书「至少有一个非空 chapter_title 的 chunk」才计入分母，零章节书（6 本）被**静默排除** → 69% Recall@10 只在 20 本可召回书上测出。修正后的分母与口径：

| 指标 | 定义 |
|---|---|
| 语料覆盖率 | 可召回分块 / 总分块（应纳入 6 本书修复后的增量） |
| 可检索书籍覆盖率 | 可召回书数 / 总书数（修复前 20/30=67%，修复后 30/30=100%） |
| NULL 分块覆盖率 | 被排除的 paratext 块是否被明确标记（441 应 100% 标记） |
| Recall@10 / Recall@50 | 分母必须包含全部 counted query，并**单独披露 6 本书相关 query 的召回**（若有） |
| 按书籍分层召回 | 每本书单独报 Recall，防止「平均」掩盖个别书全盲 |

| 指标 | 全量（100 条 counted） | 未命中子集（31 条 Top10 未命中） |
|---|---:|---:|
| 评测 query 总数 | 100 | 31 |
| A 档（证据 ≤ Top10） | 70 | 1（边界 Q074，M4 记为未命中） |
| B 档（证据在 11–50） | 5 | 5 |
| C 档（证据在 50 名外） | 25 | 25 |
| D 档（语料缺失） | 0 | 0 |
| 无法确认数量 | 0 | 0 |
| **Top50 目标书籍命中率** | **75%（75/100）** | **19%（6/31）** |

> 证据命中率说明：本评测为**书籍级**口径（与 M4 的 `hit_top10` 一致）。对完整收录的书，期望书进入 Top50 即意味着其相关段落也在该书的召回块中，故书籍命中可作为证据命中的代理；6 本书的 gold chunk 级标注不全，未做逐块标注，已标「无法确认」的为 0（因全部 31 条期望书均在语料中，D=0）。

### 7.3 B 档与 C 档明细

**B 档（5 条，Reranker 潜在可作用区）**：
- Q044（Blue Castle, rank 22）、Q063（Udolpho, rank 18）、Q081（Alice, rank 45）、Q091（Room with a View, rank 28）、Q099（Middlemarch, rank 35）。

**C 档（25 条，候选集根本不含证据，Reranker 无解）**按期望书分布：
- Carmen ×3（Q083,Q084,Q074→实为 A 边界,计 C 的是 Q083/Q084）、Middlemarch ×2（Q073,Q099→Q099 为 B）、Confessions ×2（Q095,Q096）、Green Mummy ×2（Q093,Q094）、Edwin Drood ×2（Q066,Q100→Q100 为 A）、Crime and Punishment ×1（Q062）、Udolpho ×1（Q064）、Eloisa ×2（Q065,Q106）、Blue Castle ×1（Q077→实为 A）、Sense ×1（Q078→A）、Odyssey ×2（Q076→A, Q085→C）、Romeo ×1（Q087）、Alice ×1（Q082）、Jane Eyre ×1（Q072）、Sherlock ×1（Q051）、Mystery Edwin Drood 等。
- 同一本书（如 Carmen、Middlemarch）部分 query 命中 Top1、部分落在 50 名外 → 证实这是**查询级召回差异**，非「书整体不可召回」，进一步说明瓶颈在召回而非排序精度。

### 7.4 结论：Reranker 当前不优先（实证）

- 仅 **5/31（16%）** 未命中的证据位于 Reranker 能作用的 11–50 区；**25/31（81%）** 证据根本不在 Top50 候选集 → Reranker（仅重排候选）**无法**改善它们。
- D=0：没有证据是「语料缺失」导致，即问题不是「书没收录」，而是「检索没把相关块排上来/排进候选」。
- **优先级**：① 修 6 本书章节（零算法改动，+19.4% 语料召回）→ ② 扩大候选池（LIMIT 50→200）+ 混合 BM25 关键词检索 → ③ 残余未命中再评估 Reranker。
- 若届时残余未命中仍集中在 11–50 区，再引入 Reranker（建议用轻量 cross-encoder，如 `bge-reranker-v2-m3`，与现有 bge-m3 同生态）。
