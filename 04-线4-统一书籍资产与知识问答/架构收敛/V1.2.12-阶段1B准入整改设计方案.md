## 三、P0-1：R2 与 PostgreSQL 对象一致性设计【整改建议】

> 目标：补齐收敛稿 §三.3 / R2 设计稿 §二.4 只"断言"的部分，给出可落地的状态机、Outbox、对账、孤儿回收、签名 URL 撤销控制。

### 3.1 最终一致性机制（核心判定）

R2 与 PostgreSQL **无分布式事务**。采用机制：**PostgreSQL 为唯一真相源（source of truth）+ Outbox 可靠投递 + R2 操作幂等 + 定期对账 + tombstone 延迟物理删除**。

- 所有"对象应存在/应删除"的判定以 PG 行 `status` 为准。
- R2 仅为物化副本；任何 R2 状态偏差最终由对账/Outbox 收敛。
- 创建顺序严格：**先 PG 行(pending) + 预留容量配额 → 再 R2 上传 → 校验 sha256 → PG 行 committed**。绝不允许"先 R2 后 PG 且无回滚指针"。

### 3.2 对象记录表与状态字段【整改建议】

新增 `user_objects`（与业务表同属私有 schema，受 RLS）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `object_id` | uuid PK |  |
| `owner_id` | uuid NOT NULL REFERENCES app_users(sub) | 用户归属（复合 FK 同 §三.2 双列 NOT NULL 约定） |
| `bucket` | text NOT NULL | `public` / `private` |
| `object_key` | text NOT NULL | 服务端生成：`<owner_id>/<user_book_id>/<sha256>.<ext>` |
| `sha256` | text NOT NULL | 服务端计算 |
| `size_bytes` | bigint |  |
| `content_type` | text | 白名单校验 |
| `status` | enum | 见 3.3 |
| `idem_key` | text UNIQUE | 幂等上传去重 |
| `r2_version_id` | text | R2 版本化返回的 version（便于回滚/校验） |
| `delete_after` | timestamptz | tombstone 延迟物理删除时间点 |
| `last_verified_at` | timestamptz | 对账最后校验时间 |
| `created_at` / `updated_at` | timestamptz |  |

外键/删除：`owner_id` 走复合 FK；用户销号时由销号作业统一处理（见 P1-9），**不**对 `user_objects` 设 `ON DELETE CASCADE` 到 `app_users`（避免误删物理对象先于清理）。

### 3.3 对象状态机【整改建议】

```
        ┌─────────────┐   R2 PUT 成功 + sha256 校验   ┌────────────┐
        │pending_upload│ ───────────────────────────▶ │ committed  │
        └──────┬──────┘                               └─────┬──────┘
               │ R2 失败/超时/客户端断网(中止)                 │ 用户删除(校验 owner)
               │ 或 pending 超时回收                          │
               ▼                                            ▼
        ┌─────────────┐                              ┌────────────────┐
        │   aborted    │                             │ marked_deleted  │  (tombstone)
        └─────────────┘                              └───────┬────────┘
                                                            │ Outbox DELETE 成功
                                                            │ 或 delete_after 到期且清理成功
                                                            ▼
                                                   ┌────────────┐
                                                   │  deleted    │ (R2 对象物理删除 + 行归档)
                                                   └────────────┘
        committed ── 对账发现 R2 HEAD 404 ──▶ orphaned ── 重建/人工
        marked_deleted ── 对账发现 R2 仍在 ──▶ 重新投递 Outbox DELETE
```

| 状态 | 进入条件 | 退出条件 | 物理对象存在? |
|---|---|---|---|
| `pending_upload` | 预留配额成功 + 插入行 | R2 成功校验 → committed；失败/超时 → aborted | 可能部分（multipart 残件） |
| `committed` | R2 200 + sha256 匹配 | 删除请求 → marked_deleted；对账 404 → orphaned | 是 |
| `marked_deleted` | 校验 owner 通过，写 tombstone | Outbox 删 R2 成功 → deleted；delete_after 到期清理成功 → deleted | 是（延迟删除） |
| `deleted` | 物理删除完成 | — | 否 |
| `orphaned` | 对账：DB=committed 但 R2 缺失 / R2 有对象无 DB 行 | 重建成功 → committed；确认无用 → 物理删 + 行删 | 视情况 |
| `aborted` | 上传失败终态 | 保留用于审计，可定期清理行 | 否 |

### 3.4 关键时序图【整改建议】

**(a) 上传提交（含场景 1 修复）**
```
C->>API: POST /api/books/upload (JWT, file, sha256)
API->>Q: 原子预留容量(BEGIN; UPDATE resource_usage...; INSERT user_objects(pending))
Q-->>API: 成功
API->>R2: PUT object_key (multipart, 服务端凭据)
R2-->>API: 200 + ETag/version
API->>API: 服务端重算 sha256 == 声明? 
API->>PG: UPDATE user_objects SET status=committed, r2_version_id=?
PG-->>API: 成功 -> 201
Note: 若最后 UPDATE 失败 -> 行停留 pending -> 回收扫描删 R2 残件 + 释放配额
```

**(b) 删除（含场景 6/7 修复：DB 不先于 R2 物理删除）**
```
C->>API: DELETE /api/objects/:id (JWT)
API->>PG: 校验 owner_id=current_user_id(); UPDATE status=marked_deleted, delete_after=now+24h
API->>OUTBOX: INSERT event=DELETE_OBJECT(object_id)
API-->>C: 202 Accepted (逻辑已删)
WORKER->>OUTBOX: poll event (FOR UPDATE SKIP LOCKED)
WORKER->>R2: DeleteObject(object_key)
R2-->>WORKER: 204 / 404(已删)
WORKER->>PG: UPDATE status=deleted; 删除行或归档
Note: 若 R2 删失败 -> 重试(退避) -> 死信; 行保持 marked_deleted, R2 对象仍在(安全)
```

### 3.5 Outbox / 可靠任务投递【整改建议】

新增 `object_outbox`：
```
id bigserial PK, object_id uuid, event_type text, payload jsonb,
status enum(pending, processing, done, dead), retry_count int,
locked_by text, lock_expire timestamptz, created_at, next_retry_at
```
- 写入：状态变更需触发 R2 操作时，在同一事务内写 `user_objects` + `object_outbox`（保证原子）。
- 消费：`ObjectCleanupWorker`（`shutree_worker` 角色）`SELECT ... WHERE status=pending AND next_retry_at<=now FOR UPDATE SKIP LOCKED`，置 processing + lock；执行 R2 操作；成功置 done；失败 `retry_count+1`，指数退避 `next_retry_at=now+min(2^n*base, max)`；`retry_count>=5` → `dead`。
- 死信：`object_dead_letter` 表，人工介入（见 3.10）。

### 3.6 幂等键与 SHA256【已有设计 + 整改建议】

- **SHA256**：【已有设计】R2 设计稿 §二.4"上传前/后服务端计算 sha256 比对"。补齐：在 `committed` 前强制比对，不符即 abort + 清理 R2 残件。
- **幂等上传**：【已有设计】R2 设计稿 §二.3"同用户同 sha256 不重复落盘"。补齐：`idem_key = hash(owner_id, sha256, purpose)`，`user_objects.idem_key UNIQUE`；重复上传命中已 committed → 直接返回既有 `object_id`，仅建业务关系，不重复占用配额（场景 4）。跨用户各自存储（设计如此，非缺陷）。

### 3.7 Worker 租约、超时回收、并发控制【整改建议】

- 上传为同步 API 操作，无多 Worker 竞争（场景 5 的"两 Worker 同对象"实为 convert 派生任务，见 P0-3）。
- 清理 Worker 多实例：`object_outbox` 用 `FOR UPDATE SKIP LOCKED` 保证单实例处理；`lock_expire` 防僵尸锁（处理超时则锁失效，他实例接管）。

### 3.8 重试 / 退避 / 死信【整改建议】

- 上传侧：客户端 5xx 重试 ≤3（R2 设计稿 §二.4）；容量配额预留带 `expires_at`，失败即释放。
- 清理侧：如上 3.5 指数退避 + 死信（场景 6/7/10）。
- 绝不允许"无限重试"或"静默吞错"。

### 3.9 tombstone 与延迟物理删除【整改建议】

- `marked_deleted` 不立即物理删；`delete_after = now + 24h`（【待负责人决策】：延迟时长）。
- 双保险：给用户"撤销删除"窗口；且保证场景 7（DB 已删 R2 失败）下 PG 行仍在，清理可重试。
- R2 桶生命周期规则作为兜底（孤儿二次清理）。

### 3.10 定期 DB↔R2 对账 + 孤儿回收【整改建议】

新增 `ObjectReconcileWorker`（每日/每小时）：
- **DB 有行 committed 但 R2 HEAD 404** → 置 `orphaned`；若有源字节可重建则重 PUT（同 key/sha256），否则置需人工（数据丢失，场景 2）。
- **R2 有对象但无对应 `user_objects` 行**（按 `<owner_id>/` 前缀列举） → 记为孤儿；若属 `marked_deleted` 未清理则补投递 Outbox DELETE；若完全无主（异常） → 入 `object_dead_letter` 人工判定（【待验证】列举成本对 410MB 公共桶须排除，仅扫 private 前缀）。
- **DB marked_deleted 但 R2 仍在** → 补 Outbox DELETE。
- 对账写 `last_verified_at`，异常计数告警。

### 3.11 签名 URL 与权限撤销【整改建议 + 待负责人决策】

- 【已有设计】R2 设计稿 §二.4：私有文件短时效签名 URL（60–300s）。
- **场景 8 缺口（P1-7）**：权限撤销后已发 URL 仍有效至过期。整改建议：
  1. 私有下载**统一走服务端代理端点** `/api/objects/:id/stream`：每次请求重新校验 `owner_id=current_user_id()` AND `status=committed` AND 账号未禁用，**再**用 60s 签名 URL 或直代理流式返回。撤销即时生效（下次请求即拒）。
  2. 仅在非敏感/公开衍生资源使用直链签名 URL。
- 【待负责人决策】是否对所有私有下载强制代理（增加延迟/带宽），还是仅对"可撤销敏感"资源代理。

### 3.12 P0-1 十场景落点小结

| 场景 | 机制 | 状态 |
|---|---|---|
| 1 R2 成功 PG 失败 | pending 停留 + 回收扫描删残件+释放配额 | 【整改建议】 |
| 2 PG 有行 R2 缺失 | 对账 orphaned → 重建/人工 | 【整改建议】 |

| 6 删除 R2 失败 | Outbox 重试→死信，行保持 marked_deleted | 【整改建议】 |

## 四、P0-3：配额预留、结算与 Worker 状态机【整改建议】

> 目标：在收敛稿 §四（原子计数）+ §五（idem_key 九步）基础上，补齐状态机、租约、fencing、周期切换、部分失败计费、死信。

### 4.1 资源五概念严格区分【已有设计】

| 概念 | 含义 | 表/字段 |
|---|---|---|
| 资源限制 | 平台技术上限（50MB/超时/并发） | 配置，非配额 |
| 配额预留 | 任务开始前锁定的额度 | `quota_reservations.reserved_amount` |
| 实际消耗 | 任务真实用量 | `quota_reservations.actual_amount` |
| 最终计费 | 按实际消耗入账 | `resource_usage.used` 终值 |
| 退款/补偿 | 失败/超时释放 | `used` 回退或 `actual<reserved` 差额回退 |

### 4.2 表结构补充【整改建议】（与 A2 统一）

`quota_reservations`：`reservation_id uuid PK`, `idem_key text UNIQUE`, `user_id uuid`, `resource_key text`, `window_start timestamptz`（**预留时锁定，结算同窗**）, `reserved_amount numeric`, `actual_amount numeric DEFAULT 0`, `status enum(created,reserved,running,succeeded,failed,settled,released)`, `lease_token text`, `claimed_by text`, `heartbeat timestamptz`, `expires_at timestamptz`, `settled_at timestamptz`, `created_at`.

`convert_tasks`（异步任务）：`task_id uuid PK`, `idem_key text`, `reservation_id uuid`, `owner_id uuid`, `status enum(created,reserved,running,succeeded,failed)`, `lease_token text`, `claimed_by text`, `heartbeat`, `expires_at`, `created_at`.

### 4.3 任务状态机【整改建议】

```
created → reserved → running → succeeded → settled
                     │           ↓
                     │         failed → released
                     │           ↓(部分消耗)
                     │         (actual 记录 + 退款差额)
                     └─(lease 超时/崩溃)─ 回收扫描 → reserved(重新派发)
```

### 4.4 配额预留状态机【整改建议】

```
created → reserved (原子 UPDATE resource_usage used+=cost; 写 reservation)
                  ↓ 任务成功结算
               succeeded → settled (used 已含; actual<=reserved; 差额释放)
                  ↓ 任务失败
               failed → released (used-=reserved 或 used-=actual 后补差)
```

### 4.5 完整时序图【整改建议】

```
C->>API: POST /api/convert (idem_key=K)
API->>PG: BEGIN; 
  UPDATE resource_usage SET used=used+:cost WHERE ... AND used+:cost<=limit RETURNING used;  -- 原子(P0-R2)
  INSERT quota_reservations(K, reserved=:cost, window_start=:w, status=reserved, expires_at=now+30m);
  INSERT convert_tasks(K, reservation_id, status=reserved);
API->>PG: COMMIT  -> 201 task_id
API->>W: 派发(仅消费已扣)
W->>PG: 领取: UPDATE convert_tasks SET claimed_by=:w, lease_token=gen_random_uuid(), heartbeat=now, expires_at=now+lease_ttl, status=running WHERE task_id=? AND status='reserved' AND (claimed_by IS NULL OR expires_at<now)  -- SKIP LOCKED
W->>R2/LLM: 执行(携带 lease_token)
W->>PG: 阶段写: UPDATE ... SET actual_amount=?, lease_token=:cur WHERE lease_token=:cur  -- fencing
W->>API: 成功
API->>PG: UPDATE reservation SET actual_amount=?, status=succeeded; 
         UPDATE resource_usage SET used = used - reserved + actual WHERE window_start=:w;  -- 结算(用预留窗)
         UPDATE reservation SET status=settled, settled_at=now;
```

### 4.6 idem_key 作用域/唯一性/生命周期【已有设计+整改】

- 作用域：单次用户意图（一次转换/一次上传）。【已有设计】收敛稿 §五.1①。
- 唯一性：`quota_reservations.idem_key UNIQUE` + `convert_tasks.idem_key`；重复提交（场景 7）命中已 reserved/succeeded → 直接返回既有 task，不新建预留（防双扣）。
- 生命周期：预留创建时生成，结算/释放后置为终态；过期未结算由回收扫描处理。

### 4.7 Worker 租约 + fencing token【整改建议】（防场景 5/6）

- 领取时生成 `lease_token=gen_random_uuid()`，写入 `convert_tasks.lease_token` + `expires_at=now+lease_ttl`（【待负责人决策】lease_ttl，建议 5–15min）。
- **fencing**：Worker 任何对任务的写（actual/status/结果对象写 R2）必须 `WHERE lease_token=:current`，旧 Worker 被接管后其 lease_token 已被新 Worker 覆盖 → 旧写 0 行生效，杜绝"旧 Worker 在接管后继续写入"（场景 6）。
- 心跳：`heartbeat=now` 周期性更新；接管扫描：`status=running AND expires_at<now` → 重置为 reserved（清空 claimed_by/lease_token）重新派发。

### 4.8 预留超时回收【整改建议】

- 回收 Worker 扫 `quota_reservations`：`status IN (reserved,running) AND expires_at<now`。
- 区分：**reserved 未 running 且过期** → released（used-=reserved）；**running 但任务 succeeded 未 settled（场景 9）** → 触发重新结算（读取任务结果 actual 入账）；**running 且任务 failed/无结果** → released。
- 这修正了审计场景 9"过期扫描误把成功未结算当过期释放"的混淆。

### 4.9 部分消耗计费 + 失败退款【整改建议】

- 部分失败（场景 8）：Worker 在任务失败前已耗 Token/容量，写 `actual_amount=已耗`；结算时 `used = used - reserved + actual`（仅扣实际），差额释放。
- 完全失败：`actual=0` → `used-=reserved`（全额释放）。
- 计数型（次数）：任务要么成要么败，reserved=actual=1；失败即释放。
- 容量型：reserved=预申请字节，actual=真实字节（≤reserved）；成功扣 actual，失败释放 reserved。
- 【待负责人决策】AI Token 免费期仍仅观测不扣（收敛稿 C-7 / Q24），上述逻辑为付费期准备。

### 4.10 结算幂等 + 失败补偿 + 死信【整改建议】

- 结算幂等：`settled_at IS NULL` 才执行；重复结算请求（场景 3/4）因 idem_key/settled 标志幂等。
- 结算失败（场景 9）：reservation 保持 succeeded 未 settled → 回收扫描重新结算（读任务结果）→ 仍失败超重试 → `quota_dead_letter` 人工（防止 used 永久偏差）。
- 死信表：`quota_dead_letter(reservation_id, reason, actual_snapshot, created_at)`。

### 4.11 周期切换账务归属【整改建议】（场景 10）

- 预留时锁定 `window_start`（UTC 自然日或 total），写入 reservation。
- 结算**必须用 reservation.window_start**（非"now"），命中同一 `resource_usage` 行；若该窗行不存在（轮转后懒创建）`INSERT ... ON CONFLICT`。
- 规则：跨周期运行的任务，其消耗归属**预留所在窗口**（用户视角可解释：任务发起时额度已扣）。

### 4.12 P0-3 十场景落点

| 场景 | 机制 | 状态 |
|---|---|---|
| 1 预留后 Worker 未领崩溃 | expires_at 回收 → released | 【整改建议】 |
| 2 Worker 领取后崩溃 | lease 超时 → 接管重派 | 【整改建议】 |
| 3 结算超时 | settled 幂等重试 | 【已有设计+整改】 |
| 4 结算成功响应丢 | 客户端重试 → 已 settled 幂等 | 【已有设计】 |
| 5 重复领取 | SKIP LOCKED + lease_token 防双写 | 【整改建议】 |
| 6 旧 Worker 接管后写入 | fencing: WHERE lease_token=cur → 0 行 | 【整改建议】 |
| 7 客户端重复提交 | idem_key UNIQUE 去重 | 【已有设计】 |
| 8 部分消耗失败 | actual_amount + 差额释放 | 【整改建议】 |
| 9 成功但结算失败 | succeeded 未 settled 区分 → 重结算/死信 | 【整改建议】 |
| 10 周期切换中运行 | reservation 锁 window_start 结算 | 【整改建议】 |

**P0-3 结论**：本 §四 给出完整状态机/租约/fencing/周期归属/死信。**判定【整改建议·待验证】**——须经 G9 预演（注入 Worker 崩溃、周期边界）通过方闭环。

## 五、G8：备份与恢复准入设计【整改建议】

> 审计 P0-2：G8 原标 P0/未启动。本轮形成可执行设计，并把"恢复演练"列为独立门禁。

### 5.1 PostgreSQL 备份范围与频率
- 范围：全部业务库（含 `app_users`/私有表/资源治理表/对象记录）；**不含**公共 `discovered_*`? 【待负责人决策】公共表是否同备（建议同备，体积小且保证可整库恢复）。
- 方式：`pg_basebackup` 物理全量（每日）+ WAL 连续归档（每 5min 或归档即时）→ 支持 PITR。
- 频率：全量每日 03:00；WAL 持续。

### 5.2 R2 对象备份/版本保护
- 私有桶开启 **版本控制**（保留 30 天）；公共 `shushu-public`（410MB 词库）额外冷备到独立区域桶或保留本地 `data/linguabase/v1/` 副本（【待负责人决策】跨区复制成本 vs 本地副本）。
- 生命周期：旧版本 30 天后过期；孤儿由 §3.10 回收。

### 5.3 Dexie 本地与云端备份边界
- **边界**：服务端备份仅覆盖云端归属数据（PG + R2）。Dexie 本地数据属用户设备，**不纳入服务端备份**；用户链接云端账号后，其数据成为云端归属 → 自动纳入上述备份。
- 明确：本地误删由用户设备负责；云端同步删除受 tombstone 保护（§3.9）。

### 5.4 加密与密钥管理
- PG 备份 `pg_dump | gpg`/服务端加密（KMS）；R2 SSE-KMS。
- 密钥存 Secret Manager（非 `.env`/代码）；定期轮换；与业务密钥隔离。

### 5.5 保留周期
- PG：每日保留 30 天 + 每月 1 份保留 1 年。
- R2 版本：30 天。

### 5.6 RPO / RTO 目标【待负责人决策】
- RPO ≤ 5 min（WAL 归档）。RTO ≤ 4 h（恢复+校验）。【待验证】取决于数据量/带宽。

### 5.7 恢复流程（runbook）
1. 从最近全量 + WAL 恢复到临时实例（PITR）。
2. R2：从版本/冷备恢复缺失对象。
3. 完整性校验（5.8）。
4. 冒烟（读写/RLS/配额）。
5. 确认后切换/并跑观察。

### 5.8 恢复后完整性校验
- 行数对比（关键表）；FK 一致性；抽样 `user_objects` 对 R2 `HEAD` 校验 sha256；资源 `used` 与 reservation 对账。

### 5.9 定期恢复演练【独立门禁 G8-drill】
- 频率：季度；记录实际 RTO/RPO。
- 验收：演练报告 + 校验通过 + 回滚原环境无影响。
- 【红线】"已配置自动备份" ≠ "可恢复"；未通过演练不得宣告 G8 完成。

### 5.10 备份失败告警与责任
- 监控：dump 成功标志、WAL 延迟、R2 版本写入。
- 告警 → DBA/运维（OP-7）；连续失败升级负责人。

**G8 结论**：本 §五 给出可执行设计。**判定【整改建议·待验证】**——须实际执行一次演练（G8-drill）方闭环 P0-2。
