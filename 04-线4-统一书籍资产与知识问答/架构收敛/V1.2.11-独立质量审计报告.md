## 三、R2 对象存储故障一致性审计（审计二，重点）

> 审计方法：对十种故障场景，比对现有设计（R2 设计稿 §二/§三/§四、收敛稿 §三.3/§五）是否给出**可落地的状态/机制**，而非"使用重试"式断言。
> **总体判定：10 项中 0 项【已解决】、2 项【部分解决】、8 项【尚未设计】。** 数据模型缺少支撑字段（`upload_state` / `deleted_at`），使 §三.3/§2.4 所述"DB 先记待确认→对象上传→标记已落盘""DB 先标记删除→异步清理"**协议无落地表列**。

### 3.3 R2 审计结论

- **P0（阻止 G10 实施）**：对象存储一致性设计缺失——无状态机、无 Outbox、无 tombstone、无对账、无孤儿回收作业、无死信；且**数据模型缺 `upload_state`/`deleted_at` 使所述协议无落地表列**。10 场景中 8 项未设计。
- 即便 R2 账户开通（OP-5），按当前设计直接上线私有书存储，**必然产生孤儿对象且无法自动回收、删除失败无法补偿、DB-R2 不一致无法检测**。
- 须补：① 数据模型增加 `upload_state`/`deleted_at`；② 上传状态机；③ 清理 Outbox + 死信；④ 定期对账作业；⑤ 孤儿回收。此五项定稿且经 G9 预演后，G10 方可进 P3。

## 四、资源配额完整性审计（审计三）

> 审计方法：构造十种故障，比对现有设计（收敛稿 §四 原子 SQL、§五 九步生命周期、决策稿 Q21–Q25）。
> **总体判定**：**原子计数检查【已解决】（落实 P0-R2）；幂等去重【已解决】（idem_key）；但预留—结算状态机、Worker 租约/fencing、周期切换、部分失败计费、结算失败终态、死信【尚未设计/部分解决】。**

### 4.1 原子 SQL 复检（并发 + 周期切换）

- **并发（10 额度/11 请求）**：§四.1 生产形式 `UPDATE…WHERE u.used+:cost <= c.limit_value RETURNING u.used` 对该 `resource_usage` 行加行锁，11 并发串行化，第 11 个因 `10+1<=10` 不成立不更新 → 终值恰 ≤10，**无幽灵计数**。✅ 落实 P0-R2。
- **周期切换**：SQL 以 `window_start` 为参数，不同窗口命中不同行，窗口内安全。但**预留（reservation）跨窗口的释放/结算归属未设计**（见场景 10）——原子检查本身正确，缺口在预留生命周期。⚠️

|---|---|---|
| 形式化状态机 `created→reserved→running→succeeded/failed→settled/released` | 仅九步散文（§五.1） | 无显式状态枚举/转移表/非法转移防护 |
| Worker 租约（lease）+ fencing token | 无 | 场景 2/5/6 旧 Worker 接管后继续写无防；缺 fencing 防旧 Worker 在任务被接管后写入 |
| 实际消耗 vs 预留分离 | §五.2 提"容量型预留—结算" | 无 `actual_consumed` 列；部分失败（场景 8）无计费细则 |
| 结算失败终态区分 | `settled=true` 唯一终态 | 无"成功未结算"与"过期未启动"区分（场景 9 误释放） |
| 周期切换处理 | `window_start` 参数 | 预留/结算须锁定同一窗口，未规定（场景 10） |
| 死信队列 | 仅断言 | 无设计 |

### 4.4 配额审计结论

- **P0-R2（原子计数超额）已落实**；**P0-R3（幂等去重）已落实**（idem_key）。
- **P1（须先于 P4）**：状态机、lease/fencing、部分失败计费、结算失败终态、周期切换、死信均**未设计**；且容量型资源的"预留—结算"与 R2 上传一致性（§三）**耦合未显式化**——容量预留释放失败即回到 R2 场景 6/7。
- 建议：在 G5 数据模型补 `quota_reservations(status, lease_token, actual_consumed, window_start, expires_at)` 与 `convert_tasks(lease_token, claimed_by, heartbeat)`；定义状态机与 fencing；容量型与 R2 清理共用 Outbox。

### 6.1 关键缺陷 L1：公共书籍下架/删除对书架与知识库的级联未设计（P1）

- `kb_books.public_book_id BIGINT REFERENCES discovered_books(id)`（§三.2）。该 FK 的 **ON DELETE 行为未定义**。
- 若 `ON DELETE CASCADE`：删除一本公共书 → 所有引用它的 kb_books 行被级联删 → **跨用户知识库数据无声丢失**（灾难性）。
- 若 `ON DELETE NO ACTION/RESTRICT`：删除公共书被 FK 阻塞 → **无法下架**（需先清理所有用户 KB/书架引用，未设计流程）。
- 两种默认都危险且均未在文档中明确。须规定：`discovered_books` 删除前**先置下架标志 + 扫描解除所有 kb_books/public 引用 + 保留书架关系或转"已下架"占位**。

### 6.2 关键缺陷 L2：账号注销的云端数据生命周期缺失（P1）

- 五份文档**从未描述"用户删除账号"**时的云端清理：user_books / user_book_chunks / embeddings / knowledge_bases / kb_books / R2 私有前缀 / app_users 行 如何删除或匿名化。
- 这是 GDPR/隐私合规与存储成本的直接缺口，且 R2 私有前缀删除依赖 §三 缺失的 Outbox。

### 6.3 关键缺陷 L3：用户书架仅建模私有书（P1）

- `user_bookshelf` 复合 FK 仅→user_books（私有）。产品上用户书架通常含 discovered（公共）书。公共书书架关系未建模 → 或隐含在别处未说明 → **模型与产品行为可能不符**。

### 6.4 公私资源生命周期分离结论

- 私有链（user_books→chunks→embeddings→R2）级联方向正确，但 R2 侧机制缺失（§三）。
- 公共链独立无 RLS，正确；但公共书删除对下游引用（L1）未设计。
- **P1 项**：L1、L2、L3。

## 十、是否建议批准阶段 1B

### 结论：**不建议批准阶段 1B。**

**理由（三层）**：

1. **原 V1.2.11 自判未就绪**（R1–R7 七项 P0 无一关闭；设计定稿 ≠ 批准 ≠ 实施）——本审计**确认该结论依然成立**，且未因本审计而降低标准。
2. **本审计坐实两项新增 P0 设计债务**：
   - **P0-1 R2 对象一致性**：10 故障场景 8 项未设计，且无 `upload_state`/`deleted_at` 落地表列。即便 R2 账户开通，按当前设计上线私有书存储将**必然产生不可自愈的孤儿对象、删除失败不可补偿、DB↔R2 不一致不可检测**。
   - **P0-3 配额异步状态机/Worker 租约/fencing/周期切换/部分失败计费/死信未设计**：核心原子计数已解，但异步任务处理缺故障恢复，且与 R2 上传一致性耦合。
   - **P0-2 备份 G8 仍为 P0/未启动**（文档自承），无备份则任何生产变更无兜底。
3. **P1 设计缺口 12 项**（门禁映射错配、配额表未进模型、身份开户流程、连接池/GUC、Worker×RLS、SECURITY DEFINER、签名 URL 撤销、公共书下架级联、账号注销、书架建模、RLS 回退、Dexie 回退演练）——均须于 P4 实施前闭环。
