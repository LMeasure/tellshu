## 一、任务目标与核心结论

### 1.1 目标
对 V1.2 / V1.2.1 / V1.2.2 提出的「GUC + RLS」身份隔离方案做边界压力测试：找出它在 SQL 注入面前的真实强度，给出威胁模型、方案比较与专项测试，明确「GUC 能否作为认证边界」这一悬而未决问题的最终答案。

### 1.2 核心结论（直接回答用户问题）
**能。GUC 本身提供零身份保护。**

如果 Express（`server/src/db/*`）或 FastAPI（`api/retrieve.py` 及后续数据层）存在 SQL 注入漏洞，攻击者**无需任何特权**即可在同一数据库连接上执行 `set_config('app.current_user_id','<受害者UUID>', true)`（或 `SET LOCAL`），把 GUC 伪造成任意用户，随后所有以该连接执行的、依赖 `current_user_id()` 的 RLS 谓词都会按「受害者身份」求值——从而读取甚至写入受害者的私有数据。

原因（已用 PostgreSQL 官方文档证实，见 §二）：

- 任意角色（含普通 `NOSUPERUSER/NOBYPASSRLS` 角色）都可通过 `SET`/`set_config` 设置**任意两段式占位 GUC**，例如 `app.current_user_id`。
- `set_config(name, value, is_local)` 的 `value` 参数**没有任何身份约束**——它接受调用者传入的任意字符串，不会校验「该值是否属于当前登录用户」。

因此，**GUC 不是认证机制，只是「受信任的 API 层写入的、供 RLS 读取的上下文变量」**。它的安全性完全依赖两件事：
1. 受信任的 API 层**从不**让用户可控的字符串进入 GUC 写入路径；
2. 更根本地——API 层**没有任何 SQL 注入点**（全部参数化），使攻击者根本没有机会在同一连接上执行 `SET`。

当前代码审计结论（§二.8）：`api/retrieve.py` 与 `server/src/db/*` 目前**全部使用参数化查询，未发现字符串拼接 / 动态 SQL / `${}` 模板注入**，即当前不存在注入面。但这只是「现状安全」，不是「架构免疫」——一旦任何数据层引入拼接 SQL，GUC+RLS 隔离会立即被绕过。故本复核**强烈建议采用方案 D（纵深防御）**，而非把安全寄托在「GUC 隐含可信」上。

### 1.3 当前最危险的不是注入，而是连接池角色错误（T3）
与「注入→伪造 GUC」相比，当前生产实际暴露的缺口更直接：**连接池以 `postgres` 超级用户身份连接（V1.2.1 已证实 `is_superuser: on`，且仅 login 角色为 postgres）**。超级用户**绕过一切 RLS**（含 `FORCE RLS`），即**无论有无注入，RLS 当前都处于失效状态**。这是优先级高于 T2 的真实风险，必须先于 1B 通过 V1.2.2 §P0 闸门修复（创建 `shutree_app` 专有权限角色并切换连接池）。

## 二、必须核实的技术事实（§二 八项）

| 编号 | 事实 | 结论 | 证据 |
|---|---|---|---|
| F1 | 普通角色能否设置自定义 GUC | **能**。任意角色可 `SET app.current_user_id = 'x'` 或 `set_config('app.current_user_id','x',...)` | PostgreSQL 19.16「Customized Options」：*PostgreSQL will accept a setting for any two-part parameter name. Such variables are treated as placeholders.* 两段式占位参数不要求任何特权 |
| F2 | `set_config` 的 value 是否受调用者身份约束 | **不受约束**。value 可为任意字符串，系统不校验其是否属于当前用户 | PG `set_config` 文档：仅声明 `is_local` 控制作用域（事务级/会话级），对 value 内容无身份校验语义 |
| F3 | 参数化 SQL 的防护范围 | 参数化使「用户数据」与「SQL 指令」分离，注入无法拼接出新语句；但参数化**不阻止**已有权限者主动执行 `SET` | `api/db.py:90` `cur.execute(sql, params)`；`server/src/db/repository.ts` 等 `$1/$2` 占位符 |
| F4 | 注入能否执行其它 SQL（含 SET） | **能**。若存在注入，攻击者可在同一连接、同一事务内追加任意语句（如 `; SET LOCAL app.current_user_id='victim'`） | 注入的常规危害即「语句追加/堆叠」，SET 属普通 SQL 语句 |
| F5 | 能否用 set_config 改身份 | **能**。注入后执行 `set_config('app.current_user_id','<victim>', true)` 即把后续 RLS 求值身份改为受害者 | 由 F1+F2 直接推出；`current_user_id()`（V1.2 设计）读取该 GUC |
| F6 | SECURITY DEFINER 是否会被绕过 | **存在风险**。SECURITY DEFINER 函数以**所有者**权限运行；若函数内部读取 GUC 作为身份依据且未重新校验，注入者可在调用前 SET 伪造身份，使函数以受害者上下文执行写操作 | PG「SECURITY DEFINER」文档要求函数体对 GUC/搜索路径保持警惕；需结合 §四 方案 B 约束 |
| F7 | 连接池复用 / 事务边界 | `SET LOCAL` 在 COMMIT/ROLLBACK 时清除；但 `SET`（会话级）**跨事务持久**，直到连接被重置/归还。若池在 checkout 时不清算 GUC，上一请求的「身份」会泄漏给下一请求 | `api/db.py:89` `set_config('hnsw.ef_search',%s,true)` 用 `true`（事务级，安全）；`server/src/db/pool.ts` 用 BEGIN/COMMIT/ROLLBACK。若任何代码用 `set_config(...,false)`（会话级）写身份 GUC，则需池级重置 |
| F8 | 现有数据层是否存在动态 SQL | **当前未发现**。已审计 `api/retrieve.py`、`api/db.py`、`server/src/db/repository.ts`、`convertStore.ts`、`pool.ts`：全部参数化（`%s` / `$1/$2`），无 `${}` 查询模板、无字符串拼接 SQL；`validate.ts` 对 UUID/整数做校验 | 代码审计（Grep + Read），详见 §二.8 |

### 2.8 数据层审计明细（F8 证据链）
- `api/retrieve.py`：`SEARCH_SQL` 全程 `%s` 占位；`search()` 调 `run_query(pool, SEARCH_SQL, (literal, include_front_matter, literal, top_k))`，无拼接。
- `api/db.py:89-90`：`set_config('hnsw.ef_search', %s, true)`（事务级，安全示范）→ `cur.execute(sql, params)`（参数化）。`finally` 中 commit/rollback 后 `putconn` 归还连接。
- `server/src/db/repository.ts`：示例 `this.pool.query(\`UPDATE scan_records SET status = $2 ... WHERE id = $1\`, [scanId, status])`，全参数化。
- `server/src/db/convertStore.ts:30,41,47…`：同上，`$1/$2` 占位。
- `server/src/db/pool.ts`：事务用 `BEGIN/COMMIT/ROLLBACK`，无 GUC 会话级写入（仅事务级 ef_search 在 FastAPI 侧）。
- `server/src/db/validate.ts`：UUID / 整数边界校验，输入在边界处校验。
- **未发现** `${}` 用于构造 SQL；`${}` 仅出现于日志字符串拼接（非查询）。

**结论：当前数据层无注入面，T2 威胁在当前代码下不可达；但架构层面 GUC 仍属「非权威上下文」，须以纵深防御维持。**

## 三、威胁模型（T0–T4）

每条威胁含 6 属性：攻击者能力 / 入口 / 能否直达 PG / 能否伪造 GUC / 能否绕过 RLS / 当前可达性。

| 编号 | 攻击者能力 | 入口 | 能否直达 PG | 能否伪造 GUC | 能否绕过 RLS | 当前可达 |
|---|---|---|---|---|---|---|
| **T0** | 外部匿名 Web 用户，无 DB 凭据 | 仅经前端→反向代理→Express/FastAPI 公开端点 | **否**（PG 仅 localhost，无外部监听；无凭据） | 不能直接；须经 API 间接（仅当存在注入 T1/T2） | 不能（无连接） | 受限于 API 层，无直接风险 |
| **T1** |  exploit Express SQLi | `server/src/db/*` 某端点若存在拼接 SQL | 经被攻破的 API 连接（池中以 `postgres` 或 `shutree_app` 身份） | **能**（注入 `SET LOCAL app.current_user_id='victim'`） | 若池为 `postgres`→天然绕过；若为 `shutree_app`→伪造后 RLS 按受害者求值 | 当前代码无注入面→**不可达**；但属「若回归即致命」 |
| **T2** | exploit FastAPI SQLi | `api/retrieve.py` 或后续 `api/*` 数据层若存在拼接 | 经 FastAPI 连接池（当前同以 `postgres` 身份，见 `st_12_ro_roles.py` 探针） | **能**（同 T1 机制） | 同上 | 当前 `retrieve.py` 全参数化→**不可达**；不推断「T0 不能连故 T2 不能伪造」——T2 走 API 连接而非直连，逻辑独立 |
| **T3** | 误配置 / 角色权限过大 | 连接池以 `postgres` 超级用户连接（**已证实现状**） | 是（应用自身连接即超级用户） | 无需伪造——超级用户**直接绕过 RLS** | **完全绕过**（含 `FORCE RLS`） | **已可达（真实缺口）**，优先级高于 T1/T2 |
| **T4** | 连接池 GUC 跨请求泄漏 / SECURITY DEFINER 滥用 | 池 checkout 未重置会话级 GUC；或某 SECURITY DEFINER 函数内部读 GUC 作身份 | 经应用连接 | 间接（上一请求残留身份被下一请求继承） | 若残留为受害者身份→下一请求越权读 | 取决于代码是否用会话级（非 LOCAL）GUC 写身份；当前审计未见会话级身份 GUC→**低**；但须写入 P0 闸门强制「checkout 重置」 |

**关键澄清（用户特别要求）**：不要从「T0 不能直连 PG」推出「T2 不能伪造 GUC」。T2 的伪造**不依赖直连**——它利用的是 API 进程已经持有的、指向 PG 的连接。只要该连接上发生 SQL 注入，攻击者即在该连接上下文内 `SET`，无需自己连 PG。T0→T2 的桥梁是「注入点」，不是「直连能力」。

## 四、可选安全方案比较（A/B/C/D）

| 方案 | 机制 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A｜GUC + RLS** | API 受信任层写 `app.current_user_id`，RLS 谓词 `WHERE owner_id = current_user_id()` | 实现简单、与 Supabase 模式一致、细粒度行级隔离 | GUC 非权威（F1/F2）；一旦注入即被伪造；超级用户绕过（T3） | **作为基础层保留**，但必须配最小权限角色 + 参数化 + 池重置，单靠它不够 |
| **B｜DB 函数封装** | 所有私有表访问经 `SECURITY DEFINER` 存储过程，**用户 ID 作为显式参数传入**，函数体**不读 GUC**；调用方权限收窄到只 `EXECUTE` | 身份由「调用参数」而非「会话变量」决定，注入无法直接改身份；强隔离 | 代码量大；若函数内部仍读 GUC 则失效（F6）；需仔细审计 DEFINER 所有者权限 | **受限采用**：对新私有写路径（知识库/书架）优先用 B；旧表保留 A |
| **C｜每用户连接隔离** | 为每个用户建独立 DB 连接/角色，物理隔离 | 身份与连接绑定，无法伪造 | 连接池耗尽、无法复用、严重性能与运维成本；与 Supabase 共享池模型冲突 | **拒绝**。成本高且破坏池化架构，不划算 |
| **D｜纵深防御（推荐）** | A（RLS 基础）+ B（新写路径参数化函数）+ 全参数化（消除注入面）+ 最小权限 `shutree_app` 角色（消除 T3）+ 池 checkout 重置 GUC（消除 T4）+ JWKS 失败关闭（V1.2.2）+ RLS 单元测试 | 无单点失效：即使某一层失误，其余层仍挡住 | 实施项较多，须纳入 1B 前 P0 闸门与 24 项测试 | **主方案**。GUC 仅作为「受信任层写入的上下文」，绝不视为认证边界 |

**推荐组合**：以 **D** 为总架构；其中 **A 是 RLS 地基**（必须保留，配合最小权限角色），**B 用于新增高敏感写路径**，**C 不采用**。核心是——把「身份可信」从「GUC 隐含可信」改为「参数化 + 最小权限 + 多层校验显式可信」。

## 五、专项测试设计（10 项）

> 原则：既然 GUC 可伪造是**事实**（F1/F2），应设计「正向证明可伪造」的测试来暴露架构依赖，再设计「防御有效」的测试验证纵深防御成立。4xx 不重试、5xx 自动重试（前端边界，V1 规范）与此处后端测试无关。

| 编号 | 测试 | 类型 | 期望结果 | 验证点 |
|---|---|---|---|---|
| **T-01** | 以普通 `shutree_app` 角色执行 `set_config('app.current_user_id','arbitrary-uuid',true)` | 正向（暴露） | 成功，无权限错误 | F1/F2：证明 GUC 可由普通角色任意设，非认证边界 |
| **T-02** | 同上，value 设为**不属于**当前登录用户的 UUID | 正向（暴露） | 成功写入 | F2：value 无身份约束 |
| **T-03** | 对每个接受用户输入的端点注入 `; SET LOCAL app.current_user_id='victim'` | 注入正向 | 被参数化拦截，语句原样作为数据，不执行 SET | F3/F4：当前无注入面，注入串不生效 |
| **T-04** | 以 `shutree_app` 连 PG，SET GUC=受害者，SELECT 私有表 | RLS 生效 | 仅返回受害者行；不能见他人 | A 方案有效性（前提：非超级用户） |
| **T-05** | 以 `postgres` 超级用户连 PG，读私有表 | RLS 绕过证明 | **返回全部行**（RLS 被绕过） | T3：证明当前池角色错误使 RLS 失效；驱动 P0 切换角色 |
| **T-06** | 请求 A 写会话级 GUC=用户 X，归还连接；请求 B 复用同连接，未重置 | 池泄漏 | B 不应见到 X 的身份上下文 | F7/T4：驱动「checkout 重置 GUC」强制项 |
| **T-07** | 审计所有 `SECURITY DEFINER` 函数：是否读 GUC 作身份、是否带 `search_path` 固定 | 代码审计 | 函数均**以参数接收 user_id**，不读 GUC；`search_path` 显式限定 | F6/B 方案安全前提 |
| **T-08** | 静态扫描数据层：禁止 `${}`/字符串拼接构造 SQL，强制占位符 | 静态 | 零违规 | F8：维持无注入面 |
| **T-09** | JWT 算法混淆：以 HS256 签名（若期望非对称）、`alg:none`、未知 alg 提交 | 鉴权负向 | 全部拒绝；不回退到 HS256 默认 | V1.2.2：拒绝不支持 alg，不默认 HS256 |
| **T-10** | JWKS 不可达时，所有需鉴权请求 | 失败关闭 | 全部拒绝（不降级放行） | V1.2.2 §P0：JWKS 失败关闭 |

**与 V1.2.2 §P0 的衔接**：T-04/T-05/T-06/T-09/T-10 即 P0 闸门中「24 项测试」的核心子集；本复核新增 T-01/T-02（正向证明 GUC 可伪造）与 T-03/T-07/T-08（注入面与 DEFINER 审计），补齐「GUC 非权威」这一维度的可测性。

## 七、最终给用户的回答（一页结论）

> **问：若攻击者利用 Express/FastAPI 的 SQL 注入，能否通过当前数据库连接伪造 GUC，读取/修改他人私有数据？**
>
