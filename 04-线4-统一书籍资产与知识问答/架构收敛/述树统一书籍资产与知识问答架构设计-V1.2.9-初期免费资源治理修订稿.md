## 一、初期免费产品模型（产品决策落地）

> 对应交付标准 §1。

- **核心功能免费**：普通用户免费使用核心功能（单词、生词本、阅读器、公共书检索等）。
- **消耗型资源公平使用限制**：对 AI 问答、AI 学习稿、云存储、文件上传、格式转换、语义检索设置**公平使用（fair-use）额度/限速/容量上限**。`限额`是**资源治理**，不是「付费门槛」；初期所有用户（无论身份）适用同一套限额。
- **本阶段不建设**：会员系统、会员等级、会员有效期、会员订单、支付系统、会员专属权限。
- **会员权益 ≠ 平台管理权限**（强制分离）：`super_admin` 是**平台管理权限**，与任何未来会员身份互不相干；本阶段仅 `user` 与 `super_admin` 两种平台角色。
- **未来扩展保留空间**：个人高级 AI、更大云存储、更高文件处理额度、团队知识库、学校/企业机构服务——但本阶段**不提前实现**会员订单/支付/订阅/会员有效期。
- **关键纪律**：不得因是否付费产生初期用户身份差异；不得把资源额度误设计为会员权益（见 §六·E 与 §八）。

## 二、用户身份与资产权限模型

> 对应交付标准 §2。四类概念必须区分：**用户身份 / 平台权限 / 资产归属 / 资产可见性 / 资源治理**。

### 2.1 用户身份（who is using）
- 真实用户 = 经认证的稳定 UUID（`sub`）；初期来源为 Supabase Auth（B2）或自建 JWT，二者均须签发稳定 UUID `sub`。
- 数据库镜像：`app_users(sub uuid PK, email, role, created_at)`（`role ∈ {user, super_admin}`，平台权限；默认 `user`）。

### 2.2 平台权限（what user can administer）
- 仅两种：`user`（普通）、`super_admin`（平台管理）。
- `super_admin` **不是** DB 登录角色，而是 `app_users.role` 上的一个平台权限标记；其跨用户管理能力由**服务端**经 `SECURITY DEFINER` 函数（V1.2.3 方案 B）或独立的、仅管理员端点使用的 BYPASSRLS 连接实现，**绝不**让普通用户面对的连接具备 BYPASSRLS（见 §五）。

### 2.3 资产归属（who owns the asset）
- **公共资产**（Gutenberg 等来源书）：`discovered_books` / `discovered_book_chunks` / `works` / `editions` / `content_versions` —— **无 `owner_id` 列**，全局共享，任何人可读。**严禁使用 `__public__` 作为虚拟用户身份**（本轮产品硬约束）。
- **私有资产**（用户上传书、笔记、学习资料）：`user_books` / `user_book_chunks` / `user_bookshelf` / `knowledge_bases` / `kb_books` —— 带 `owner_id uuid NOT NULL`（= 真实 `sub`）。

### 2.4 资产可见性（visibility）
- 公共：全局可读，无 RLS。
- 私有：仅 `owner_id = current_user_id()`（RLS）。
- 知识库：是「选哪些书作为 AI 问答来源」的**关系**，不改变所有权；取消引用只删 `kb_books` 关系，不删原书；查询时重验每本书访问权限（公共直接读、私有走 RLS）。

### 2.5 资源治理（how much resource a user may consume）
- 见 §三；额度按真实 `user_id` 追踪，服务端强制，与付费身份无关。

## 三、AI / 存储 / 文件处理资源治理模型

> 对应交付标准 §3。本阶段为「初期免费公平使用」，但机制须为未来商业化预留扩展点。

### 3.1 资源清单与治理维度

| 资源 | 治理维度 | 初期公平使用（建议值，待裁定） | 统计周期 | 客户端可见 |
|---|---|---|---|---|
| AI 问答 | 请求额度 / 并发 / 异常频率 | 例如每用户每日 N 次请求；并发 ≤ K；单用户频率熔断 | daily | 是（剩余次数） |
| AI 学习稿 | 任务额度 / 文本长度 | 例如每日 M 个任务；单次输入 ≤ L 字符 | daily | 是 |
| 云存储 | 容量统计 / 上限 | 例如每用户总容量 ≤ C MB（含上传原文 + 标准化正文） | total（累计，可降级清理） | 是（已用/上限） |
| 文件上传 | 单文件大小 / 类型 / 次数 | 单文件 ≤ 50MB（沿用现有 `CONVERT_MAX_FILE_BYTES`）；类型白名单；每日上传次数 | daily | 是 |
| 格式转换 | 并发 / 队列 / 超时 / 失败恢复 / 次数 | 并发 ≤ J；任务超时沿用 `CONVERT_TASK_TIMEOUT`；每日任务数 | daily | 是 |
| 语义检索 | 请求频率 / 资源保护 | 每用户每秒/每日请求上限；HNSW 保护沿用 `ef_search` 矩阵 | daily + 速率 | 是 |

> 注：**平台容量类限制**（如单文件 50MB、转换超时 300s、连接池大小）属于**基础设施限额**，保留在各服务 config（与现有 `api/config.py`、`convert_worker/config.py` 一致），**不属于**按用户配额；按用户配额只管「每人能用多少」。

### 3.2 设计原则（逐条对齐产品约束）

1. **可追踪到真实 `user_id`**：用量表以 `user_id`（=JWT `sub`）为主键维度，服务端从 JWT 取 `sub`，**绝不**接受客户端传入的 `user_id`/额度参数。
2. **额度规则集中配置**：单一 `resource_quota_config` 表（或读取该表的配置服务）为唯一真相源；各业务模块**调用 `QuotaService`** 而非各自硬编码限额（消除「散落在各业务模块」）。
3. **对普通用户公开透明**：提供 `GET /api/quota` 返回当前用户各资源 `limit/used/remaining/window`，前端展示剩余额度。
4. **不因付费产生身份差异**：初期所有用户命中 `scope='all', role='user'` 的同一行配置；未来商业化**只新增** `scope='role', role='premium'` 行，不改动机制。
5. **明确统计周期与恢复**：采用**固定日历窗口**（`window_start`/`window_end`，如每日 UTC 00:00）；窗口过期后自动开新窗口行，旧行归档/清理；`used` 在新窗口从 0 起算（恢复=窗口轮转，非人工）。
6. **客户端不可自改额度/用量/权限**：`resource_usage` 与 `resource_quota_config` **仅服务端 `QuotaService` 可写**；权限（`app_users.role`）仅管理员后端可改；无任何写权限的 API 暴露给客户端。
7. **不可经请求参数绕过**：server 端强制——`user_id` 仅来自 `sub`；`resource_key` 由服务端按接口语义决定；`cost` 由服务端计算；限额查询在授信后、资源消耗前完成，超额返回 **429**（不降级放行）。

### 3.3 服务端强制顺序（伪代码）
```
auth middleware:  提取并验证 JWT → sub（失败 401）
quota middleware:  QuotaService.check_and_increment(sub, resource_key, cost)
                   ├─ 读 resource_quota_config（缓存）→ limit/period/window
                   ├─ 原子：INSERT … ON CONFLICT(user_id,resource_key,window_start)
                          DO UPDATE SET used = used + cost
                   ├─ used > limit → 429（含 Retry-After）
                   └─ 通过 → 继续业务处理
business handler:  执行实际资源消耗（AI/存储/转换/检索）
```

## 四、数据库表结构建议

> 对应交付标准 §4。在 V1.2.8 D2（已修订，见 §六）之上新增资源治理表；资产表沿用 V1.2.6 A 的复合外键方案，**公共表无 owner_id**。

### 4.1 资产表（修订后，owner_id = uuid，公共表无 owner）

| 表 | 关键列 | owner | RLS | 说明 |
|---|---|---|---|---|
| `discovered_books` / `discovered_book_chunks` | 现有 BIGSERIAL；`work_id`/`edition_id`/`content_version_id`/`section_type` 兼容列 | **无** | 无（全局可读） | 公共书，绝不引入 `__public__` 哨兵 |
| `works` / `editions` / `content_versions` | uuid PK / BIGSERIAL（legacy_book_id 回溯） | **无** | 无（全局身份） | 公共逻辑身份，无 owner |
| `user_books` | `user_book_id uuid PK`, `owner_id uuid NOT NULL`, `UNIQUE(user_book_id, owner_id)`, `FK owner_id→app_users(sub)` | uuid | ENABLE RLS | 私有书 |
| `user_book_chunks` | `owner_id uuid NOT NULL`, `FK(user_book_id, owner_id)→user_books(...)`（复合，双列 NOT NULL） | uuid | ENABLE RLS | 结构性禁跨用户引用 |
| `user_bookshelf` | `owner_id uuid NOT NULL`, 复合 FK→`user_books` | uuid | ENABLE RLS | 关系，不复制书 |
| `knowledge_bases` | `kb_id uuid PK`, `owner_id uuid NOT NULL`, `UNIQUE(kb_id, owner_id)` | uuid | ENABLE RLS | 关系 |
| `kb_books` | `public_book_id BIGINT REFERENCES discovered_books(id)`（公共，无 owner） + `user_book_id uuid REFERENCES user_books(user_book_id, owner_id)`（私有，复合锁 owner） + `owner_id uuid NOT NULL REFERENCES knowledge_bases(kb_id, owner_id)`（复合锁 KB owner） + `CHECK` 二选一 | uuid | ENABLE RLS | 跨用户引用禁止 |

### 4.2 资源治理表（新增，B4 迁移范围）

```sql
-- 用户身份镜像 + 平台权限（两角色之一）
CREATE TABLE app_users (
  sub    uuid PRIMARY KEY,                 -- = 认证 sub（Supabase/自建 JWT）
  email  text,
  role   text NOT NULL DEFAULT 'user' CHECK (role IN ('user','super_admin')),
  created_at timestamptz DEFAULT now()
);

-- 集中式额度配置（唯一真相源；scope/role 为未来商业化预留扩展点）
CREATE TABLE resource_quota_config (
  key          text NOT NULL,              -- 如 'ai_qa','ai_study_notes','cloud_storage','file_upload','format_convert','semantic_retrieval'
  scope        text NOT NULL DEFAULT 'all' CHECK (scope IN ('all','role')),
  role         text NOT NULL DEFAULT 'user',
  limit_value  bigint NOT NULL,            -- 额度（次数/字节）；存储用字节
  period       text NOT NULL CHECK (period IN ('daily','monthly','total')),
  unit         text,                       -- 'count' | 'bytes'
  description  text,
  is_public    boolean DEFAULT true,       -- 是否向用户公开展示
  PRIMARY KEY (key, scope, role)
);

-- 按用户、按资源、按窗口的用量（服务端权威；客户端只读）
CREATE TABLE resource_usage (
  user_id      uuid NOT NULL REFERENCES app_users(sub),
  resource_key text NOT NULL,
  window_start timestamptz NOT NULL,       -- 固定日历窗口起点（如每日 UTC 00:00）
  window_end   timestamptz NOT NULL,
  used         bigint NOT NULL DEFAULT 0,
  PRIMARY KEY (user_id, resource_key, window_start)
);
-- 索引：按用户查全部剩余额度；按窗口过期归档
CREATE INDEX idx_usage_user ON resource_usage(user_id);
CREATE INDEX idx_usage_expire ON resource_usage(window_end);
```

> 容量类（云存储 `total` 周期）用累加且可降级清理；次数类（daily/monthly）用窗口轮转恢复。所有写仅经 `QuotaService`（事务内原子 `INSERT … ON CONFLICT … DO UPDATE SET used=used+cost`）。

## 五、RLS 与服务端授权方案

> 对应交付标准 §5。

### 5.1 私有表 RLS（沿用 V1.2.8 D6 推荐）
- **`ENABLE ROW LEVEL SECURITY`（非 `FORCE`）**：运行时 `shutree_app` 非所有者 → 受策略约束；迁移角色 `shutree_migrator` 为所有者可批量回填跨用户行（ENABLE 下豁免）。
- 策略：`USING/WITH CHECK (owner_id = current_user_id())`；`current_user_id()` 读事务级 GUC `app.current_user_id`（值来自已验证 JWT `sub`）。
- **公共表（discovered_*/works/editions/content_versions）无 RLS、无 owner_id**：全局可读，绝不引入 `__public__` 虚拟身份。

### 5.2 服务端授权分层
1. **认证中间件（B2）**：验证 JWT（ES256/JWKS，V1.2.2）→ 取 `sub` → `SET LOCAL app.current_user_id = sub` → 注入请求上下文。
2. **配额中间件（新增，B2 范围）**：`QuotaService.check_and_increment(sub, resource_key, cost)`（见 §3.3），超额 429。
3. **普通用户请求**：经 RLS 自动限 `owner_id=sub`；不可见他人私有数据。
4. **`super_admin` 跨用户管理**：`app_users.role='super_admin'` 经**服务端**判定；跨用户读/写走 **`SECURITY DEFINER` 函数**（V1.2.3 方案 B）——函数内部以调用者 `current_user_id()` 校验其管理员身份，再显式按参数 `target_user_id` 操作，**不读 GUC 作身份、不依赖 BYPASSRLS**。→ 普通用户面对的连接保持 `NOBYPASSRLS`，管理员能力不破坏用户数据隔离。

### 5.3 防绕过要点（重申 V1.2.3）
- GUC **不是**认证边界：任意角色可 `set_config('app.current_user_id',任意值,true)`；RLS 只在查询参数化、无注入面时成立。故全参数化（G8 静态审计）是 RLS/B2 有效性的必要前提。
- 客户端**无法**直连 DB、无法自设 GUC；`user_id`/`quota` 一律服务端派生，请求参数不可注入身份。

## 八、未来商业化扩展方案

> 对应交付标准 §7。

- **个人高级 AI 服务 / 更大云存储 / 更高文件处理额度**：在**不改 schema** 前提下，向 `resource_quota_config` 插入 `scope='role', role='premium'` 行即可覆盖默认值；`QuotaService` 按「用户 role → 命中专属行，否则命中 `scope='all'`」解析。
- **团队知识库 / 学校企业机构**：在 `app_users` 之外引入「组织（org）」实体与「组织配额/成员」关系（本阶段不建），届时 `resource_quota_config.scope` 增 `'org'`、`resource_usage` 增加 `org_id` 维度即可承载，无需重做机制。
- **会员订单/支付/订阅/有效期**：本阶段**明确不实现**；未来如需，作为**独立计费子系统**，与资源治理的「额度机制」通过 `role`/`scope` 关联，但**不得**将「是否已付费」耦合进用户身份或破坏 RLS 隔离（H6）。
- 扩展点清单（已预留）：`resource_quota_config.(scope, role)`、`app_users.role`、`resource_usage.(user_id/org_id)`、`works/editions/content_versions` 公共身份表（与私有表解耦，便于未来机构资产归属）。
