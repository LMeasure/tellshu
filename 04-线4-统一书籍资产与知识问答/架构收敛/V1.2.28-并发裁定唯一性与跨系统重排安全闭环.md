### 1.3 最重要的诚实结论（不掩饰、不沿用前轮）

3. **阻断清单不得为缩短而重定义验收标准**：V1.2.27 §16.3 判 5 项阻断；本轮复审后**不减少**，且因新增 DB 对象与 R2 终止性前置，A 类预演由 5 项增至 **11 项阻断**（其中 3 项为本轮新增的待 PG 验证对象，§16.1）。档 2 **仍为「不具备条件」**。`[推演]`

## 2. V1.2.27 两项新增缺陷的原文定位

### 2.1 P0-1：DECIDE 并发互斥缺陷（逐行证据链）

| # | 位置（V1.2.27 原文） | 逐字内容 | 隐含的（错误）保证 |
|---|---|---|---|
| 1 | §6.1 L233 | `UNIQUE (outbox_id, from_gen, to_gen, phase) -- ① 防相同 (outbox_id+from_gen+to_gen) 重复裁定/重复阶段` | 认为该约束能防「重复裁定」；实际只防**同一 phase** 重复 |
| 2 | §6.2 Q9 L253 | 「并发操作员如何单次裁定 \| DECIDE 的 CAS `WHERE NOT EXISTS (... phase IN ('decided','rejected','dispatched'))` + 唯一约束；**一者赢**，败者 0 行 + 审计追加」 | 声称并发单次裁定已被保证 |
| 3 | §6.3 DECIDE「锁定对象」L283 | 「`cross_gen_adjudication` 已 registered 行（**`FOR SHARE` 只读**）+ `backup_control`（`FOR SHARE`）」 | 用**共享锁**串行化写裁定 —— 共享锁之间互相兼容 |
| 4 | §6.3 DECIDE「唯一约束」L285 | 「`UNIQUE (outbox_id,from_gen,to_gen,phase)`；`CHECK (phase='decided' ⇒ ...)`」 | 不同 phase 不冲突 |
| 5 | §6.3 DECIDE「CAS」L286 | 「存在 `phase='registered'` ∧ **不存在** `phase IN ('decided','rejected','dispatched')` ∧ …」 | 依赖应用层 `NOT EXISTS` 在并发快照中的可见性 |
| 6 | §6.3 DECIDE「并发冲突」L292 | 「两操作员并发送 DECIDE → 唯一约束 + `NOT EXISTS` **一者赢**」 | 同上，未证明 |
| 7 | §6.3 DECIDE「重复请求」L291 | 「已 decided/rejected → CAS 0 行 + 审计追加 `duplicate_adjudication_rejected`」 | 只覆盖**已提交**后的重复请求，不覆盖并发 |
| 8 | §11 事务总表 ⑪ L784 | 「唯一约束 + `NOT EXISTS` 一者赢」 | 同上 |
| 9 | §14 故障注入 #3 L890 | 「两名操作员并发裁定 → `NOT EXISTS` + 唯一约束一者赢 → 单条 decided」 | 把未证明的结论写成用例**预期行为** |
| 10 | §17.1 P1-1 #4 L1011 | 「不存在重复授权和重复执行 ✅ 唯一约束 + CAS + 幂等退出」 | 把未证明结论计入 24/24 验收 |

> **推演结论**：`[推演]` 设两事务 T1=`DECIDE(authorize_new)`、T2=`DECIDE(rejected)`，均针对 `(O1,G,G+1)`，且 `registered` 行已提交。① T1、T2 各自 `SELECT ... FOR SHARE` 同一 registered 行与 `backup_control` 行 —— **`FOR SHARE` 与 `FOR SHARE` 兼容，两者同时持锁成功**；② 在 READ COMMITTED 各自语句快照中，T1 看不到 T2 未提交的 INSERT，T2 也看不到 T1 的，双方 `NOT EXISTS` 均为 TRUE；③ T1 INSERT `(O1,G,G+1,'decided')`，T2 INSERT `(O1,G,G+1,'rejected')`；④ `UNIQUE(outbox_id,from_gen,to_gen,phase)` 的两组键**第四列不同**，两条均插入成功；⑤ COMMIT 后审计表同时存在「授权创建新一代任务」与「拒绝裁定」两条**互相矛盾**的最终记录；⑥ 若 DISPATCH 随后读取 `phase='decided' AND decision='authorize_new'`，会在 `rejected` 存在的情况下照常创建新任务。**这是写偏斜，不是死锁，数据库不会报错，应用层也无从发现。** `[推演]` + `[待PG]`（并发实际行为须实测）
>
> **补充说明**：`FOR UPDATE` 于**已存在的 registered 行**确实能串行化两个 DECIDE，但 V1.2.27 §6.1 明文规定 `cross_gen_adjudication` 为 append-only 且 `REVOKE UPDATE/DELETE/TRUNCATE`；PostgreSQL 中 `SELECT ... FOR UPDATE` 要求对目标表持有 `UPDATE` 权限 —— **「把 `FOR SHARE` 改成 `FOR UPDATE`」与 append-only 权限模型直接冲突**。这构成本轮新发现 N-2（§15.2），也是本轮必须引入独立 decision-slot 表而非直接改锁的原因。`[推演]` + `[待PG]`

## 4. T-CROSSGEN-DECIDE 并发缺陷分析

### 4.1 现有方案的四层失效（逐层静态推演）

| 层 | V1.2.27 机制 | 失效原因 | 标签 |
|---|---|---|---|
| ① 锁 | `FOR SHARE` 于 registered 行 + `backup_control` | `FOR SHARE` 是**共享**行锁，两个 DECIDE 同时持有互不阻塞；共享锁的设计意图是「防他人修改我读的行」，**不能防他人在同表中 INSERT 新行** | `[推演]` + `[待PG]` |
| ② 谓词 | `NOT EXISTS (SELECT 1 ... phase IN ('decided','rejected','dispatched'))` | 在 READ COMMITTED / REPEATABLE READ 下，未提交 INSERT 对其他事务不可见；`NOT EXISTS` 只能看到**已提交**的最终裁定，无法覆盖并发窗口。**这是写偏斜，SERIALIZABLE + SSI 可捕获，但 V1.2.27 未声明隔离级别，且 SSI 会 abort 其中一事务并要求重试协议（上游未定义）** | `[推演]` + `[待PG]` |
| ③ 唯一约束 | `UNIQUE (outbox_id, from_gen, to_gen, phase)` | 冲突键第四列 `phase` 不同（`decided` vs `rejected`）→ 两条记录**不冲突**；`ON CONFLICT (outbox_id,from_gen,to_gen,phase) DO NOTHING` 同样不触发 | `[推演]` + `[待PG]` |
| ④ CHECK | `CHECK (phase='decided' ⇒ adjudicator/settled_at/decision 非空)` | 只校验单行字段组合，**无法表达跨行互斥**；且 V1.2.27 §6.1 的 CHECK 已用 `IS TRUE` 收口（三值逻辑正确），但作用域仅本行 | `[推演]` |

> **结论**：`[推演]` 四层**没有任何一层**能阻止「两个不同最终 phase 并发双成功」。V1.2.27 所称「一者赢」是把「唯一约束存在」误当成「唯一约束覆盖所需语义」。任务书 §3.1 的判断成立。`[推演]`

### 4.2 必须先澄清的语义歧义（本轮新发现 N-1）

V1.2.27 对「最终裁定」存在**两套并存表达**：

| 出处 | 表达 |
|---|---|
| §6.1 L221 | `phase CHECK (phase IN ('registered','decided','rejected','dispatched'))` |
| §6.1 L226 | `decision CHECK (decision IN ('authorize_new','note_only','rejected'))` |
| §6.2 Q10 L254 | 「不足或矛盾 → `phase='rejected'` + `decision='rejected'`」 |
| §6.3 DECIDE 写入字段 L288 | 「新记录：`phase='decided'\|'rejected'`, … `decision`」 |

即「拒绝」既可作为 `phase` 也可作为 `decision`，而 `CHECK (phase='decided' ⇒ decision IN ('authorize_new','note_only'))` 又**排除**了 `phase='decided' AND decision='rejected'` 的写法。若不做收敛，「最终裁定唯一」本身就无良定义。本轮统一为：

```
最终裁定（final decision）= 且仅 = 一条 phase ∈ ('decided','rejected') 的审计记录
  phase='decided'  ⇒ decision ∈ ('authorize_new','note_only')，adjudicator/settled_at/evidence_snapshot_id 非空
  phase='rejected' ⇒ decision='rejected'（或 NULL 但由 CHECK 强制为 'rejected'），reason 非空
  phase='registered'（登记阶段） / phase='dispatched'（派发阶段）均**不是**最终裁定
  note_only 不是「第三种结果」而是 decided 下的一个 decision 值 —— 三种 decision 结果互斥由单值列保证
```
> 任务书 §3.2 第 2 点「`authorize_new`、`note_only`、`rejected` 三种结果互斥」由此满足：三者是**同一列 `decision` 的三个互斥取值**，且 DECIDE 至多写一条最终裁定记录。`[推演]`

### 4.3 方案比较（为何选「部分唯一索引 + 独立 decision-slot」）

| 方案 | 评估 | 结论 |
|---|---|---|
| **A**：仅把 DECIDE 的 `FOR SHARE` 改成 `FOR UPDATE` | 能串行化两个 DECIDE（锁同一 registered 行）；但 ① 与 §6.1 append-only 表 `REVOKE UPDATE` 冲突（`SELECT FOR UPDATE` 需 UPDATE 表权限）；② 只防「已存在 registered 行」的并发，若 DECIDE 被允许在无 registered 行时直接裁定则失效；③ 仍是**应用层锁约定**，DB 约束层没有跨 phase 互斥 | ❌ 拒绝（不充分） |
| **B**：仅加部分唯一索引 `UNIQUE (outbox_id,from_gen,to_gen) WHERE phase IN ('decided','rejected')` | **DB 级硬保证**，任何绕过应用层的 INSERT 都会被 `23505` 拒绝；但两事务并发时胜者 COMMIT、败者**事务整体回滚**（`unique_violation`），信息以「异常」而非「0 行幂等退出」呈现，且 `ON CONFLICT` 推断须精确匹配谓词（V1.2.23 §10 教训） | ✅ 采纳为**第二层硬兜底**，不单独使用 |
| **C**：`ON CONFLICT (outbox_id,from_gen,to_gen) WHERE phase IN (...) DO NOTHING` | 可让败者幂等退出；但 `cross_gen_adjudication` 同时存在 `UNIQUE(...,phase)`，arbiter 推断可能歧义；且 `DO NOTHING` 丢失「与哪条已存在裁定冲突」的信息（V1.2.23 §10 L695 明确教训）；`rejected` 与 `decided` 冲突时无法区分「已有授权」与「已有拒绝」 | ❌ 不作为 DECIDE 主路径（仅在 REGISTER 的普通主键幂等上使用） |
| **D**：SERIALIZABLE + SSI | 能捕获写偏斜，但需全链路声明隔离级别、`serialization_failure` 重试协议、且 SSI 谓词锁行为本身 `[待PG]`；上游从未定义 | ❌ 拒绝作为唯一依赖，可作纵深防御 `[待决策]` |
| **E（本轮选定）**：**独立 `cross_gen_decision_slot` 表（可 UPDATE）** + **槽位行 `FOR UPDATE` 串行化** + **审计表部分唯一索引硬兜底** + **CHECK `IS TRUE`** + **DISPATCH 有效性 CAS** | ① 串行化由真实**排他行锁**保证，败者锁后重读得到「0 行 + 幂等退出」；② 跨 phase 互斥由 **DB 约束本身**保证（满足完成标准 #2），不依赖应用逻辑；③ 审计表仍严格 append-only（`REVOKE UPDATE/DELETE/TRUNCATE`），槽位表是可变状态表，**两者职责分离**，不违反任务书 §3.2 第 4/5 点；④ 保留「已有 registered/decided/rejected 记录全部 append-only」 | ✅ **选定** |

> **效果不弱于任务书 §3.2 建议组合的证明**：`[推演]` 任务书建议「`FOR UPDATE` 行锁策略 + 数据库级约束 + CAS 双重保证」。本方案 E 含 `FOR UPDATE`（槽位行）、数据库级约束（部分唯一索引 + CHECK + 槽位 PK + `UNIQUE(final_adjudication_id)`）、CAS（槽位 `final_phase IS NULL` + DISPATCH 四条件），且**额外**提供 append-only 与可变状态的职责分离、撤销语义、fence_gen 有效性校验，故效果不弱。`[推演]` + `[待PG]`

## 5. DECIDE 最终互斥协议

### 5.1 三事务重写（REGISTER / DECIDE / DISPATCH，每事务 13 项）

#### ① T-CROSSGEN-REGISTER（登记 + 创建槽位，单事务）

| 项目 | 设计 |
|---|---|
| 输入 | `outbox_id`, `from_gen`, `to_gen`, `origin_snapshot_id` |
| 锁定对象 | `backup_control` 行 `FOR SHARE` → 旧终局 `object_outbox` 行 `FOR SHARE`（只读）→ **INSERT 槽位行 + INSERT registered 审计行** |
| 锁顺序 | **先 control，后事件**（沿用 V1.2.27，避免与屏障事务死锁）→ 槽位 → 审计 |
| 唯一约束 | 槽位 `PRIMARY KEY (outbox_id,from_gen,to_gen)`；审计 `UNIQUE(outbox_id,from_gen,to_gen,phase)` |
| CAS | 旧事件 `status IN ('done','skipped')` ∧ `terminal_at IS NOT NULL` ∧ `unresolved_request IS FALSE` ∧ `from_gen <> to_gen` ∧ `to_gen = backup_control.fence_gen` ∧ 不存在同键槽位 |
| 写入表 | `cross_gen_decision_slot`（INSERT）、`cross_gen_adjudication`（INSERT registered）、`adjudication_log`（INSERT） |
| 写入字段 | 槽位：`slot_id`, `outbox_id/from_gen/to_gen`, `registered_adjudication_id`, `created_at`，其余列 NULL；审计：`phase='registered'`, `origin_snapshot_id` |
| 禁止修改字段 | **旧 `object_outbox` 行全部字段**；任何已存在审计记录；`final_phase`（REGISTER 不写） |
| COMMIT 边界 | **单事务 COMMIT**：槽位 + registered 审计 + log 同生共死 |
| 重复请求 | `ON CONFLICT (outbox_id,from_gen,to_gen) DO NOTHING` → 幂等退出；`RETURNING` 0 行即读回已有槽位 |
| 并发冲突 | 两 REGISTER → 主键一者赢；败者 0 行 + 审计 |
| 崩溃恢复 | 提交前崩溃 → 三者皆无，重跑；提交后 → 幂等退出 |
| 审计一致性 | 槽位与 registered 记录一一对应（`registered_adjudication_id` 可校验） |

#### ② T-CROSSGEN-DECIDE（最终裁定，单事务）— **本轮核心修正**

```sql
-- 设计级伪代码，不执行。隔离级别要求 READ COMMITTED 及以上；SERIALIZABLE 为可选纵深防御 [待PG]
BEGIN;
  -- ★ 层 1：排他行锁串行化（槽位行是可变状态表，允许 FOR UPDATE）
  SELECT slot_id, final_phase, final_decision, final_adjudication_id,
         registered_adjudication_id, revoked_at, dispatched_adjudication_id, to_gen
    INTO v
    FROM cross_gen_decision_slot
   WHERE outbox_id = :id AND from_gen = :g1 AND to_gen = :g2
     FOR UPDATE;                       -- ★ 不是 FOR SHARE；无行 → 0 行退出

  IF NOT FOUND THEN
     INSERT INTO adjudication_log(...) VALUES (...,'DECIDE_no_slot');
     COMMIT; RETURN;                     -- fail-closed：无 REGISTER 不得裁定
  END IF;

  -- ★ 层 2：锁后重读的 CAS（不能信任锁前快照）
  IF (v.final_phase IS NULL) IS NOT TRUE THEN
     INSERT INTO adjudication_log(...) VALUES (...,'duplicate_decision_rejected');
     COMMIT; RETURN;                     -- 幂等退出：0 行，不 INSERT、不 UPDATE 审计
  END IF;
  IF (v.revoked_at IS NULL) IS NOT TRUE THEN
     INSERT INTO adjudication_log(...) VALUES (...,'decide_after_revocation_rejected');
     COMMIT; RETURN;
  END IF;
  -- 证据 / 授权 / 在途请求守卫（沿用 V1.2.27 §6.3，全部 IS TRUE 收口）
  IF ( (:evidence_auditable = 'true') IS TRUE
       AND (:dual_signoff = 'true') IS TRUE
       AND (:unresolved_request_is_false = 'true') IS TRUE
       AND (v.to_gen = :current_fence_gen) IS TRUE
       AND (:to_gen_unchanged = 'true') IS TRUE ) IS NOT TRUE THEN
     INSERT INTO adjudication_log(...) VALUES (...,'DECIDE_rejected_insufficient');
     COMMIT; RETURN;
  END IF;

  -- ★ 层 3：INSERT 最终裁定审计记录（append-only，新 INSERT 不 UPDATE 历史）
  --   不使用 ON CONFLICT：若有人绕过槽位直接 INSERT，uq_cg_one_final_decision 抛 23505 → 事务回滚 + 告警
  INSERT INTO cross_gen_adjudication(
      adjudication_id, outbox_id, from_gen, to_gen, phase, adjudicator,
      settled_at, decision, reason, evidence_snapshot_id, origin_snapshot_id, created_at)
    VALUES (:aid, :id, :g1, :g2, :final_phase, :op, now(), :final_decision,
            :reason, :sid, v.registered_adjudication_id, now());

  -- ★ 层 4：同一事务原子推进槽位（CAS 再次确认 open）
  UPDATE cross_gen_decision_slot
     SET final_phase = :final_phase, final_decision = :final_decision,
         final_adjudication_id = :aid, settled_at = now(),
         adjudicator = :op, evidence_snapshot_id = :sid
   WHERE outbox_id = :id AND from_gen = :g1 AND to_gen = :g2
     AND (final_phase IS NULL) IS TRUE
     AND (revoked_at IS NULL) IS TRUE;
  GET DIAGNOSTICS v_rows = ROW_COUNT;
  IF v_rows <> 1 THEN ROLLBACK; RETURN; END IF;   -- 并发败者（理论上层 1 已排除）

  INSERT INTO adjudication_log(...) VALUES (...,'crossgen_decided');
COMMIT;
```

| 项目 | 设计 |
|---|---|
| 输入 | `outbox_id/from_gen/to_gen`、`final_phase ∈ ('decided','rejected')`、`final_decision`、`adjudicator`、双人签核凭证、证据快照 `sid`、`reason` |
| 锁定对象 | **槽位行 `FOR UPDATE`（排他）**；`backup_control` 只读；审计表仅 INSERT（不加行锁） |
| 锁顺序 | 槽位行 → 审计 INSERT → 槽位 UPDATE → log；**所有 DECIDE/DISPATCH/REGISTER 统一先槽位**，避免死锁 |
| 唯一约束 | `uq_cg_one_final_decision`（跨 phase 硬互斥）、`UNIQUE(final_adjudication_id)`、槽位 PK |
| CAS | 锁后重读 `final_phase IS NULL` ∧ `revoked_at IS NULL` ∧ 证据可审计 ∧ 双人签核 ∧ 旧事件 `unresolved_request IS FALSE` ∧ `to_gen = current fence_gen` |
| 写入表 | `cross_gen_adjudication`（**INSERT 新记录**）、`cross_gen_decision_slot`（**UPDATE 本事务新建/已存在的可变槽位**）、`adjudication_log`（INSERT） |
| 写入字段 | 见上；`final_phase`/`final_decision`/`final_adjudication_id`/`settled_at`/`adjudicator`/`evidence_snapshot_id` |
| **禁止修改字段** | **任何已存在审计记录（registered/decided/rejected/dispatched 全部字段）**；**旧 `object_outbox` / `promotion_intents` 终局主行全部字段**；`new_outbox_id`（DECIDE 不填）；`dispatched_adjudication_id` |
| COMMIT 边界 | **单事务**：审计 INSERT + 槽位 UPDATE + log 三者同生共死 |
| 重复请求 | 槽位 `final_phase` 非空 → **0 行 + `duplicate_decision_rejected` 审计**，幂等退出 |
| 并发冲突 | 两 DECIDE 争同一槽位行 `FOR UPDATE` → **一者持锁、一者等待**；胜者 COMMIT 后败者锁后重读发现 `final_phase` 非空 → 0 行退出 |
| 崩溃恢复 | 锁定后、INSERT 前崩溃 → 事务回滚，槽位仍 `open`，registered 记录仍在 → **重跑 DECIDE**；提交成功响应丢失 → 重放得到 0 行 + 幂等退出 |
| 审计一致性 | 三条审计记录（registered / decided 或 rejected / dispatched）全部 append-only；历史永不被 UPDATE |

#### ③ T-CROSSGEN-DISPATCH（消费唯一合法未撤销授权，单事务）

| 项目 | 设计 |
|---|---|
| 输入 | `outbox_id/from_gen/to_gen`、新 `session_id`/`intent_id` 生成素材、`current_fence_gen` |
| 锁定对象 | **槽位行 `FOR UPDATE`** → 新 `cleanup_bundle` 行 → 新 `object_outbox` 行 → dispatched 审计 INSERT |
| 锁顺序 | 槽位 → bundle → 新事件 → 审计（与 DECIDE 同起点，避免死锁） |
| 唯一约束 | `UNIQUE(dispatched_adjudication_id)`（槽位至多一次派发）、`UNIQUE(new_outbox_id)`、`UNIQUE(session_id,event_type,op_seq)`、审计 `UNIQUE(...,phase)` |
| **CAS（六条件全部 `IS TRUE`）** | ① `final_phase='decided'` ∧ ② `final_decision='authorize_new'` ∧ ③ `dispatched_adjudication_id IS NULL` ∧ ④ `revoked_at IS NULL` ∧ ⑤ **`to_gen = current fence_gen`**（授权后 fence_gen 再变则旧授权自动失效） ∧ ⑥ 存在且仅存在一条 `phase='decided'` 审计记录（`final_adjudication_id` 可查，且 `NOT EXISTS phase='rejected'`） |
| 写入表 | 审计（INSERT dispatched）+ 槽位（UPDATE `dispatched_adjudication_id`）+ `cleanup_bundle`（INSERT）+ `object_outbox`（INSERT 新行）+ `adjudication_log` |
| 写入字段 | 审计：`phase='dispatched'`, `new_outbox_id`, `new_attempt_no`, `new_intent_id`；槽位：`dispatched_adjudication_id=:aid`；新事件行全部新身份（`outbox_id`/`bundle_id`/`request_id`/`idempotency_key` 均新，`attempt_no=旧+1`，`origin_outbox_id=旧 id`，`unresolved_request=true` 危险默认值） |
| 禁止修改字段 | **旧 `object_outbox` / `promotion_intents` 终局主行全部字段**；任何已存在审计记录；旧 `request_id`；槽位 `final_*` 字段 |
| COMMIT 边界 | **单事务**：dispatched 审计 + 槽位标记 + 新 bundle + 新事件行四者同生共死 |
| 重复请求 | 槽位 `dispatched_adjudication_id` 非空 → 0 行 + 幂等退出（查回新任务身份返回一致结构） |
| 并发冲突 | 两 DISPATCH 争同一槽位 `FOR UPDATE` → 一者赢；败者锁后重读发现已派发 → 0 行；`UNIQUE(new_outbox_id)` 兜底 |
| 崩溃恢复 | 提交前崩溃 → 四者皆无，重跑；提交成功 Worker 未收到响应 → 重放幂等退出 |
| 审计一致性 | dispatched 是**新 INSERT**，不 UPDATE 历史；`(outbox_id,from_gen,to_gen)` 可拉取完整链 |

> **「未被撤销的授权裁定」的精确定义（任务书 §3.2 第 6 点）**：`[推演]` append-only 审计表**不允许 UPDATE 已 decided 记录**，因此「撤销」以两种不改写历史的方式表达：① **事实失效** —— 授权记录绑定 `to_gen`，若 `fence_gen` 再推进（`to_gen ≠ current fence_gen`），DISPATCH CAS ⑤ 自动拒绝，旧授权永久保留但不可消费；新一代须重新 REGISTER/DECIDE（新键 `(outbox_id, G+1, G+2)`）；② **显式撤销** —— 在派发前由双人签核追加 `cross_gen_revocation` 审计记录并 UPDATE 槽位 `revoked_at`（槽位是可变状态表，不是审计记录），CAS ④ 拒绝后续 DISPATCH；已派发后不允许撤销（槽位 CHECK 保证）。两条都不修改任何已存在审计记录，满足任务书 §3.2 第 4/5 点。`[推演]` + `[待决策]`（撤销治理流程）

### 5.2 八项必须满足项逐一对照（任务书 §3.2）

| # | 要求 | 本轮落实 | 标签 |
|---|---|---|---|
| 1 | 同一 `(outbox_id,from_gen,to_gen)` 只能产生一个最终裁定 | 槽位 `FOR UPDATE` 串行 + `uq_cg_one_final_decision` 跨 phase 唯一 + `UNIQUE(final_adjudication_id)` | `[推演]` + `[待PG]` |
| 2 | 三种结果 `authorize_new`/`note_only`/`rejected` 互斥 | 统一为同一列 `decision` 的三个互斥取值（§4.2）；单条最终裁定记录 | `[推演]` |
| 3 | 两名操作员并发只允许一个成功 | 同一槽位行排他锁 → 败者锁后重读 0 行退出 | `[推演]` + `[待PG]` |

### 5.3 数据库约束本身能阻止矛盾裁定（完成标准 #2 的证明）

```
[推演] 令 K = (outbox_id, from_gen, to_gen)。
假设存在任意写入者 W（普通应用、旧 Worker、Reconciler、绕过槽位的迁移脚本、手误的 SQL），
试图使 K 下出现两条 phase ∈ ('decided','rejected') 的记录 R1、R2（可同 phase 或不同 phase）。
∵ 部分唯一索引 uq_cg_one_final_decision 的索引键恰为 K，谓词恰为 phase IN ('decided','rejected')
∴ R1 与 R2 在索引中映射到同一索引键 K
∴ 第二条 INSERT 必触发 unique_violation (SQLSTATE 23505)，该语句及所属事务回滚
∴ 在 DB 约束层，K 下最多一条最终裁定记录 —— 与 W 的身份、是否经过槽位、是否使用 ON CONFLICT 无关
前提：phase NOT NULL（§4.4 ③ 已显式复核），否则 NULL 行使谓词为 UNKNOWN 而不入索引 → 见 §4.4 ⚠️ 审查
例外：超级用户 DISABLE 索引 / ALTER INDEX ... INVALID / 直接改系统目录 —— V1.2.26 §6.2.3 已如实登记的固有旁路，本轮不宣称消除
```
> **结论**：`[推演]` + `[待PG]` 完成标准 #2 在**设计规格层满足**；实际索引行为（部分索引推断、`23505` 触发时机、并发 INSERT 的等待/报错顺序）须纯 PG 预演。**注意**：本证明只覆盖 PG 内部记录互斥，与 R2 外部副作用无关（§6 处理）。

## 6. T-REQUEUE 跨系统迟到请求分析

### 6.1 A / B / C 三类证据的严格定义（任务书 §4.1）

| 类 | 名称 | 定义 | 可证明什么 | **不可**证明什么 | 可授权动作 |
|---|---|---|---|---|---|
| **A** | 观察性证据（observational） | 在某一时刻 `t₀` 通过 HEAD/GET/List 未观察到对象或副作用 | 仅「在 `t₀` 的某次读取中未观察到」 | ① 读取自身的最终一致性（U-4 #7）；② `t₀` 之后是否出现；③ 在途请求是否已排队；④ 其他版本/元数据 | 仅记录，**不得**推进任何状态 |
| **B** | 回溯性证据（retrospective） | 证明**截至某时刻**该次请求未产生副作用（如 `explicit_failure` + `not_applied` + 请求身份绑定） | 「过去未发生（可观察范围内）」 | **未来不会生效**（C）；请求是否在服务端排队；预签名 URL 是否仍有效；旧 Worker 是否会重发 | 保持隔离；**不得**创建新 attempt |
| **C** | **终止性证据（terminality）** | 证明该**请求标识**在 R2 服务端已到达**不可反转的终态**，且所有可再次触发该副作用的通道（凭证、URL、Worker 进程、条件写）均已确定性关闭 | 「此后不可能再迟到生效」 | —— | **只有 C 成立**才可能允许新 attempt 执行（且仍须全部硬门禁） |

> **A ≠ B**：`[推演]` A 可以只是 `ListObjectsV2` / `ListMultipartUploads` 的**最终一致性滞后**（V1.2.22 §12 U-4 #7 原文「HEAD / GET / COPY 的一致性语义，含 `ListObjectsV2` / `ListMultipartUploads` 最终一致性」，L830）；B 至少要求把「未观察到」绑定到**具体请求身份**并说明观察方法，A 连这一点都没有。
> **B 不必然等于 C**：`[推演]` B 是**过去时**命题「截至 `t₀` 未生效」，C 是**将来时**命题「∀ t > t₀ 不会生效」。从前者推不出后者，除非存在服务端级的终止性保证（§6.2）。V1.2.27 §7.1 事实② 直接把 B 写成「可作为新 attempt 的安全前提」，是本轮判定的规格层错误。`[推演]`

### 6.2 什么证据能证明 C？——逐通道审查（任务书 §4.2）

> C 不是单个布尔值，而是**对下列 6 条通道逐一关闭**的合取命题：任一通道未关闭，C 即不成立。`[推演]`

| # | 通道 | 关闭该通道所需的可验证证据 | 当前状态 | 标签 |
|---|---|---|---|---|
| C1 | **服务端请求状态** | R2 提供按 `request_id` / 幂等键查询「该请求已终结且不会重试」的**确定性终态**（U-4 #11：幂等响应查询 / 服务端请求 ID / 结果可回放） | ❌ **未提供、未实测**；V1.2.22 §12 #11 原文「`copy_unknown` 无可靠取证路径 → 只能隔离」 | `[待R2]` |
| C2 | **服务端排队与迟到执行** | 证明超时后服务端**不会**继续处理已接收的请求（U-4 #10「超时后操作是否仍会落地」） | ❌ **不可证明**；V1.2.22 §5.4 L312 原文「无法由 PG 侧任何机制排除」 | `[待R2]` |
| C3 | **凭证 / 预签名 URL** | 确定性 TTL 上界 + 到期后不可再用（U-4 #13），桶策略条件前缀拒绝（U-4 #12） | ❌ 未实测；V1.2.20 §4.6 #5/#6 列为待实测 | `[待R2]` |

> **🔴 本轮核心结论（任务书 §4.2 明确要求的结论）**：`[推演]` + `[原文]` + `[待R2]`
> **Cloudflare R2 或现有协议没有提供足够的官方保证或真实测试证据能够证明 C1–C6 的合取成立。** 本轮**未查证任何新的官方文档**（§1 执行边界），上游唯一登记为「官方文档事实」的是 V1.2.20 §6.1 L320 的 Wrangler 删除警示，且明确注明「其与版本化开启时的交互未核实」；版本化、条件删除、`ListObjectVersions` 均为「未核实 / U-4 待核实」；U-4 十三条**一条未实测**（V1.2.26 §16.1 #6 / V1.2.27 §15.1 #6）。
> ∴ **`not_applied` 当前不足以授权 T-REQUEUE。** `not_applied` 在本轮被**降格为 B 类证据**，只能作为 `terminal_proof` 的一个输入，绝不能单独放行重排。`[推演]`

### 7.4 「保持隔离」是合法稳态而非状态无出口（任务书 §十一 #4）

| 当前状态 | 证据级别 | 允许操作 | 禁止操作 | 目标状态 | 标签 |
|---|---|---|---|---|---|
| `unknown/registered`（A 或更低） | A / `unresolved` | 保持隔离、只读取证、屏障 ABORT | 重试、跳过、重排、置 done、宣布静默 | 不变 | `[推演]` |
| `unknown/failed` + `non_applied_observed`（B） | B | 保持隔离 + 人工裁定 + 只读取证 | **重排**、跳过、置 done、把 `unresolved_request` 提前置 false | `recovery_phase` 保持 `requeue_eligible` 或转 `adjudication_pending` / `dead` | `[推演]` |
| `unknown/failed` + `terminal_proven`（C，**当前运行时不可达**） | C | **仅当**六通道全闭 + 全部硬门禁 → T-REQUEUE | 缺任一通道即重排 | 旧行 `requeued` + 新行 `scheduled/none`（仅设计规格） | `[推演]` + `[待R2]` |
| 证据矛盾 / 取证能力不可用 | B/A | 隔离 + `adjudication_pending` + 人工裁定 | 自动重试、自动跳过、自动重排 | 不变或 `dead_letter` | `[推演]` |
| 人工裁定「确无需执行」 | 需 C | T-SKIP 第二入口（保留 `failed` 相位 + EVENT-INV-4b） | 直接改 skipped、伪造 `none` 相位 | `skipped/failed` | `[推演]` + `[待决策]` |
| 人工裁定「不可恢复」 | 任意 | `recovery_phase='dead'` + `dead_letter` + 审计 | 改 `done`、覆盖历史、自动恢复 | 保持隔离 | `[推演]` |

> **状态无出口检查（任务书 §六 #14）**：`[推演]` `unknown/failed` 在本轮**仍有合法出口**：保持隔离（稳态）、人工裁定、死信、只读取证、以及**未来 C 成立后的受控重排**（规格保留，运行时阻断）。因此不构成「状态无合法出口」；同时满足任务书「不得为了让状态机有出口而降低安全条件」—— 我们没有降低，而是把「自动重排」这一出口**按证据条件关闭**，并明确隔离就是设计意图中的合法终点。`[推演]`

**§8.1.1 `abortSatisfied()` 跨代 OR 右支的本轮修正（设计级）**：
```sql
-- 在 V1.2.27 §6.6 基础上追加 to_gen 校验与撤销排除（全部 IS TRUE 收口）
AND ( (COALESCE(e.abort_evidence->>'fence_gen','-1') = :current_fence_gen)
      OR EXISTS (SELECT 1 FROM cross_gen_adjudication cg
                  JOIN cross_gen_decision_slot s
                    ON s.outbox_id = cg.outbox_id AND s.from_gen = cg.from_gen
                   AND s.to_gen   = cg.to_gen
                  WHERE cg.outbox_id = e.outbox_id
                    AND cg.from_gen = COALESCE((e.abort_evidence->>'fence_gen')::bigint,-1)
                    AND cg.to_gen   = :current_fence_gen            -- ★ 新增：排除失效授权
                    AND cg.phase = 'decided'
                    AND cg.decision IN ('authorize_new','note_only')
                    AND cg.settled_at IS NOT NULL
                    AND s.final_adjudication_id = cg.adjudication_id  -- ★ 新增：必须是唯一最终裁定
                    AND s.revoked_at IS NULL                          -- ★ 新增：排除已撤销
                 ) ) IS TRUE
```

**§8.2.1 EVENT-INV-10（本轮新增，`[待PG]`）**：
```
EVENT-INV-10  request_terminality 与 recovery_phase / terminal_proof 的组合约束
  ① request_terminality='terminal_proven'
        ⇒ (terminal_proof IS NOT NULL AND terminal_proof_at IS NOT NULL
           AND terminal_proof_by IS NOT NULL AND unresolved_request IS FALSE)
```

### 一句话总结

V1.2.28 对 V1.2.27 的三个 P1 做了**事务级对抗性复核**，确认两个新增 P0 阻断缺陷成立并给出设计规格层修正：**① P0-1** —— 证明 `UNIQUE(outbox_id,from_gen,to_gen,phase)` 中 `phase='decided'` 与 `'rejected'` 不互斥、`FOR SHARE` 共享锁 + 应用层 `NOT EXISTS` 构成**写偏斜**（V1.2.27 所称「一者赢」未被证明），改用**部分唯一索引 `uq_cg_one_final_decision` 跨 phase 硬互斥 + 独立 `cross_gen_decision_slot` 表 `FOR UPDATE` 串行 + 锁后重读 CAS + DISPATCH 六条件有效性校验**，使**数据库约束本身**即可阻止互相矛盾的最终裁定，且审计表仍严格 append-only、旧终局主行零变化；**② P0-2** —— 严格区分 A（时点观察）/B（过去未生效）/C（终止性）三类证据，逐通道核对 C1–C6 后明确结论「**`not_applied` 当前不足以授权 T-REQUEUE**」：`not_applied` 降为 B 类必要非充分条件，新增正交 `request_terminality` 三态与 `terminal_proof` 16 键结构，重排守卫升级为 `requestTerminalProven()` 六通道合取，**U-4 十三条一条未实测 → 守卫恒 FALSE → `unknown/failed` 保持隔离、不自动重排，人工裁定亦不得绕过**，并补齐旧 Worker 迟到**外部副作用**的只读检测/隔离/人工裁定策略（不宣称 PG 阻止了 R2）。另含三个 P1 逐事务复核、状态转换矩阵、13 项要素 × 全部事务总表、字段字典及唯一写入者、权限矩阵、终局免疫 12 操作覆盖、18 项新增故障注入（10 信息列）、19 项遗留阻断、16 项待决策、A/B 两种预演分开的 14 项准入复审。**六个新发现（3 项 P1 / 3 项 P2）如实登记，未隐瞒或降级**；完成标准 10 项在**设计规格层**全部满足，但 **四个准入等级一个都没有提升**：档 1 ⚠ 文档完整、供审阅、**设计审查未通过**；档 2 ❌ 不具备纯 PG 预演条件（11 项阻断，含本轮新增 3 类待验证 DB 对象）；档 3 ❌ 不具备 R2 集成预演条件；档 4 ❌ 不具备阶段 1B 条件。🔴 **旧请求终止性无法证明，按任务书 §十一 保留为独立技术阻断项，不以人工审批或文字承诺代替技术保证**。按要求只做静态设计与文档新增：**零 PG/R2 连接、零 SQL 执行、零 R2 API、零测试、零构建、零官方文档查证、零 Git 清理或暂存、零委派**；完成后立即停止，等待负责人独立审阅与明确授权，**不自动开启 V1.2.29**。
