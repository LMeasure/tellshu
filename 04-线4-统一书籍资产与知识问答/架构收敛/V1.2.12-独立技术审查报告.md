### F-01 ｜ P1 ｜ §3.2 / §3.6 ｜ idem_key UNIQUE 与删除后重传冲突

- **原文依据**：§3.2 `idem_key text UNIQUE`；§3.6「重复上传命中已 committed → 返回既有 object_id」。
- **故障场景**：对象已 `deleted`（行归档）后，用户重新上传同一文件（同 owner+sha256+purpose）→ 新插入的 `idem_key` 与已删行唯一约束冲突 → INSERT 失败或返回已删对象。
- **技术原因**：`idem_key UNIQUE` 跨所有行（含 `deleted`）生效，删除未释放该键；设计只考虑了"上传中命中 committed 去重"，未考虑"删除后再上传"。
- **影响**：用户删除私有书后无法重新导入同文件；或实现被迫复用已删行导致状态错乱。
- **修正建议**：`idem_key` 唯一约束仅覆盖活跃态（`pending_upload`/`committed`/`marked_deleted` 未物理删），或删除行时清空 `idem_key`；重传一律生成新行。
- **验收方法**：删除对象→同文件重传→新 `object_id` 创建成功，无唯一约束冲突。
- **状态**：未解决（V1.2.12 未覆盖）。

### F-02 ｜ P1 ｜ §4.5 ｜ 配额结算 UPDATE 未加 lease_token 围栏

- **原文依据**：§4.5 结算段 `UPDATE reservation SET actual_amount=?, status=succeeded; UPDATE resource_usage SET used=used-reserved+actual ...; UPDATE reservation SET status=settled` —— 三个 UPDATE **均无 `WHERE lease_token=:cur`**。
- **故障场景**：旧 Worker 失去租约后，仍可对 `reservation_id` 执行上述 UPDATE（无 lease 守卫）→ 将已接管任务标记为 succeeded/settled 并改写 `used`。
- **技术原因**：§4.7 声称"任何写须 `WHERE lease_token=:cur`"，但 §4.5 时序图未落实于结算语句；`resource_usage` 无 lease_token 列，结算 UPDATE 未与 reservation 的 lease 守卫同事务绑定。
- **影响**：旧 Worker 在接管后仍能写入结算结果 → 重复/错误计费、覆盖新 Worker 结果。
- **修正建议**：结算须为单事务，且 `UPDATE quota_reservations ... WHERE reservation_id=? AND lease_token=:cur`（0 行则中止）；`resource_usage` 的变更作为该事务内从属操作，经 reservation 的 lease 守卫间接保护；或把 `lease_token` 冗余到结算事务的校验。
- **验收方法**：注入"旧 Worker 租约过期后发结算"→ 其 UPDATE 影响 0 行，新 Worker 结算生效。
- **状态**：未解决（V1.2.12 自相矛盾：§4.7 要求 fence，§4.5 未执行）。

### F-03 ｜ P1 ｜ §4.7 / §4.8 ｜ release/refund 未失效 lease_token

- **原文依据**：§4.8「released（used-=reserved）」未提及清空 `lease_token`；§4.2 列 `lease_token` 但无"释放时置 NULL/重随机"规则。
- **故障场景**：任务失败→退款(released)，`lease_token` 仍保留旧值；若旧 Worker 随后提交结果，其 `WHERE reservation_id=? AND lease_token=:cur`（旧值仍匹配）→ 把 released 任务翻回 succeeded/settled → 重复扣费。
- **技术原因**：fencing 仅在"接管时覆盖 lease_token"，未规定"释放/退款时也失效"，导致已释放行的旧 token 仍可被陈旧 Write 命中。
- **影响**：退款后旧 Worker 仍可重结算 → 用户被二次扣费。
- **修正建议**：任何终态（released/settled/failed/dead）均须 `lease_token = NULL` 或重随机化；fence 判定同时要求 `status IN (reserved,running)`。
- **验收方法**：退款后旧 Worker 持旧 token 提交→0 行生效。
- **状态**：未解决。

### F-04 ｜ P1 ｜ §4.5 / §4.9 ｜ 部分消耗未持久化 → 重试重复计费

- **原文依据**：§4.9「Worker 在任务失败前已耗 Token/容量，写 actual_amount=已耗」；但 §4.5 仅把 `actual_amount` 写作"阶段写"，未定义崩溃前如何持久化中间消耗；LLM 调用本身发生在写库之前。
- **故障场景**：Worker 调用 LLM 消耗 30% Token 后崩溃，未写入 `actual_amount`；新 Worker 接管从头重跑 → 再耗 30%（总计 60%）。
- **技术原因**：部分消耗只在最终写盘，中途消耗无 append-only 消费日志；重试从零开始。
- **影响**：付费期实际 Token 双倍/多倍计费（免费期仅观测不扣，暂不影响，但付费期即资损）。
- **修正建议**：引入 `token_consumption_log(Reservation_id, seq, amount, created_at)`，边消费边追加；重试从该日志已记录额度续算，已记录的不再重计；或 LLM 结果按 `idem_key` 缓存复用。
- **验收方法**：注入"消耗 30% 后崩溃"→恢复后总消耗≈30% 而非 60%。
- **状态**：未解决。

### F-05 ｜ P1 ｜ §5.7 ｜ PG↔R2 恢复协调缺失

- **原文依据**：§5.7「PG 恢复到临时实例(PITR) → R2：从版本/冷备恢复缺失对象」；未定义 R2 如何对齐到同一时间点 T，也未定义"备份点之后新建的 R2 对象"如何处置。
- **故障场景**：PG 恢复到 T（PITR），但 R2 对象 O 创建于 T 之后且无对应 PG 行 → 对账（§3.10）判定"R2 有对象无 DB 行"→ 强制物理删 → **用户数据丢失**。反之 PG 有行 R2 缺 → orphaned 数据丢失。
- **技术原因**：R2 无事务日志/PITR，无法回滚到任意 T；PG PITR 与 R2 版本化是两个独立时间轴，无协调协议；对账只区分"有无行"不区分"是否备份点后合法创建"。
- **影响**：恢复即触发对备份点后合法对象的误删或孤儿丢失，且无法区分"合法新建"与"真孤儿"。
- **修正建议**：① 恢复进入**维护模式**禁止新写入；② 恢复后先以"创建时间 > 备份点 T"为窗口把 R2 对象暂存隔离（不立即删），人工/策略判定；③ 提供"R2 仅回滚到 T 的桶级快照"选项（牺牲 T 后写入）；④ 重建 Outbox/死信/配额终态（§5.8 须显式含此）。
- **验证方法**：构造"备份点后新建对象"，演练恢复→对象被隔离而非误删，且可选择性保留。
- **状态**：未解决（G8 设计仍不完整，不足以"可恢复"）。
- **对任务九的回答**：仅有 PG PITR + R2 版本控制**不足够**；缺协调时间轴、维护模式、恢复后 Outbox/账务重建、孤儿判定窗口。

### F-06 ｜ P1 ｜ §4.6 ｜ 重试 idem_key 稳定性未强制 → 配额可能双预留

- **原文依据**：§4.6「`quota_reservations.idem_key UNIQUE`；重复提交命中已 reserved → 返回既有」；但未规定客户端重试必须复用同一 `idem_key`，也未规定服务端以业务键(owner+resource+purpose)兜底去重。
- **故障场景**：客户端断网后用**新** idem_key 重试 → 新 reservation 行 → 双预留（`used` 双扣）。
- **技术原因**：去重仅依赖客户端遵守 idem_key 稳定，缺服务端业务键兜底。
- **影响**：网络抖动下用户被重复扣配额。
- **修正建议**：服务端以 `(user_id, resource_key, business_ref)` 做预留幂等查找，idem_key 仅作客户端关联；或预留创建前先 `SELECT ... WHERE business_ref=? AND status IN(reserved,running)`。
- **验收方法**：换 idem_key 重试→仅 1 条预留生效。
- **状态**：未解决（同 F-01 类，上传与配额两侧皆存在）。

### F-07 ｜ P1 ｜ §7.7 ｜ 账号注销未释放进行中 reservation/任务

- **原文依据**：§7.7 销号作业「user_objects 全量 marked_deleted；删 user_books 级联；删 app_users」。未提 `quota_reservations`/`convert_tasks` 中该用户的活跃行。
- **故障场景**：用户注销时存在 running 任务/未结算 reservation → 任务继续以已删 owner 运行、结算写入孤立 reservation。
- **技术原因**：销号只处理对象与书，未处理配额/任务终态。
- **影响**：孤立 reservation 长期占用额度统计、Worker 处理已删用户任务越权读。
- **修正建议**：销号前先把该用户所有 `reserved/running` reservation 置 `released`（释放 used），`convert_tasks` running 置 `failed` 并停止派发；再以 SECURITY DEFINER 执行对象/书清理。
- **验收方法**：注销时有 running 任务→任务终态化、used 释放、无孤儿 reservation。
- **状态**：未解决。

### F-08 ｜ P1 ｜ §7.3 ｜ Worker 经 GUC 提权风险（须强制 SECURITY DEFINER）

- **原文依据**：§7.3「Worker 读私有表须经 SECURITY DEFINER 函数按 owner_id 参数读，函数内不读 GUC；或 Worker 仅操作平台表」并标「【待验证】选其一」。
- **故障场景**：若实现误用 GUC 为 Worker 设 `app.current_user_id`（任意角色可 `set_config`），Worker 可置任意 owner → 跨用户读私有数据。
- **技术原因**：GUC 非认证机制（审计已确认），Worker 用 GUC 即越权；方案留"二选一"未钉死。
- **影响**：Worker 角色可遍历所有用户数据。
- **修正建议**：**强制** Worker 一律经 SECURITY DEFINER 按 `owner_id` 参数访问，禁止 Worker 会话设 GUC；代码层禁用 `SET app.current_user_id` 于 Worker 路径（CI 断言）。
- **验收方法**：静态扫描 Worker 代码无 `SET ...current_user_id`；越权读测试返回 0 行。
- **状态**：部分解决（方向正确，须钉死实现约束）。

### F-09 ｜ P1 ｜ §7.2 ｜ 连接池模式须钉死事务模式

- **原文依据**：§7.2「连接池设为事务模式；中间件用 SET LOCAL（事务结束自动清除）；会话模式须 reset 钩子」。
- **故障场景**：若实际为会话模式且 reset 钩子缺失 → 请求 A 设 GUC=用户甲，连接复用给请求 B 时 GUC 残留甲 → B 以甲身份读写。
- **技术原因**：`SET LOCAL` 仅事务模式安全；会话模式需显式重置，设计留"若…则"未强制。
- **影响**：跨请求身份残留 → 越权。
- **修正建议**：部署强制 PgBouncer `pool_mode=transaction`；并在 CI/配置断言；若必须会话模式，连接 checkout 强制 `RESET app.current_user_id`。
- **验收方法**：并发混合用户请求压测，断言无跨用户行泄漏。
- **状态**：部分解决（须部署层钉死）。

### F-10 ｜ P2 ｜ §3.2 ｜ user_objects 复合 FK 偏差

- **原文依据**：§3.2「owner_id 走复合 FK」但字段仅 `owner_id uuid NOT NULL REFERENCES app_users(sub)`，无父表 (id,owner_id) 可挂复合 FK；与收敛稿 §三.2 双列 NOT NULL 复合 FK 规则不一致。
- **故障场景**：对象表无法用复合 FK 防跨用户引用（隔离仅赖 RLS + key 前缀）。
- **技术原因**：对象以 `owner_id` 单列 + key 前缀 `<owner_id>/` 标识，复合 FK 无合适父表。
- **影响**：一致性表述矛盾；隔离正确性依赖 RLS 正确（须 G3 验收覆盖）。
- **修正建议**：明确 user_objects 不套用复合 FK（无父表），隔离由 RLS + 服务端 key 前缀强校验保证；在文档中消除"走复合 FK"措辞。
- **验收方法**：文档措辞一致；RLS 测试覆盖。
- **状态**：部分解决（功能可接受，表述待修）。

### F-11 ｜ P2 ｜ §3.10 ｜ 对账 TOCTOU 须显式排除中间态

- **原文依据**：§3.10「R2 有对象但无对应 user_objects 行 → 孤儿」未排除 `pending_upload`/`aborted` 过程态（上传中 R2 已有对象但行未 committed）。
- **故障场景**：对账扫描时恰逢上传进行中 → 误判在途对象为孤儿 → 删除（与 §3.4a 顺序冲突）。
- **技术原因**：对账只判"有无行"，未排除非终态行。
- **影响**：并发上传中的对象被误删。
- **修正建议**：对账仅对 `committed`/`marked_deleted` 行做 R2 校验；`pending_upload`/`aborted` 行若对应 R2 对象由回收扫描（按 expires_at）处理，不归入孤儿删除。
- **验收方法**：上传进行中被对账→不删。
- **状态**：未解决（易补）。

### F-12 ｜ P2 ｜ §3.5 ｜ Outbox 同事务仅覆盖删除路径（上传无 Outbox）

### F-14 ｜ P2 ｜ §7.9 ｜ RLS 回退须预部署双策略

- **原文依据**：§7.9「引入 app.rls_strict 开关，异常切宽松审计模式（仍 ENABLE）」+「固化已知良好回退策略」。

### F-15 ｜ P2 ｜ §4.10 / §3.10 ｜ 死信安全重放协议缺失

- **原文依据**：§4.10 `quota_dead_letter`、§3.10 `object_dead_letter` 仅"人工介入"，无重放协议。

## 六、最终结论（回答任务书七问）

1. **P0-1 是否真正达到设计闭环？** —— **否（部分解决）**。V1.2.12 在状态机/Outbox/tombstone/对账/签名 URL 上给出完整设计，但对抗推演暴露 **F-01（删除后重传 idem 冲突）、F-05（PG↔R2 恢复协调缺失）、F-11（对账 TOCTOU）** 三项 P1 缺口，且其本身标注【待验证】。故 P0-1 **未闭环**，降为"设计完整但有 P1 残留 + 待验证"。

2. **P0-3 是否真正达到设计闭环？** —— **否（部分解决）**。核心原子计数与 idem 保留完好，但 **F-02（结算 UPDATE 未加 lease fence，且 §4.5 与 §4.7 自相矛盾）、F-03（退款未失效 lease→旧 Worker 可重结算）、F-04（部分消耗未持久化→重试双计费）、F-06（重试换 idem→双预留）** 四项 P1 缺口，使"全流程无重复扣/无幽灵计数/无丢失"的承诺**未能在设计中坐实**。P0-3 未闭环。

3. **G8 是否达到可恢复、可验证的备份设计标准？** —— **部分达到**。备份范围/频率/加密/演练门禁齐备，但 **F-05（PG↔R2 恢复协调缺失）** 使"仅有 PG PITR + R2 版本控制不足够"——恢复会误删备份点后合法对象或丢失孤儿，且 §5.8 未含 Outbox/死信/账务重建。G8 仍不足以宣告"可恢复"。

4. **V1.2.12 是否存在新的 P0 风险？** —— 原三项 P0 **未关闭**（降为 P1 残留）。本轮审查发现的 **最高严重级为 P1**（F-01~F-09）；其中 **F-05 在真实恢复场景会升级为 P0（恢复即误删用户数据）**，F-02/F-03/F-04 在付费期会造成资损。即：**无独立新增的"已激活 P0"，但原 P0 均未闭环，且 F-05 构成恢复路径的 P0 级隐患。**

5. **是否存在状态机竞态或循环依赖？** —— **无循环依赖**（门禁链线性）。**存在竞态**：F-01（idem 重传）、F-02/F-03（lease 未在结算/释放处围栏）、F-04（部分消耗）、F-11（对账 TOCTOU）。均须在设计定稿前修补。

6. **是否可以进入负责人决策阶段？** —— **可以**。V1.2.12 已把审计 P0/P1 转化为可裁定事项（D1–D7、Q15–Q28、N1–N8、U1–U8），设计成熟度满足负责人审阅与裁定条件。此"决策阶段"≠"实施阶段"。

7. **是否可以进入阶段 1B 实施？** —— **不可以**。理由：① P0-1/P0-3/G8 均未闭环（残留 P1 + 待验证）；② F-01~F-09 须先修补并经理预演/注入（门禁 8/9/10）；③ 负责人决策（门禁 2）未下达；④ R2 未开通、临时库未就绪。须负责人先裁定，再授权预演，预演通过后防线方可进入实施。
