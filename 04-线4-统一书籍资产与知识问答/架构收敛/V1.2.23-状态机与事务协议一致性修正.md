## 3. V1.2.22 七项缺陷复现（基于原始文本，逐条定位）

### 3.1 V23-01｜`call_issued` 混淆意图持久化与请求实际发出（P1）

| 位置 | 原文（摘录） | 隐含语义 |
|---|---|---|
| V1.2.22 §7.4 L518–524（T-A 伪 SQL） | `INSERT INTO promotion_intents(... lease_expires_at, call_issued) VALUES (..., true)`；注释「T-A：发起前，独立提交『COPY 已发起』这一 PG 事实」 | 意图创建时即宣称「请求已发出」 |
| V1.2.22 §7.1 L447 | 「在向 R2 发出任何 COPY 请求**之前**，先…持久化『COPY 已发起』这一事实」 | 同上 |
| V1.2.22 §5.4 L284 | `call_issued boolean NOT NULL DEFAULT false -- 「是否已向 R2 发出请求」` | 布尔 = 请求是否已发出 |
| V1.2.22 §8.3 场景 B L634 | `copy_issued`（**`call_issued=false`**）；「`call_issued=false` 且无请求日志 → 确定未发 → 由新 Worker 发 COPY」 | 布尔 = 确定未发，允许重发 |
| V1.2.22 §5.2 #5 L248 | 「崩溃点在『认领后、发请求前』且 `call_issued=false` 已先行提交 → 退回 `scheduled`」 | 同上 |
| V1.2.22 §11 用例 #2/#3 L794–795 | `copy_issued`，`call_issued=false` → 新 Worker 发 COPY | 同上 |
| V1.2.22 §11 用例 #4 L796 | `copy_issued`，`call_issued=true` → `copy_unknown` | 布尔 = 已发 |

> **矛盾（静态推演）**：T-A 在**任何 R2 请求发出之前**就写 `call_issued=true`；而恢复章节把 `call_issued=false` 当作「可证明请求从未发出」并据此**安全重发 COPY**。同一字段在写入侧表示「意图已提交」、在读取侧表示「请求已发出」，两者不等价。
> - 若按 T-A（恒 `true`）：所有「意图已提交但请求未发」的崩溃被误判为 `copy_unknown`，自动恢复率被压低（**保守但安全**）。
> - 若按恢复章节（T-A 写 `false`、发请求前再置 `true`）：**「发请求」与「置 true」之间必然存在崩溃窗口**，此时 `false` 但 R2 请求可能已落地 → 恢复者按「确定未发」重发 COPY → 覆盖副作用。这正是 V1.2.18 §6.1 **D-1**「两步独立 UPDATE 崩溃窗口 + 无 `unknown` 状态」在对象存储域的复现，V1.2.22 自称已闭合但**换了个位置重新引入**。
> **根因**：一个布尔无法同时表达「意图是否持久化」「请求是否可能已发出」「结果是否已确认」三个概念，且「实际发出」这一瞬间**无法与 PG 写入原子绑定**。

> **矛盾（静态推演）**：不可逆终态不能同时承担「暂停等待」。若冻结时置 `skipped`，DRAIN 后重排必然违反「终态不可逆」；若遵守终态，则冻结时被跳过的清理动作**永久丢失**（temp 永远不清），且屏障误以为「已收敛」。此外 §5.2 #4 把「删除契约冻结 gate 拒绝」也列为 `skipped` 条件，混淆「确实无需执行」与「当前不可执行」。

| 位置 | 原文 |
|---|---|
| V1.2.22 §7.4 L515–517 | `CREATE UNIQUE INDEX uq_one_inflight_copy ON promotion_intents(sha256) WHERE state IN ('copy_issued','copy_confirmed','copy_unknown');` |

| V1.2.22 §7.3 L501 | 「`intent_id` UUIDv4 幂等；`(sha256, attempt_no)` UNIQUE」 |

> **不一致（静态推演）**：`ON CONFLICT (sha256, attempt_no)` 的推断目标是 `(sha256, attempt_no)` 上的唯一约束，**不带谓词**；而 `uq_one_inflight_copy` 是 `(sha256)` 上的**部分唯一索引**。PostgreSQL 的 `ON CONFLICT` 不会把「部分唯一索引冲突」归到 `(sha256, attempt_no)` 目标下（部分索引须在冲突目标中带相同 `WHERE` 谓词才可被推断）。因此**同一 sha256、不同 `attempt_no` 的并发 Promotion**（L506 明确允许的重试路径）会触发 `uq_one_inflight_copy` 抛出 `unique_violation`，而 `DO NOTHING` 不生效 → 事务整体失败、无明确处置、无「读取现有行并验证」的入口。任务书 §8 要求逐场景分析并明确「哪些必须读取并验证现有行、哪些必须拒绝创建新 attempt」，且**不得通过删除唯一约束掩盖冲突**。

## 4. V23-01：`call_issued` 语义修正

### 4.1 三个必须分离的语义（不得再用一个布尔混合）

| # | 语义 | 定义 | 可原子确定？ | 本轮持久载体 |
|---|---|---|---|---|
| 1 | **`intent_committed`** | PG 已提交「本次操作的意图」（要做什么、对哪个 key、哪个 attempt、哪个 gen） | ✅ 是（T-A `COMMIT` 即确定） | `promotion_intents.intent_id` 存在 + `state` + `intent_committed_at` |
| 2 | **`request_may_have_been_sent`** | 请求**可能已经离开本进程**；其真实结果可能已在 R2 落地 | ❌ **否** —— 「实际发出」那一瞬无法与 PG 写入原子绑定 | `request_phase='registered'` + `request_id` + `request_registered_at` + `request_lease_epoch` |
| 3 | **`result_confirmed`** | 已取得足够证据确认操作结果（须满足 §9 `copyConfirmed()`） | ✅ 是，但**依赖 U-4 能力** | `result_evidence` + `evidence_level` + `result_confirmed_at` |

**核心设计：不试图精确记录「请求已发出」，而是记录「从这一刻起不再能证明请求未发出」。**

```
T-A   COMMIT  → intent_committed = true, request_phase = 'none'
T-B0  COMMIT  → request_phase = 'registered'（预登记请求凭证）
                 ★ 该提交发生在【任何 R2 请求发出之前】
T-B   发 R2 请求（PG 之外，非事务）
T-R   COMMIT  → result_confirmed / unknown / failed
```

> **为什么这消除崩溃窗口**：请求发出 ⟹ T-B0 已提交（单向蕴含，因为协议强制「先 T-B0、后 T-B」）；反之不成立（T-B0 已提交但请求可能还没发）。因此恢复者看到 `request_phase='registered'` 时，**必须按「可能已发出」处理**，永远不会把「已发出」误判为「确定未发」。代价是「预登记已提交但请求实际未发」被保守归入 `unknown`（B 类），**这正是正确的 fail-closed 方向**；任务书 §3.3 明确「不得为了提高自动恢复率，把未知状态转换成可重试状态」。

**字段设计（设计级，不执行）**：

```
promotion_intents 增补/替换列:
  intent_committed_at   timestamptz NOT NULL      -- T-A COMMIT 时刻
  request_phase  text NOT NULL DEFAULT 'none'
      CHECK (request_phase IN ('none','registered','resolved','unknown','failed'))
  request_id            uuid                      -- T-B0 生成，幂等请求凭证
  request_registered_at timestamptz
  request_lease_epoch   bigint
  result_evidence       jsonb
  result_confirmed_at   timestamptz
  unresolved_request    boolean NOT NULL DEFAULT false  -- 供静默屏障/死信检查
  CHECK (request_phase <> 'none' OR request_id IS NULL)  -- none 时不得有请求凭证
  CHECK (request_phase <> 'registered' OR request_id IS NOT NULL)
```
> **`call_issued` 布尔列在本轮设计中被废弃**；V1.2.22 §5.4 L284 / §7.4 L521 的该字段登记为需后续统一修订的既有条目（§13.3），本轮不修改原文。Reaper 的 `object_outbox` 采用**同一套 `request_phase`/`request_id`/`unresolved_request` 字段**（§4.5）。

### 4.2 八个崩溃/并发场景（逐场：三语义取值 → 可证明什么 → 处置）

| # | 场景 | `intent_committed` | `request_may_have_been_sent` | `result_confirmed` | 恢复者可证明 | 允许动作 | 禁止动作 | 类别 |
|---|---|---|---|---|---|---|---|---|
| 1 | **意图提交前崩溃** | ✗（无 intent 行） | ✗ | ✗ | 「从未发起」确定 | 重新走 T-A（新 `intent_id`）→ T-B0 → T-B | ❌ 领养；❌ 置 `committed` | **A 自动恢复** |
| 2 | **意图提交后、调用 R2 前崩溃** | ✓ | ✗（`request_phase='none'`） | ✗ | T-B0 未提交 ⟹ 请求**确定未发** | 保持同一 `intent_id`，新 Worker 走 T-B0 → T-B | ❌ 新建第二条意图；❌ 复位 `pending` 当「首次登记」 | **A 自动恢复** |
| 3 | **请求发送过程中崩溃** | ✓ | ✓（`registered`） | ✗ | **无法证明请求未发出** | 强制 `copy_unknown`（P3）→ §9 证据恢复 | ❌ 自动重发 COPY；❌ 假定失败 | **B 结果未知** |
| 4 | **R2 成功但响应丢失** | ✓ | ✓ | ✗ | 同上；canonical 可能已存在 | E1/E2/E3 取证；`copyConfirmed()` 为真 → T-C1/T-C2；不足 → 隔离 | ❌ 重复 COPY「试一试」；❌ HEAD 存在性当校验 | **B → A/C** |
| 5 | **R2 失败但响应丢失** | ✓ | ✓ | ✗ | 同上（**不能当失败**） | 同 #4；只有 `result_evidence` 明确证明「失败且未生效」才可 P4 | ❌ 归 `copy_failed_retry` 后自动重发 | **B → C** |
| 6 | **请求超时但 R2 可能仍在执行** | ✓ | ✓ | ✗ | 同上，且 R2 侧可能仍在飞 | `copy_unknown`；等待可验证结果或隔离；`unresolved_request=true` | ❌ 自动重试；❌ 宣布静默成立 | **B/C** |
| 7 | **Worker lease 过期、旧 Worker 仍在执行** | ✓ | ✓ | ✗ | 新 `lease_epoch` 有效；旧回写 CAS 0 行；**R2 请求不受 PG lease 约束** | 丢弃旧回写；`copy_unknown` + 证据比对 | ❌ 宣称「lease 过期 = R2 操作已停止」；❌ 新 Worker 自动重发 | **B/C** |

### 4.3 安全规则（核心，逐类明确）

> **核心规则**：**无法证明请求未发出时，不得按「尚未执行」自动重发可能产生覆盖副作用的 COPY。**

| 状态组合 | 可安全重试？ | 必须 `copy_unknown`？ | 必须隔离？ | 只能靠 U-4 能力恢复？ |
|---|---|---|---|---|
| `request_phase='none'`（意图已提交、预登记未提交） | ✅ **是**（A 类，同 `intent_id` 走 T-B0） | 否 | 否 | 否 |
| `registered` ∧ `result_evidence` 满足 `copyConfirmed()` | ✅ 是（幂等重放 T-C1/T-C2，**零 R2 写**） | 否 | 否 | 证据本身依赖 U-4 |
| `registered` ∧ 明确「失败且未生效」证据 | ✅ **受限是**（P4 受控重试，须证前次未生效） | 否 | 否 | ✅ **是**（须 U-4 #1/#11 证明前次未落地） |
| `registered` ∧ 无结果 / 超时 / 断连 / 5xx / 响应丢失 | ❌ **否** | ✅ **是** | 视取证 | 取证依赖 U-4 |
| `registered` ∧ 证据矛盾 / 版本或 gen 漂移 / 旧 Worker 迟到成功 | ❌ 否 | — | ✅ **是**（C 类） | 裁定依赖 U-4 |
| `copyConfirmed()` 中任一 U-4 依赖项为 `unknown` | ❌ 否 | ✅ **唯一安全结果 = `copy_unknown`** | ✅ 证据不足时隔离 | ✅ 是 |
| `request_phase='registered'` ∧ R2 能力不可用（无法取证） | ❌ 否 | ✅ 是 | ✅ **是** | ✅ 是 |

**禁止**：❌ 不得把「超时」转换成「可重试」；❌ 不得把 `unknown` 自动升级为 `copy_confirmed`；❌ 不得为提高自动恢复率放宽上述任一条件；❌ 不得把 `result_evidence` 的「若可得」写成默认可得。

### 4.4 与 V1.2.18 D-1 的闭合证明（静态推演）

V1.2.18 §6.1 L149 的原缺陷是「发出外部调用」与「置 `call_issued=true`」为**两步独立 UPDATE**，崩溃窗口内 `false` 但外部可能已执行。本轮把顺序改为**「先提交预登记（T-B0），再发请求」**，使 `call_issued=false` 的等价语义（`request_phase='none'`）**只可能出现在请求发出之前**；请求一旦可能发出，`registered` 已是已提交事实。窗口不再指向错误方向。此为静态时序推演，**未在任何 PG 实例验证**。

### 4.5 Reaper 的同一语义原则，但不假定 COPY 与 DELETE/ABORT 幂等性质相同

| 维度 | COPY（Promotion） | DELETE temp / ABORT MPU（Reaper） |
|---|---|---|
| `request_phase` 三语义 | ✅ **完全同一套**（意图提交 / 请求预登记 / 结果确认） | ✅ 同一套 |
| 副作用性质 | **覆盖性写**：同 key 可能产生新 VersionId、覆盖 `metadata.gen`、复活已删除内容（V1.2.21 §5.1） | **收敛性操作**：目标是「对象不存在」/「UploadId 不可再用」；但**仍可能误删被旧预签名 URL 写回的同 key 新对象**（V1.2.22 §5.4 L312） |
| `registered` ∧ 结果未知 | 强制 `copy_unknown`；**禁止重发** | 强制 `unknown`；**禁止自动重发 DELETE/ABORT** |
| 可用取证手段 | E1 幂等响应查询 / E2 版本元数据枚举 / E3 内容 SHA-256（**全部 U-4**） | **只读枚举复核**：`ListObjectsV2(prefix='uploads/{sid}/')` 为空、`ListMultipartUploads(prefix='uploads/')` 无该 UploadId（**枚举一致性 U-4 #7/#8**） |
| 若可证目标状态已达 | 走 T-C1/T-C2 重放（纯 PG） | 可置 `done`（记 `result_evidence`），**不重发请求** |
| 共同禁止 | ❌ 不得因「操作天然幂等」把 `unknown` 降级为可重试；❌ 不得把 `NoSuchUpload`/404 当作「清理已完成」（V1.2.22 §5.5/§5.6） | 同左 |

> **明确声明**：COPY 与 DELETE/ABORT 的 R2 幂等性质**不同**，二者的结果证据谓词分别定义（§9 `copyConfirmed()` vs §6 `FINAL_VERIFY`），**不共用、不互相套用**。V1.2.22 §5.4 L307 已把「no-op」与「目标状态已确认」区分，本轮沿用并强化。

> **本章成熟度**：`设计已提出 + 状态机推演 + 并发时序推演`。三语义字段、T-B0 顺序、八场景均为静态推演；**未连接 PG、未连接 R2、未验证任何请求日志持久化能力**。

## 5. V23-02：Reaper 状态机与冻结处理

### 5.1 六个语义必须分离

| 语义 | 本轮载体 | 说明 |
|---|---|---|
| **暂停** | `deferred`（非终态） | 操作意图完整保留（`idempotency_key` / `attempts` / `request_phase` / `depends_on` 全部不丢），等待条件解除 |
| **释放 lease** | 动作，不是终点 | `lease_owner=NULL` + `lease_expires_at=NULL` + `lease_epoch+1`；事件回到 `deferred` 或 `scheduled` |
| **等待冻结解除** | `deferred` 的守卫 | `freeze_outbox=false` ∧ `fence_gen` CAS 一致 ∧ 重新取得 lease |
| **已确认无需执行** | `skipped`（**不可逆终态**） | 仅此一义；`skip_reason` 必填且须附可验证证据 |
| **已执行完成** | `done`（**不可逆终态**） | 全部必需动作 + 只读复核 + `result_evidence` 落库 + 回写 CAS 成功 |
| **结果未知** | `unknown`（非终态） | `request_phase='registered'` ∧ 结果不可判定；禁止自动重试 |

**新增 `leased` 的意义**（任务书 §4.2 明确要求覆盖）：把「Worker 已取得 lease 但**尚未预登记请求**」独立成状态。这是**唯一可证明「请求确定未发出」的持有态**，因此也是唯一可安全暂停/安全重试的持有态。`in_flight` 专指 `request_phase='registered'` 之后（请求可能已发出）。

### 5.2 完整状态转换表

| 当前状态 | 触发事件 | 下一状态 | 是否终态 | 是否允许重试 | 备注 |
|---|---|---|---|---|---|
| `pending` | 调度器 CAS 生成事件（会话终态、超 grace、`freeze_outbox=false`、fence_gen 匹配） | `scheduled` | 否 | 不适用 | 事件入队，零 R2 副作用 |
| `scheduled` | Worker lease CAS 成功（`lease_epoch+1`，`request_phase='none'`） | `leased` | 否 | ✅ 是 | 最后一处「可证明未发」 |
| `leased` | T-B0 预登记提交（`request_phase='registered'`） | `in_flight` | 否 | ❌ **否** | 此后禁止自动重试 |
| `leased` | 执行期重验判定**确实无需执行**（证据可证） | `skipped` | **是** | ❌ 否 | `skip_reason` 必填 |
| `leased` | **冻结生效 / `freeze_outbox=true`** | **`deferred`** | 否 | ✅（解冻后可重试） | **保留意图、释放 lease**；修复 V23-02 |
| `leased` | lease 过期且 `request_phase='none'` | `scheduled`（`lease_epoch+1`） | 否 | ✅ 是 | 可证明未发，旧 Worker 被 fencing |
| `leased` | 删除契约 gate 拒绝 / 前置依赖未 done | `deferred` | 否 | ✅ | 属「当前不可执行」，**不是 skipped** |
| `in_flight` | 全部必需动作成功 + 只读复核通过 + 回写 CAS 成功 | `done` | **是** | ❌ 否 | 写入 `result_evidence` |
| `in_flight` | 超时 / 断连 / 5xx / 响应丢失 / Worker 崩溃 / lease 过期 | `unknown` | 否 | ❌ **否** | `unresolved_request=true`；走 §4.5 取证 |
| `in_flight` | **冻结生效 / `freeze_outbox=true`** | **`unknown`**（不是 `skipped`） | 否 | ❌ 否 | 请求可能已发出，必须等可验证结果 |
| `in_flight` | 明确可证「确实无需执行」 | `skipped` | **是** | ❌ 否 | 需证据，非失败兜底 |
| `unknown` | 证据恢复确认已完成 / 确认无需执行 | `done` / `skipped` | 是 | ❌ 否 | 裁定留审计 |
| `unknown` | 证据不足 / 矛盾 / 取证能力不可用 | `dead_letter` | 否（须人工裁定） | ❌ 否 | `unresolved_request` 保持 true 直至裁定 |
| `deferred` | `freeze_outbox=false` ∧ fence_gen CAS 一致 ∧ 重新取得 lease | `leased` | 否 | ✅ 是 | **只恢复可证明安全的状态** |
| `deferred` | 人工裁定确实无需执行 | `skipped` | 是 | ❌ 否 | 留审计 |
| `dead_letter` | 人工裁定（附审计记录） | `done` / `skipped` / 保持 | 视裁定 | ❌ 否 | 不得自动转终态 |
| `done` | 任何事件（重放 / Reconciler / 重试） | `done`（幂等退出） | **是** | ❌ 否 | 不可逆 |
| `skipped` | 任何事件 | `skipped`（幂等退出） | **是** | ❌ 否 | 不可逆，**不承担暂停语义** |

> **禁止 `in_flight → pending`**（沿用 V1.2.22 §5.2 #7）；**禁止 `skipped → 任何非终态`**（本轮新增，直接闭合 V23-02）。

### 5.3 `done` / `skipped` 的终态语义（唯一定义）

- **`done`**：本事件的所有必需动作均有可判定结果、必要的只读复核通过、`result_evidence` 已落库、回写 CAS 成功。仅表示该事件的清理动作已确认，**不表示 R2 全局无残留**（V1.2.22 §5.2 #8 沿用）。
- **`skipped`**：经可验证证据确认**确实无需执行**（例如目标已由他者幂等完成且可归因、会话已被他者推进、删除契约 gate 明确判定该动作不在合法路径）。**不含**暂停、延期、冻结等待、失败、未知。`skip_reason` 与各条证据必填。
- 二者**均不可逆**，不因重试、重放、Reconciler 扫描、冻结解除而改变。

### 5.4 `dead_letter` 的三条硬约束

1. **`dead_letter` 不等于 R2 操作已经停止**：可能仍有 `request_phase='registered'` 且 `unresolved_request=true` 的迟到请求在 R2 飞行。死信只表示「自动恢复失败」，不表示跨系统副作用收敛。
2. **`dead_letter` 不默认满足备份静默屏障**：§8.4 的 `canEnterSilentWindow()` 必须显式检查 `COUNT(* WHERE status='dead_letter' AND unresolved_request=true) = 0`；仅当人工裁定并把 `unresolved_request=false` 且留审计后，才可在屏障中视为已收敛。
3. **不得把 `dead_letter` 静默当作 `done`**，不得无限自动重试。

### 5.5 冻结期间四类处理（任务书 §4.3）

| 类 | 判据 | 状态转换 | 允许动作 | 禁止动作 |
|---|---|---|---|---|
| **A. R2 请求尚未发出** | `status='leased'` ∧ `request_phase='none'`（或 `scheduled`/`pending`/`deferred`） | → **`deferred`**，释放 lease（`lease_epoch+1`），**保留操作意图与全部依赖字段** | 保留 `idempotency_key`、`depends_on`、`attempts`、bundle 关系；等待解冻 | ❌ 置 `skipped`；❌ 丢弃事件；❌ 复位 `pending` |
| **B. R2 请求可能已经发出** | `status='in_flight'` ∧ `request_phase='registered'`，或 `unknown` | → **`unknown`**（`unresolved_request=true`） | 等待可验证结果 / §4.5 只读取证 | ❌ 置 `skipped`；❌ 释放后自动重排；❌ 自动重发 DELETE/ABORT；❌ 宣布静默成立 |
| **C. R2 操作已确认完成** | 全部成功判据 + 复核通过 + CAS 回写成功 | → **`done`** | 记录 `result_evidence` | ❌ 重复执行动作 |
| **D. 确实无需执行** | 可验证证据确认目标已达成 / 动作不在合法路径 | → **`skipped`**（`skip_reason` + 证据） | 幂等退出 | ❌ 把失败/超时/未知归入此类 |

**冻结解除后只能恢复可证明安全的状态**：仅 `deferred` ∧ `request_phase='none'` ∧ `fence_gen` 与冻结前 CAS 一致 ∧ 重新通过 lease CAS 取得所有权 → `leased`。`in_flight` / `unknown` / `dead_letter` / `done` / `skipped` **一律不因解冻而自动改变**；`unknown`/`dead_letter` 须走证据恢复或人工裁定。

> **本章成熟度**：`设计已提出 + 状态机推演`。状态表与冻结分类为静态规格，**未在任何 PG 实例求值、未连接 R2**。

## 6. V23-03：Abort → Delete → FINAL_VERIFY 强制事件依赖

### 6.1 采用的机制（明确选型）

> **本轮采用「数据库级事件依赖（主） + 会话级聚合清理任务 `cleanup_bundle`（辅）」的组合协议**，理由：① 单纯 `op_seq` 只是编号不是约束（任务书 §5.3 明确指出不足）；② 数据库级 `depends_on` + 领取 SQL 的 `NOT EXISTS` 双条件可**证明先后关系**并直接阻止多 Worker 越阶；③ 聚合 bundle 保证「Abort 完成时才创建 Delete」不会引入「Abort done 但 Delete 事件尚未创建」的崩溃窗口，并保证三事件同属一个逻辑清理批次、共享 `fence_gen`。

**不采用**：仅靠 `op_seq` 排序、仅靠应用层顺序调用、仅靠 `freeze_outbox` 门控（都不构成可证明的先后约束）。

### 6.2 结构（设计级 DDL，不执行）

```
cleanup_bundle（会话级聚合）:
  bundle_id     uuid PRIMARY KEY
  session_id    uuid NOT NULL
  fence_gen     bigint NOT NULL
  state         text NOT NULL CHECK IN ('open','abort_done','delete_done','verified','quarantined')
  created_at    timestamptz NOT NULL DEFAULT now()
  -- 设计级部分唯一索引：同一会话至多一个未收敛 bundle
  CREATE UNIQUE INDEX uq_one_active_bundle ON cleanup_bundle(session_id)
    WHERE state <> 'verified';

object_outbox 增补列:
  bundle_id              uuid NOT NULL REFERENCES cleanup_bundle(bundle_id)
  event_type  text NOT NULL CHECK IN ('ABORT_MPU','CLEANUP_TEMP','FINAL_VERIFY')
  step_no     smallint NOT NULL CHECK IN (1,2,3)
  depends_on_outbox_id   uuid NULL REFERENCES object_outbox(outbox_id)
  request_phase / request_id / unresolved_request / lease_epoch / status / result_evidence ...
  UNIQUE (bundle_id, event_type, step_no)      -- 复合幂等键，沿用 V1.2.22 §5.3 并加 bundle 维度
  CHECK ( (event_type='ABORT_MPU'     AND step_no=1 AND depends_on_outbox_id IS NULL)
       OR (event_type='CLEANUP_TEMP'  AND step_no=2 AND depends_on_outbox_id IS NOT NULL)
       OR (event_type='FINAL_VERIFY'  AND step_no=3 AND depends_on_outbox_id IS NOT NULL) )
```

### 6.3 强制依赖的实际领取 SQL（多 Worker 并发防越阶，设计级伪代码不执行）

```sql
-- Worker 领取「当前可执行的最小 step」事件；单事务原子 CAS
BEGIN;
  UPDATE object_outbox e
     SET status='leased', lease_owner=:wid, lease_epoch=e.lease_epoch+1,
         lease_expires_at=now()+:T_lease, attempts=e.attempts+1
   WHERE e.outbox_id = (
     SELECT e2.outbox_id
       FROM object_outbox e2
      WHERE e2.bundle_id = :bid
        AND e2.status IN ('pending','scheduled','deferred')
        AND (SELECT freeze_outbox FROM backup_control WHERE id=1) = false
        -- 条件①：直接前置事件必须已达不可逆终态 done（或经裁定 skipped 且记录理由）
        AND NOT EXISTS (
              SELECT 1 FROM object_outbox dep
               WHERE dep.outbox_id = e2.depends_on_outbox_id
                 AND dep.status NOT IN ('done','skipped') )
        -- 条件②：同 bundle 中更小 step_no 的事件必须全部 done/skipped（防依赖字段被误填/绕过）
        AND NOT EXISTS (
              SELECT 1 FROM object_outbox prev
               WHERE prev.bundle_id = e2.bundle_id
                 AND prev.step_no < e2.step_no
                 AND prev.status NOT IN ('done','skipped') )
        -- 条件③：前置事件若存在未确认 R2 请求，禁止越阶
        AND NOT EXISTS (
              SELECT 1 FROM object_outbox pr
               WHERE pr.bundle_id = e2.bundle_id
                 AND pr.step_no < e2.step_no
                 AND pr.unresolved_request = true )
      ORDER BY e2.step_no ASC
      FOR UPDATE SKIP LOCKED
      LIMIT 1 )
    AND e.status IN ('pending','scheduled','deferred')
  RETURNING e.*;
COMMIT;
-- 受影响 1 行 = 领取成功；0 行 = 无可执行事件 / 前置未完成 / 已冻结 → 退出
```

> **如何阻止 `CLEANUP_TEMP` 越过未完成的 Abort（任务书 §5.3）**：`CLEANUP_TEMP.step_no=2` 的领取谓词含三条 `NOT EXISTS`；只要 `ABORT_MPU` 不是 `done`/`skipped`，或它 `unresolved_request=true`，`SELECT` 就不返回 step 2 行 → **任何 Worker 都领取不到 Delete 事件**。`FOR UPDATE SKIP LOCKED` 保证多 Worker 并发时既不互相阻塞也不重复领取；`ORDER BY step_no ASC LIMIT 1` 保证同一 Worker 也按序推进。PG 唯一约束 `uq_one_active_bundle` 与 `UNIQUE(bundle_id,event_type,step_no)` 防止重复建 bundle/事件。
> **诚实边界**：以上仅串行化 **PG 领取与状态**，**不锁 R2**；Abort 请求已发出但仍未确认时，`unresolved_request=true` 阻止 Delete 领取，这是 PG 侧保守闸门，不是 R2 围栏。

### 6.4 十个必答（任务书 §5.2）

| # | 问题 | 本轮答案 |
|---|---|---|
| 1 | **Abort 事件创建条件** | 会话达终态且 `cleanupEligible()`（含超 grace、`freeze_outbox=false`、fence_gen 匹配）；`upload_id IS NOT NULL`；同 `(bundle_id,'ABORT_MPU',1)` 不存在；`uq_one_active_bundle` 允许。**在 bundle 创建时与 step 2/3 一次性同时生成**（避免「Abort done 但 Delete 未创建」窗口）。对 `completed_unpromoted` 已消耗 UploadId 的情形仍创建 Abort 事件，但标 `role='idempotent_sweep'`：**不得作为终止判据**（V1.2.21 §4.2） |

| 10 | **最终枚举复核何时完成** | `CLEANUP_TEMP` 置 `done` 后领取 `FINAL_VERIFY`（step 3），执行**只读**复核：`ListObjectsV2(prefix='uploads/{sid}/')` 无该 temp key ∧ `ListMultipartUploads(prefix='uploads/')` 无该 UploadId（U-4 #7/#8/#11）。通过 → bundle `verified` + `cleanup_state='done'` 投影回写；不确定/矛盾 → `unknown` → 隔离，**绝不置 done** |

> **两条特别注意（任务书 §5.2 原文）**：① `NoSuchUpload` ≠ temp 对象不存在 —— 已由 #5、#10 的强制 Delete + 枚举复核保证；② `AbortMultipartUpload` 返回成功**不能自动证明所有在途上传部分已停止** —— 由 #4 的 `ListMultipartUploads` 复核 + U-4 #8/#10（Abort 与已完成上传的实际行为、迟到请求边界）保证；**在 U-4 未实测前该复核结论标【未证明】，FINAL_VERIFY 不得宣称闭环**。

> **本章成熟度**：`设计已提出 + SQL 伪代码静态审查 + 并发时序推演`。领取 SQL **未在任何 PG 实例执行**；`FOR UPDATE SKIP LOCKED` / 部分唯一索引 / 三条 `NOT EXISTS` 的实际行为须纯 PG 临时库预演；R2 枚举语义全部 U-4。

## 8. V23-04（下）：T-A/T-B/T-C 事务边界与静默屏障

### 8.1 事务拆分说明（回答任务书 §6.3 的「T-C 是否单事务登记四表」）

> **明确回答：否。** V1.2.22 的 T-A/T-B/T-C 在本轮拆为 **T-A / T-B0 / T-B / T-R / T-C1 / T-C2** 六个边界，其中 T-B 是**非 PG 事务的 R2 请求**。理由：① V23-01 要求「请求可能已发出」必须先于请求持久化为独立已提交事实，故 T-B 必须拆出 T-B0；② V23-04 要求 P6/P7 各自对应真实提交点，故 T-C 必须拆为 T-C1/T-C2；③ T-R 独立承载结果回写，使「结果证据写入」与「资产登记」不共用事务，崩溃恢复入口单一。

### 8.3 五个必答（任务书 §6.3）

1. **T-A 提交后系统究竟能证明什么**：只能证明「**操作意图已持久化**、请求**确定尚未发出**（`request_phase='none'`）」；**不能**证明 R2 已 COPY、也不能证明 `content_blobs` 有行。这直接修正 V1.2.22 §7.1 L447 把 T-A 称为「持久化『COPY 已发起』」的错误表述。
2. **T-B 发出 COPY 前后如何持久化「请求可能已发出」**：T-B0 在**发出请求之前**独立提交 `request_phase='registered'` + `request_id`（§4.1）；请求发出后不再需要额外写入即可保证「已发 ⟹ 已预登记」。请求发出前后的可观察差异仅为 `result_evidence` 是否存在。
3. **T-C 是否在一个 PG 事务内同时登记四表**：**否**（见 §8.1）。`content_blobs`+`asset_blob_refs`+`promotion_intents` 在 **T-C1**；`upload_sessions`+`promotion_intents` 在 **T-C2**。四表不在同一事务，但每个事务内部原子，且 P6/P7 各自是真实提交点。
4. **T-C 提交成功但响应丢失时如何幂等确认**：T-C1 成功 → 状态 P6；客户端超时重试 → `copyConfirmed()` 已为真 → 幂等重放 T-C2（`WHERE state='pg_registered'`）。T-C2 成功但响应丢失 → 状态 P7；同 `session_id` 重试 → `UPDATE ... WHERE status='promoting'` 受影响 0 行 → 查回 `committed` 返回 `{asset_id, status:'committed'}`（**不暴露 `deduped`，N-07**）。两次重放均**零 R2 写**。
5. **`copy_confirmed` → `pg_registered` → `promoted` 每个转换由谁完成**：`P2 → P6` 由 **Promotion Worker 的 T-C1** 完成；`P6 → P7` 由 **Promotion Worker 的 T-C2** 完成；Reconciler 只在 P2/P6 滞留超时后**幂等重放相应事务**（不得另起 COPY、不得直接改 `status`）；两者所有写回均带 `lease_epoch` CAS（V1.2.22 §8.3 H）。

### 8.4 静默屏障：只引用真实存在的数据库状态

**禁止**（任务书 §6.4）：❌ `copy_confirmed→promoted`；❌ `P2 → P6 → P7`；❌ 任何把状态转换表达式当作 SQL 状态值或屏障判断条件的写法；❌ 未经论证把 `dead_letter` / `quarantined` / `awaiting_reupload` 当安全终态。

**阻断状态集合（真实 `promotion_intents.state` 值）**：

```sql
-- 设计级查询，不执行：屏障阻断集合 = 下列真实状态值的行数必须全部为 0
BLOCKING_STATES = {
  'intent_committed',   -- P1，含 request_phase='none' 与 'registered'；意图在途、可能有请求
  'copy_confirmed',     -- P2，结果已确认但 T-C1/T-C2 尚未完成 → PG 资产集未定
  'copy_unknown',       -- P3，结果未知，R2 可能仍在写
  'copy_failed_retry',  -- P4，可能受控重发，未收敛
  'pg_registered'       -- P6，资产已登记但会话未 completed，T-C2 未完成
}

canEnterSilentWindow_promotion(drain_gen) :=
    (COUNT(*) FROM promotion_intents
      WHERE state IN ('intent_committed','copy_confirmed','copy_unknown',
                      'copy_failed_retry','pg_registered') = 0)
AND (COUNT(*) FROM promotion_intents
      WHERE unresolved_request = true = 0)                 -- 任何未确认 R2 请求
AND (COUNT(*) FROM promotion_intents
      WHERE request_phase = 'registered' AND resolved_at IS NULL = 0)
AND (backup_control.fence_gen = drain_gen)
AND (∀ 终局行：人工裁定记录存在且 settled_at IS NOT NULL)
```

**逐状态论证为何阻断 / 不阻断**：

| 状态 / 终局 | 阻断？ | 理由 |
|---|---|---|
| `intent_committed` (P1, `none`) | ✅ **阻断** | 意图在途，T-B0 随时可能提交并发 COPY；虽此刻请求未发，但屏障期间不允许保留「即将发请求」的意图 |
| `intent_committed` (P1, `registered`) | ✅ **阻断** | R2 请求可能已发出且可能仍在飞 |
| `copy_confirmed` (P2) | ✅ **阻断** | PG 资产登记未完成，`content_blobs` 与 manifest 可能不一致 |
| `copy_unknown` (P3) | ✅ **阻断** | 结果不确定，禁止宣布静默 |
| `copy_failed_retry` (P4) | ✅ **阻断** | 可能受控重发 |
| `pg_registered` (P6) | ✅ **阻断** | `upload_sessions` 仍 `promoting`，PG 会话状态未收敛 |
| `promoted` (P7) | ❌ 不阻断 | 全部 PG 事务完成、零在途 R2 请求；**唯一天然安全终态** |
| `quarantined` (P5) | ⚠ **条件阻断** | **不得未经论证视为安全**：仅当 `unresolved_request=false` ∧ `settled_at IS NOT NULL` ∧ 人工裁定记录存在 ∧ 无在途请求时，才不阻断；否则阻断 |
| `awaiting_reupload` | ⚠ **条件阻断** | 仅当确认 `unresolved_request=false` ∧ 无在途 R2 请求 ∧ 已返回终止态时不阻断；若仍可能迟到 COPY → 阻断 |
| `dead_letter`（Outbox 侧） | ⚠ **条件阻断** | 同 §5.4：`unresolved_request=true` 时**必然阻断**；只有人工裁定并置 false + 留审计后才可视为收敛 |
| 无行 (P0) | ❌ 不阻断 | 没有意图、没有请求；但须与 §6.5 的会话状态检查联合使用 |

## 9. V23-05：`copyConfirmed()` 唯一最终确认谓词

### 9.1 谓词定义（fail-closed，九项合取）

```
copyConfirmed(intent, candidate) :=
    E_op      本次 COPY 有可信成功证据：
              E1  请求明确成功响应可被找回（持久化请求日志/幂等响应缓存，
                  含 request_id + version_id + etag + gen，且与 intent.request_id 匹配）
              OR E2  版本/元数据枚举显示与 intent_id / gen_at_write 唯一匹配的版本，
                      且不存在其他竞争版本
    AND E_content  对象内容 SHA-256 已【可信验证】且 == key 中 sha256
              ── 非 HEAD 结果、非对象存在性、非 ETag 代用、非推测（U-4 #6）
    AND E_size     candidate.size_bytes == intent.expected_size
    AND E_key      candidate.key == 'blobs/' || sha256
                   且过 ^blobs/[0-9a-f]{64}$ 白名单（V1.2.20 §3.3）
    AND E_version  VersionId 可被准确记录（或存在「该桶版本化关闭」的可验证事实），
                   且与 result_evidence / 既有 content_blobs.r2_version_id 一致（U-4 #5/#9）
    AND E_meta     metadata.gen == intent.gen_at_write
                   AND content_type 符合业务约束与 intent.expected_content_type（U-4 #4）
    AND E_concurrent  不存在同 sha256 的其他 state IN
                   ('intent_committed','copy_confirmed','copy_unknown','copy_failed_retry','pg_registered')
                   且 lease 有效的意图；不存在未解决的并发 COPY（U-4 #1/#3）
    AND E_no_late  不存在 request_phase='registered' 且 lease_epoch < 当前有效 epoch 的旧请求；
                   或已有可验证证据证明旧请求未产生副作用 / 已人工裁定（U-4 #10/#11）
    AND E_freeze   intent.gen_at_write 与当前 fence_gen 关系可解释，且提交时 CAS 一致；
                   跨代情形须有明确裁定记录
```

**求值规则**：任一条件为 `false` **或 `unknown`** → `copyConfirmed() = false`。**不存在「部分通过」**；任一条件不可用即整体不可用。

### 9.2 五类证据不可互相替代（任务书 §7.2）

| # | 证据类 | 覆盖谓词项 | 能证明什么 | **不能**证明什么 |
|---|---|---|---|---|
| 1 | **操作成功证据** | E_op（E1/E2） | 本次 COPY 请求曾成功返回 / 存在匹配版本 | ❌ 内容正确、元数据一致、无并发迟到请求 |
| 2 | **内容完整性证据** | E_content | 字节内容 == sha256 | ❌ 操作是否本次成功、版本是否唯一 |
| 3 | **对象版本证据** | E_version | VersionId / 删除标记可准确记录 | ❌ 内容正确、元数据一致 |
| 4 | **元数据一致性证据** | E_meta / E_size / E_key | `gen` / `content_type` / size / key 符合意图 | ❌ 内容正确、操作成功 |
| 5 | **并发安全证据** | E_concurrent / E_no_late / E_freeze | 无在途/迟到/跨代竞争 | ❌ 前四类任一结论 |

> 与 V1.2.22 §7.5「四个不得互相替代的概念」（内容相同 / 版本相同 / 元数据相同 / 操作幂等）一致，本轮把「操作幂等」升级为「操作成功证据 + 并发安全证据」两类并形式化为合取谓词。**不得用其中一项替代其他项**（V1.2.22 §8.2 L627 已提出要求但未给出谓词，本轮补齐）。

### 9.3 U-4 未验证能力：阻断、不得假定通过、不得自动升级

| 谓词项 | 依赖 U-4 | 未实测时的取值 | 后果 |
|---|---|---|---|
| E_op（E1 幂等响应查询 / E2 版本枚举） | #1/#3/#5/#11 | `unknown` | `copyConfirmed()=false` |
| E_content（可信 SHA-256 获取方式） | #6 + V1.2.22 §7.6 范围外登记 | `unknown` | 同上 |
| E_version | #5/#9 | `unknown` | 同上 |
| E_meta | #4/#10 | `unknown` | 同上 |
| E_concurrent / E_no_late | #1/#3/#10/#11 | `unknown` | 同上 |

> **🔴 必须如实写明的结论（静态推演）**：在 U-4 十三条**一条未实测**的当前状态下，上述多项恒为 `unknown`，因此 **`copyConfirmed()` 在正常路径上无法返回 `true`**，`P1 → P2` 的设计出口实际不可用，绝大多数「COPY 成功但响应丢失」场景只能落到 **P3 `copy_unknown` → 隔离人工裁定（C 类）**。这是**正确的 fail-closed 结果**，不是缺陷被掩盖；但意味着自动恢复链路**未闭环**，R2 Promotion 集成预演必须继续阻断（§16）。
> **证据不足时唯一安全结果**：`copy_unknown`（P3）+ `unresolved_request=true` + 隔离人工裁定。**禁止**：❌ 把 `copy_unknown` 自动升级为 `copy_confirmed`；❌ 用「对象存在」或 HEAD 结果替代证据；❌ 重复 COPY「试一试」；❌ 静默置 `committed`；❌ 凭空构造 `content_blobs` / `user_assets` 行（前提卡红线 L1086）。

### 9.4 与 `canAdoptCanonical()` 的接口

`copyConfirmed()` 与 §11 领养谓词**共享** E_content / E_version / E_meta 的证据条件（同一 U-4 能力），但**二者不可互相替代**：前者判定「本次 Promotion 的 COPY 结果」，后者判定「无意图的孤儿对象能否登记为正确内容」。`copy_unknown` 且 canonical 存在时**不得直接领养**，须先按 §4.2/§9.3 裁定意图（V1.2.22 §8.4 沿用）。

> **本章成熟度**：`设计已提出 + 静态逻辑推演`。谓词为静态规格，**未在任何 PG / R2 环境求值**；所有 U-4 依赖项【未证明】。

> **核心修正**：保留 `uq_one_inflight_copy`（**不得通过删除唯一约束掩盖并发冲突**，任务书 §8.2），但**放弃用 `ON CONFLICT (sha256, attempt_no)` 处理它**。理由：① 部分索引的 `ON CONFLICT` 推断须精确匹配谓词，脆弱；② `DO NOTHING` 丢失「为什么冲突」的信息，无法区分「他者已成功 / 他者 unknown / 他者 quarantined」；③ 任务书明确要求「哪些必须读取并验证现有行、哪些必须拒绝创建新 attempt」。

### 10.2 修正后的 T-A（实际 SQL，设计级不执行）

```sql
BEGIN;
  -- 0) 稳定互斥点：pg advisory xact lock 仅串行化 PG 状态转移，绝不宣称锁住 R2
  PERFORM pg_advisory_xact_lock(hashtext('promote:' || :s));

  -- 1) 显式读取同 sha256 的未收敛意图（不用 ON CONFLICT 吞掉）
  SELECT intent_id, state, request_phase, attempt_no, lease_epoch,
         resolved_at, result_evidence
    INTO v_prev
    FROM promotion_intents
   WHERE sha256 = :s AND resolved_at IS NULL
   ORDER BY attempt_no DESC
   FOR UPDATE;                       -- 行锁，串行化并发 attempt 判定

  IF FOUND THEN
     CASE v_prev.state
       WHEN 'promoted'          THEN /* 幂等收敛到该行，不新建、不重发 COPY */ RETURN;
       WHEN 'copy_unknown'      THEN /* 拒绝新建 attempt → B 类取证 / C 类隔离 */ RETURN;
       WHEN 'quarantined'       THEN /* 拒绝新建 attempt → 人工裁定 */ RETURN;
       WHEN 'intent_committed'  THEN /* 在途 → 拒绝新建 */ RETURN;
       WHEN 'copy_confirmed'    THEN /* 待 T-C1/T-C2 → 幂等重放，不新建 */ RETURN;
       WHEN 'pg_registered'     THEN /* 待 T-C2 → 幂等重放，不新建 */ RETURN;
       WHEN 'copy_failed_retry' THEN
            /* 仅在 result_evidence 证明前次 R2 未生效（U-4 #1/#11）
               且已置 resolved_at + 留裁定后，才允许 attempt_no = v_prev.attempt_no + 1 */
       ELSE RETURN;
     END CASE;
  END IF;

  -- 2) 只处理「同 sha256 同 attempt_no 重复投递」
  INSERT INTO promotion_intents(
      intent_id, sha256, session_id, state, attempt_no, request_phase,
      gen_at_write, expected_size, expected_content_type,
      lease_owner, lease_epoch, lease_expires_at, intent_committed_at)
    VALUES (:iid, :s, :sid, 'intent_committed', :n, 'none',
            :gen, :sz, :ct, :wid, :epoch, now()+:T_lease, now())
  ON CONFLICT (sha256, attempt_no) DO NOTHING;
  GET DIAGNOSTICS v_rows = ROW_COUNT;
  IF v_rows = 0 THEN ROLLBACK; /* 幂等退出并读取现有行状态 */ END IF;

  -- 3) 若并发漏判仍触发 uq_one_inflight_copy 的 unique_violation：
  --    事务整体回滚 → 恢复入口 = 重新执行本事务的「读取现有行 → 按上表判定」，
  --    绝不吞掉异常、绝不删除唯一约束
COMMIT;   -- ★ T-A COMMIT：此刻 request_phase='none'，R2 请求确定未发出
```

### 10.3 七个并发场景逐一分析（任务书 §8.2）

| # | 场景 | 命中约束 | 处置 | 可 `DO NOTHING`？ | 须读取并验证现有行？ | 须拒绝新 attempt？ |
|---|---|---|---|---|---|---|
| 1 | **同 sha256、同 `attempt_no` 并发** | `uq_intent_attempt` | 败者 `DO NOTHING` → **读取现有行状态** → 幂等退出/重放（A 类） | ✅ **是**（仅此场景） | ✅ 是 | 否 |
| 2 | **同 sha256、不同 `attempt_no` 并发** | **`uq_one_inflight_copy` 部分唯一索引** | 显式 `SELECT ... FOR UPDATE` 现有行；若仍在途 → 拒绝；若已 `promoted` → 幂等收敛；若已明确失败且证前次未生效 + `resolved_at` 已置 → 才允许新 attempt | ❌ **否**（会抛 `unique_violation`） | ✅ **是** | 视现有行状态（在途时**是**） |
| 3 | **前一 attempt 处于 `copy_unknown`** | 同上 | 拒绝创建新 attempt → B 类取证 / C 类隔离；`unresolved_request=true` 保持 | ❌ 否 | ✅ 是 | ✅ **是** |
| 4 | **前一 attempt 处于 `quarantined`** | 同上 | 拒绝创建新 attempt → 人工裁定；不得自动重试 | ❌ 否 | ✅ 是 | ✅ **是** |
| 5 | **前一 attempt 已 `promoted`** | 同上 | 幂等收敛到现有行，**不新建 attempt、不重发 COPY、不改元数据** | ❌ 否 | ✅ 是 | ✅ 是（不需要新的） |
| 6 | **前一 attempt 已失败且允许新 attempt** | 同上（`resolved_at` 已置，故不在部分索引谓词内） | 仅当 `state='copy_failed_retry'` ∧ `result_evidence` 证明前次 R2 未生效（**U-4 #1/#11**）∧ `resolved_at` 已置 ∧ 留裁定记录 → `attempt_no=max+1`、`lease_epoch` 重置、新 `intent_id` | ❌ 否 | ✅ 是 | 否（受控允许） |
| 7 | **旧 Worker 迟到成功** | `lease_epoch` CAS（非唯一约束） | 旧回写带旧 epoch → 0 行丢弃；证据比对发现版本/gen 漂移 → **P5 隔离人工裁定**；**不得**新建 attempt 覆盖 | ❌ 否 | ✅ 是（比对 `result_evidence`） | ✅ **是** |

> **不变量**：任何情况下 `uq_one_inflight_copy` 保持存在；并发冲突从「`DO NOTHING` 吞掉」改为「读取 + 验证 + 显式判定」，冲突原因可审计。任务书 §8.2「不得通过删除唯一约束来掩盖并发冲突」已遵守。

> **本章成熟度**：`设计已提出 + SQL 伪代码静态审查 + 并发时序推演`。`ON CONFLICT` 推断、部分唯一索引、`FOR UPDATE`、advisory lock 的实际行为**须纯 PG 临时库预演**，本轮未执行。

## 11. V23-07：Canonical 领养一致性（A/B/C 三结果，无 TOCTOU）

### 11.1 三种互斥结果

| 结果 | 判据 | 动作 | 禁止 |
|---|---|---|---|
| **A. 不存在现有 Blob** | `INSERT ... RETURNING` 命中（确无 `content_blobs` 行）且 C1–C9 全部通过（含 C2 内容哈希、C5 VersionId、C6 无并发、C7 freeze CAS） | 登记候选对象的**可信版本信息**（`r2_gen` / `r2_version_id` / size / content_type）；写 `adoption_evidence` + C1–C9 求值快照 + 审计行；处理业务引用关系 | ❌ 发 R2 COPY；❌ 删对象；❌ 写入未验证的元数据 |
| **B. 已存在且完全一致** | 逐项验证：内容哈希 ✓、对象版本 ✓、元数据（gen / content_type / size / key）✓、业务引用关系（`asset_blob_refs` / `user_assets` 与会话归属）✓ | **幂等成功**，不改写任何已有元数据，写 `adoption_audit(outcome='idempotent_consistent')` | ❌ 覆盖 `r2_gen`/`r2_version_id`（V1.2.21 §5.4 冻结触发器）；❌ 静默返回成功而不验证 |
| **C. 已存在但不一致** | 任一验证项 `false` 或 `unknown` | **隔离**：写 `adoption_conflicts(existing_snapshot, candidate_snapshot, evidence)` + `adoption_audit(outcome='quarantined')`；等待人工裁定 | ❌ 覆盖；❌ 静默成功；❌ 自动删除任一对象；❌ 构造 `content_blobs` 行；❌ `DO NOTHING` 后当成功 |

### 11.2 事务级伪代码（避免「先 SELECT、后 INSERT」TOCTOU，设计级不执行）

```sql
BEGIN;
  -- 0) 稳定互斥点：同一 sha256 的领养事务串行化（仅 PG 内，不宣称锁 R2）
  PERFORM pg_advisory_xact_lock(hashtext('adopt:' || :s));

  -- 1) 前置谓词求值（全部为可审计证据；任一 unknown/false → 直接走结果 C 的隔离记录）
  --    C1 key_valid / C2 content_verified(U-4 #6) / C3 size_match / C4 metadata_ok
  --    C5 version_known(U-4 #5) / C6 no_concurrent / C7 freeze_ok(CAS) / C9 evidence_only
  IF NOT canAdoptCanonical_precheck(:s, :candidate, :gen) THEN
     INSERT INTO adoption_conflicts(sha256, reason, candidate_snapshot, evidence) VALUES (...);
     INSERT INTO adoption_audit(sha256, outcome) VALUES (:s, 'quarantined_precheck');
     COMMIT;  RETURN;                       -- 结果 C
  END IF;

  -- 2) 原子尝试插入；ON CONFLICT 不做任何写，用 RETURNING 判断是否真的插入
  INSERT INTO content_blobs(
      sha256, r2_object_key, size_bytes, content_type,
      r2_gen, r2_version_id, adoption_evidence, ...)
    VALUES (:s, 'blobs/'||:s, :sz, :ct, :gen, :ver, :ev, ...)
  ON CONFLICT (sha256) DO NOTHING
  RETURNING sha256 INTO v_inserted;

  IF v_inserted IS NOT NULL THEN
     -- ★ 结果 A：无现有 Blob，全部条件已过 → 登记可信版本信息
     INSERT INTO adoption_audit(sha256, outcome, evidence_snapshot)
       VALUES (:s, 'inserted', :ev);
     -- 业务引用关系（按会话，幂等）
     INSERT INTO asset_blob_refs(...) VALUES (...) ON CONFLICT DO NOTHING;

  ELSE
     -- 3) 已有行：同一事务 + 同一 advisory lock + FOR UPDATE 行锁，杜绝 TOCTOU
     SELECT r2_object_key, size_bytes, content_type, r2_gen, r2_version_id, ref_count
       INTO v_existing
       FROM content_blobs WHERE sha256 = :s FOR UPDATE;

     IF  v_existing.r2_object_key  = 'blobs/'||:s
     AND v_existing.size_bytes     = :sz
     AND v_existing.content_type  = :ct
     AND v_existing.r2_gen        = :gen
     AND v_existing.r2_version_id IS NOT DISTINCT FROM :ver
     AND business_refs_consistent(:s, :sid, :owner)     -- 引用关系与会话归属一致
     THEN
        -- ★ 结果 B：完全一致 → 幂等成功，不改任何元数据
        INSERT INTO adoption_audit(sha256, outcome, evidence_snapshot)
          VALUES (:s, 'idempotent_consistent', :ev);
     ELSE
        -- ★ 结果 C：不一致 → 隔离，留冲突证据，等待人工裁定
        INSERT INTO adoption_conflicts(sha256, existing_snapshot, candidate_snapshot, evidence)
          VALUES (:s, to_jsonb(v_existing), :candidate, :ev);
        INSERT INTO adoption_audit(sha256, outcome) VALUES (:s, 'quarantined');
        -- 不 RAISE：保留证据；业务登记不发生
     END IF;
  END IF;
COMMIT;
```

**无 TOCTOU 的静态推演依据**：① `pg_advisory_xact_lock(hashtext('adopt:'‖sha))` 使**同一 sha256 的所有领养事务**在 PG 内串行化；② `INSERT ... ON CONFLICT DO NOTHING RETURNING` 把「探测是否存在」与「插入」合成**单条原子语句**（并发未提交插入会等待，再返回 0 行）；③ 已有行的读取用 `FOR UPDATE` 且在同一事务、同一 advisory lock 保护下，不存在「SELECT 后、INSERT 前」的窗口。④ 结果 C 的隔离记录与业务登记**互斥**（不同分支），且审计行与冲突证据同事务提交。
> **诚实边界**：以上为**静态 SQL 伪代码审查**，PostgreSQL 的 `ON CONFLICT` 等待语义、`RETURNING` 与 `FOR UPDATE` 的组合行为、advisory lock 的作用域**须纯 PG 临时库预演**；C2/C5 的内容哈希与 VersionId 证据依赖 U-4 #5/#6，未实测前前置谓词恒 `unknown` → **一律走结果 C 隔离**（fail-closed）。

### 11.3 与 V1.2.22 C8 的关系（登记，不修改原文）

V1.2.22 §9.1 C8（L681–684）「`INSERT ... ON CONFLICT (sha256) DO NOTHING` + 领养全程零 R2 写」中的**「零 R2 写」保持**；`DO NOTHING` 由本轮 §11.2 升级为「`RETURNING` 判定 + 已有行逐项验证 + 三结果分支」。§9.2 #8 与 §11 用例 #19 的「已提交 → `DO NOTHING` 幂等退出」相应升级为「已提交 → 重放本事务，按 A/B/C 判定；结果 B 才幂等成功」。**本轮不修改 V1.2.22 原文**，仅在 §13.3 登记。
