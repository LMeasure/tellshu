## 1. 第十轮修复的语义矛盾（先登记再解决）

第九轮 `08` §3.1 声明 `evidence_signing_key` **append-only、绝不 UPDATE 旧行**，但 §3.5 又写「旧行 `UPDATE compromised_at`（治理例外）」——二者不可同时成立。若保留 UPDATE 例外，则「证据链不可变」论断被自身推翻。

**根因**：把两类语义相反的数据塞进一张表——
- **不可变密钥材料**（公钥、主体、有效期边界）：一旦生成永不改变，是证据验签的锚点。
- **可变治理状态**（是否被撤销、是否泄露、何时发现）：本质是随时间演进的事件，注定要追加/更新。

**统一方案（本轮采纳）**：**分表**。这是唯一自洽的选择，理由见 §3.0。V1.2.30 §6.x 已确立「证据本体 append-only + 独立可变槽位表」的同构模式（N-1 拆表），本设计沿用该成熟范式。

## 2. 统一状态模型：不可变材料表 + 可变治理状态表

### 2.1 `evidence_signing_key`（不可变材料，append-only）

```
key_id, subject_id, subject_type, public_key, org_unit,
valid_from, valid_to,            -- 生命周期边界（预置，不随事件改）
created_at
```
- **只 INSERT，永不 UPDATE/DELETE**（`REVOKE UPDATE,DELETE,TRUNCATE` + 无例外）。
- 轮换 = **新 `key_id` INSERT**；旧材料永久保留。
- 私钥**只在 KMS/HSM**，DB 仅有 `public_key`；DBA/超级用户不可从库内取得私钥。

### 2.2 `evidence_signing_key_status`（可变治理状态，append-only 事件流）

```
id            bigserial PK,
key_id        text NOT NULL REFERENCES evidence_signing_key(key_id),
status        text NOT NULL CHECK (status IN ('active','revoked','compromised','expired')),
effective_at  timestamptz NOT NULL,   -- 状态「生效时刻」（见 §4 语义）
discovered_at timestamptz,            -- 仅 compromised 用：发现时刻（可晚于 effective_at）
reason        text,
actor         text NOT NULL,          -- 治理主体（来自可信身份，见 U-R8-2）
recorded_at   timestamptz NOT NULL DEFAULT now()
```
- **也是 append-only**：状态变化通过**追加新事件行**表达，不 UPDATE 旧状态行 → 治理历史本身不可篡改、可审计。
- 「密钥当前状态」= 按 `(key_id, effective_at, recorded_at)` 取**最新一条**；历史时点状态 = 取 `effective_at <= t` 的最新一条。
- 第九轮 `revoked_at`/`compromised_at` 两个可变列**取消**（它们才是矛盾源），其语义由本表的事件行承载。

> 预演最小桩说明：`03-init-cleanup.sql` 为保持 SQL-A~E 闭环精简，暂保留 OBJ-02 原列（含 `revoked_at`/`compromised_at`）作为**可执行桩**，但本文件定义的**目标模型是分表**；二者差异登记为 `08-D1`（生产实施项，非本轮预演阻断）。预演本身不验签、不读这两个列。

## 3. 唯一推荐方案（Agent 自主裁定，不等待负责人选择）

### 3.0 为什么分表是唯一自洽方案
- 若维持单表且 `compromised_at` UPDATE：违反 append-only，证据不可变论断失效，且与 V1.2.30 N-1 拆表范式冲突。
- 若维持单表但禁止任何状态更新：无法表达「泄露后停用」，治理能力缺失，U-R8-3 目标落空。
- 只有**材料表 append-only + 状态事件表 append-only**同时满足「不可变锚点」与「可演进治理」，且都保持不可篡改审计。故采纳分表。

### 3.1 认证通道：**推荐 `mTLS` 为主，短期令牌仅作边缘补充**
- **唯一推荐**：内部 CA 签发的 **mTLS 客户端证书**作为 Worker 身份根，证书 SAN 绑定 `subject_id` 与 `org_unit`，与 `evidence_signing_key.subject_id` 对齐。
- **理由**：① 三主体（采集/复核/DB 写入）需**强、可吊销、非承载自报**的身份，mTLS 由 PKI 提供可验证根；② 常驻 Worker 场景证书轮换成本可接受；③ 配合 §2.2 治理主体 `actor` 字段，可把「谁撤销了密钥」绑定证书身份，避免"凭角色伪造撤销"（V1.2.30 §10.2 明确禁止）。
- **短期令牌**（SPIFFE/JWT ≤15min）仅用于无法挂载证书的一次性作业；**不作为主通道**，因其签发服务可用性与时钟同步引入新信任根，而当前**无可信身份系统**（V1.2.30 P0-7）。
- **强制纪律**：`collector_id`/`verifier_id`/`org_unit` 由服务端从 mTLS 身份**派生注入**，不接受客户端自报，杜绝 I4「字面不同但同控」绕过。

### 3.2 签名与密钥管理：**推荐 KMS 托管非对称签名（RSA-PSS / ECDSA），私钥不出 KMS**
- 唯一推荐：云 KMS 或自托管 HSM（二选一由部署合规决定，属**运维选型**非协议分歧），签名在 KMS 内完成，DB 只存 `public_key`。
- 默认参数（给出唯一值，不再上交决策）：签名密钥有效期 **90 天**；新旧并行重叠 **≥7 天**；到期前 **14 天**告警预置新钥；历史密钥**随证据法定保留期永久保留**（默认取证据留存上限）。
- 轮换 = 新 `key_id` + 在状态表追加 `active` 事件；旧钥追加 `expired` 事件（状态事件，非材料 UPDATE）。

## 4. 三种时间判断（签署时有效 / 验证时有效 / 事后泄露）——统一判定规则

设证据签名时刻 `t_sig = r2_evidence_record.collected_at`，验证发生时刻 `t_ver = now()`。

### 4.1 判断 A：**签署时有效**（历史合规，验签主判据）
```
key = evidence_signing_key WHERE key_id = evidence.signature_key_id
签名有效 ⇔ key 存在
   AND key.valid_from <= t_sig < key.valid_to
   AND 在 t_sig 时点 key 状态 = active
        (即 status 事件中 effective_at<=t_sig 的最新一条为 active，或尚无事件)
   AND 密码学验签(public_key, payload, signature, t_sig 时公钥) = TRUE
```
- **过期但签署时有效的密钥**：仍判**有效**（历史合规）。过期只影响「能否用于新签名」，不否定既有签名。
- **证据携带的 `signature_key_id` 精确选钥**，绝不用「当前最新密钥」验旧证据。

### 4.2 判断 B：**验证时有效**（是否可用于新的消费决策）
```
在 t_ver 时点，key 最新状态 ∈ {active}
```
- 已被 `revoked`/`compromised` 的密钥：**不得**作为新消费决策的信任依据 → 触发证据复核/隔离，但**不自动否定**判断 A 已成立的历史签名。

### 4.3 判断 C：**事后发现泄露**（不可抵赖 vs 风险处置的平衡）
- 若状态事件 `compromised` 的 `effective_at > t_sig`（泄露发生在签署之后）：**历史签名仍有效**（判断 A 不变），因为签名时刻密钥未泄露，不能事后否认。
- 处置：追加审计告警、进入复核队列、此后该 key 判断 B = False（停止新消费）。
- 若 `effective_at <= t_sig`（泄露早于或等于签名时刻）：**判断 A 不成立**，签名自始无效，相关证据隔离。
- `discovered_at`（发现时刻）**不参与**签名有效性判定，仅用于审计 SLA（发现延迟 = `discovered_at - effective_at`）。

### 4.4 时间语义汇总

| 字段 | 语义 | 是否影响历史签名 |
|---|---|---|
| `valid_from/valid_to` | 材料生命周期边界（预置） | 是（判断 A 用 t_sig 落入区间） |
| `status.effective_at` | 状态**实际生效时刻**（撤销/泄露真正发生时刻） | 是（与 t_sig 比较） |
| `status.discovered_at` | 治理系统**发现时刻** | 否（仅审计） |
| `recorded_at` | 事件入库时刻 | 否（时序排序用） |

## 5. 历史证据重新核验（re-verification）

- 触发：密钥泄露/撤销事件、合规审计、周期性重验。
- 方法：**只读**重放判断 A/B/C，不修改任何证据行（证据本体 append-only）。
  ```
  FOR each evidence with signature_key_id = K:
      A = verify_at_signing_time(evidence, K, t_sig)   -- §4.1
      B = key_state_at(K, now()) == active             -- §4.2
      C = compromise_effective_at(K) > t_sig           -- §4.3
      result = (A AND B AND C) ? 'still_trusted' : 'quarantine'
  ```
- 结果写入独立审计表（append-only），不回写证据；`quarantine` 只影响**后续消费决策**，历史证据本体不动。
- 因 U-4 十三条未实测、`r2_operation_id` 恒 NULL（V1.2.30），**本重验在当前运行时不改变 `terminal_proven` 不可达的结论**。

## 6. 请求唯一标识与重放防护（nonce + 业务幂等双重）

**两种机制作用在不同层，缺一不可**；短 TTL 单独不足以防重放：

| 层 | 机制 | 防什么 | 失效边界 |
|---|---|---|---|
| 传输层 | mTLS 通道 + 每请求一次性 `nonce`（服务端去重缓存，TTL=5min） | 截获报文重放 | nonce 缓存淘汰后（5min）依赖业务层兜底 |
| 业务层 | `UNIQUE(bound_request_id, bound_attempt_no, bound_lease_epoch, op_type, bound_environment, bound_bucket, bound_canonical_key, payload_sha256)`（OBJ-03） | 同一逻辑请求重复落库 | 永久（DB 约束） |
| 审计层 | 每次写入 append-only `r2_evidence_record` / `r2_evidence_verification` | 事后追查重放尝试 | 永久 |

判定：① nonce 命中缓存 → 传输层拒绝（重放）；② 业务 UNIQUE 冲突 → 23505 拒绝（重复请求）；③ 两道都过才进入受控写入口。
- **关键**：nonce 的 5min TTL **不是**唯一防线；即便攻击者熬过 TTL 重放，业务 UNIQUE 仍拒绝落库。二者是「或」关系取严，不是「仅 TTL」。

## 7. 与 O-4A 纯 PG 预演的关系（诚实边界）

- U-R8-2/U-R8-3 是**独立实施工程**，不部署真实 KMS/CA/认证服务，不使用真实密钥。
- 进入 SQL-A~E 预演的唯一交叉点：**I4 三主体隔离**由 `verifier_id/collector_id` + `org_unit` 在 TRG-01 逻辑强制（本轮已由 DEFINER 修复保证可执行）；本设计把它升级到密码学身份根是**后续增强**。
- 超级用户旁路（V1.2.30 §13 #10）不因本设计消除；mTLS/KMS 属生产实施层治理，如实登记为独立阻断项，**不计入本轮 P0/P1**。
